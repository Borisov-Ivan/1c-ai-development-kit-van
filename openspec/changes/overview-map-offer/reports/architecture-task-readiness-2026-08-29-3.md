## Замечания (не блокируют старт)

1. **Правило «несколько отчётов — все пути» остаётся в третьем месте того же скилла.** Задача снятия правила названа для раздела порядка действий (п. 1) и раздела источников узлов, но в шаге про макет того же файла отдельно записано «передать все пути источников по теме». После правки по текущей формулировке этот фрагмент останется. Практического расхождения нет (к моменту шага про макет источник уже выбран одним файлом), но текст будет читаться двусмысленно. Рекомендация уровня правки формулировки: дописать в ту же задачу третий адрес — шаг про макет.

2. **Ничья предпочтения при описании двух ЗНИ.** Если в одном описании названы две ЗНИ и у каждой есть журнал пошагового прохода, правило предпочтения обе ставит в один разряд, а решение по расхождению отсылает к «источнику, на котором прошла проверка» — для ничьей это круг. Обязательная приёмка идёт на одной ЗНИ, поэтому старт не блокируется. Рекомендуемое закрытие одной строкой: при равном разряде брать отчёт **первой названной** ЗНИ — тем же принципом, по которому уже выбирается каталог для имени файла описания.

3. **Файл команды описания не объявлен в перечне затронутых файлов.** Одна задача правит `.cursor/commands/opsx-overview.md`, но в колонке файлов среза и в разделе влияния постановки перечислены только скилл описания, контракт чата, скилл карты и дельта требований. Расхождение чисто описательное; закрывается добавлением файла в перечень.

**Отдельно, не замечание:** соглашение «тип отчёта из индекса, иначе по префиксу» устойчиво и при неполном индексе — индекс этой же ЗНИ сейчас перечисляет два файла из девяти. Естественное чтение правила — построчное (нет записи о файле → префикс), и оно даёт детерминированный результат; переоткрывать закрытый вопрос распознавания типа не нужно.

Отсутствие в наборе прямо сейчас конкретной ЗНИ с журналом прохода в каталоге отчётов пробелом не считается: это состояние стенда, а не постановки.

## Simplicity Check

- **Viable alternatives:**
  1. Выбранный вариант — инвентарь отчётов после записи файла, уже существующая проверка формы связей, вариант схемы в постоянной строке следующего шага, сборка по согласию из того же одного отчёта. Четыре файла набора плюс дельта требований, новых механизмов нет.
  2. Отдельный вопрос про схему после описания — плюс один слот вопроса, минус: превращает намёк в отдельный вопрос, что запрещено контрактом «намёк только на существующей строке».
  3. Вложить схему или перечень этапов в файл описания — минус файлов не даёт, зато делает картой список этапов и смешивает текст для заказчика с панелью механизма.
  4. Собирать панель сразу после описания без согласия — самый короткий текст правки, но отменяет инвариант ADR-0008 «без просьбы и без принятого предложения панель не создаётся».
- **Selected simplest viable design:** вариант 1. Он единственный, который добавляет только один слот в чат и не заводит ни новой команды, ни нового источника данных, ни нового файла: проверка формы связей, сборщик манифеста и резолв каталога ЗНИ переиспользуются как есть.
- **Why not simpler:** более простой путь «ничего не менять в скилле карты, только напечатать намёк в описании» не проходит: при согласии сработает действующий отказ «вне разбора укажите отчёт», и намёк окажется обещанием без результата. Ещё более простой «одна строка в чате без проверки трёх условий» ломает требование предложения по форме связей и даст ложный намёк на плоском наборе.
- **Complexity budget:** файлов набора — 4 (плюс дельта требований, уже записана); точек перехвата поведения — 0 (перехватов нет, добавлен один слот чата); новых процедур/механизмов — 0; условных ветвлений — 3 (инвентарь есть/нет, три условия прошли/нет, ответ согласие/молчание/«без карты»); рабочих задач — 13, срез один.
