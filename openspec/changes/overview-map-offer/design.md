## Context

Команда описания ЗНИ компилирует постановку и решения в связный текст для согласования и в чат отдаёт путь к файлу плюс пункты «что согласовать». Скилл карты сценария предлагает схему только в исследовании и в пошаговом разборе кода; вне них панель строится из журнала или из отчёта, который человек указал. Сборщик схемы принимает пути отчётов и диапазоны доказательств и не рисует стрелки из формулировок «мы планируем».

В результате согласующий видит этапы поставки и не видит механизм и ловушку, даже когда отчёты разбора по этой ЗНИ уже есть. Отдельной команды карты нет и не будет (ADR-0008). Соседняя открытая ЗНИ `scenario-map-readability-meaning` чинит читаемость уже собранной панели — сюда не входит.

Панель после согласия видит разработчик в сессии описания; согласующему она попадает только показом схемы рядом с чатом. Путь к файлу панели и вложение схемы в файл описания не печатаются и не создаются (ADR-0008, Non-Goal 5).

Связанные ADR: ADR-0008 (нативная регистрация панели родителем) — Load-Bearing. Инварианты не отменяются: без просьбы и без принятого предложения панель не создаётся; намёк на существующей строке — только вариант; у узла имя и доказательство; главный вид — граф; предложение считается по форме связей.

Архив: `2026-08-28-scenario-map-canvas` — контракт «когда рисовать». Эта ЗНИ расширяет вход: сессия описания ЗНИ может предложить схему по отчётам, не делая постановку источником узлов.

## Goals / Non-Goals

**Goals:**

1. После описания ЗНИ, если по ней уже есть отчёты разбора со связями и доказательствами, в чате появляется намёк схемы с конкретным «что станет видно».
2. Согласие собирает панель из этих отчётов тем же порогом и той же регистрацией, что прямая просьба. Постановка, список задач и файл описания не становятся узлами.
3. Без отчётов или без связного набора намёка нет; причина в чат не печатается. «Без карты» до конца сессии не повторяется.

**Non-Goals:**

1. Отдельная команда карты; автосборка панели после описания.
2. Карта на `/review` и `/opsx:verify`.
3. Читаемость шаблона панели и смена модели сборщика (открытая соседняя ЗНИ и её Non-Goals).
4. Ослабление словаря связей, порога четырёх сущностей и запрета выдуманных рёбер.
5. Включение протокола карты в файл описания ЗНИ.

## Existing Mechanisms

1. Скилл описания ЗНИ — компиляция из постановки и решений; отчёты разбора в сюжет файла не входят; сборщик схемы не вызывается.
2. Контракт чата описания — путь к файлу и блок согласования; строки «следующий шаг» сейчас нет.
3. Скилл карты сценария — молчание, намёк на существующей строке, проверка формы связей, источники (разбор / исследование / указанный отчёт).
4. Сборщик схемы — манифест из пути источника и диапазонов; файл пишет родитель.
5. ADR-0008 — регистрация родителем, граф не список, нет отдельной команды.

Почему не оставляем как есть: описание ЗНИ — как раз момент обоснования плана, а схема механизма к этому моменту уже может быть доказана отчётами. Новый механизм не вводится: расширяем те же входы «когда предлагать» и «какой источник».

## Design Rationale

Разбор постановки: `reports/architecture-new-2026-08-29.md`. Точка правки — скилл описания (инвентарь отчётов после записи файла + намёк) и скилл карты (сессия описания как место намёка и исключение «укажите отчёт» для принятого предложения и прямой просьбы при готовом инвентаре). Файл описания остаётся текстом для заказчика. Этапы поставки не мапятся в узлы: это список без причинных стрелок, такой вид публиковать нельзя.

## Behavior Contract

1. Строка следующего шага — безусловный элемент чата описания: печатается всегда, в том числе когда отчётов нет и карта не рассматривалась. По умолчанию в ней одно действие: передать записанный файл на согласование. На повторном прогоне в той же сессии строка идемпотентна: печатается та же фраза «Передать файл на согласование», а не второе безымянное действие. Заглушка «достаточно» не печатается. Пока человек не отказался от карты в этой сессии, эта строка — единственное место намёка. Это не строка «следующий шаг» финала исследования с постановкой ЗНИ: тот запрет сохраняется.
2. Намёк печатается только если одновременно выполнены три условия **на том же одном отчёте**, который при согласии уйдёт в сборщика (предпочтение — Decision 2). Объединение нескольких отчётов топологическим признаком не считается. Три условия: можно назвать конкретный вывод, которого нет в списке этапов; есть хотя бы один топологический признак формы связей (слои, где один питает другой; ветвление со схождением; жизненный цикл состояний; причинная петля или повторное использование устаревшего результата; одно порождает несколько представлений; разные технические пути); после отсева без доказательства и без связи остаётся не меньше четырёх связанных сущностей. Признак определяется по форме связей в выбранном отчёте, не по теме ЗНИ и не по числу этапов поставки. Формулировка намёка — «что станет видно», не общий вопрос «хотите карту?». Панель на этом шаге не создаётся.
3. Источник проверки и последующей сборки — отчёты разбора, журналы пошагового прохода и архитектурные отчёты по теме в каталогах названных ЗНИ. Постановка, список задач, файл описания и отчёты проверки постановки в сюжет карты не входят.
4. Согласие на намёк строит панель из источника проверки: тот же порог, та же раскладка и подписи, что прямая просьба; команда сессии не меняется; отказ «укажите отчёт» к этому входу не применяется. Прямая просьба «покажи карту сценария» в той же сессии описания, пока инвентарь отчётов уже есть, берёт **один** отчёт, выбранный из инвентаря правилом предпочтения Decision 2 (если проверка трёх условий уже прошла — тот же файл). Правило скилла карты «несколько отчётов — передать все пути» к входу описания до поставки соседней ЗНИ про читаемость не применяется.
5. Если отчётов нет или проверка не проходит — намёка нет, причина в чат не печатается. «Без карты» — до выхода сессии намёк не повторять. Этапы поставки как цепочка узлов публиковать запрещено.
6. Сборщику передаются пути отчётов и диапазоны доказательств; вопрос шапки — зачем меняем, не какие этапы. Код модулей сборщику не отдаётся.

## Implementation Options

**Вариант A.** После записи описания родитель собирает отчёты ЗНИ, прогоняет уже существующую проверку связей и при успехе добавляет вариант схемы в постоянную строку следующего шага. Согласие вызывает сборщика с этими отчётами.

**Вариант B.** Отдельный вопрос про карту после описания.

**Вариант C.** Вставить схему (или перечень этапов) в файл описания.

**Вариант D.** Сразу собирать панель после описания, без согласия.

Выбран A: совпадает с контрактом «намёк на существующей строке» и не смешивает текст для заказчика с панелью механизма. B ломает «не отдельный вопрос». C делает картой список этапов или дублирует панель в markdown. D ломает ADR-0008.

Словарь связей, порог четырёх, запрет выдуманных рёбер, регистрация родителем, успех кнопкой среды — **не отменяются**. ADR-0008 не заменяется.

## Decisions

1. **Строка следующего шага в чате описания всегда есть.** Она вводится в макет чата описания независимо от карты и печатается даже когда карта не рассматривалась. Канон строки — «Передать файл на согласование» (одно действие), в том числе на повторном прогоне в той же сессии. Заглушка «достаточно» не печатается. Лимит тонкого чата: путь, блок согласования, одна строка шага.
2. **Источник — каталоги названных ЗНИ, папка отчётов.** Активный и архивный каталог равноправны, путь резолвится тем же способом, что в самой команде описания. Кандидаты: журнал пошагового прохода, отчёт разбора, архитектурный отчёт по теме. Распознавание типа: при наличии `reports/_manifest.yaml` — по полю `type`; иначе по префиксу имени (`explain-*`, `exploration-*`, `architecture-*`). Сам манифест и отчёты проверки постановки, контроля качества, независимого разбора постановки и приёмки среза в инвентарь не входят. На момент этой ЗНИ проверка трёх условий и сборка используют **один и тот же** отчёт: сначала предпочтение (журнал прохода, затем разбор, затем архитектурный отчёт по теме), и три условия считаются только по выбранному файлу. Выбор файла предпочтением происходит **до** проверки и от её исхода не зависит: при прямой просьбе без прошедшей проверки в сборщика уходит тот же выбранный один файл. Объединение файлов признаком не считается. Правило «несколько отчётов — все пути» к входу описания до поставки соседней ЗНИ не применяется. Архитектурный отчёт может быть единственным источником, только если после обоих отсевов в нём есть доказанные сущности и видимые связи; формулировки «мы планируем» рёбрами не являются. Несколько путей включатся сами после поставки соседней ЗНИ про читаемость карты, без правок здесь. Временные отчёты вне каталога ЗНИ — только если путь уже назван в этой сессии. Две ЗНИ в одном описании: панель по тому источнику, на котором проверка прошла (или по выбранному предпочтением, если проверки не было); расхождение на полотно не выносить и ребро не дорисовывать.
3. **Проверка предложения — три условия на выбранном одном отчёте:** вывод, которого нет в списке этапов; топологический признак формы связей; ≥4 связанных сущности после обоих отсевов. Объединение файлов признаком не считается. Отказ проверки в чат не печатать.
4. **Шапка панели — вопрос обоснования** («зачем меняем»), не перечень этапов.
5. **Соседнюю ЗНИ про шаблон не трогать.** Эта ЗНИ независима: работает на текущем контракте сборщика (один или несколько путей).
6. **Связь с архивом:** новый change, класс `extends`. Инварианты ADR-0008 не отменяются.

## Risks / Trade-offs

1. Строка следующего шага раздует тонкий чат описания → один слот, без второго вопроса и без дампа узлов.
2. Архитектурный отчёт без доказанных рёбер даст ложный намёк → в набор только сущности с доказательством и видимой связью; иначе молчание.
3. Человек примет этапы поставки за карту механизма → явный запрет публиковать этапы как узлы; источник только отчёты разбора.
4. Намёк без согласия забудут → это штатно: как в разборе, панель сама не появляется.
5. Две ЗНИ в одном описании с разными отчётами → инвентарь по всем названным; расхождения не разрешают дорисовать ребро.

## Migration Plan

1. Ввести строку следующего шага как безусловный третий элемент тонкого чата в `.cursor/docs/opsx-output-style.md` §5.6 и в `.cursor/skills/openspec-overview/SKILL.md` (шаг «Write + чат», Self-check про тонкий чат). Строка печатается и когда карты нет.
2. В скилле описания: после записи файла — инвентарь отчётов названных ЗНИ (активных и архивных), проверка трёх условий предложения, намёк в строке шага, согласие → сборщик. В секции «Источники (только Read)» две ветки: сюжет файла — постановка и решения; инвентарь карты — отчёты разбора, журналы прохода, архитектурные отчёты по теме; список задач и отчёты проверки постановки не входят ни в одну ветку. Guardrail делегирования: сборщик манифеста карты выведен из-под запрета явно; обследование кода и правки модулей из команды описания по-прежнему запрещены.
3. В скилле карты: сессия описания как место намёка, источник при согласии и третье исключение отказа «укажите отчёт» для прямой просьбы при готовом инвентаре. Дельта требований переписывает эти места как MODIFIED, не как новые требования рядом. Запрет публиковать этапы поставки как цепочку узлов — явно.
4. Записать дельту требований.
5. Откат: убрать слот шага и ветку намёка из описания; скилл карты вернуть к «только исследование и разбор». Контракт данных панели не затрагивается.

## Assumptions

1. Каталог панелей по-прежнему резолвит родитель; живые файлы панели не в git.
2. Сборщик по-прежнему не пишет файл панели и не обходит код шире переданных диапазонов.
3. Таксономия базы знаний в kit не заведена — Discovery пуст, опираемся на ADR-0008 и архивный spec.
4. Приёмка — ручной прогон описания на ЗНИ, в чьём каталоге отчётов есть журнал прохода или архитектурный отчёт с доказанными сущностями и видимыми связями, и на ЗНИ только с постановкой. Конкретный стенд и наличие таких файлов на момент проверки постановки — transient, не блокер старта. Автотестов панелей в kit нет.
5. Проверка трёх условий читает из выбранного отчёта только секции сущностей, связей и доказательств (узлы, рёбра, якоря), не полный нарратив и не сюжет файла описания. Полный текст отчёта в контекст компиляции описания не входит.

## Открытые вопросы

1. Искать отчёты только в каталоге ЗНИ или ещё во временных отчётах исследования с той же темой, если путь в сессии не называли. По умолчанию — каталог ЗНИ (активный или архивный) и явно названный путь; не блокирует старт.
2. При расхождении отчётов двух ЗНИ в одном описании: публиковать панель по одной ЗНИ или молчать. По умолчанию — публиковать по источнику, на котором прошла проверка, расхождение на полотно не выносить; не блокирует старт.

| S1: Намёк схемы после описания ЗНИ | Разработчик вызывает описание ЗНИ, у которой уже есть отчёты разбора со связями, видит в строке следующего шага, что станет видно на схеме, соглашается — открывается панель из того же отчёта, не из этапов | Вызвать описание ЗНИ с отчётами разбора → в чате предложение схемы с «что станет видно» без панели → согласие → панель из того же отчёта, на котором прошла проверка | «Описание предлагает схему при топологии в отчётах»; «Намёк описания не рисует панель»; «Согласие на намёк описания рисует карту из отчётов»; «Описание без отчётов схему не предлагает»; «Плоский набор без формы связей в описании не даёт намёка»; «Этапы поставки не становятся картой»; «Отказ без карты в описании не повторяется»; «Прямая просьба в описании берёт инвентарь отчётов» | скилл описания, контракт чата описания, скилл карты, дельта требований | ручной прогон описания на ЗНИ с отчётами; прогон без отчётов — optional |

### Граф зависимостей

- S1 → нет

### Критерии приёмки по срезам

- **S1** SHALL: после описания ЗНИ с отчётами разбора в чате есть намёк схемы без панели; согласие открывает панель из того же отчёта. Отсутствие намёка на ЗНИ только с постановкой — optional (не блокирует подпись среза).
