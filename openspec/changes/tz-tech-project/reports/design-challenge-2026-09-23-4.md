## Three-Question Challenge

### Q1 — Problem-Solution Fit

- **Why говорит:** «По каждому входящему частному заданию техпроект и оценка часов собираются заново. Шаблоны и обзор задачи не связаны одной командой, поэтому вопросы к заказчику идут по одному в чат. После согласования часов та же команда готовит каркас техпроекта».
- **Design адресует:**
  - «собираются заново» → одна команда с перенесёнными в навык нормативами, чеклистом дыр и каркасом сюжета (D3, D4);
  - «вопросы по одному в чат» → лист `<имя>-вопросы.md` с формулировкой, ≥2 вариантами и местом для ответа; чат не источник ответов; пометки в согласовании лист не заменяют (D1, spec MUST NOT);
  - «после согласования — техпроект» → второй запуск пишет `<имя>-техпроект.md` только при подтверждении в листе (D1, EC-1).
- **Покрытие:** полное. Каждый пункт боли из Why имеет адресующий механизм в D1–D5, зеркалированный MUST/MUST NOT в spec.

### Q2 — Optimality

- **Выбранный путь:** новая команда `/opsx:techproject` + навык; шаблоны переработаны в копии внутри навыка; состояние диалога живёт в самом листе вопросов.
- **Альтернативы (не упомянутые в Implementation Options):**
  1. **Цепочка существующих команд** — оформить задание как change через `/opsx:new`, текст согласования собирать `/opsx:overview`, часы вручную. Плюс: ноль новых команд. Минус: создаёт артефакты разработки на стадии, когда решения делать задачу ещё нет; обзор по spec «Обзор задачи не меняется» не читает сырое задание и не считает часы. Отклонена: инвазивнее и ломает роль обзора — совпадает с причиной отклонения Option B.
  2. **Две команды вместо одной** — `techproject-вопросы` (лист + согласование) и `techproject-сборка` (техпроект), без определения фазы по содержимому листа. Плюс: нет логики распознавания повторного запуска. Минус: две точки входа для ежедневного потока, состояние всё равно в листе (подтверждение проверять надо), а закрытое решение second-step-confirmation уже фиксирует «та же команда, повторный запуск». Отклонена: усложняет вход без выигрыша. `reopen-blocked: second-step-confirmation` — подтверждённого кодом факта против одной команды нет.
  3. **Маркер состояния вне листа** — статус подтверждения в frontmatter согласования или отдельном файле-маркере вместо чтения листа. Плюс: машинно-однозначная проверка. Минус: третий артефакт рядом с заданием, у заказчика в руках согласование, а не маркер; EC-1 закрепил лист как носитель подтверждения. Отклонена: лишний артефакт. `reopen-blocked: second-step-confirmation`.
- **Вердикт по Q2:** выбранный путь оптимален — одна команда, файлы как состояние, минимальная поверхность (команда + навык, конфигурация 1С не трогается), переиспользование голоса обзора без правки его файлов. Ни одна альтернатива не даёт преимущества, оправдывающего переоткрытие закрытой оси.

### Q3 — Fresh-Eye Approval

- **Согласовал бы (или нет):** с оговорками.
- **Причины:**
  - «за»: контракт поведения полный и проверяемый — формула часов, округление, запрет нормативов в выводе, идемпотентность повторного запуска описаны как наблюдаемые факты;
  - «за»: границы честные — входящий файл не переписывается, обзор не трогается, папка шаблонов перестаёт быть источником с явным планом отката;
  - «против»: свежий читатель спотыкается о место подтверждения — D1 помещает строку подтверждения «в конце согласования», а условие второго вывода читает «лист вопросов»; при листе из одной фразы «вопросов нет» в листе физически нет места, куда подтверждение вписать (G6 ниже).

## Verdict

**CHALLENGE** — постановка решает Why оптимальным путём, но два не закрытых текстом инварианта реализации (место подтверждения при пустом листе; несколько названных факторов надбавки) способны сломать второй запуск и сделать часы неоднозначными — их надо закрыть фразой в design/spec до приёмки.
