## Task

Проверить подход из четырёх пунктов:

1. Пока блока постановки нет, создание с готовым именем не пишет описание и решение: сначала короткий бриф, либо разбор доработки обязан отдать блок до команды с именем.
2. Текст остановки — одна команда с темой и именем заявки; пустой разбор из текста убрать.
3. Если каталог уже есть, а требований нет, следующий шаг — дозавершение тем же именем, не дописывание и не вторая заявка.
4. Пустой разбор в новом чате по-прежнему ждёт описание; меняется только команда возврата.

## Complexity

Medium: правка контракта трёх скиллов и одного правила процесса, без кода 1С.

## Chosen Approach

**Вердикт: сузить.** Направление верное, все четыре пункта бьют в подтверждённые разрывы. Но в нынешнем виде подход оставляет петлю, из-за которой остановка сработает снова сразу после брифа и при дозавершении.

### Почему подход в текущем виде не закрывает петлю

Условие остановки (`.cursor/skills/openspec-new-change/SKILL.md:330`) — «нет `exploreContext`» плюс структурные признаки плюс нет отчёта архитектора плюс нет флага пропуска. `exploreContext` наполняется только из четырёх источников: блок в чате, журнал explain, файл передачи, legacy (строки 28–36, 44–49). Бриф B1 на стороне создания в этот список **не входит** (строка 38 лишь выводит из него имя). Значит:

- Пункт 1 (бриф перед описанием) сам по себе не снимает остановку: после подтверждённого брифа `exploreContext` по-прежнему пуст, на доработке с несколькими файлами остановка сработает снова.
- Пункт 3 (дозавершение тем же именем) упирается в то же условие: при повторе создания с именем блока в чате нет, `exploreContext` пуст, остановка повторяется. Это ровно то, что произошло бы с `absence-gantt-rules`.
- Пункт 2: если «одна команда с темой и именем» — это разбор (`/opsx:explore <тема> …`), то разбор доработки по строке 80 и строке 322 скилла разбора снова отправляет в создание без блока. Петля из отчёта stop-gates, разрыв 4, остаётся.
- Вилка в пункте 1 («бриф на создании **либо** блок из разбора») оставляет два места ответственности за один и тот же артефакт; это и есть исходный разрыв 2 из отчёта entry-handoff.

### Сужение (одно)

**Постановку для доработки без блока собирает только создание: подтверждённый бриф на стороне создания засчитывается как постановка в условии остановки, а при дозавершении каталога без требований бриф строится из уже записанного описания. Команда возврата из остановки — дозавершение `/opsx:new <name>`, не разбор.**

Что это даёт по пунктам подхода:

- Пункт 1: остаётся только ветка «бриф на создании». Ветку «разбор обязан отдать блок» убрать — она переписывает маршрутизацию фич в разборе (строка 80) и противоречит «без переписывания скиллов».
- Пункт 2: одна команда — `/opsx:new <name>`; имя несёт тему, каталог несёт описание. Разбор в тексте остановки не нужен вообще.
- Пункт 3: принимается как есть; дозавершение больше не упирается в остановку, потому что подтверждённый бриф по записанному описанию её закрывает.
- Пункт 4: принимается как есть.
- Архитектурная проверка не теряется: после подтверждённого брифа при структурных признаках срабатывает уже существующая ветка «анализ запускается сейчас» (строки 336–343). Это совпадает с картой `.cursor/rules/architect-gate.mdc:114` (на создании — блокировка, выход только флагом) и не вводит нового пути.

## Simplicity Check

- **Viable alternatives**:
  1. Подход как есть (бриф или блок из разбора; одна команда возврата неуточнённого вида) — оставляет повторную остановку после брифа и при дозавершении.
  2. Сужение выше — одна точка сборки постановки (создание), бриф засчитывается в условие остановки, возврат через дозавершение.
  3. Убрать остановку на строке 330 целиком и всегда идти в ветку «анализ запускается сейчас» — проще, но тогда описание и решение пишутся без подтверждения постановки, и согласованные правила диаграммы снова не попадают в заявку (исходный дефект).
- **Selected simplest viable design**: вариант 2. Меняются условие остановки, её текст и вход создания с именем; маршрутизация разбора не трогается.
- **Why not simpler**: вариант 3 убирает симптом остановки, но не причину — постановку никто не подтверждает.
- **Complexity budget**: файлов — 3 (скилл создания, скилл разбора строки 250/257/322, `sdd-workflow.mdc` при необходимости формулировки); новых шагов — 0 (бриф B1 уже существует, переиспользуется); новых флагов — 0.

## Что правка не должна сломать

1. Путь с готовым блоком в чате: создание по блоку идёт одной строкой без подтверждения и без остановки хода (`openspec-new-change/SKILL.md:28–31`, B0).
2. Выход из архитектурной проверки только флагом со следом в файле заявки (`.gate-override.yaml`, строки 345–351; `architect-gate.mdc:114`, `:151`) — бриф не должен стать вторым способом пропустить архитектора.
3. Дозавершение не создаёт второй каталог и не переспрашивает уже записанное: разработчик (строки 62–64), валидный режим формы (запрет в `forms-mxl-mode-gate.mdc` «resume — не переспрашивать»).
4. Пустой разбор остаётся новой темой и сам не читает отчёты и следы (`openspec-explore/SKILL.md:23`, `:29`, `:44`).
5. Дописывание уже полной заявки (есть требования и задачи) по-прежнему идёт через `/opsx:extend`, и создание/разбор не правят код (граница из отчёта stop-gates, параметр 7).

Вне сужения остаётся разрыв 6 отчёта entry-handoff: дописывание не читает блок из чата, хотя разбор (строка 257) это обещает. Подход его не закрывает; при правке строки 250 стоит не повторять это обещание.

## Режим формы в СППР

Факт: `proposal.md:18` — `"Report.сп_ОтсутствияСотрудников.Form.ФормаОтчета": bsl-only`. Слова заказчика (раздел «Результат», «What Changes» 1–8) описывают наблюдаемое поведение диаграммы и не содержат ни одного признака из `forms-mxl-mode-gate.mdc:47` («в модуле», «разметку не трогаем», программные элементы). Признак «разметка формы не меняется» появился только в собственном решении агента: `design.md:22`, `:30`, `:90–94` («Option A (выбран). Всё поведение в модуле формы отчёта. Разметка формы не меняется»; Option B с разметкой отклонён агентом).

Оценка: **дефект хода**, ставший возможным из-за **дыры правила**. Классификатор (`forms-mxl-mode-gate.mdc:43–47`) не говорит, откуда берутся «достаточные признаки» — из слов заказчика/постановки или из выбранного агентом варианта реализации. Агент закрыл класс «только модуль» собственным выбором места поставки, то есть сделал ровно то, что строка 45 запрещает («сомнение = вопрос, не угадывать»). Узкая дописка в правило: признаки «только модуль» берутся из постановки заказчика или кода, а не из варианта, выбранного в собственном решении того же хода.

Отдельный проход по форме в СППР **нужен**: при дозавершении записанный режим считается валидным и по правилу не переспрашивается и не перезаписывается, поэтому само дозавершение вопрос не задаст.
