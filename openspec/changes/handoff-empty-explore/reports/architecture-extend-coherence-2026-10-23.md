# Scope Coherence Audit — handoff-empty-explore (дополнение «вариант 1»)

## KB references

## Verdict

**drift-warning**

Дополнение остаётся внутри одной цели заявки и прямо усиливает Why: оно закрывает место, где постановка терялась на стороне разбора. Расползания на вторую цель нет. Но в нынешнем тексте артефактов три тихих расхождения, которые станут нарушением, если дописать только требование:

1. Отклонённая альтернатива в design («обязать разбор печатать блок до команды с именем», Option B) после дополнения частично становится принятым правилом — без сужения текста отклонения design противоречит сам себе.
2. Новое наблюдаемое правило не покрыто ни задачей, ни сценарием, ни строкой приёмки.
3. Отмена архивного «баг при открытой заявке — всегда дописать» для недособранной заявки не названа в `## Blast Radius`.

Оценка брифа «scope-violation» не подтверждается: отмена архивного правила — часть того же исправления (см. п. 7), а не выход за цель. Она недокументирована, а не чужая. После рекомендаций ниже вердикт становится `coherent`.

## Findings

### 1. Задачи ↔ Why

Why: после согласия постановка в чате не появилась; создание записало описание и решение и остановилось до требований; следующий разбор был без текста задачи.

|---|---|---|
| S1.1–S1.3 подтверждение на создании с именем без блока | «постановка не появилась», «создание остановилось» | соответствует |
| S1.4 подтверждение по записанному описанию | «остановилось до требований» → возврат к той же заявке | соответствует |

Отклонения:

- **S2 (признаки «только модуль»)** — не следует из Why. Он вытекает из того же инцидента (в заявке диаграммы режим «только модуль» взят из собственного решения хода, `reports/architecture-2026-10-23-handoff-empty-explore.md` § «Режим формы в СППР») и стоит в What Changes п. 6 и в Capabilities. Это не дрейф от дополнения: он был до него, срез независим и мал. По указанию брифа в другую заявку не выносится. Рекомендация — одна фраза в Why, чтобы связь была записана, а не выводилась.
- **Дополнение (вариант 1) задачи не имеет.** Ни S1.7, ни S1.8 его не покрывают: они различают «продолжить / дописать», а не «показывать ли команду создания без блока». Место утечки в скилле разбора — слот «Дальше» синтеза (`.cursor/skills/openspec-explore/SKILL.md:218`, разрешает `/opsx:new` без блока) и строка таблицы «feature … если по фиче шли шаги исследования» (`:322`), которая блок требует, но не запрещает команду без него. Нужна новая задача (см. Recommendations).

### 2. Non-Goals

Нарушений нет, при одном условии формулировки.

- «Маршрут доработки без обследования сразу идёт в создание не переписывается…» — дополнение действует только в исследовании, которое идёт понять и исправить. Строка `/opsx:new` напрямую для доработки без шагов исследования (`openspec-explore/SKILL.md:80`, первая половина `:322`) остаётся. Условие: в требовании явно назвать эту границу, иначе слово «исследование» в правиле читается как «любой запуск разбора», включая перенаправление доработки, и Non-Goal нарушается.
- «Готовый блок без повторного подтверждения» — не затронут: дополнение как раз опирается на блок.
- «Короткое подтверждение не заменяет пропуск разбора решения» — не затронут.
- «Дописывание полной заявки не начинает само читать блок из чата» — не затронут.
- «Пустой разбор не читает прошлый разговор» — не затронут.
- «Чужой режим формы не правится» — не затронут.

### 3. Согласованность Decisions с дополнением

Тихие противоречия есть, все текстовые, не по сути:

- **Decision «Подтверждение считается постановкой», альтернатива «обязать разбор печатать блок до команды с именем» — «Отклонено».** После дополнения для исследования с шагами разбор как раз обязан печатать блок до команды создания. Отклонение верно только для доработки без обследования (его же довод: «доработка без обследования как раз имеет право блока не собирать»). Текст нужно сузить: отклонено для маршрута без обследования; для исследования, которое понимает и чинит, принято (вариант 1).
- **Implementation Options, Option B (отклонён)** — та же формулировка «разбор доработки обязан печатать блок». Сузить так же; Option A дополнить: «плюс из исследования с шагами команда создания только рядом с блоком».
- **Decision «Куда вести финал разбора»** — с дополнением согласован, но команда продолжения недособранной заявки синтаксически та же (`/opsx:new <name>`), что и команда создания. Без оговорки правило «без блока команду создания не показывать» читается как запрет и на продолжение — против третьего пункта варианта 1. Нужна явная фраза: запрет касается создания новой заявки; продолжение уже существующего каталога тем же именем блока не требует.
- **Design Rationale** «Новый маршрут не заводится» — остаётся верным: дополнение сужает показ уже существующей команды, нового пути нет.
- **Goals** — дополнения нет; нужен пункт.

### 4. Behavior Contract ↔ чеклисты приёмки

Да, если дописать правило без задачи, контракт станет шире приёмки.

- Новый пункт Behavior Contract («из исследования, которое понимает и чинит, команда создать заявку стоит только в том же сообщении, где есть блок постановки») не имеет сценария в `specs/kit-protocol-coherence/spec.md`, строки в матрице приёмки design, задачи в S1 и строки в `S1.accept`.
- Граничные случаи варианта 1 (создание сразу — короткий ответ остаётся; продолжение недособранной без блока) уже покрыты: «Создание с именем без блока», «Подтверждение снимает остановку», «Недособранная заявка продолжается тем же именем». Новых сценариев на них не нужно, нужен только один на само новое правило.
- Primary S1 менять не нужно: он про создание. Новый сценарий — опциональная строка `S1.accept`. Срез S1 не раздувается до второй цели: тот же сценарий «постановка не теряется», только со стороны разбора.

### 5. Extend-секции в debug.md

Нет. `debug.md` содержит только пустой Verify decision ledger (`closed_decisions: []`). Работ без архитектурного сопровождения из Extend нет. Дополнение — первое, и этот отчёт его сопровождает.

### 6. Одна цель или несколько

Одна. Цель — «согласованная доработка доходит до требований и задач, а не теряется между разбором и созданием». Дополнение закрывает ту же потерю с другой стороны стыка: создание теперь само получает постановку (подтверждение), а разбор с шагами больше не отдаёт команду без постановки. Обе половины нужны, чтобы инцидент не повторился: без варианта 1 разбор по-прежнему может отдать команду без блока, и создание будет спрашивать то, что уже согласовано в исследовании, вместо того чтобы взять готовый блок.

S2 — смежная, но независимая подцель (тот же инцидент, другое правило). Она уже в заявке, мала и отдельным срезом изолирована; выносить её не требуется.

### 7. Отмена архивного «баг при открытой заявке — всегда дописать»

Это осознанная часть того же исправления, не выход за цель, — при условии явной записи.

- Why прямо описывает недособранную заявку: «остановилось до требований и списка задач», «следующий разбор … не продолжил». Дописывание (`/opsx:extend`) вставляет задачи в существующий список и не проходит остановленную цепочку «решение → требования → задачи» (design, Decision «Куда вести финал разбора»). Значит архивное правило для этого случая ведёт ровно в тот обрыв, который заявка чинит.
- Отмена узкая: каталог (`openspec/specs/kit-protocol-coherence/spec.md:133`, сценарий `:135–137`) и архив (`openspec/changes/archive/2026-10-05-kit-protocol-coherence/specs/kit-protocol-coherence/spec.md:95–99`) сохраняются для заявки с требованиями и задачами; сохраняется и главное обещание архивного правила — вторая заявка не заводится.
- Вариант 1 эту отмену не расширяет и не сужает: его третий пункт (продолжение коротким ответом без блока) — то же самое правило со стороны создания.
- Недостаёт только записи: секции `## Blast Radius` в design нет. Это и есть основание брифа для «scope-violation»; после записи основание снимается.

## Recommendations

### proposal.md

- **Why:** дописать одно предложение-связку: «В той же заявке режим формы был записан как „только модуль“ по собственному варианту хода, а не по словам заказчика». Это привязывает S2 к инциденту.
- **What Changes:** новый пункт: «В исследовании, которое идёт понять и исправить, команда создать заявку стоит только в том же сообщении, где уже есть блок постановки. Доработку без шагов исследования разбор по-прежнему сразу отправляет в создание, а там короткий ответ считается постановкой. Продолжение уже начатой заявки тем же именем блока не требует».
- **Acceptance Criteria:** новый пункт 7 тем же смыслом (одна строка наблюдаемого поведения).
- **Scope:** без изменений (файлы те же).

### specs/kit-protocol-coherence/spec.md (MODIFIED «Создание заявки читает один источник»)

- В текст требования дописать: «Исследование, которое идёт понять и исправить, SHALL показывать команду создания новой заявки только в том же сообщении, где напечатан блок постановки. Это SHALL NOT распространяться на доработку без шагов исследования и на продолжение уже существующей заявки тем же именем».
- Новый сценарий, например «Команда создания только рядом с блоком»: WHEN исследование с шагами дошло до предложения новой заявки, а блока постановки в этом сообщении нет — THEN команды создания в сообщении нет; сначала печатается блок.
- Остальные сценарии не трогать: граница «создание сразу — короткий ответ» уже покрыта «Создание с именем без блока», «продолжение без блока» — «Недособранная заявка продолжается тем же именем».

### design.md

- **Goals:** пункт «Из исследования с шагами команда создания новой заявки показывается только вместе с блоком постановки».
- **Decision «Подтверждение считается постановкой»:** сузить текст отклонённой альтернативы — «Отклонено для доработки без обследования. Для исследования, которое понимает и чинит, блок до команды создания обязателен (см. Decision ниже)».
- **Новый Decision «Команда создания из исследования — только рядом с блоком»:** правило; граница (доработка без обследования, создание сразу, продолжение тем же именем — не затронуты); довод — согласованная в исследовании постановка не должна снова собираться коротким подтверждением на создании; место — слот «Дальше» синтеза и строки финала разбора.
- **Decision «Куда вести финал разбора»:** одна фраза — продолжение существующего каталога тем же именем не считается командой создания и блока не требует.
