Три прямых противоречия предлагаемому расширению — **явные**, документированные, не тихие:

| Решение | Что говорит сейчас | Чем противоречит | Требуемый статус |

| **D7** | «Панель считается доступной, если пользователь уже открыл её или сам назвал файл» | C4: предикат удаляется, панель создаётся с нуля в managed-каталоге | MODIFIED |
| **D3** | Контракт узла `step / name / effect / evidence` | C5: `header + nodes + edges + views`, свод обратно к плоскому контракту запрещён | MODIFIED |
| **D6** | Эталон — пример узлов в скилле (список) | Фаза 2.1: эталон «хорошо» = граф, добавляется эталон «плохо» = аккордеон | MODIFIED |

**Тихие противоречия внутри действующего `design.md`** (обнаруживаются только при исполнении, verify их не поймал):

1. **D7 замкнут сам на себя.** Три утверждения D7 вместе делают первую карту недостижимой: «путь в артефактах не фиксируем» + «доступна, если пользователь сам назвал файл» + «агент путь не изобретает». Назвать ещё не созданный managed-файл пользователь не может — значит первая просьба всегда уходит в fallback. Это не расхождение с расширением, это дефект самого D7, существующий сегодня.
2. **D3 не противоречит ни одному решению, но не выполняет Why.** Плоский контракт без рёбер, слоёв и состояний не запрещает аккордеон — он его предписывает как единственную возможную форму. Запрет «панель не навигатор» (Behavior Contract п. 3, Risks «Панель снова навигатор») неисполним при таком контракте данных: HALT «без доказательства не публиковать» отсекает пустые узлы, но не отсекает список.
3. **D3 и предлагаемый порог считают разные единицы.** D3: «≥4 **узла** с эффектом» (узел = пройденная точка рассказа). C3: «≥4 доказанные **сущности** механизма» (источник, кэш, преобразование, событие инвалидации, результат). Семь линейных шагов проходят порог D3 и не проходят порог C3. Подмена единицы измерения без явной оговорки даст расхождение приёмки — verify не отличит один порог от другого.
4. **D5 перечисляет два законных входа, расширение вводит третий.** «Только по прямой просьбе или сработавшему намёку» → добавляется «принятое конкретное предложение» (три места). Формально это подвид намёка, но always-apply строка в `gate-dispatcher.mdc` уже реализована в двухвходовой формулировке и требует правки, иначе диспетчер и скилл разойдутся.

**D2 и D4 расширение не затрагивает** — два имени и отсутствие команды сохраняются (в словарь добавляется третье различение: текстовый резерв ≠ карта).

### 6. Одна цель или 2+ независимых

**Одна цель. Отдельная ЗНИ «предложение карты в командах» не требуется.**

Проверка на независимость (если срезы независимы — это две ЗНИ):

| Признак независимости | Результат |
|---|---|
| Отдельный пользовательский результат | Нет. Topology Test без карты, умеющей слои и рёбра, не имеет что предложить; карта без Topology Test не находит адресата. Результат один: «разработчик видит причинность механизма рядом с чатом, когда это даёт прибавку» |
| Отдельная приёмка, не ссылающаяся на второй срез | Нет. Приёмка S3 (сценарии «предложили / промолчали») проверяется только через построенную карту S2 |
| Возможность выпустить порознь | Нет в обе стороны. S3 без S2 предлагает то, чего нет; S2 без S3 работает только на прямую просьбу — это ровно Option B действующего `design.md`, зафиксированный откат, а не самостоятельная поставка |
| Отдельный контракт требований | Нет. Оба среза правят требования одной capability в одной дельте |

Граф `S3 → S2` в redesign это подтверждает: связь жёсткая, не «удобно вместе».

**Универсальный принцип держит одну capability.** Topology Test и Insight Test — предикаты по **форме связей между доказанными сущностями**: два слоя, где один питает другой; ветвление со схождением; жизненный цикл со состояниями; причинная петля; одно порождает несколько представлений; разные форматы разными путями. Ни один не упоминает предметную область. Они одинаково работают на штампе ЭП, на кэшах файлов, на маршруте согласования, на регистрах и на обмене. Предметность нужна расширению только в двух местах, и оба — не предикаты:

- эталон-fixture «хорошо» в скилле (образец для сверки);
- приёмочный кейс среза S2 (золотой сценарий).

**Единственный реальный риск расползания** — Open Question 3 redesign: «другие поверхности для картографа (`/review`, `/opsx:verify`)». Вот **это** уже другая цель: другой пользовательский вход, другая приёмка, другая роль карты (ревью вместо понимания механизма). Держать вне scope явной строкой, иначе следующий круг extend расползётся именно здесь.

**Расщепить стоит другое.** Срез S2 в предложенном виде содержит два разных предмета:

- (а) **семантика и носитель карты** — контракт `nodes + edges + layers`, два эталона, создание панели с нуля, технический гейт. Приёмка: «эталон в скилле — граф, не список; прямая просьба в чистом проекте даёт схему».
- (б) **маршрутизация субагента-картографа** — файл агента, строка в таблице ролей, `tool-name-guard`, `1c-agent-delegation`, навигатор паттернов, intent-шаблон, `AGENTS.md`, журнал агентов. Приёмка: «`grep` по имени роли даёт совпадения во всех пяти источниках маршрутизации».

Это восемь файлов инфраструктуры делегирования с собственным проверяемым результатом, никак не пересекающимся с приёмкой (а). Один slice-gate на два таких предмета даёт срез, который нельзя принять по частям.

## Recommendations

Порядок — как выполнять при `/opsx:extend scenario-map-canvas`.

### A. Rebrick срезов

Предметный сценарий допускается ровно в двух ролях: **(а)** эталон-fixture в скилле; **(б)** приёмочный кейс среза. Золотой сценарий штампа ЭП — приёмка и эталон, **не** условие «когда предлагать».
