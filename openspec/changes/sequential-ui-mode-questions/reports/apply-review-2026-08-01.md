## Зазоры постановки (не блокеры, усилить при apply/extend)

1. **S1.accept Primary** уже говорит «первый Mode на design», но задачи S1 **не** переносили Mode на design — это обещание S2. Текст приёмки S1 чуть опережает поставку.
2. **Триггер «форма в файлах»:** Decision 3a включает Form.xml **и** модуль формы. Если в handoff есть путь к `Module.bsl` формы «на всякий случай», вопрос всё равно появится на design — это ожидаемо. Нужно явно в S2.2: не путать «упомянули форму в тексте» с «форма в scope правок»; список строить из явных имён/путей Form + задач на UI.
3. **Пояснение «программно» в чате:** в SSOT вопроса стоит одна строка-пример под **эту** форму (кнопка/элементы в модуле, Form.xml не трогаем) — иначе ответ «3» остаётся абстракцией.
4. **Explore:** кроме переименования поля — правило вёрстки: каждое поле с пустой строкой; Файлы/Срезы/Открытые решения — маркированные списки; черновик режима формы — не обязательный выбор, а подсказка «уточнят на design», без давления ответить в new.

## Риски после S2 (остаются)

- N форм → N ходов на design (осознанный trade-off).
- Старые change с `artifact_mode` — fallback на весь form-scope.
- Пока S2 не влит в consumer (PavDO), поведение new не изменится.

Продолжать **apply S2 как есть** — ось постановки верная; кейс PavDO закрывается задачами S2.1–S2.5 (+ структура handoff). Отдельный extend не обязателен, если при реализации S2.1/S2.2 зафиксировать: (a) вопрос только после стабильного списка форм; (b) в тексте вопроса — имя формы + короткая расшифровка «программно»; (c) explore-блок со структурой.
