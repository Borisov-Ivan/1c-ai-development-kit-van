# Исследование проверки постановки tz-tech-project

**Вопрос:** менялась ли суть задачи между кругами проверки, или архитектура переоткрывала один и тот же вопрос.

**Исходный запрос:** заказчик считает, что проверка ходит по кругу без новой причины, и просит посмотреть постановку и архитектурные отчёты.

**Симптом:** за день несколько архитектурных отчётов и правки постановки.

**Объекты:** только файлы списка (proposal, design, tasks, debug, spec, три architecture-*.md). Код 1С не читался.

## Суть задачи сейчас

По файлу частного задания одна команда сначала пишет рядом лист вопросов и текст согласования часов языком обзора (без таблицы нормативов). После подтверждения согласования в листе и повторного запуска появляется техпроект таблицами для технического задания — объекты, проводки только если они есть в задании, внедрение/откат, часы — без кода процедур. Входящий файл задания не переписывается; имена сверяются с выгрузкой конфигурации; конфигурация 1С не меняется. Часы из прозы: (нижняя граница × коэффициент) + надбавка; надбавка на коэффициент не умножается; дробь поднимается до целого часа.

## Что менялось в постановке

Следы правок есть в `debug.md` (секции Extend) и в живом тексте design/tasks/spec (зеркало «Решения verify», D1–D3, S1.accept, Requirement).

1. **Extend (1)** — имена `<имя>-вопросы.md` / `<имя>-техпроект.md`, чтение ответов из листа, дыра если имени нет в `src/КАСК/cf/`, форма пункта листа, часы из прозы, папка шаблонов не второй источник. Цитата: «Ось команды (два файла, копии правил в навыке) не менялась.»
2. **Extend (2)** — ≥2 варианта у вопроса; часы как нижняя × коэффициент; надбавка за названный фактор; сохранение ответов; не копировать ожидание «да» в чате. Цитата disposition: «`two-phase-output rejected` (один запуск по-прежнему пишет оба файла).»
3. **Extend (3)** — после брифа вариант 1: **два последовательных вывода**; техпроект тогда «только по этой просьбе»; надбавка после умножения на коэффициент. Цитата: «`two-phase-output` (прежний отказ…) superseded этим подтверждением.»
4. **Extend (4)** — дробный результат часов вверх до целого.
5. **Extend (5)** — техпроект по **подтверждению в листе**, не по просьбе. Цитата: «Триггер „по просьбе подготовить техпроект“ superseded подтверждением в листе.»
6. **Extend (6) / slice-text-freeze** — текст среза не переписывать до прогона на файле задания. Цитата ledger: «Текст среза не переписывать. Дальше реализация команды, не новая правка постановки, пока её не прогонят на файле задания.»

Итог по смыслу Why: ядро «одна команда / вопросы пакетом / часы без нормативов в документе / техпроект после согласования» не сменилось на другую задачу. Менялись формулировки **когда** появляется второй файл и **как** считаются часы.

Правило, которое обрывает круг: закрытое решение `slice-text-freeze` + рекомендация architecture-loop-redesign «minimum» — не патчить постановку до прогона команды на файле задания; EC-1/EC-2/EC-3 не переоткрывать.

## Архитектурные отчёты по отдельности

### architecture-new-2026-09-23.md

- **Вывод:** `changes-required` — направление верное, но без G1–G3 (желательно G4–G6) риск разъезда листа и техпроекта, правки обзора, утечки нормативов.
- **Что потребовал изменить в постановке:**
  - G1 — контракт двух результатов (топология файлов, связка дыр, повторный запуск обновляет оба);
  - G2 — не трогать `.cursor/skills/openspec-overview/**`, копия голоса в навыке;
  - G3 — HALT нормативов/формул в любом выходе;
  - G4 — карта проводок только если есть в задании;
  - G5 — лист вопросов в Primary acceptance;
  - G6 — `[УТОЧНИТЬ]` не заменяет лист вопросов.
- **Метка:** НОВОЕ (первый архитектурный отчёт по change).
- **Вопрос:** открыл новые пробелы стартовой постановки (контракт выхода, обзор, нормативы), не крутил уже закрытый EC.

### architecture-extend-coherence-2026-09-23.md

- **Вывод:** `drift-warning` — подтверждённое расширение (два последовательных вывода + порядок надбавки) ломает согласованность артефактов и отменяет отказ `two-phase-output`.
- **Что потребовал изменить в постановке:**
  - proposal/design — два последовательных вывода и порядок надбавки;
  - Non-Goals — запрет только на перепись *входного* файла, разрешить выходной каркас для ТЗ;
  - D1/D2/D4/Behavior Contract/Slices/tasks/spec — под фазы и формулу;
  - debug — явный пересмотр disposition `two-phase-output`;
  - open question: модель артефакта фазы 2 (тот же `-техпроект.md` / отдельное имя / второй запуск).
- **Метка:** УТОЧНЕНИЕ относительно предыдущего (ось «два результата» из G1 → «два последовательных вывода»; плюс новая деталь формулы надбавки).
- **Вопрос:** вернул к уже решённому в Extend (2) отказу `two-phase-output` и заставил пересмотреть его после брифа заказчика — не новая пользовательская цель, а переформулировка той же оси «когда/как второй вывод».

### architecture-loop-redesign-2026-09-23.md

- **Вывод:** корень один (недоспецифицированная поверхность приёмки на осях trigger + hours); рекомендация **minimum** — не пересобирать срез, стоп патчей до прогона на файле задания.
- **Что потребовал изменить в постановке:**
  - не переписывать S1 (отказ consolidation);
  - зафиксировать freeze до Primary acceptance на реальном файле;
  - не переоткрывать EC-1, EC-2, EC-3;
  - следующий ход — реализация/приёмка, не шестой текстовый патч.
- **Метка:** ПОВТОР относительно предыдущего (те же оси trigger и hours, уже закрытые EC после Extend 3–5).
- **Вопрос:** вернул к уже решённому и явно сказал остановить круг, а не открыл новый контракт.

## debug.md

Записаны не круги дефектов кода, а круги **правки постановки после проверки**:

- Verify decision ledger: закрыты EC-1 (триггер техпроекта), EC-2 (надбавка после коэффициента), EC-3 (округление вверх), `slice-text-freeze`; `decision_round: 2` / `decision_round_max: 2`.
- Extend (1)–(2) — repair-from-verify, затем снова проверка постановки.
- Extend Coherence Audit + Extend (3)–(5) — брифы/ответы verify, снова `/opsx:verify`.
- Loop Detection — порог PatchRounds 5 > 3 → architecture-loop-redesign → Extend (6) freeze.

Связь с повторной проверкой постановки: прямая — каждый Extend заканчивался «следующий шаг: повторная проверка» / verify, пока не сработал freeze.

## Сводка

- Суть Why («одна команда по файлу задания → вопросы и согласование часов, затем техпроект таблицами») между кругами **не сменилась** на другую задачу (`proposal.md` ## Why / ## What Changes).
- Менялась **детализация одного контракта**: когда появляется `<имя>-техпроект.md` (оба сразу → по просьбе → по подтверждению в листе) и как считать часы (из прозы → ×k → +надбавка без ×k → округление вверх) — `debug.md` Extend (2)→(3)→(5), EC-1…EC-3.
- Первый архитектурный отчёт закрывал стартовые пробелы (G1–G6). Второй **переоткрыл ось двух выходов**, уже отвергнутую как `two-phase-output`, из‑за брифа заказчика — `architecture-extend-coherence-2026-09-23.md`.
- Третий отчёт зафиксировал: пять патчей — инкременты **двух осей**, не пять новых причин; живые артефакты с EC согласованы — `architecture-loop-redesign-2026-09-23.md`.
- Круг обрывает правило **`slice-text-freeze`**: текст среза не переписывать до прогона команды на файле задания; без нового confirmed ответа заказчика / факта после реализации — новый круг проверки постановки не обязан.
