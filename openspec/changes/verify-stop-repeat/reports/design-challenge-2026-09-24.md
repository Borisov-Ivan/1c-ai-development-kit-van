## Three-Question Challenge

### Q1 — Problem-Solution Fit

- **Why говорит:** пакет известных продуктовых вопросов сериализуется в одиночные; каждый вопрос стоит полного прогона; на техпроекте две развилки (момент второго файла и формула часов) были видны при создании задачи, но агент вписал свои ответы; заказчик пять полных прогонов отматывал по одному; контроль срезов пять раз считался с нуля; независимый разбор трижды повторял цепочку; стоп петли — на пятой правке вместо третьей.
- **Design адресует:**
  - Why «сериализация при создании» → Decision 5 (пакет до первой проверки, метка продуктовой развилки, запрет авторского ответа) + Behavior Contract п.1 + spec «Вопросы пакетом…».
  - Why «сериализация на остановке проверки / одна тема за круг» → Decision 6 (все открытые темы одной карточкой) + явное правило: формулировка «дописать вместе с ответом» не снимает уже известную тему; тема остаётся отдельным нумерованным вопросом + Behavior Contract п.2 + spec Scenario «Вторая тема остаётся на карточке».
  - Why «повтор контроля срезов с нуля» → Decision 3 (ключ: вердикт + набор названий сценариев + нормализованный текст Primary) + spec «Прошлый контроль среза остаётся».
  - Why «тройной повтор цепочки разбора» → Decision 7 (леджер как перепроверка, классификация новый/повтор/сужение, стабильные номера) + spec «Разбор сходится» / «Неподтверждённое закрытие…».
  - Why «стоп на пятой правке» → Decision 8 (тематический счётчик) + Decision 1 (порог правок — запасной, в начале прохода) + spec «Стоп по теме» / «Стоп на третьей правке».
  - Why «запись ответа снова гоняет всё» → Decision 9 (ответ ≠ смена постановки; узкий отпечаток) + стык глубины + spec «Ответ не перезапускает всё».
- **Покрытие:** полное. Новое наблюдаемое правило карточки закрывает дыру Decision 6: «все темы» можно было бы обойти сворачиванием второй темы в «дописать вместе с ответом», снова сериализуя ответы заказчика. Why про генератор «вопрос → полный прогон → следующий вопрос» этим правилом покрыт и на остановке проверки, не только при создании задачи.

### Q2 — Optimality

- **Выбранный путь:** Option A — точечные правки шести существующих файлов правил (две точки пакета, сходимость разбора, узкий отпечаток, тематический счётчик, опора на прошлый контроль); без нового контура и без кода конфигурации.
- **Альтернативы (включая не упомянутые в design):**
  1. **Карточка только из реестра ID тем (машинная схема без свободного текста сворачивания)** — сборщик карточки обязан вывести каждый open-theme-id нумерованным вопросом; канал «дописать вместе» исчезает конструктивно. Плюс: сильнее против LLM-перефраза. Минус: новый мини-контур схемы/валидации сверх точечных правок правил; для заявленного Non-Goals и Option A избыточен — исход «обе темы нумерованными» уже наблюдаемый контракт.
  2. **Одна составная развилка (оба оси в вариантах одного вопроса)** — меньше вопросов в сообщении. Плюс: короче карточка. Минус: смешивает независимые оси (момент файла / формула часов из Why); повышает риск авторского «синтеза» ответа агентом; хуже Why, чем раздельный пакет.
  3. **Только шаблон карточки без MUST в skill проверки** — дешевле по объёму правок. Плюс: меньше файлов. Минус: skill может снова породить сворачивание; Why-дыра на остановке остаётся вероятной — слабее Chosen (D6 + S3.3 в skill и шаблоне).
- **Вердикт по Q2:** оптимален. Option B/C из design справедливо отклонены (генератор остаётся / ломается дешёвый блокер). Альтернативы 1–3 не превосходят Chosen по сумме инвазивности, обратимости и покрытия Why; альтернатива 1 — усиление реализации при том же наблюдаемом исходе, не смена оси.

### Q3 — Fresh-Eye Approval

- **Согласовал бы (или нет):** да
