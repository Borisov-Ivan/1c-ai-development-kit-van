## Реализуемость как написано

### 1. MUST — назвать места в `model-selection.mdc`, которые противоречат исключениям

Migration Plan шаг 1 («записать исключения в правило назначения») и приёмка срезов («открыть правило и увидеть») не называют, где именно в файле сейчас написано обратное. В `model-selection.mdc` таких мест три, и они находятся в разных секциях:

- `:111` — секция «Цепочка для архитектора»: «Обычные режимы (`design`, **`task-readiness`**, `slice-decomposition`, `task-decomposition` и пр.)» с Primary Opus 5 на шаге 1. Прямое противоречие D1.
- `:138` — строка таблицы эскалации «Все остальные режимы (`design`, `slice-decomposition`, `task-readiness`, `task-decomposition`, **аудиты coherence**, …) → **не** Fable». Формулировка «аудиты coherence» включает `precedent-coherence-audit` — прямое противоречие D2. Требуется расщепление: `scope-coherence-audit` и `invariant-extraction` остаются «не Fable», `precedent-coherence-audit` уходит в лестницу.
- `:87` — строка роли `onec-code-architect` → `claude-opus-5-thinking-high` без оговорки о режимах. Нужна либо сноска «кроме режимов, перечисленных в цепочке для архитектора», либо явная отсылка, иначе оркестратор, прочитавший только таблицу, применит общую строку (риск, который сам design перечисляет в Risks).

Без этого перечня исключение реалистично появится в одной секции, а `:111` / `:138` продолжат утверждать противоположное — и это попадёт в один и тот же файл SSOT.

### 2. MUST — дописать в `architect-gate.mdc` или объявить перечень неполным

Дубль слага там отсутствует (архив это уже вычистил), поэтому правка текстовая, не про слаги.

### 3. MUST — последствие сбоя одношагового вызова для вердикта проверки

D1 корректно согласуется с «Целостность цепочки Task» (`model-selection.mdc:170`, п. 3: исчерпание цепочки → стоп и выбор пользователя). Но сегодня сбой платного шага у готовности задач поглощается вторым шагом на модели чата, и слой всё равно получает отчёт. После D1 второго шага нет: **один** сбой означает отсутствие `architecture-task-readiness-*.md`.

У проверки постановки формула вердикта требует `layer_5_implementation_readiness ∈ {PASS, WARNING}` (`openspec-verify-change/SKILL.md:371`), а маппинг слоя (`:356`–`:360`) знает только PASS / WARNING / FAIL и переиспользование прошлого отчёта. Статуса «агент не ответил» нет. Design должен назвать, что делает проверка: фиксирует слой как блокирующий и предлагает повтор команды, либо разрешает переиспользовать прошлый отчёт готовности, либо требует явного решения пользователя продолжить без агента (с записью риска). Это одна фраза в D1, но без неё поведение на сбое определяется по-разному двумя файлами.

### 4. MUST — дельты spec должны менять текст требований, а не только добавлять сценарии

Оба среза указывают только новые Scenario. Между тем меняется текст самих требований:

- «Мэппинг ролей на актуальные модели» (`spec.md:10`) сейчас утверждает `architect → claude-opus-5-thinking-high` без оговорки по режимам → MODIFIED с полным текстом.
- «Fable только как закрытая эскалация архитектора» (`spec.md:43`) содержит закрытый перечень (а)(б)(в) → MODIFIED: добавляется (г) `precedent-coherence-audit`; правила про отсутствующий слаг, строку в чат и «не запас после сбоя» переносятся без изменений.
- «Двухшаговая цепочка вызова» (`spec.md:31`) дельты **не** требует — полезно написать это в design, чтобы дельта не появилась «на всякий случай».

Без MODIFIED-текста живой spec продолжит утверждать безусловную тяжёлую модель для архитектора, и это разойдётся с текстом правила.

### 5. SHOULD — где строка в чат разрешена вне проверки постановки

Единственная точка запуска `precedent-coherence-audit` в рантайме — `verified-cause-gate.mdc:54` (HALT 4 Precedent Awareness). Она срабатывает в потоках фикса и ревью, **не** только в `/opsx:verify` (алгоритм Layer 2.4 в `precedent-regression-gate.mdc:64` механический и субагента не зовёт). При этом все тексты, разрешающие строку «Разбор постановки (Fable)» / «Разбор постановки (Opus 5)» до финальной карточки, привязаны к сценарию проверки: `chat-output-budget.mdc:22`, `chat-output-budget-full.mdc:26` и `:165`, `verify-user-communication.mdc:17`, шаблоны verify, а в specs — `session-api-mode/spec.md:83` и `chat-surface-clarity/spec.md:119`.

Нужна одна фраза в D2 или D4: строка идёт как обычная одиночная строка хода вне сценария проверки, файлы бюджета чата не меняются. Иначе реализация либо погасит строку (нарушив D2), либо добавит четвёртый файл сверх scope.

Смысловой момент («Разбор постановки» звучит в потоке фикса, где постановки нет) — решение заказчика «та же строка», не переоткрываю; достаточно пометки, что совпадение текста намеренное.

### 6. SHOULD — распределить файлы по срезам

Срезы заявлены независимыми, но не сказано, какие файлы правит каждый: S1 — `model-selection.mdc` + текст запуска в `openspec-verify-change/SKILL.md`; S2 — `model-selection.mdc` + `verified-cause-gate.mdc`. ## Simplicity Check

- **Viable alternatives:**
  1. Option A (выбрано автором) — исключения по режиму в одном правиле назначения, тексты запуска только ссылаются. 3 файла, 0 новых ролей, 2 исключения.
  2. Option B — отдельные роли субагента под два режима. 2+ новых файла агентов, дубль промптов, цепочки на каждую роль.
  3. Option C — снять тяжёлую модель со всех архитектурных шагов, кроме независимого разбора. Отменяет решение заказчика о создании плана.
- **Selected simplest viable design:** Option A. Переиспользует уже существующие конструкции (запись «без `model=`», лестница закрытой эскалации, одна строка в чат) и не заводит новых сущностей.
- **Why not simpler:** ещё проще — одна правка только таблицы ролей `:87`. Не проходит: таблица роль-ориентирована, а исключения режим-ориентированы; без правки цепочки `:111` и таблицы эскалации `:138` файл станет внутренне противоречивым (пункт 1).
- **Complexity budget:** файлов — 3 (после пункта 2 возможно 4); новых ролей и агентов — 0; исключений по режиму — 2; новых условных ветвлений в рантайме — 1 (проверка режима до общей строки роли).
