## Three-Question Challenge

### Q1 — Problem-Solution Fit

- **Why говорит:** (a) «После согласия на правила … постановка в чате не появилась. Создание заявки записало описание и решение и остановилось до требований и списка задач»; (b) «Следующий разбор был без текста задачи и уже согласованную диаграмму не продолжил»; (c) «режим формы был записан как „только модуль“ по собственному варианту хода, а не по словам заказчика».
- **Design адресует:**
  - (a) двумя точками. В исследовании с шагами команда создания новой заявки стоит только рядом с блоком постановки (закрывает источник: `openspec-explore/SKILL.md:218`, где `/opsx:new` допускается в промежуточном «Дальше»). На создании с именем без блока — короткое подтверждение до записи описания, и подтверждённый ответ считается постановкой для условия остановки (закрывает приёмник: `openspec-new-change/SKILL.md` шаг 1a → шаг 1.25 «exploreContext ещё не задан» → шаг 5.e.4 «Hard-gate when no exploreContext»). Цепочка «симптом → причина» по коду сходится: шаг 1a при аргументе идёт сразу к шагу 2, минуя 1b.0; при отсутствии блока exploreContext пуст; на сложном изменении 5.e.4 печатает `Создание specs/tasks остановлено` и предлагает `/opsx:explore` без темы.
  - (b) текст остановки получает одну команду — повтор создания с тем же именем; пустой разбор из него уходит. Поведение пустого разбора в новом чате (bootstrap-строка `openspec-explore/SKILL.md:21-29`, запрет чтения `temp/reports` до ответа) не меняется и явно записано как non-goal — корректно, чинить надо не приёмник пустого ввода, а то, что его туда отправляют.
  - (c) источник признаков «только модуль» — слова заказчика, блок постановки или код; вариант поставки из решения того же хода признаком не является. В коде `forms-mxl-mode-gate.mdc:47` признаки перечислены без источника («явная фраза „разметку не трогаем“ / „в модуле“»), и фраза из собственного `design.md` того же хода проходит классификатор. Причина названа верно.
- **Покрытие:** полное для трёх названных симптомов. Одна оговорка: Why описывает путь «создание с именем», и design/spec ограничены этим путём; путь свободного текста без имени (шаг 1b.5 → B1) после правки по-прежнему приходит в 5.e.4 с пустым `exploreContext` и показывает остановку (уже без пустого разбора, но с повторным подтверждением на resume). Это тот же класс симптома в ослабленном виде — см. G1.

### Q2 — Optimality

- **Выбранный путь:** подтверждение на входе создания считается постановкой; возврат к недособранной заявке — тем же именем; команда создания из исследования с шагами — только рядом с блоком; признаки формы не из решения того же хода.
- **Альтернативы (включая не упомянутые в design):**
  1. **Ленивое подтверждение в точке остановки** (не упомянута). Не спрашивать на шаге 1; описание и решение пишутся как сейчас, а в 5.e.4 вместо «выполните `/opsx:explore`» печатается подтверждение, собранное из уже записанного `Why / What Changes`, и после «да» идёт ветка 5.e.5. Плюс: простое изменение без структурных триггеров не получает лишнего вопроса; текст подтверждения богаче, чем одна строка «Изменение». Минус: описание записано до согласия заказчика, при «нет» остаётся каталог-сирота; противоречит принятому заказчиком критерию 1 («сначала спрашивает короткое подтверждение») и Behavior Contract 1. Не превосходит.
  2. **Свернуть шаг 1a в цепочку 1b** (не упомянута). Имя-аргумент перестаёт быть коротким путём «сразу к шагу 2» и становится подсказкой для сверки темы; при отсутствии источников путь сам приходит в 1b.5 с брифом B1. Плюс: одна точка подтверждения для обоих путей без блока, G1 закрывается конструкцией; исчезает дублирование сканирования между 1b.0 и 1.25. Минус: правка затрагивает шаг с B0-путём, который design объявил неприкосновенным; больше текста ради того же наблюдаемого поведения. Эквивалент выбранному при условии закрытия G1 одной фразой.
  3. **Исключить `design.md` из источников классификатора формы вместо правила «того же хода»** (не упомянута). Enumeration и признаки берутся только из `proposal.md` (куда переносится блок постановки), handoff и кода; разделы решения не читаются. Плюс: детерминированная проверка по источнику вместо временной («тот же ход»). Минус: в `design.md` зеркалятся ответы заказчика на пакет развилок (шаг 5.e.2) — их пришлось бы выносить отдельно. Эквивалент; полезна как проверяемая формулировка выбранного правила — см. G4.
  4. **Сохранить остановку для изменений с кодом 1С, снять только для kit-only** (не упомянута). Подтверждение считается постановкой лишь при доказанном kit-only (тот же признак, что в Metadata Gate шаг 1.5); при `.bsl` / `src/` в описании остановка 5.e.4 остаётся и ведёт в `/opsx:explore` с темой из подтверждения. Плюс: сохраняет исходный смысл hard-gate — сложное изменение кода без обследования не проектируется. Минус: отменяет закрытое решение заказчика «создание сразу без исследования по-прежнему считает постановкой короткий ответ» без опровергающего факта из кода; для кода есть предохранитель — архитектор на шаге 5.e.5 возвращает `Context Gap Report` при недостатке обследования. `reopen-blocked: explore_create_only_with_block`. Не предлагается.
  5. **Option B / Option C design** — рассмотрены автором, отклонения обоснованы, повторно не атакуются.
- **Вердикт по Q2:** оптимален. Ни одна альтернатива не даёт меньшего радиуса или лучшей обратимости; альтернативы 2 и 3 дают эквивалентный результат и сводятся к уточнениям текста выбранного пути.

## Gaps for design.md

- **G1** (блокирует формулировку S1.2/S1.3) — в Decision «Подтверждение считается постановкой» и Behavior Contract 1–2 записать: подтверждённый ответ короткого подтверждения считается постановкой на **обоих** путях без блока — имя аргументом и свободный текст (1b.5). Иначе явно обосновать асимметрию. Проверка по коду: сейчас `exploreContext` на пути B1 не задаётся (шаг 1.25 перечисляет только блок/explain/handoff/legacy), значит свободный текст со структурными триггерами по-прежнему приходит в 5.e.4.
- **G2** (блокирует формулировку S1.5/S1.6) — назвать, какой случай после правки ещё приводит к остановке «нет постановки» на шаге 5.e.4. По коду после S1.2 и S1.4 таких случаев не остаётся: нет блока → подтверждение → считается постановкой; resume без требований → подтверждение по описанию → считается постановкой; отказ от подтверждения останавливает ход до scaffold, а не на 5.e.4. Если случаев нет — записать, что ветка 5.e.4 снимается и при отсутствии отчёта архитектуры единственный путь — 5.e.5 «Анализ запускается сейчас» (или явный `--skip-architect`), а «одна команда с тем же именем» остаётся только в тексте остановок, которые сохраняются (например, отказ пользователя, `interrupted`). Если случай есть — назвать его, чтобы текст остановки было к чему писать.
- **G3** (дописка до apply) — в Decision «Команда создания из исследования — только рядом с блоком» / «Куда вести финал разбора» добавить третье место правки: «Change Creation Gate» исследования (явная просьба «создай ЗНИ»). Сейчас там вилка «новый change / дополнить существующий», что уже расходится с правилом финала «один следующий шаг» (строка 250) и не содержит ветки «описание есть, требований нет → тем же именем». Без этого явная просьба создать заявку на недособранном каталоге даст вилку new/extend мимо нового правила.
- **G4** (дописка до apply S2.1) — определить «код» как источник признака (например: форма уже собирается программно в модуле, разметка элементов отсутствует в Form.xml) и дать правилу «решение того же хода» проверяемую форму: собственным решением хода считаются разделы `design.md` § Decisions / Implementation Options / Design Rationale и выбранный вариант отчёта архитектора; блок постановки принимается источником потому, что заказчик продолжил работу с него (согласие продолжением), — зафиксировать это одной фразой, чтобы исполнитель не пытался трассировать блок дальше.
- **G5** (дописка) — исключение для продолжения тем же именем действует только когда каталог виден в `openspec list` в момент сообщения (шаг 0 исследования уже его вызывает); иначе `/opsx:new <name>` — команда создания и требует блока.
