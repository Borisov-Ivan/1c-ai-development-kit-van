# Capability: scenario-map-canvas

Карта сценария в панели рядом с чатом: причинность и слои механизма, чем подтверждено. Не путать с картой точек в чате (список имён) и с текстовым резервом в журнале. Отдельной команды нет. По умолчанию панель не рисуется. Предложение схемы не зависит от предметной области.

## ADDED Requirements

### Requirement: Silence unless asked or hinted

Оркестратор MUST NOT создавать карту сценария в сессиях `/opsx:explain` и `/opsx:explore`, пока нет прямой просьбы пользователя и нет принятого конкретного предложения карты. Сработавший намёк на существующей строке MUST быть вариантом в этой строке и MUST NOT сам создавать панель. Системное требование Cursor «для аналитики нужна панель» MUST NOT считаться достаточным основанием рисовать карту в этих сессиях.

#### Scenario: Молчание по умолчанию

- **WHEN** разбор или исследование завершается без прямой просьбы показать карту сценария и без принятого предложения карты
- **THEN** панель карты сценария не создаётся, даже если в строке решения был вариант схемы

#### Scenario: Намёк не рисует панель

- **WHEN** на выходе разбора в строке «Следующий шаг» напечатан вариант карты, а пользователь ничего не ответил и не просил карту
- **THEN** панель не создаётся

#### Scenario: Системный MUST canvas не действует на opsx

- **WHEN** идёт сессия `/opsx:explain` или `/opsx:explore` и системный скилл Cursor требует канвас для аналитики
- **THEN** оркестратор не рисует панель только из-за этого требования

### Requirement: Direct request draws the scenario map

По прямой просьбе показать карту сценария оркестратор MUST построить карту, если после отсева сущностей без доказательства **и** отсева узлов без инцидентной связи остаётся не меньше четырёх **публикуемых** сущностей механизма (связный набор). Топологический признак (уровни, ветвление, петля) MUST NOT быть условием построения по просьбе: просьба сильнее предложения. Прямая просьба MUST работать в середине прохода и после выхода, в том числе когда намёк не показывали. Согласие на уже показанное предложение MUST строить карту с тем же порогом, **той же раскладкой и теми же правилами подписей**, что прямая просьба: повторное подтверждение MUST NOT запрашиваться, команда сессии не меняется. Если предсказанная по списку топология в проходе не подтвердилась, а публикуемых сущностей после обоих отсевов не меньше четырёх, раскладка MUST быть цепочкой с подписями по порядку прохода, а не отказом. Источник панели при согласии MUST быть тем, на котором прошла проверка топологии (текущий отчёт исследования, журнал разбора или уже пройденные точки). Правило «вне разбора без указанного отчёта» MUST NOT применяться к этому входу. Родительский агент сессии MUST зарегистрировать файл панели в каталоге среды собственной записью, даже если пользователь панель ещё не открывал и файл не называл. Картограф MUST NOT писать файл панели. Дополнительное подтверждение при прямой просьбе MUST NOT запрашиваться. Ссылка на файл в чате MUST NOT быть критерием успеха: успех — схема рядом с чатом штатной кнопкой среды после чистой проверки панели.

#### Scenario: Прямая просьба рисует карту

- **WHEN** после разбора с достаточным числом сущностей пользователь просит показать карту сценария
- **THEN** открывается панель, где видно, что происходит, какие связи между сущностями и чем это подтверждено

#### Scenario: Карта во время прохода из уже пройденных точек

- **WHEN** пользователь просит карту сценария до записи журнала, уже разобрав достаточное число шагов
- **THEN** на карте только уже разобранные шаги и связи, без фактов, которых ещё не было в проходе

#### Scenario: Прямая просьба после выхода разбора

- **WHEN** журнал разбора уже записан и пользователь просит карту сценария
- **THEN** карта строится из журнала так же, как по просьбе в середине прохода; отдельного подтверждения нет

#### Scenario: Просьба при числе сущностей ниже порога

- **WHEN** пользователь просит карту сценария, а доказанных сущностей механизма меньше четырёх
- **THEN** панель не строится, в чате одна строка — чего не хватает

#### Scenario: Первая просьба в проекте без открытой панели

- **WHEN** пользователь впервые просит карту сценария, панели в проекте ещё не было и файл он не называл
- **THEN** родитель регистрирует файл панели в каталоге среды вне репозитория; в чате одна строка о готовности схемы без пути к файлу; схема открывается штатной кнопкой среды

#### Scenario: Панель открывается штатной кнопкой среды

- **WHEN** родительский агент зарегистрировал файл панели и получил чистую проверку панели
- **THEN** среда показывает штатную кнопку панели рядом с чатом; схема открывается этой кнопкой; ссылка в чате критерием успеха не является

#### Scenario: С узла открывается доказательство, новый чат с панели не запускается

- **WHEN** карта сценария уже показана и разработчик выбирает узел
- **THEN** открывается доказательство узла (диапазон модуля или журнал); новый чат из панели не запускается

#### Scenario: Порядок прохода не выдаётся за причинность

- **WHEN** карта построена по прямой просьбе из линейного порядка уже разобранных шагов
- **THEN** связи между соседними шагами подписаны как следование, а не как причинное отношение; причинные ярлыки есть только у рёбер, видимых в отчёте или журнале

#### Scenario: Просьба при линейной цепочке

- **WHEN** пользователь просит карту сценария, публикуемых сущностей не меньше четырёх, и они идут цепочкой без ветвления и без разных уровней
- **THEN** открывается панель: цепочка с подписями следования по порядку уже разобранных шагов, не список пунктов и не выдуманные ветки; порядок прохода не выдаётся за причинную связь

#### Scenario: Согласие на предложение рисует карту

- **WHEN** пользователь отвечает согласием на конкретное предложение схемы в существующей строке решения
- **THEN** карта строится так же, как по прямой просьбе: тот же порог, источник — тот, на котором прошла проверка топологии, отдельного подтверждения нет, команда сессии не меняется

#### Scenario: Согласие до первой карточки разбора запоминает фокус

- **WHEN** пользователь соглашается на «сразу карту» в строке подтверждения списка точек, а доказанных связанных сущностей ещё меньше четырёх
- **THEN** фокус запоминается, панель не публикуется, повторного вопроса «хотите карту?» нет; команда сессии не меняется

#### Scenario: Отложенное согласие публикует карту без повторного вопроса

- **WHEN** фокус «сразу карту» уже запомнен и в проходе набралось не меньше четырёх доказанных связанных сущностей
- **THEN** строка о готовности схемы — одна строка в том же сообщении, где карточка прохода впервые довела набор до порога; повторного вопроса «хотите карту?» нет; команда сессии не меняется; шаблон карточки точки не меняется

#### Scenario: Согласие было, порог до выхода не набрался

- **WHEN** фокус «сразу карту» запомнен, разбор дошёл до выхода, а доказанных связанных сущностей после обоих отсевов меньше четырёх
- **THEN** панель не публикуется; в уже существующей строке «Следующий шаг» на выходе одна честная фраза, что схема не собралась и каких связей не хватило; повторного вопроса «хотите карту?» нет

#### Scenario: Согласие при неподтвердившейся топологии даёт цепочку

- **WHEN** пользователь согласился на предложение схемы по предсказанной топологии списка, а в проходе после обоих отсевов не меньше четырёх публикуемых сущностей, но уровней и ветвления нет
- **THEN** открывается панель: цепочка с подписями следования по порядку прохода, как по прямой просьбе, а не отказ и не выдуманные ветки

### Requirement: Technical fallback is not a map

Если интерактивную панель создать нельзя, узлы и связи MUST попасть в журнал разбора в секцию текстового резерва, а в чат — одна строка, что интерактивная схема не создана и почему. Текстовый резерв MUST NOT называться картой на панели. Штатная запись журнала на выходе MUST сохранять уже записанную секцию резерва.

Допустимые причины резерва — только: среда без панели; каталог панелей не определился; запись или проверка панели исчерпала разрешённый ремонт. Отсутствие уже открытой панели и то, что пользователь не назвал файл, MUST NOT быть причинами резерва. Если проверка панели уже чистая, а пользователь явно сообщает, что схемы рядом с чатом нет, оркестратор MAY напечатать одну аварийную строку с путём к файлу либо уйти в текстовый резерв; это восстановление, MUST NOT становиться штатным критерием успеха.

#### Scenario: Среда без панели — резерв в журнале

- **WHEN** пользователь просит карту сценария, сущностей достаточно, но интерактивная панель в этой среде недоступна
- **THEN** узлы и связи записываются в журнал разбора как текстовый резерв; в чате прямо сказано, что интерактивная схема не создана

#### Scenario: Запись журнала сохраняет резерв

- **WHEN** текстовый резерв уже записан в журнал в середине прохода и на выходе идёт штатная запись журнала
- **THEN** секция резерва в журнале остаётся, а не затирается

### Requirement: Node contract forbids empty or code-primary nodes

Узел карты сценария MUST содержать идентификатор, человекочитаемое имя, тип сущности, слой, короткое описание «что происходит» и доказательство (диапазон модуля или путь журнала/отчёта). Узел без доказательства MUST NOT попадать на панель. Каждый опубликованный узел MUST быть связан хотя бы одной подписанной связью. У связи MUST быть отношение из закрытого перечня, человекочитаемая подпись и ссылка на источник отношения. Подписанная связь MUST опираться на уже видимое в источнике отношение: порядок уже разобранных шагов MUST отображаться отношением следования и MUST NOT подписываться причинным ярлыком; причинное отношение MUST быть явно видным в переданном отчёте, журнале или списке имён. Выдумывать связи MUST NOT. Если после отсева доказанных связей не хватает для порога, оркестратор MUST NOT публиковать панель, MUST сказать одной строкой, чего не хватает, и MAY продолжить разбор или исследование, чтобы добрать видимые связи. Код модуля, SQL и блок «на что смотреть» MUST оставаться в чате и журнале, а не быть основным содержимым панели. Панель MUST быть статичной: без статусов «сейчас разбираем этот шаг». Главный вид панели MUST NOT быть вертикальным списком или набором раскрывающихся пунктов без связей. С узла панели MUST открываться доказательство; запуск нового чата с панели MUST NOT.

#### Scenario: Узел без доказательства не публикуется

- **WHEN** для сущности нет строки модуля и нет пути журнала
- **THEN** эта сущность на панель не попадает

#### Scenario: Панель без статусов прохода

- **WHEN** карта сценария уже показана во время или после разбора
- **THEN** на узлах нет подписи вроде «сейчас разбираем»

#### Scenario: Код остаётся в чате

- **WHEN** карта сценария показана
- **THEN** фрагменты модуля и «на что смотреть» остаются в карточке чата и журнале, а не как основное содержимое панели

#### Scenario: Список без связей не публикуется как карта

- **WHEN** собран набор пунктов с эффектом, но нет подписанных связей между ними
- **THEN** панель как карта сценария не публикуется

#### Scenario: Связь без видимого отношения не выдумывается

- **WHEN** пользователь просит карту, а между сущностями нет отношения, видного в отчёте, журнале или порядке уже разобранных шагов
- **THEN** ребро не ставится; панель не публикуется за счёт выдуманных стрелок; в чате одна строка — чего не хватает; разбор или исследование можно продолжить

### Requirement: Causal map has layers or branches

Карта сценария MUST отвечать на центральный вопрос в шапке. Если в наборе есть причинные связи, шапка MUST показать главный причинный вывод. Если в наборе только следование по порядку прохода, шапка MUST назвать вывод из расположения и MUST NOT формулировать причинное утверждение о переходах. Порог публикации считается по **публикуемым сущностям механизма** после отсева узлов без доказательства **и** после отсева узлов без инцидентной связи (публикуется связный набор), а не по числу шагов рассказа. Число шагов MUST NOT быть достаточным основанием строить или предлагать карту. Скобки вроде «источник, кэш, преобразование, хранилище, событие сброса, результат» — примеры ролей, MUST NOT быть закрытым списком охвата.

Если на панели есть топологический признак, раскладка MUST показать либо не меньше двух уровней, либо ветвление со схождением. Если публикуемых сущностей достаточно, а признака нет (линейная цепочка по прямой просьбе), раскладка MUST быть цепочкой с подписанными связями следования. Вертикальный список или набор раскрывающихся пунктов **без связей** MUST NOT быть главным видом. Главный вид MUST быть графом (расположение узлов и стрелки), а не колонкой одинаковых карточек.

#### Scenario: Слои или ветвление видны на панели

- **WHEN** карта сценария опубликована и у сущностей есть разные уровни или ветвление
- **THEN** разработчик взглядом отличает уровни или ветки и видит подписанные связи между сущностями

#### Scenario: Семь линейных шагов не обязаны давать карту

- **WHEN** в разборе семь последовательных шагов без слоёв, ветвлений и повторного использования результата, и пользователь карту не просил
- **THEN** карта не предлагается и не строится только из-за числа шагов

### Requirement: Offer by topology not by topic

Оркестратор MUST предлагать карту сценария только если можно назвать конкретный вывод, которого нет в списке, и есть хотя бы один топологический признак (слои, где один питает другой; ветвление со схождением; жизненный цикл состояний; причинная петля или повторное использование устаревшего результата; одно порождает несколько представлений; разные технические пути). На выходе разбора и в «Дальше» исследования предложение MUST требовать не меньше четырёх публикуемых сущностей после обоих отсевов. На строке подтверждения списка точек разбора предложение MAY печататься по предсказанной топологии списка (или отчёта, из которого список собран), **без** требования ≥4 публикуемых сущностей уже сейчас; публикация панели на этом шаге MUST NOT происходить — действует отложенная постройка. Предложение MUST формулироваться через сущности и вывод, а не общим вопросом «хотите карту?». Предикаты предложения MUST NOT ссылаться на предметную область, тип объекта метаданных или конкретный механизм. Замеры времени MUST NOT быть условием предложения; время MAY быть признаком только вида «временная шкала».

Отказ предложения в исследовании и на выходе разбора MUST NOT печататься в чат. Если пользователь отказался («без карты»), повторно предлагать до выхода сессии MUST NOT.

#### Scenario: Исследование предлагает схему при топологии без замеров

- **WHEN** отчёт исследования содержит не меньше четырёх связанных сущностей с топологическим признаком и замеров времени нет
- **THEN** в «Дальше» ровно одно действие — показать схему, с фразой, что станет видно; пошаговый разбор в том же сообщении не предлагается

#### Scenario: Разбор предлагает схему на подтверждении списка без порога публикации

- **WHEN** на строке подтверждения списка точек разбор видит предсказанную топологию списка или отчёта, из которого список собран, замеров времени нет, и есть эта строка решения
- **THEN** в этой строке есть вариант «сразу карту» с фразой, что станет видно; порог «уже четыре публикуемые сущности» не требуется; панель на этом шаге не публикуется; слов про замеры времени как условие нет

#### Scenario: Разбор предлагает схему на выходе без замеров времени

- **WHEN** на выходе разбора есть строка «Следующий шаг», после обоих отсевов не меньше четырёх публикуемых сущностей, есть топологический признак, замеров времени нет
- **THEN** в этой строке есть вариант получить схему; слов про замеры времени как условие нет

#### Scenario: На линейных двух шагах схему не предлагают

- **WHEN** разбор проходит два линейных шага без слоёв, ветвлений и состояний
- **THEN** предложения схемы нет; в чате нет строки, почему схему не предложили

#### Scenario: Предложение не зависит от темы механизма

- **WHEN** топология есть у механизма любой предметной области
- **THEN** правило предложения то же, что у любого другого механизма; отдельного условия «если это такая-то тема» нет

### Requirement: No dedicated map command

В наборе команд `/opsx:*` MUST NOT появляться отдельная команда карты. Вызов идёт из исследования или из разбора по прямой просьбе, по принятому предложению или по намёку на выходе, без смены команды сессии.

#### Scenario: Нет отдельной команды карты

- **WHEN** разработчик смотрит список команд кита
- **THEN** отдельной команды «нарисовать карту» нет; разбор и исследование не нужно прерывать, чтобы получить панель

### Requirement: Two map names stay distinct

В чате и в словаре кита MUST различаться карта точек (список имён эффектов в сообщении до прохода), карта сценария (панель со связями) и текстовый резерв (запись в журнале, когда панели нет). Классы точек разбора MUST NOT выводиться на панель.

#### Scenario: Карта точек и карта сценария различимы

- **WHEN** после подтверждения брифа разбора показывается список шагов в чате
- **THEN** это карта точек (имена), а не панель карты сценария

#### Scenario: Эталон карты в скилле — граф, не список

- **WHEN** автор кита открывает скилл карты сценария
- **THEN** в нём есть эталон с узлами, слоями и подписанными связями и отдельный эталон, который нельзя публиковать как карту (список без связей)

### Requirement: Hint only on an existing decision line

Намёк или предложение показать карту сценария MUST быть вариантом в уже существующей строке решения: «Дальше» исследования, подтверждение списка точек разбора или «Следующий шаг» на выходе разбора — а не отдельным вопросом и не второй командой. Намёк MUST печататься только если пройдены условия предложения по топологии **и** в этом сообщении уже есть эта строка. Если на выходе разбора задан вопрос про доп. анализ, строки «Следующий шаг» нет — намёка нет. Если в исследовании проверка топологии не пройдена, а есть цепочка точек, «Дальше» MAY предложить пошаговый разбор. Если печатается блок постановки ЗНИ и строки «Дальше» нет — предложения схемы нет как следствие. Строка «Следующий шаг» в том же финале (команда создать ЗНИ) MUST NOT быть слотом предложения карты.

#### Scenario: Намёк на выходе разбора при топологии

- **WHEN** разбор закончен, проверка топологии пройдена, кандидатов анализа нет (есть строка «Следующий шаг»)
- **THEN** в той же строке «Следующий шаг» есть вариант попросить карту сценария

#### Scenario: Нет намёка, если уже вопрос анализа

- **WHEN** на выходе разбора задан вопрос, нужен ли доп. анализ
- **THEN** намёк про карту сценария не печатается

#### Scenario: Исследование не предлагает карту и разбор сразу

- **WHEN** исследование формирует «Дальше»
- **THEN** в сообщении ровно одно действие: либо схема, либо пошаговый разбор, либо иное одно действие по правилам исследования

#### Scenario: Нет предложения в финале исследования с постановкой

- **WHEN** исследование печатает блок постановки ЗНИ, и строки «Дальше» в этом сообщении нет
- **THEN** предложения схемы нет; отдельного вопроса про карту нет; строка «Следующий шаг» с командой создать ЗНИ вариантом карты не становится

### Requirement: Map outside walkthrough uses named source

Вне сессии разбора карта MUST строиться только из существующего журнала разбора или из отчёта, который пользователь указал. Иначе оркестратор MUST отказать одной строкой и MUST NOT собирать карту из произвольного контекста чата. Исключения, на которые отказ «укажите отчёт» MUST NOT применяться: (1) принятое конкретное предложение карты — источник тот, на котором прошла проверка топологии; (2) прямая просьба в активной сессии исследования, пока есть текущий отчёт исследования — источник этот отчёт.

#### Scenario: Вне разбора без источника — отказ

- **WHEN** пользователь просит карту сценария вне разбора, журнала нет, сессии исследования нет и отчёт не указан
- **THEN** панели нет, в чате одна строка, что карта строится из журнала или указанного отчёта

#### Scenario: Просьба в исследовании берёт текущий отчёт

- **WHEN** идёт сессия исследования, есть текущий отчёт, пользователь просит карту сценария и путь к файлу не называл
- **THEN** карта строится из этого отчёта; отказа «укажите отчёт» нет
