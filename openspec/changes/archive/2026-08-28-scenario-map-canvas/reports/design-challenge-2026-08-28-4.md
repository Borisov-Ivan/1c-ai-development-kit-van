# Design Challenge — scenario-map-canvas

## Three-Question Challenge

### Q1 — Problem-Solution Fit

- **Why говорит:** панель должна показывать причинность и слои (что питает что, оригинал и производная), а не столбик шагов. Три провала текущего контракта: (1) исследование сложной топологии предлагает только текстовый разбор; (2) разбор предлагает схему только при замерах времени; (3) прямая просьба «покажи карту сценария» уходит в плоский текст, потому что панель «доступна» лишь если её уже открыли или назвали файл. Предложение должно быть универсальным, от темы не зависеть.

- **Design адресует:**
  - Why говорит о причинности и слоях → design адресует через D3 (`header` + `nodes` + `edges` + `views`; узел без связи не публикуется; запрет списка/аккордеона без рёбер) и через закрытый словарь `kind`/`relation` в скилле (D9: без предметных имён в предикатах).
  - Why говорит о провале №1 (исследование → только разбор) → design адресует через D1 п.1: слот «Дальше» при прошедшей проверке топологии занимает схема, иначе — разбор; карта и разбор не в одном сообщении. Живой скилл исследования сейчас при цепочке точек предпочитает `/opsx:explain` (`.cursor/skills/openspec-explore/SKILL.md`, слот «Дальше») — это и есть провал №1; выбранный путь его снимает.
  - Why говорит о провале №2 (намёк только при замерах) → design адресует через D1 п.3 и Behavior Contract 10: замеры не условие; spec «Offer by topology not by topic» то же. Живой `exit-card.md` и скилл карты до сих пор требуют «≥5 точек и замеры времени» — это цель правки, не дыра постановки.
  - Why говорит о провале №3 (первая просьба → журнал из-за предиката доступности) → design адресует через D7: предикат снят; каталог из путей сессии по глобальному скиллу Canvas; резерв только технический. Живой скилл карты шаги 3–4 и секция «Без панели» подтверждают, что сейчас отсутствие открытой панели = запись в журнал под именем карты. Глобальный скилл Canvas (`~/.cursor/skills-cursor/canvas/SKILL.md`, Workflow §2 Location) подтверждает: файл пишется в managed-каталог, каталог не создавать вручную — D7 на этом и стоит.
  - Why говорит «предложение универсально» → design адресует через D9 / Invariant U; spec scenario «Предложение не зависит от темы механизма».

- **Покрытие:** частичное. Три непроходимых предиката и оба контура закрыты текстом design+spec. Не закрыто, **из чего берутся рёбра** при публикации. Живые карточки и журнал разбора не содержат полей связи или слоя (`inventory-card.md` — только имена; `explain-report.md` — «Что берётся» / доказательство; скилл карты — `step/name/effect/evidence`, эталон — нумерованный список без `edges`). Design Assumptions: «связи извлекаются из отчёта/журнала, не выдумываются»; D8: картограф не обследует код шире переданных диапазонов. Без правила происхождения ребра исполнитель либо додумает стрелки (карта лжёт про «что питает что»), либо не поставит рёбра → второй отсев обнулит набор → прямая просьба при четырёх узлах снова не даст панель (провал №3 в новой одежде: не «каталог», а «нет связей»). Для линейной просьбы закрытая ось требует цепочку с подписями — это возможно только если порядок прохода **явно** допускается как источник рёбер. Сейчас этого предложения в D3/D8 нет.

### Q2 — Optimality

- **Выбранный путь:** расширить существующий скилл карты и три уже существующие строки решения; макет панели — отдельный картограф (`Task`, `model: inherit`); публикация по просьбе при ≥4 связных доказанных сущностях даже на линейной цепочке; предлагать только при топологии.

- **Альтернативы (включая не упомянутые в `## Implementation Options`):**

  1. **Связи как поля карточки точки разбора** (не в Implementation Options). В шаблон карточки и журнал добавить слой и подписанную связь; картограф только рисует. Плюс: ребро имеет то же доказательство, что узел; второй отсев предсказуем. Минус: каждая карточка прохода толще; задевается chat-facing поверхность разбора (ADR-0001: в чат только продуктовые формулировки; риск жаргона `relation`); больше blast radius, чем «вариант в существующей строке». Почему не лучше целиком: Why лечится предикатами предложения и контрактом панели, а не новым полем в каждом шаге; инвазивность выше при том же наблюдаемом результате, если происхождение ребра зафиксировать без смены карточки.

  2. **Канонический граф всегда в журнале (YAML), канвас — проекция** (не в Implementation Options). Штатная запись разбора всегда содержит `nodes`+`edges`; панель — необязательный рендер. Плюс: технический резерв = тот же граф, нет расхождения «журнал vs панель». Минус: граф пишется даже когда карты не просили (давление на молчание и на объём журнала); два представления одного контракта. Почему не лучше: Non-Goals и D5 сохраняют «не рисовать и не собирать панель без входа»; обязательный граф в каждом журнале — скрытый автосбор.

  3. **Сборку панели откладывать до выхода разбора даже при просьбе в середине** (не в Implementation Options). Проще автомат состояния (нет публикации с неполного прохода). Минус: ломает spec «Карта во время прохода из уже пройденных точек» и приёмку «первая просьба даёт схему». Хуже по Why: разработчик в середине сложного прохода снова смотрит столбик карточек.

  4. **Симметричный топологический заслон и для прямой просьбы** — отклонена закрытым решением. `reopen-blocked: direct_request_linear_publish`. Живой эталон скилла — четыре линейных узла без рёбер: если вернуть заслон, просьба на последовательном разборе снова не даст схему.

  5. **Option A из design (оркестратор рисует сам)** — уже отклонена: нельзя задать рабочую модель макета параметром вызова и изолировать контекст прохода. Глобальный скилл Canvas всё равно обязан быть прочитан при записи `.canvas.tsx`; это не замена точке вызова, а носитель.

  6. **Option D из design (снять только время и доступность, плоский узел оставить)** — уже отклонена: список воспроизведётся. Согласен: без обязательных рёбер живой эталон так и останется столбиком.

- **Вердикт по Q2:** выбранный путь оптимален по числу точек перехвата (три существующие строки + скилл + одна роль) и по обратимости (выключить варианты в шаблонах, скилл по просьбе остаётся). Лучшей архитектуры среди неназванных нет. Преимущество альтернативы 1 — только доказанность рёбер; его нужно забрать **инвариантом происхождения ребра**, не сменой оси.

### Q3 — Fresh-Eye Approval

- **Согласовал бы (или нет):** с оговорками.

- **Причины «да»:**
  - Три провала Why снимаются точечно: приоритет в «Дальше», снятие замеров, снятие предиката доступности; молчание и отсутствие отдельной команды сохранены (D4/D5; ADR-0001 — формулировка предложения chat-facing; ADR-0002 — бриф Охвата не трогаем; ADR-0006 — прогресс по-русски, отдельного слага модели у картографа нет).
  - Предложение живёт внутри уже существующих слотов, а не второй командой — согласуется с эксклюзивным «Дальше» и с «одним следующим шагом» разбора.
  - Закрытая ось «просьба сильнее предложения» согласована с Why: первая просьба не должна упираться в отказ «нет ветки».

- **Причины «нет» (оговорки):**
  - Контракт причинности (обязательные рёбра) не стыкуется с живым источником узлов (карточка/журнал без связей). Пока это не записано как инвариант, свежий читатель не может быть уверен, что панель покажет «что питает что», а не подписи на искусственной цепочке или отказ после второго отсева.
  - Момент публикации отложенного согласия («сразу карту» на подтверждении списка) в spec есть как WHEN порог набран, но не сказано, в каком ходе относительно карточки прохода появляется ссылка на панель — риск отобрать слот шага или отложить до выхода вопреки сценарию.

## Verdict

**CHALLENGE** — ось решения Why верная и имплементируема, но до apply в design/spec не хватает инварианта происхождения рёбер (иначе причинность и первая просьба снова разъедутся с живыми карточками); развилку закрытой оси не открывать.

## Gaps for design.md

Инварианты реализации, не смена оси. Закрытые формулировки (намёк не рисует; просьба в исследовании берёт текущий отчёт; «сразу карту» MAY по предсказанной топологии; линейная цепочка по просьбе допустима) не переоткрывать.

1. **Происхождение ребра (блокирует причинность).** В D3 или D8 явно: (a) для линейной публикации по просьбе источником подписанных связей MAY быть порядок уже опубликованных карточек/записей журнала (это не выдуманная ветка); (b) для топологии — только отношение, которое уже видно в переданном отчёте/журнале/списке имён, отображённое на закрытый перечень `relation` без дочитывания модулей вне диапазонов; (c) додумывать рёбра из кода запрещено столь же жёстко, как публиковать узел без доказательства. Иначе второй отсев или ложная причинность.

2. **Ход публикации отложенного согласия.** В D1 / Behavior Contract 13 / spec scenario «Отложенное согласие…»: ссылка на панель — одна строка в том же ходе, где карточка прохода впервые дала ≥4 публикуемых связанных сущностей после обоих отсевов (или сразу следом, без нового вопроса и без смены команды); не ждать выхода разбора; не занимать слот «Следующий шаг» карточки отдельным предложением карты.

3. **Сценарий spec «Разбор предлагает схему без замеров»** сейчас одним WHEN смешивает подтверждение списка и выход («точек достаточно»). Тело требования уже разделяет: на списке — MAY без порога публикации «уже сейчас»; на выходе — MUST ≥4 после обоих отсевов. Развести сценарии или уточнить «точек достаточно», чтобы приёмка списка не требовала уже доказанных четырёх сущностей.

## Architectural alternatives

Нет. Равноправной развилки по коду/поведению, которую нужно выбирать до apply, нет. «Связи в карточке» vs «извлечение из журнала» закрывается Gap 1 внутри выбранной оси. Требовать топологию для прямой просьбы — `reopen-blocked: direct_request_linear_publish`.
