## Three-Question Challenge

### Q1 — Problem-Solution Fit

- **Why говорит:** по каждому частному заданию техпроект и часы собираются заново; шаблоны и обзор не связаны одной командой; вопросы к заказчику идут по одному в чат.
- **Design адресует:**
  - «техпроект и оценка часов заново» → D1/D3: команда по файлу задания пишет техпроект с часами через закрытый справочник навыка;
  - «шаблоны ↔ обзор не связаны» → D2/D4: голос/каркас обзора копируются в навык без правок `openspec-overview`; правила из `template/Техпроект` переносятся в навык без семиэтапного ритуала и баннера `[КОНТЕКСТ:…]` (факт: `_system_prompt.txt` этапы 0–6 + баннер статуса);
  - «вопросы по одному в чат» → D1: лист `<имя>-вопросы.md` с формулировкой, ≥2 вариантами и местом для ответа; чат не источник ответов; подтверждения до записи нет (факт: overview Entry Protocol ждёт «да» — D2 явно не копирует).
- **Покрытие:** полное по Why. Побочные цели Acceptance (имена из выгрузки, без нормативов в документе) закрыты D5 и D3.

### Q2 — Optimality

- **Выбранный путь:** новая команда + навык; копии правил и нормативов в навыке; `template/Техпроект` после переноса командой не читается; два выходных файла; голос обзора без протокола подтверждения; часы из прозы = нижняя граница строки × коэффициент, надбавка только за названный фактор.
- **Альтернативы (включая не упомянутые в design Options A/B/C):**
  1. **Полная формула §8 `labor_standards.md`** — Итого = (проектирование + разработка × множитель + тестирование) × коэффициент; в примерах того же файла берётся середина диапазона (12–16 → 14). Плюсы: ближе к исходному справочнику, который копируют. Минусы: раскрывает больше внутренней методики через числа; противоречит уже зафиксированному в design/spec правилу нижней границы. Почему не Chosen: ось часов в постановке уже выбрана; перенос файла «как есть» без вычёркивания §8/примеров создаёт риск, что агент следует файлу, а не D3.
  2. **Середина диапазона × коэффициент (без §8 надстроек)** — как в примере §9 `labor_standards.md`. Плюсы: ближе к исторической практике файла. Минусы: выше оценка для заказчика; ломает уже записанное «нижняя граница». Не превосходит Chosen при закрытой оси D3.
  3. **Тонкий навык + очищенная `template/Техпроект` как runtime-SSOT** — не Option C (папка «как есть» с ритуалом): ритуал вычищен, папка остаётся единственным источником. Плюсы: один SSOT нормативов. Минусы: команда снова зависит от папки вне навыка; риск вернуть `_system_prompt.txt`. Ось «копии в навыке» не переоткрывается без verified code fact.
  4. **Общий модуль голоса (symlink/include) между overview и techproject** — без полной копии каркаса. Плюсы: меньше дрейфа тона. Минусы: правка обзора начинает влиять на техпроект; выше связность. Why не требует общей поставки — слабее Chosen.
- **Вердикт по Q2:** Chosen оптимален относительно Options A/B/C и относительно альтернатив 2–4 при закрытой оси. Альтернатива 1 не лучше по Blast Radius для заказчика, но **файл-источник нормативов противоречит Chosen**, если копируется целиком без явного вычитания §8/§9 — это пробел постановки, не повод менять ось.

### Q3 — Fresh-Eye Approval

- **Согласовал бы (или нет):** с оговорками
- **Причины:**
  - Why закрыт одной командой и двумя файлами без чат-ритуала — согласуемо.
  - Обязательные контракты (≥2 варианта, формула нижней границы, сохранение ответов, папка не runtime, без подтверждения обзора) **есть в тексте** design/spec/tasks.
  - Не согласую «в apply как есть» без уточнений: (a) D4 формулировка «новый каркас техпроекта» в блоке «переносится из шаблонов» конфликтует с D2 (каркас = обзор) и с отказом от разделов 4.1.1–4.1.4 `template_technical.md`; (b) перенос `labor_standards.md` без явного запрета §8/середины диапазона даёт два конкурирующих алгоритма часов в одном навыке; (c) нет правила, что делать, если проза однозначно не указывает одну строку справочника.

## Verdict

**CHALLENGE** — решение закрывает Why и ось двух файлов / копий в навыке удержана, но перед apply остаются пробелы согласованности каркаса и детерминизма часов при переносе `labor_standards.md`.

## Gaps for design.md

- **D4 vs D2 (каркас):** в D4 явно: из шаблонов переносятся запрет выдумывать / фильтр / чеклист / нормативы; **каркас сюжета берётся из обзора (D2)**, структура `template_technical.md` (архитектура / алгоритм / интеграции / вопросы внутри техпроекта) **не** является выходным каркасом. Иначе writer может собрать «4.1 Архитектура» вопреки Behavior Contract.
- **Перенос нормативов (implementation_invariant):** при копировании `labor_standards.md` в навык MUST зафиксировать: расчёт для команды = нижняя граница выбранной строки × коэффициент справочника; надбавка = нижняя граница фактора и только если фактор прямо назван; **не применять** формулу §8 и **не брать** середину диапазона из §9. Иначе Scenario часов недетерминирован относительно файла-справочника.
- **Выбор строки справочника:** если описание работ в задании допускает ≥2 строки каталога — дыра в листе вопросов (не молчаливый выбор «сложнее»); если строка однозначна — писать часы по D3. Это уточнение Behavior Contract / tasks, не смена оси.
- **Порядок операций надбавки:** одна фраза в D3: `(нижняя граница строки × коэффициент) + надбавка_фактора` **или** `нижняя × (1 + доля_фактора) × коэффициент` — выбрать одно; сейчас «надбавка по нижней границе фактора» не фиксирует базу.
- **Единая фраза «дыр нет»:** выровнять design («вопросов нет»), tasks («дыр нет») и spec — одна наблюдаемая строка для приёмки.
- **Architectural forks:** не предлагаются. Ось «два файла / копии в навыке / папка не runtime / нижняя×коэффициент» удерживается; пробелы — `implementation_invariant`.

## Architectural alternatives

Нет равноправных развилок по коду/поведению, которые следовало бы выносить пользователю: альтернативы часов (середина / §8) хуже или ломают уже записанный контракт; runtime-SSOT папки ломает ось D4 без verified code fact.
