## Three-Question Challenge

### Q1 — Problem-Solution Fit

- **Why говорит:** техпроект и часы собираются заново; шаблоны и обзор не связаны одной командой; вопросы к заказчику идут по одному в чат.
- **Design адресует:**
  - «заново / одна команда» → D1: `/opsx:techproject` по файлу задания → рядом `<имя>-вопросы.md` и `<имя>-техпроект.md`;
  - «вопросы в чат» → D1: лист с формулировкой, ≥2 вариантами и местом для ответа; чат не источник ответов; повтор читает лист и обновляет те же пути;
  - «шаблоны ↔ обзор» → D2/D4: голос/каркас обзора копируются в навык без правок `openspec-overview`; правила из `template/Техпроект` переносятся в навык без семиэтапного ритуала и баннера `[КОНТЕКСТ:…]` (факт: `_system_prompt.txt` этапы 0–6 + баннер статуса);
  - часы без таблицы нормативов → D3; сверка имён с `src/КАСК/cf/` → D5 (путь подтверждён `openspec/project.md`, каталог существует).
- **Покрытие:** полное по Why. Симптом «вопросы по одному в чат» закрыт контрактом листа и запретом чата как источника ответов; «нет одной команды» закрыт D1; «часы / без нормативов наружу» закрыт D3.

### Q2 — Optimality

- **Выбранный путь:** новая команда + навык; правила и нормативы скопированы внутрь навыка; `template/Техпроект` после переноса командой не читается; два выходных файла; голос обзора скопирован без изменения файлов обзора; часы из прозы через закрытый справочник навыка.
- **Альтернативы (включая не упомянутые в design ## Implementation Options):**
  1. **Двухфазная команда (сначала только лист, техпроект — после ответов)** — наблюдаемое поведение: при дырах в первом прогоне нет отдаваемого техпроекта/часов, только `<имя>-вопросы.md`; второй запуск после заполнения листа пишет/обновляет `<имя>-техпроект.md`. Плюсы: заказчику не уходит черновик с открытыми дырами и спорной оценкой. Минусы: ломает цель «один запуск → оба файла» из Goals/Acceptance. Почему не превосходит Chosen: Why и Acceptance явно требуют оба артефакта за прогон; D5 уже фиксирует «не останавливаться из‑за одной дыры».
  2. **Часы только при готовой таблице работ во входящем файле** — если во входе только проза, в лист добавляется дыра «перечислите работы», строки часов в техпроекте не собираются из справочника. Плюсы: нет спорного маппинга прозы→нормативы (`labor_standards.md` даёт диапазоны вроде «12-16» и коэффициент). Минусы: не закрывает Why «оценка часов» на типичном неструктурированном задании. Почему слабее Chosen при закрытой оси D3: D3 уже выбирает сбор строк через справочник навыка; это уточнение алгоритма выбора числа внутри диапазона, а не смена оси.
  3. **Один файл с двумя крупными разделами (вопросы + техпроект)** — один артефакт для отправки. Плюсы: проще вложить в письмо. Минусы: смешивает лист для правок ответов с текстом согласования; ось «два файла» зафиксирована постановкой и не меняется без нового факта в коде. Не предлагается как reopen.
  4. **Тонкий навык + переписанная `template/Техпроект` как runtime-SSOT (без ритуала)** — не то же, что Option C (оставить папку «как есть» с ритуалом). Плюсы: один источник нормативов/чеклиста. Минусы: команда снова зависит от папки вне навыка; риск вернуть `_system_prompt.txt`. Ось D4 («копии в навыке, папка не runtime») не переоткрывается без verified code fact; закрывается предупреждением в Migration Plan, не сменой Chosen.
- **Вердикт по Q2:** выбранный путь оптимален относительно Options A/B/C и цели Why; альтернативы 1–2 жизнеспособны по поведению, но не превосходят Chosen по сумме «один прогон / часы на прозе / изоляция от ритуала». Остаточные сомнения — в недописанных инвариантах apply (см. Gaps), не в смене оси.

## Gaps for design.md

- **Spec ↔ D3/D4/D1:** в `specs/tz-tech-project/spec.md` добавить наблюдаемые MUST/Scenario: команда MUST NOT читать `template/Техпроект` как runtime-источник; при отсутствии готовых строк часов во входе строки MUST собираться по описанным работам через справочник навыка без таблицы нормативов в выходе; пункт листа MUST содержать формулировку, не меньше двух вариантов и место для ответа (сейчас «с вариантами» без нижней границы «два»).
- **Выбор часов из диапазона:** в design D3 / навык — правило, какое значение брать из строки `labor_standards.md` (нижняя/середина/верх диапазона или явное суждение с обоснованием) и как учитывать коэффициент из того же файла; иначе Scenario часов недетерминирован при apply.
- **Пересборка листа при повторном запуске:** зафиксировать, что уже вписанные ответы не затираются при обновлении формулировок/вариантов (или когда пункт считается «тем же» вопросом); иначе Scenario «Повторный запуск с ответами» допускает потерю ответов.
- **Граница копирования обзора:** явно: копируются каркас и голос (`customer-overview` / эталоны голоса), не Entry Protocol обзора (бриф B1, пауза до «да») — иначе риск вернуть вопросы/подтверждения в чат вопреки D1.
- **Migration Plan:** одно предупреждение «папка `template/Техпроект` может остаться в репо, но правки для команды — только в копии навыка» (без смены Chosen D4).

## Architectural alternatives

Равноправных развилок по коду/оси при текущих closed constraints нет. Ниже — только поведенческие альтернативы, уже оценённые в Q2 как не превосходящие Chosen; reopen оси «два файла» / «папка не runtime» не предлагается.

### Когда писать техпроект при дырах

**A. Один прогон: оба файла даже при дырах (Chosen, D5):** техпроект пишется по тексту задания; дыры — в листе. Trade-off: быстрее отдать пакет, выше риск черновика с открытыми вопросами.

**B. Двухфазно: техпроект только после ответов:** первый прогон — лист; второй — техпроект. Trade-off: чище согласование, хуже Acceptance «один запуск → оба файла».
