## Verdict

**drift-warning**

ЗНИ остаётся одной пользовательской целью (файл задания → вопросы + оценка/техпроект без выдумок и без нормативов в документе), но подтверждённое расширение **ломает согласованность текущих артефактов** с Why/Non-Goals/Design/Spec/Tasks и **отменяет** уже зафиксированный отказ `two-phase-output` в `debug.md`. Это не расползание в две независимые ЗНИ «по умолчанию», пока оба вывода — этапы одного конвейера одной команды; но без правок постановки принимать расширение нельзя — артефакты противоречат друг другу и брифу.

Отдельно по «два последовательных вывода»: **укладывается в ту же ЗНИ** как последовательные стадии одного сценария (сначала согласование часов голосом обзора, затем каркас ЧТЗ для ТЗ), **не scope-violation**, если Non-Goal про ЧТЗ переформулировать как запрет переписывать *входной* файл, а не запрет ЧТЗ-формата на выходе. Становится **scope-violation**, только если второй вывод оформить как отдельный продукт/команду вне Why «одна команда по файлу задания» или если сохранить формулировку S1.7/D4 «выход не бланк ЧТЗ» без снятия запрета.

## Findings

### 1. Задачи vs Why

**Why (текущий proposal):** по каждому частному заданию техпроект и часы собираются заново; шаблоны и обзор не связаны одной командой; вопросы идут по одному в чат.

| Задача | Соответствие Why |
|---|---|
| S1.1–S1.2 команда + Entry Protocol, два файла | Да — одна команда по файлу, не чат вместо файлов |
| S1.3–S1.4 каркас обзора + лист вопросов | Да — связный текст + вопросы пакетом |
| S1.5–S1.6 перенос правил и нормативов | Да — часы не выдумываются, таблица не в документ |
| S1.7 карта входящего, «не бланк ЧТЗ» | Частично / конфликт с расширением — см. п.2 и п.6 |
| S1.8 сверка с выгрузкой | Да — не выдумывать имена |
| S1.accept | Да по текущему BC; **не покрывает** два последовательных вывода и уточнённый порядок надбавки |

**Отклонения относительно подтверждённого расширения (ещё не в tasks):**

- Нет задачи на **порядок** «нижняя граница × коэффициент, затем + нижняя граница надбавки без повторного умножения» — в S1.6 формула описана слабее («часы = нижняя граница × коэффициент; надбавка — нижняя граница фактора»), без явного запрета `(база+надбавка)×k` или `надбавка×k`.
- Нет задач/приёмки на **два последовательных вывода** (согласование часов ≈ обзор → затем ЧТЗ для ТЗ, без кода разработчику, таблица без воды).
- S1.7 прямо запрещает превращение выхода в бланк ЧТЗ — **против** подтверждённого расширения.

### 2. Non-Goals

| Non-Goal (design) | Текущие артефакты | После расширения |
|---|---|---|
| Не создавать задачу в конфигурации / не править модули | Соблюдается | Соблюдается — расширение не ломает |
| Не показывать таблицу нормативов и формулу | Соблюдается (D3, spec) | Соблюдается — расширение не требует формулы в документ |
| Не переписывать входящее задание в полный бланк частного задания | Интерпретируется в tasks S1.7 / D4 как **запрет ЧТЗ-формата на выходе** | **Напряжение:** пользовательский ЧТЗ — *выход* техпроекта для размещения в ТЗ, не перепись входного файла |

**Вывод по Non-Goal «ЧТЗ»:** расширение **не ломает** Non-Goal, если читать его буквально: «не переписывать *входящее* задание». Ломает **текущую операционализацию** Non-Goal в D4/S1.7 («не превращая выход в бланк ЧТЗ»). Нужна явная переформулировка Non-Goal + Goals, иначе постановка internally inconsistent.

Нарушений остальных Non-Goals нет.

### 3. Согласованность Decisions

| Решение | Статус |
|---|---|
| D1 одна команда → `-вопросы.md` + `-техпроект.md` | Внутри себя согласован; с расширением — **тихий конфликт**: «два результата» ≠ «два последовательных вывода» (фаза 1 согласование / фаза 2 ЧТЗ). Неясно: один `-техпроект.md` с двумя фазами записи, два разных имени файлов, или два запуска |
| D2 сюжет = голос обзора + приложение разработчика в том же файле | Конфликт с расширением: фаза 1 ≈ обзор (без кода); фаза 2 = ЧТЗ-таблица техническим языком «разработчику не пишем код» — роль «приложение для разработчика» из D2 размывается |
| D3 нормативы внутри навыка, надбавка только за названный фактор | Согласован с Why; **недостаёт** явного порядка операций (база×k, затем +надбавка без ×k) — расширение уточняет, не отменяет |
| D4 перенос шаблонов; карта ЧТЗ только для *входа* | Конфликт с расширением: сейчас «карта входящего», запрет бланка на выходе; нужно разрешить **выходной** каркас ЧТЗ для ТЗ |
| D5 сверка с `src/КАСК/cf/` | Без конфликта |

**Тихие противоречия уже сейчас (до вписывания):** нет. **После вписывания без правки D1/D2/D4:** будут.

Дополнительно: `debug.md` Extend (2) — disposition **`two-phase-output rejected`**. Подтверждённое расширение **пересматривает** этот отказ → нужна явная запись в ledger/design, иначе тихий откат closed disposition.

### 4. Behavior Contract vs приёмка S1.accept

Текущий BC (design): один запуск → лист + один техпроект (сюжет обзора + приложение + часы); формула часов без порядка надбавки; повторный запуск обновляет те же два пути.

Чеклист S1.accept покрывает текущий BC (лист, этапы, приложение, часы, опциональные сценарии) **достаточно для текущего текста**.

После расширения BC станет шире:

1. Явный порядок надбавки — в S1.accept / scenario «Часы собраны из прозы» **нет**.
2. Два последовательных вывода (согласование ≈ обзор → ЧТЗ для ТЗ) — **не покрыты** primary и optional сценариями.
3. Запрет кода в выходе для разработчика / «однозначная таблица» — **не в приёмке**.

**Ответ:** да, после расширения Behavior Contract **шире**, чем S1.accept (и шире текущего spec).

### 5. Extend-секции без архитектурного сопровождения

В `debug.md`:

- `## Extend — 2026-09-23` — Architect Gate: **не требовался**
- `## Extend — 2026-09-23 (2)` — Architect Gate: **не требовался**; отвергнут `two-phase-output`

Счётчик «Extend без архитектора» M = 2 (< 3), объективный counter-триггер ещё не срабатывал; семантический drift-warning из брифа — да.

Объём, накопленный без architect-сопровождения: уточнения имён файлов, дыр, формы вопроса, часов из прозы, запрет копирования entry обзора — в основном **сужение/фиксация** оси. Риск: отказ `two-phase-output` сейчас **конфликтует** с подтверждённым выбором пользователя — без этого аудита отказ остался бы «тихим» барьером.

### 6. Одна цель или 2+ независимых?

**Сейчас (артефакты):** одна цель — `/opsx:techproject` по файлу задания → вопросы + техпроект с часами.

**С расширением:**

| Часть расширения | Вердикт по единству цели |
|---|---|
| Порядок надбавки (база×k, затем +надбавка) | Та же цель Why («часы не выдумываются») — **coherent** уточнение D3/spec |
| Два последовательных вывода | Та же ЗНИ, **если** это фазы одного конвейера одной команды по тому же файлу задания и тот же лист вопросов. **Не** вторая независимая цель, пока нет отдельной команды/отдельного Why «генератор ЧТЗ» |

**Итог п.6:** всё ещё **одна** цель ЗНИ при правильной формулировке Goals/D1/D2; риск расползания — если фаза 2 станет полноценным автором частного задания вместо «техпроект уже в формате ЧТЗ для размещения в ТЗ» (тогда Why и Non-Goal разъедутся → scope-violation и кандидат на `/opsx:new`).

## Recommendations

Без правки файлов этим отчётом — действия для оркестратора / следующего `/opsx:extend`:

### proposal.md

- В `## What Changes` явно: (1) порядок часов/надбавки; (2) два последовательных вывода — сначала текст для согласования часов (голос обзора), затем предложение/файл каркаса ЧТЗ для ТЗ без кода.
- В Acceptance Criteria добавить проверяемые пункты по обеим фазам и по формуле надбавки.
- Why можно усилить одной фразой: «после согласования часов — каркас для ТЗ», не меняя ядро «одна команда / не по одному вопросу».

### design.md

- **Goals:** добавить фазу 2 (ЧТЗ-каркас для ТЗ).
- **Non-Goals:** переформулировать пункт про ЧТЗ: «не переписывать и не заменять *входящий* файл задания полным бланком»; явно разрешить *выходной* каркас ЧТЗ для размещения в ТЗ. Сохранить запрет таблицы нормативов.
- **D1:** описать модель двух последовательных выводов (имена файлов, один или два запуска, связь с листом вопросов). Снять противоречие с «два файла = вопросы + один техпроект», если появляется третий артефакт или смена содержимого `-техпроект.md` по фазам.
- **D2:** развести аудитории: фаза 1 = сюжет обзора для согласования часов; фаза 2 = техническая однозначная таблица/каркас ЧТЗ без кода; уточнить судьбу «приложения для разработчика» (оставить в фазе 1, перенести в фазу 2, или сузить).
- **D3:** зафиксировать формулу: `часы = нижняя_граница_строки × коэффициент + (нижняя_граница_надбавки | 0)`; надбавка **не** умножается на коэффициент; фактор только если прямо назван в задании.
- **D4 / Behavior Contract:** убрать запрет «выход не бланк ЧТЗ»; оставить карту разделов для чтения входа.
- **Slices / S1.accept:** расширить primary или ввести подпункты фаз; обновить граф сценариев.
- В `debug.md` (оркестратор): зафиксировать пересмотр disposition `two-phase-output` → accepted с отсылкой к этому отчёту.

### tasks.md

- Уточнить S1.6 под явный порядок надбавки.
- Переписать S1.7: карта входа + **выходной** каркас ЧТЗ для ТЗ (не «не бланк ЧТЗ»).
- Добавить задачу(и) на два последовательных вывода и критерии в S1.accept (оба артефакта/фазы проверяемы).
- Согласовать S1.3 с фазой 1 (голос обзора) vs фазой 2 (технический язык, таблица).

### specs/tz-tech-project/spec.md

- В Requirement про часы — MUST порядок: база×k, затем +надбавка без повторного ×k.
- Новый Scenario (или AND в существующем) на два последовательных вывода: сначала согласование часов ≈ обзор; затем ЧТЗ-каркас для ТЗ без кода и без «воды».
- Убрать/не закреплять запрет выходного ЧТЗ-формата, если он появится при синхронизации со старым S1.7.

### Не делать

- Не выносить порядок надбавки в отдельную ЗНИ.
- Не объявлять scope-violation только из-за слова «ЧТЗ», если Non-Goal переформулирован про входной файл.
- Выносить в `/opsx:new` только если пользователь потребует отдельную команду/продукт «полный автор ЧТЗ» вне согласования часов.
