## Замечания (SUBOPTIMAL, не блокируют старт)

### 1. Приёмка третьего среза сформулирована по-разному в постановке и в задачах

- **Артефакт:** `design.md` § Slices (строка S3) против `tasks.md` — заголовок среза S3 и пункт S3.accept.
- **Что расходится:** в постановке главный критерий приёмки — «учебный `/opsx:new` на ЗНИ только из правил kit проходит без вопроса маркера», то есть демонстрация в живой сессии; в задачах — «в протоколе `/opsx:new` вопрос маркера только если будет BSL», то есть чтение текста скилла (и строка «Приёмка: чтение скилла и карточки брифа»).
- **Почему не блокер:** вариант из задач согласован с собственным прецедентом этой ЗНИ — в дельте `subagent-model-mapping` прямо записано «наблюдаемая приёмка среза — текст правил, не успешный вызов». Исполнителю понятно, что делать; расходится только формулировка.
- **Рекомендация:** привести строку S3 в таблице срезов постановки к формулировке задач.
- **Сниппет для авто-исправления** (`design.md`, § Slices, ячейка Primary acceptance строки S3):

```markdown
В протоколе `/opsx:new` вопрос маркера только если будет BSL; ЗНИ без `.bsl` не спрашивает маркер; в proposal сразу n/a / minimal; при позднем `.bsl` apply не пишет `n/a` в маркер
```

### 2. У первого среза не указан режим правки

- **Артефакт:** `tasks.md`, шапка среза S1.
- **Что отсутствует:** строка «**Режим apply:** mechanical», которая есть у срезов S2 и S3.
- **Почему не блокер:** правки только в markdown, участие агента-разработчика BSL исключено по определению scope, поэтому неоднозначности «через кого править» на практике не возникает.
- **Рекомендация:** добавить строку для симметрии, чтобы исполнитель не искал различие там, где его нет.
- **Сниппет для авто-исправления** (`tasks.md`, после строки «**Зависимости:** нет.» в шапке S1):

```markdown
**Режим apply:** mechanical
```

### 3. В задаче S3.6 не назван порядок между вопросом автора и значением из карточки проекта

- **Артефакт:** `tasks.md`, S3.6 — «задать вопрос про автора (или взять разработчика по умолчанию из карточки проекта)».
- **Что отсутствует:** явный порядок приоритета в тексте, который исполнитель будет записывать в протокол apply.
- **Почему не блокер:** порядок уже зафиксирован в самом целевом файле (`openspec-apply-change/SKILL.md`, блок Metadata Prep): при пустом значении берётся разработчик по умолчанию, и только если его нет — один вопрос про ФИО. Исполнитель, правящий этот блок, унаследует существующий порядок.
- **Рекомендация:** дописать порядок в формулировку задачи, чтобы новый текст правила не получился двусмысленным.
- **Сниппет для авто-исправления** (`tasks.md`, S3.6, замена скобочной вставки):

```markdown
(если разработчик по умолчанию из карточки проекта задан — взять его без вопроса; если пусто — один вопрос про ФИО)
```

### 4. Нумерация задач первого среза не совпадает с порядком исполнения

- **Артефакт:** `tasks.md`, срез S1: S1.14 стоит между S1.1 и S1.2, S1.15 — после S1.13.
- **Почему не блокер:** порядок исполнения задаётся положением в документе, а идентификаторы стабильны и используются в отчётах; перенумерация сломала бы ссылки.
- **Рекомендация:** оставить как есть; при следующем расширении среза добавлять пункты в конец соответствующей подсекции.
