# Architecture: decision-evidence-reopen — декомпозиция на срезы

## Task

Разбить ЗНИ kit-репозитория `decision-evidence-reopen` на вертикальные срезы для блока `## Slices` в `design.md`. Код 1С не меняется; приёмка — прогон команды kit на модельной тестовой ЗНИ (фикстуре) с наблюдаемым результатом в чате и в файлах этой фикстуры.

## Complexity

Complex: 14 файлов kit, три команды (`/opsx:verify`, `/opsx:archive`, развилка `/opsx:apply`), оценка объёма задач ≥ 16 → порог Full: минимум два среза при двух и более независимых результатах.

## Проверка независимости трёх результатов

| Результат | Команда приёмки | Общие файлы с другими | Нужен ли другой срез для приёмки | Вывод |
|---|---|---|---|---|
| (а) доказательство в карточке + возврат решения по опровергнутой предпосылке | `/opsx:verify` | verify `SKILL.md`, `report-header.md`, `architect.md`, `onec-code-architect.md` (с б); `openspec-apply-change/SKILL.md` (с в, только при ответе P1 = останавливать) | нет | отдельный срез |
| (б) сигнал упрощения из готовности + строка о непроверенной простоте | `/opsx:verify` | те же четыре файла с (а) | нет: ремонт по критерию 7 и строка простоты не читают ни `premise`, ни `refuted_premises[]` | отдельный срез |
| (в) следы замечаний качества до архива | `/opsx:archive` (+ развилка `/opsx:apply`) | `openspec-apply-change/SKILL.md` с (а) только при P1 = останавливать | нет: файл следов не входит во входы проверки и в ключ свежести архива | отдельный срез |

Почему (а) и (б) не объединены, хотя правят одни файлы. Общие файлы задают порядок реализации, а не зависимость приёмки. Primary (б) проходит на фикстуре без единого решения с предпосылкой, Primary (а) — без отчёта готовности. Боль в `proposal.md` `## Why` тоже разная: «выбор на неверном факте» и «замечание об избыточности не дошло до решения» — два отдельных абзаца и две отдельные частоты аудита (1 из 17 и 2 из 7). Реализация всё равно идёт по срезам по порядку S1 → S2 → S3, поэтому правки одного файла не конфликтуют.

Почему (б) и (в) не объединены: разные команды приёмки, разные файлы, разные пункты `proposal.md` (п.4, 6 против п.5).

## Simplicity Check

Для `mode=slice-decomposition` сравниваются варианты нарезки, а не технические решения.

- **Варианты:**
  1. Один срез на всё: один Primary покрыл бы только один из трёх результатов. Два других остались бы optional, и приёмка ЗНИ не подтвердила бы п.4–6 `proposal.md`.
  2. Три среза по результатам (выбран).
  3. Четыре среза: доказательство в карточке отдельно от возврата решения. Отклонён: Primary для «доказательства в карточке» требует, чтобы проверка сама породила тему с различающим утверждением, а это полный прогон слоёв с архитектором (дольше 15 минут и недетерминированно). Наблюдаемая часть доказательства и так видна в пункте возврата решения (`путь:строка` у исправленного факта). Правила шаблонов проверяются статически.
- **Почему не проще:** вариант 1 ломает правило «один blocking journey на срез» при трёх независимых результатах.

### Граф зависимостей

- S1 → нет
- S2 → нет
- S3 → нет

Приёмка каждого среза не требует других. Порядок реализации S1 → S2 → S3 фиксирован последовательной реализацией срезов, а не зависимостью приёмки. S1 и S2 правят одни и те же места в `openspec-verify-change/SKILL.md`, `report-header.md` (канонический перечень контролей), `architect.md` и `onec-code-architect.md` (блок закрытых решений в промптах разбора и готовности). S2 дописывает поверх правок S1 и не переписывает их.

**Связь между срезами, которую нужно закрепить в `design.md` до задач.** Имя файла следов (S3) фиксируется в `design.md` заранее. Сверка предпосылок из S1 смотрит в `reports/` новые отчёты после прошлого снимка и должна исключать из них этот файл, как и `verification-*`. Иначе каждая запись следа запускала бы лишнюю сверку предпосылок. Класс: правка постановки агентом, не продуктовая развилка.

### Критерии приёмки по срезам

- **S1** SHALL: на ЗНИ без правок постановки отдельный отчёт с опровергающей ссылкой на код превращает повтор прошлого итога проверки в вопрос о подтверждении именно того решения, предпосылку которого он опроверг.
- **S2** SHALL: неучтённое замечание готовности об избыточности к концу прогона проверки превращается в правку задач или записанную причину со ссылкой на источник, а итог проверки для разработчика не меняется.
- **S3** SHALL: архив ЗНИ с открытым замечанием о спорном качестве не выполняется молча: разработчик видит замечание и выбирает ревью, архив без ревью или стоп.
