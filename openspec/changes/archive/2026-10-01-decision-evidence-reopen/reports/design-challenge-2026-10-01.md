## Three-Question Challenge

### Q1 — Problem-Solution Fit

- **Why говорит:** «утверждение о текущем поведении системы было подано как факт без доказательства… код опроверг это утверждение, но выбор остался в силе и продолжал запрещать простой путь… проверка готовности задач и ревью отметили избыточность кода, но оба замечания до решения не дошли… в 12 карточках из 17 доказательство не стоит рядом с утверждением… ссылка была, но показывала не то место, где возникает значение… замечания готовности об избыточности потерялись в двух задачах из семи… открытые замечания ревью о качестве ушли в архив без ревью в двух задачах из четырёх».
- **Design адресует:**
  - факт без доказательства → Behavior Contract п.1–2 (доказательство у утверждений, различающих варианты; без него — вопрос о факте в той же карточке) — **полное** покрытие, включая пакет при создании (spec «Непроверенный факт в пакете»);
  - ссылка «не туда» → п.1 «где значение возникает», п.9 смысловая проверка в разборе — **частичное**: п.9 действует «если разбор и так запущен», а после ответа заказчика следующий прогон по ADR-0014 точечный, разбор не стартует; остаётся только текстовое правило, то есть тот же механизм, который в эталоне и подвёл (см. альтернативу 2 в Q2 и G1);
  - выбор остался в силе после опровержения → п.3–8, D2–D4 — **полное** для решений без внешнего контракта; для решения с `EC-*` п.4 опирается на «действующее правило парного закрытия», которое в текущем тексте сравнивает `closed_at` только с `primary_event_at` сигналов внешнего контракта (`openspec-verify-change/SKILL.md:242`) — опровержение туда не входит, правило без дописки блокер не выведет (G2);
  - замечания готовности потерялись → п.10, D5 — **полное** по цели, с незакрытым критерием выбора «правка задач или причина» (G6);
  - замечания ревью ушли в архив → п.12–14, D7–D8 — **полное**; закрыть замечание архив не может, «архив без ревью» — не решение по качеству (ADR-0003 соблюдён);
  - обещание `architect-simplicity-missing` не работает → п.11, D6 — **частичное**: контроль проверки покрывает три режима, а правило требует секцию в семи (G3).
  - Пункт 7 What Changes (карточка приёмки, «принято без проверки») в `## Why` не мотивирован — это ответ заказчика (закрытые решения `acceptance_card_shows_remainder`, `untested_acceptance_mark`); проблемы с ним нет, фиксирую как наблюдение, не разрыв.
- **Покрытие:** частичное — все боли из Why адресованы верной точкой, но два механизма (парное закрытие, контроль простоты) обещают больше, чем даёт текущий текст, на который они ссылаются.

### Q2 — Optimality

- **Выбранный путь:** всё поверх существующих мест — правило доказательства в одном шаблоне, поле `premise` и дописываемый `refuted_premises[]` в журнале решений, детерминированная сверка предпосылок оркестратором проверки перед быстрым путём, внутренний ремонт по критерию 7, строка «к сведению» о простоте, один файл следов в `reports/`, вопрос архива, строка места среза в передаче.
- **Альтернативы (не упомянутые в design):**
  1. **Структурное объявление опровержения в самом отчёте агента** вместо сканирования свободного текста. У архитектора и исследователя уже есть обязательная секция `## Knowledge conflicts` с «KB says / code says» при конфликте с фактом базы знаний (`onec-code-architect.md:25`, `onec-code-explorer.md:28`). Зеркальная секция `## Premise conflicts` (`decision_id`, `refuting_anchor`, «решение опиралось на / код показывает») делает сверку п.5 действительно детерминированной: оркестратор ищет секцию, а не читает каждый новый отчёт целиком. Плюсы: контекст проверки не растёт с числом отчётов, тот же паттерн, что для KB; минус: отчёт, написанный не агентом kit (ручная заметка), секции не несёт — нужен запасной путь (поиск по пути `premise.anchor` в тексте отчёта). Design D3 говорит «детерминированный контроль», но не задаёт, по какому признаку отчёт считается опровергающим; без этого контроль либо недетерминирован, либо дорог. **Превосходит** в части определённости; совместима с D3 (отдельного агента нет) → G1, не развилка.
  2. **Проверка живости ссылки оркестратором при сборке карточки.** Перед выводом утверждения с `путь:строка` проверка читает эту строку (один `Read offset/limit`) и требует, чтобы в ней встречался символ или значение из утверждения; иначе утверждение подаётся как «без доказательства» (п.2). Дешёвый детерминированный заслон против эталонного случая «ссылка есть, но не туда», который сейчас закрыт только текстом п.1 и условной смысловой проверкой п.9. Минус: не отличает «строку, где значение возникает» от «строки, где используется», если символ встречается в обеих — но это уже уровень п.9. **Дополняет** выбранный путь; не упомянута.
  3. **Отпечаток опровержения без номера строки.** D4 задаёт `fingerprint = SHA-256(decision_id|refuting_anchor)` с `refuting_anchor = путь:строка`. Сдвиг строки после любой правки файла даёт новый отпечаток, и пересказ того же опровержения эскалируется снова — вопреки сценарию «Повтор опровержения без нового факта». Вариант: отпечаток по `decision_id` + нормализованный путь (без строки) + хэш утверждения-опровержения; строка остаётся в `refuting_anchor` для показа. **Превосходит** по устойчивости; минус — два разных опровержения из одного файла сольются, что приемлемо: тема одна и та же до нового ответа → G4.
  4. **Включить листинг `reports/` во входы быстрого пути** (хэш списка имён). Отклоняется: любая запись следа, handoff или отчёта ломает кэш — хуже точечной сверки п.5. Подтверждает, что выбранный путь лучше этой альтернативы.
  5. **Следы качества как записи `## Slice Gate Decisions`** (исключены из ключа свежести, как и пометка D9). Отклоняется: след — не решение по срезу, значения поля `Решение:` закрыты (`vertical-slices.mdc:309`), `/review` отмечает результат по замечанию, а не по срезу; смешение ломает читателей секции. D7 (файл в `reports/`) лучше.
  6. **Критерий 7 как строка «к сведению» пользователю вместо тихого ремонта.** Отклоняется как замена: `proposal.md` п.4 требует «либо учтено в задачах, либо записана причина»; строка без записи это не даёт. Но она показывает, что в D5 не хватает критерия выбора между правкой задач и причиной (G6).
- **Вердикт по Q2:** оптимален по форме (ни одна альтернатива не меняет выбранную ось: без новых агентов, прогонов, секций постановки), но три не упомянутые альтернативы (1–3) закрывают дыры в определённости выбранного пути и должны войти в design как уточнения.

### Q3 — Fresh-Eye Approval

- **Согласовал бы:** да, с оговорками.
- **Причины «да»:**
  - Каждый пункт контракта встраивается в проверенную существующую точку (быстрый путь, журнал решений, Repair Loop, шаг 3.5–4 архива, развилка последнего среза, `## Slice Gate Decisions`); факты о ките, на которых это держится, подтверждены текстом.
  - Blast Radius честный: ни один контракт не отменяется, ADR-0003/0012/0013/0014 соблюдены, запись заказчика не переписывается.
  - Срезы независимы и у каждого есть фикстура с ручной приёмкой за один прогон.
- **Причины «с оговорками»:**
  - Design в трёх местах ссылается на «действующее правило» или «детерминированный контроль», не показывая, по каким входам они работают (G1, G2) — читатель, впервые видящий текст, не сможет реализовать п.4–5 без догадок.
  - Десять новых каталогов `openspec/changes/fixture-*` при одном существующем; в ките нет ни одного правила, исключающего `fixture-*` из `/opsx:status`, `/opsx:overview`, `/opsx:bulk-archive` (поиск `fixture-` по `.cursor/` — пусто). Это цена проверяемости, но её нужно назвать (G7).
  - Карточка приёмки живёт в лимите 4–8 строк (`opsx-output-style.md:385`, `chat-output-budget-full.mdc:36`), а design добавляет до трёх строк и не упоминает бюджет (G5).

## Verdict

**CHALLENGE** — design решает все боли из Why верными точками и без отмены контрактов, но в четырёх местах обещает поведение, которое текущий текст kit без явной дописки не даст (вход сверки предпосылок, вход парного закрытия, охват контроля простоты, устойчивость отпечатка), и в двух — не называет ограничение, в которое встраивается (бюджет карточки, критерий выбора ремонта). Все разрывы — уточнения внутри закрытой оси; архитектурных развилок нет; закрытые решения не оспариваются.
