## Three-Question Challenge

### Q1 — Problem-Solution Fit

- **Why говорит:** «Чтобы заполнить колонку „Результат" в отчёте, приходится отдельно просить кратко сформулировать итог. В описании задачи такого абзаца нет, копировать неоткуда.»
- **Design адресует:**
  - «копировать неоткуда» → раздел «Результат» первым в `proposal.md`, пишется правилом создания (D1, D2) — тем же механизмом, которым сейчас дописываются `## Metadata (comment markers)` и `## Forms mode` (`openspec-new-change/SKILL.md:261–262`). Механизм существует, расширение штатное.
  - «просить переформулировать» → тон и ограничения формы заданы в D2: 2–4 предложения, без путей, внутренних номеров, имён команд и агентов; раздел включён в список разделов для заказчика (`openspec-new-change/SKILL.md:19`, где уже перечислены `Why`, `What Changes`, `Scope`, `Scenarios`, `Requirements`).
  - Скрытая часть боли — колонка отчёта заполняется о **сданном** поведении, а абзац на старте описывает **обещанное**. Design закрывает это D3: сверка при закрытии после приёмки срезов, до синхронизации требований. Это соответствует closed decision `archive_result_silent_update`.
- **Покрытие:** полное по тексту Why, с двумя оговорками, вынесенными в разрывы: (а) критерий «можно скопировать без просьбы переформулировать» в spec не имеет наблюдаемого выражения — ограничения формы живут только в design (G1); (б) для профиля дефекта источник абзаца неполон — поле «Симптом» постановки не названо, хотя именно оно описывает, что пользователь увидит после правки (G3).

Проверено, что решение не ломает соседние правила: Metadata встаёт «сразу после `## Why`» (`SKILL.md:261`) — порядок «Результат → Why → Metadata» этому не противоречит; Layer 3 verify сверяет `## Why` с требованиями (`openspec-verify-change/SKILL.md:308`) — новый раздел не участвует; обзор читает из `proposal.md` только Why, What Changes, Metadata (`openspec-overview/SKILL.md:95`) и пишет только `overview-*.md` (`:128`) — Non-Goal 2 уже выполняется текущим текстом.

### Q2 — Optimality

- **Выбранный путь:** раздел в описании задачи, пишется при создании, молча переписывается при закрытии при расхождении; три точки правки (правило создания, правило закрытия, шаблон набора).
- **Альтернативы (включая не упомянутые в design):**
  1. **Писать абзац один раз при закрытии, при создании не писать.** Наблюдаемая разница: до закрытия раздела в описании нет. Плюсы: нет окна расхождения, две точки правки вместо трёх, источник всегда окончательный (контракт поведения + принятые срезы). Минусы: прямо противоречит AC1 proposal («у новой задачи в начале описания есть раздел») и Behavior Contract п.1 — заказчик явно хочет абзац с момента создания; отчёт может заполняться до закрытия. Отклонена по тексту proposal, не по вкусу.
  2. **Собирать абзац из уже существующих строк бизнес-результата срезов** — `S<N>.accept … — <бизнес-результат>` и `<!-- slice-gate: … -->` в `tasks.md` (`openspec-new-change/SKILL.md:227, 241`). Это существующий механизм, который design не рассматривал. Наблюдаемая разница: абзац — конкатенация формулировок срезов, а не связный текст о задаче целиком. Проверка по порядку артефактов: `tasks.md` создаётся **после** `proposal.md` (шаг 5, `applyRequires`), поэтому на момент создания описания источника ещё нет — для создания альтернатива нежизнеспособна. Для сверки при закрытии она эквивалентна D3 («обязательная приёмка принятых срезов» уже в источниках). Преимущества над выбранным путём нет.
  3. **Обновлять абзац при приёмке среза / в финальной проверке, а не при закрытии.** `reopen-blocked: archive_result_silent_update`. Наблюдаемая разница: абзац актуален раньше — сразу после сдачи последнего среза, а не в момент архивации; архив описание не трогает. Преимущество реально только если отчёт заполняют между приёмкой и архивом. Опровергающего факта из кода нет (premise: none), решение заказчика по оси «при закрытии» закрыто — альтернатива фиксируется как помеченная, развилкой не является.
  4. **Хранить абзац в `design.md` § Behavior Contract или в файле обзора `overview-*.md`.** Наблюдаемая разница: копируют из другого файла. Отклонена Why («в описании задачи») и Non-Goal 2; обзор к тому же создаётся по запросу, не для каждой задачи (`openspec-overview/SKILL.md:128`), — источник не гарантирован.
- **Вердикт по Q2:** оптимален. Ни одна альтернатива не даёт преимущества, не нарушив при этом текст proposal или закрытое решение. Выбранный путь переиспользует существующий приём «правило дописывает обязательный раздел поверх шаблона», новых команд и файлов не вводит, откат — три правки.

### Q3 — Fresh-Eye Approval

- **Согласовал бы:** да, с оговорками по тексту (разрывы ниже), без смены архитектурной оси.
- **Причины «да»:**
  - Точка хранения совпадает с тем, откуда текст реально забирают; имя раздела совпадает с именем колонки.
  - Расширение штатного механизма создания (как Metadata / Forms mode), а не новая команда и не второй файл.
  - Место сверки при закрытии выбрано так, что правка абзаца не попадает под проверку свежести (2a) и идёт после всех остановок архива (3.5, 3.7) — проверено по тексту `openspec-archive-change/SKILL.md:44–56, 188–197`.
- **Оговорки:**
  - Критерий приёмки AC2 («можно скопировать без просьбы переформулировать») в spec не измерим; его измеримая форма есть только в design D2.
  - Проверка перед итогом создания описана без ветки отказа.
  - Для дефекта источник абзаца не включает «Симптом».
