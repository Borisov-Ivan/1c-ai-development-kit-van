## Итог

**APPROVE-WITH-CHANGES.** Подход верный: расширить существующую таблицу глубины verify §1c и рецепт хэша в `report-header.md`, без новых агентов и файлов. Но в текущей редакции четыре дефекта ломают либо цель заказчика, либо заявленную страховку:

1. Класс «замена значения» не требует прошедшей первой полной проверки — путь `/opsx:new → /opsx:extend → /opsx:apply` пропускает её целиком (F1).

3. Условие «не появляются задачи и срезы» исключает главный случай — смену цвета в уже принятом срезе (F4).
4. Глобальная нормализация флажков в хэше `tasks.md` ломает кэш зависимых от флажков контролей, код-сверку на границе среза и выбор следующего шага в `silent_ok` (F7).

## Findings

Класс: **ИД** — исправить в design (способ реализации); **ПР** — продуктовая развилка.

### F1 — ИД, блокер. Нет предусловия «первая полная проверка уже пройдена»

D1 не требует, чтобы до замены значения был пройден полный verify. Сценарий `/opsx:new → /opsx:extend «цвет A → B» → /opsx:apply` даёт исход «проверка не требуется», apply на входе только предупреждает об отсутствии отчёта (`apply/SKILL.md:88-97`, advisory) — первая полная проверка постановки пропущена. Это прямо нарушает Non-Goal 5 и запрет заказчика.

**Правка design D1:** добавить условие 0: «В `reports/` есть отчёт проверки, у которого в истории снимков был `verify_depth: full` с пройденным независимым разбором (`last_challenge_at` заполнен), последний вердикт — «можно запускать apply» (GO), `open_decision_id = null`. Без такого отчёта класс не присваивается, исход — «нужна проверка»». В spec — сценарий «Замена значения до первой проверки ведёт к проверке».

### F2 — ИД, блокер. Экономия переносится на границу среза

D1 пропускает verify на extend, но снимок последнего отчёта остаётся со старым хэшем оси. Если значение записано в `## Decisions` или `## Behavior Contract` (а утверждённый цвет обычно там), первая же проверка на границе среза в apply увидит изменившийся хэш оси: `SKILL.md:100` («хэш оси изменился относительно `last_challenge_at` — incremental на границе среза недоступен, нужен `full`»), `report-header.md:88-89` («хэш оси изменился → Layer 4 запускается»), `apply/SKILL.md:374` («расширять до `full` … при профильном триггере Layer 4»). Полный разбор просто сдвигается с extend на apply. D3 покрывает только «проверку, вызванную вручную после дополнения».

**Правка design D3:** строка таблицы формулируется не по вызывающему, а по дельте: «Дельта с последнего снимка целиком объясняется записями `Класс изменения: замена значения` в `debug.md` § Extend (обратная подстановка, см. F3, восстанавливает хэши снимка) → точечный проход». Строка действует для ручного `/opsx:verify`, для проверки на границе среза в apply и для внутреннего прогона архива. Добавить в `report-header.md` § `snapshot.last_challenge_at`: «Ось, изменённая только доказанной заменой значения, не запускает Layer 4. После точечного прохода её хэш становится новой базой сравнения без обновления `last_challenge_at`». В S1 добавить `report-header.md` (раздел `last_challenge_at`) и одну строку-ссылку в `apply/SKILL.md` slice-gate.

### F3 — ИД. Условие D1.5 «хэш оси с маскировкой» не вычисляется

В снимке хранятся только хэши, старого текста нет (`report-header.md:41-42`). Хэш «старого текста с маской» посчитать нельзя. D1.2 и D1.3 при этом проверяются глазами агента, не детерминированно.

**Правка design D1:** заменить D1.2, D1.3 (часть про тексты) и D1.5 одной механической проверкой — **обратной подстановкой**: в текущих `proposal.md`, `design.md` (включая ось Decisions / Behavior Contract) и `specs/**` заменить `<стало>` на `<было>`; нормализованные хэши должны совпасть с `artifact_hashes` последнего снимка. Совпало — кроме значения ничего не менялось. Если новое значение уже встречалось в тексте по другому поводу, подстановка даст расхождение — класс не присваивается. Это безопасное направление ошибки. `tasks.md` проверяется отдельно (F4): допускается добавление задачи по правилу размещения, текст остальных задач обратной подстановкой восстанавливается.

### F4 — ИД, блокер. Принятый срез и состояние кода

D1.3: «не появляются … срезы». По инварианту размещения задачу в **принятый** срез нельзя вставить тихо: нужен новый срез `S<N+1>` (`vertical-slices.mdc:354-357`, `:394`). Значит, класс никогда не присваивается после приёмки, а «утверждённое значение», которое заказчик увидел на стенде и попросил сменить, — как раз этот случай. Кроме того, design не различает, написан ли уже код.

**Правка design D1.3 + D2 (таблица трёх состояний):**

| Состояние среза со значением | Что делает дополнение | Приёмка |
|---|---|---|
| Задачи ещё `[ ]` | правит текст задачи на новое значение, новых задач нет | как была |
| Рабочие задачи `[x]`, `S<N>.accept` `[ ]` | **не** переписывает текст выполненной задачи; добавляет задачу «заменить значение в <место>» перед `S<N>.accept` | приёмка среза заново (handoff повторяется) |
| `S<N>.accept` `[x]` (срез принят) | новый срез по инварианту размещения, `Причина fix-среза: frozen` | новая ручная приёмка нового среза |

Формулировка D1.3: «места правки **в коде** те же (файлы, элементы, процедуры); добавление задачи и нового среза по инварианту размещения класс не снимает». Ручная приёмка во всех трёх строках сохраняется — страховка заказчика не ослабляется.

### F5 — ИД. Assumption 3 неверна: код со значением никто не сверяет

`code-truth-gate.mdc:31-33` отфильтровывает «доменные значения строк и флагов», а проверяет только **существование** якоря. Старый цвет или старый текст, оставшийся в модуле или в `Form.xml`, автоматически не ловится ни §3.6, ни verify. Ловит только ручная приёмка.

**Правка design:** убрать из Assumption 3 «расхождение значения с кодом ловит сверка артефактов с кодом». Вместо этого: (а) в задачу замены значения (F4) записать критерий «в затронутых файлах нет старого значения (Grep)» — apply не ставит `[x]`, пока Grep находит старое. Это та же механика, что `code-truth-gate.mdc:45` для символов; (б) в Risks честно указать, что для значений, которые в коде не литерал (например, стиль из общей картинки), остаётся только ручная приёмка.

### F6 — ИД. «Старое значение не осталось» — где, кто, когда

D3.2 требует отсутствия старого значения «ни в proposal, ни в design, ни в specs, ни в tasks». Это ложно срабатывает на выполненных задачах `[x]` (история), на записи `было → стало` и на `debug.md`. Главное — в пути D1 verify не вызывается вовсе, поэтому проверка не выполнится никогда.

**Правка design D2/D3:** (а) область проверки — нормативный текст: Requirements и Scenarios в `specs/**`, `## Decisions` / `## Behavior Contract` / Primary acceptance в `design.md`, `## What Changes` в `proposal.md`, открытые `[ ]` задачи и `S<N>.accept`. Исключения: `[x]` задачи, `debug.md`, `reports/**`. (б) Выполняет **extend** в §7 Verification Gate механическим Grep до выбора исхода; найдено — extend дописывает сам (это его зона, `extend/SKILL.md:13`), исход «не требуется» выдаётся только после чистого Grep. (в) Точечный проход verify (D3) повторяет тот же Grep и не дублирует логику.

### F7 — ИД, блокер. Глобальная нормализация флажков в хэше `tasks.md`

Детектор петли не ломается: он читает `debug.md` и состояние `S<N>.accept` напрямую (`vertical-slices.mdc:326-330`). Выбор `verify_mode` тоже не ломается: Grep `- [ ]` по файлу (`SKILL.md:147`). Ломается остальное:

1. **Кэш контролей.** Ключ `check_cache` включает хэши входов (`report-header.md:127-129`). `hygiene-checkboxes` (вход — `tasks.md`, `:137`) и `code-truth` (серьёзность зависит от `[x]`: WARNING для незавершённых, CRITICAL для выполненных, `code-truth-gate.mdc:40-44`) будут отдаваться из кэша после смены флажков. Это противоречит требованию «Точечная инвалидация» идущей `value-efficient-verify` («переиспользовать … только при совпадении хэшей его входов»): из сужения получается отмена.
2. **Правило точечной инвалидации №4** (`report-header.md:154`) становится мёртвым — дельта флажков невидима.
3. **Slice-gate в apply** (`apply/SKILL.md:374`, incremental по дельте) после отметки рабочих задач `[x]` не увидит изменения `tasks.md` и не пересчитает код-сверку для только что выполненных задач. А по аудиту СППР это единственная полезная часть проверки на границе среза.
4. **`silent_ok`**. Отчёт границы последнего среза (`pre-apply`) → приёмка → `/opsx:verify`. Если `debug.md` в хэше не изменился (см. F8), при нормализации все хэши совпадут, и `silent_ok` возьмёт `verify_mode: pre-apply` из снимка (`SKILL.md:451`, `chat-summary.md:22`) → «Следующий шаг: `/opsx:apply`» при полностью завершённой ЗНИ.
5. **invalidation_map** строится из дельты (`SKILL.md:153`) — флажковые изменения в неё не попадут.

**Правка design D4 (и Implementation Options «Нормализация флажков»):** рецепт остаётся в одном месте (`report-header.md`), но с **двумя ключами**: `artifact_hashes["tasks.md"]` — как сейчас, сырой (кэш, `silent_ok`, `invalidation_map`, slice-gate); `artifact_hashes["tasks.md#text"]` — с нормализацией флажков. Читают его только архив §2a (классификация D5) и строка §1c «между срезами». Дополнительно в `silent_ok`: текущий `verify_mode` (Grep) должен совпадать с `verify_mode` снимка, иначе обычный проход. Старые снимки без `#text` = промах кэша → D5.3 (обычный прогон), не ошибка.

### F8 — ИД. D5.2 недетерминирован по `debug.md`

«Менялись только … записи приёмки в `debug.md`»: в снимке `debug.md` — один хэш «структурных секций» (`report-header.md:42`) без разбивки. После приёмки меняется `## Slice Gate Decisions`, хэш расходится, и отличить «только приёмку» от «новой записи Extend» нечем.

**Правка design D5 + report-header:** хэши `debug.md` по секциям: `debug.md#Extend`, `#Verify decision ledger`, `#External Contract Ledger`, `#Slice Gate Decisions`. Условие D5.2: изменились только `tasks.md#text`-равный `tasks.md` (флажки) и `#Slice Gate Decisions`, причём новые записи имеют `Решение ∈ {принят, принят (manual shortcut), awaiting-acceptance}`. Записи `не принят` / `inside-slice rework` → D5.3.

### F9 — ИД, упрощение (не блокер). D5.2 дублирует собственные шаги архива

«Короткая сверка: полнота изменений требований и все `S<N>.accept` закрыты» — архив уже делает это сам: шаги 3 / 3.5 (закрытость задач и приёмок, `archive/SKILL.md:67`, `:155-158`), 3.6 (код-сверка), 4 (синхронизация дельта-спек, полнота — `openspec-specs-gate`). Новый `verify_depth: archive-check` требует расширить enum (`report-header.md:31-32`) и научить читателей снимка.

**Правка design D5.2:** на ветке 2 verify не вызывается; архив выполняет свои шаги 3–4 как сейчас и пишет одну строку в `debug.md` («перед архивом: изменились только отметки приёмки, прогон проверки не выполнялся; сверка с кодом — шаг 3.6»). Если отчёт-файл всё же нужен для истории — определить его состав через существующие `check_id` (`problem-solution-trace`, `scenario-coverage`), а не через неопределённую «полноту изменений требований». Аналогично для D3: писать `verify_depth: incremental` с `invalidation_map` из проверок значения, новое значение enum не вводить.

### F10 — ИД. Расхождения proposal ↔ design

1. `proposal.md:18`: список класса «(цвет, текст надписи, картинку, **порог**)», а D1 пороги явно исключает. Убрать «порог» из proposal.
2. `proposal.md:21`: «если после последнего принятого среза постановка **и код** не менялись» — D5 код не проверяет, только артефакты. Либо убрать «и код», либо добавить в D5.2 дешёвое условие: `git diff --name-only` с даты последнего отчёта по файлам из `tasks.md` пуст, иначе D5.3. ### F11 — ИД. Стык с verify-stop-repeat: MUST-требование против D3

### F13 — ИД. D1: цвет как признак состояния и текст как ключ

Risk 1 признан, но закрыт формулой «при сомнении не присваивать» — это не проверка. Два механических условия закрывают его:

1. **Коллизия:** новое значение не используется в нормативном тексте тем же атрибутом для другого состояния (например, «просроченные — красным, срочные — оранжевым»; смена красного на оранжевый сливает два состояния). Grep по нормативным секциям.
2. **Не условие:** значение не встречается ни в одной строке WHEN / «когда» / «если» в specs и Decisions; для текстов — не содержит параметров подстановки (`%1`) и в постановке не описан как ключ сравнения.

Добавить в D1 как условия 6–7.

### F14 — ПР. Какие атрибуты заказчик считает «мелкой правкой»

EC-1 (`debug.md`) фиксирует только «смена утверждённого значения (пример — цвет)». Список D1.1 — расширение автора: шрифт, картинка или иконка, текст надписи, **подсказки и сообщения**. Текст сообщения меняет то, что пользователю **говорят** («не проведён» → «проведён с ошибками»), — это уже граница смысла. Решать заказчику:

- **A. Только оформление: цвет, шрифт, картинка или иконка.** Надёжно, текстов нет. Но: правка опечатки в надписи пойдёт через проверку.
- **B. A + тексты надписей и подсказок, без текстов сообщений.** Покрывает частые косметические правки. Но: граница «надпись vs сообщение» тоже требует суждения агента.
- **C. Как в design: A + все тексты, включая сообщения.** Максимум экономии. Но: смена смысла сообщения пройдёт без проверки, заметит её только приёмка.

Вопрос заказчику: «Замену каких значений считать мелкой правкой без проверки: только оформление (цвет, шрифт, картинка), оформление плюс надписи и подсказки, или ещё и тексты сообщений пользователю?» До ответа строка D1.1 не должна фиксироваться авторским выбором; утверждение «Продуктовых развилок нет» в «Открытых вопросах» design снять.

## Simplicity Check

- **Viable alternatives:**
  1. **Design как есть** — новый класс в §1c, три исхода extend, глобальная нормализация флажков, `archive-check`, вариант C для отчёта. Файлов ~9; новое значение enum `archive-check`; дефекты F1, F2, F4, F7.
  2. **Design + правки F1–F13 (рекомендуется)** — тот же класс, но строка §1c ключуется по дельте (записи Extend + обратная подстановка), `tasks.md` хэшируется двумя ключами, архив на ветке 2 verify не вызывает, D6 — чёрный список из двух полей. Файлов ~10 (добавляется ссылка в apply slice-gate); новых значений enum 0; новых механизмов 0 — обратная подстановка реализуется поверх уже хранимых `artifact_hashes`.
  3. **Минимум без класса** — только D5 и D6 (архив и отчёты), замену значения не выделять. Проще, но не закрывает главный запрос заказчика (EC-1, `customer-direct`). Отклонён.
- **Selected simplest viable design:** вариант 2. Он не добавляет ни одного нового механизма к варианту 1, наоборот — убирает `archive-check` и неисполнимую маскировку хэша, заменяя их механической обратной подстановкой по уже хранимым хэшам.
- **Why not simpler:** без класса (вариант 3) не выполнен EC-1. Без ключа по дельте (F2) экономия на extend съедается полным прогоном на границе среза. Без двух ключей `tasks.md` (F7) ломается кэш и код-сверка на границе среза.
- **Complexity budget:**
  - Files touched: 10 (`extend/SKILL.md`, `verify/SKILL.md`, `report-header.md`, `executive-summary.md`, `chat-summary.md` при необходимости, `archive/SKILL.md`, `apply/SKILL.md` — одна строка, `sdd-workflow.mdc`, `task-triage.mdc`; `vertical-slices.mdc` — только ссылка, если нужна).
  - Hooks/intercepts: 0 (kit-only).
  - New procedures/functions: 0; новые поля снимка: `tasks.md#text`, посекционные хэши `debug.md`, `parent_verification`.
  - Conditional branches: +1 строка в §1c, +1 ветка архива (D5.2), +3 исхода extend.
