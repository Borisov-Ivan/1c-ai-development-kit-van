## Three-Question Challenge

### Q1 — Problem-Solution Fit

- **Why говорит:** мелкая правка утверждённого значения проходит полный цикл; ~80 прогонов проверки не нашли ни одного дефекта кода; финальный прогон перед архивом в мелких ЗНИ — формальность («изменилась только отметка приёмки»); отчёты повторных прогонов на 60–90% повторяют предыдущие; цена шага подталкивает заказчика обходить конвейер.
- **Design адресует:**
  - Боль 1 (полный цикл за замену значения) → D1–D3: класс по оценке воздействия, исход «проверка не требуется», точечный проход по дельте на любом триггере (пользователь / граница среза / архив), исключения в строке «ответ, меняющий правило» и в «Стыке глубины», база оси после точечного прохода. Атаковал маршрут на границе среза отдельно: без S1.7 экономия действительно съедалась бы guardrail'ом «хэш оси изменился → full» — дизайн это видит и закрывает. Покрытие полное.
  - Боль 2 (финал-формальность) → D4 (нормализованный ключ `tasks.md`, ключ `debug.md` без записей приёмки) + D5 (три ветки §2a). Покрытие полное; ветка 3 сохраняет проверку при реальной правке постановки.
  - Боль 3 (повторяющиеся отчёты) → D6. Покрытие **частичное по построению**: убираются только две копии (`accepted_tasks`, `closed_decisions`) и пересказ постановки; хэши, кэш и карта инвалидации остаются. Дизайн честно фиксирует это в выборе варианта C («экономия меньше, чем у A») и аргументирует, что основной объём повторов закрывают D3–D5 (прогонов и полных шапок просто становится меньше). Принимаю аргумент: боль из Why — «отчёты повторяют друг друга», и главный источник повторов — сами повторные полные прогоны, которых больше не будет.
- **Покрытие:** полное для болей 1–2, частичное с обоснованием для боли 3. Подмены проблемы (решение симптома вместо Why) не нашёл: адресована именно цена шага, страховочные контуры (первый full, ревью, приёмка, Code-Truth) не тронуты.

### Q2 — Optimality

- **Выбранный путь:** новый класс в существующей таблице глубины §1c + два ключа хэша в снимке + три ветки в archive §2a; дополнение только применяет таблицу и называет исход.
- **Альтернативы (включая не упомянутые в design § Implementation Options):**
  1. **Реестр заменяемых значений, сертифицируемый первым полным прогоном** (`reopen-blocked: value_change_class_by_impact`) — при первом full независимый разбор помечает в design «слоты оформления» (цвет, тексты подписей…), чьи будущие замены свободны; незадекларированные значения идут обычным маршрутом. Плюс: убирает главный источник риска — модельную оценку воздействия в момент дополнения — и делает класс детерминированным. Минус: это форма перечня, прямо отклонённая заказчиком 2026-09-30 (перечень пришлось бы пополнять, спорные случаи всё равно требуют оценки); нового verified-факта из кода, оправдывающего переоткрытие, у меня нет. Отклоняю как заблокированную закрытым решением.
  2. **Встроенная точечная сверка внутри самого дополнения вместо исхода «проверка не требуется»** — extend после замены сам выполняет три проверки D3 (согласованность нового, отсутствие старого, условия класса) и пишет мини-запись в `debug.md`; отдельного отчёта и вызова проверки нет. Плюс: убирает окно «дополнение ошиблось в замене — первый автоматический контроль только на границе среза». Минус: дублирует логику точечного прохода во втором скилле (дизайн-принцип «классификация в одном месте», D2) и не даёт выигрыша, когда граница среза всё равно наступит. Фактически D2.1 уже содержит половину этого варианта (поиск и замена старого значения самим дополнением); недостающая часть — доказательство сверки — закрывается дешевле через G-разрывы ниже, чем сменой архитектуры.
  3. **Свежесть финала по записи приёмки в `debug.md`, а не по нормализованным хэшам** — archive считает финал свежим, если после последнего отчёта в `debug.md` появились только записи `## Slice Gate Decisions` и флажки, определяя это по git-диффу или по последней записи приёмки. Плюс: не нужны новые ключи хэша в снимке. Минус: вводит второй, несовместимый со `silent_ok` детектор новизны (именно этим дизайн отклонил похожий вариант «список допустимых правок»), зависит от git-состояния, которого снимок не требует. Выбранный путь (два ключа одного снимка) строго лучше: один механизм новизны на все команды.
- **Вердикт по Q2:** оптимален в рамках закрытого решения заказчика. Точка врезки (общая таблица §1c + общий рецепт снимка) — минимально инвазивная из рассмотренных: не добавляет ни второго классификатора, ни второго детектора новизны, ни новых читателей снимка.

### Q3 — Fresh-Eye Approval

- **Согласовал бы (или нет):** да, с двумя оговорками, вынесенными в разрывы.
- **Причины «да»:**
  - Механизм отказоустойчив в опасную сторону: любое несовпадение — обратная подстановка не сошлась, сомнение после короткого мнения, значение занято другим состоянием — роняет класс в обычную таблицу глубины, а не в пропуск проверки.
  - Страховка от накопления замен есть и объективна: счётчик дополнений без архитектора (`architect-gate.mdc`, M ≥ 3) продолжает считать записи класса (D2, S1.15), петля по одному значению блокируется D1.4.
  - Архив ничего не теряет: полнота требований, приёмок и сверка с кодом остаются его собственными шагами на всех ветках D5; единственный реальный детектор строковых остатков в коде — задача замены значения — честно назван, включая его отсутствие в Code-Truth (Risks 2).
- **Оговорки:** механика обратной подстановки при нескольких записях класса не определена (G1); ветка 2 архива сформулирована перечнем изменённого, которого в снимке нет (G2).

## Verdict

## Gaps for design.md (всегда при CHALLENGE)

- **G1** — `implementation_invariant`. D1.5 (и задача S1.2/S1.3): определить обратную подстановку для **нескольких** записей § Extend с прошлого снимка — подстановки применяются по записям в обратном хронологическом порядке; если новое значение одной записи встречается в тексте оси вне заменённых мест, либо пары «было → стало» разных записей пересекаются по строкам (новое значение одной = старое другой), подстановка признаётся неоднозначной → класс не присваивается, действует обычная таблица глубины. Без этого правила строка D3 «все изменения объяснены записями § Extend» (множественное число) опирается на механизм, определённый только для единственного числа, — реализация в S1.2 разойдётся по усмотрению исполнителя.
- **G2** — `implementation_invariant`. D5 ветка 2 (и задача S2.8): переформулировать условие ветки через **совпадение ключей снимка**, а не через перечень изменённого: хэши `proposal.md`, `design.md`, `specs/**` совпали + нормализованный ключ `tasks.md` совпал + ключ `debug.md` без записей приёмки совпал → ветка 2; `reports/` в условии не участвует, потому что в снимок не входит. Текущая формулировка («менялись только флажки, записи приёмки и файлы reports/») подталкивает реализацию к диффу каталога или git-истории, которых у снимка нет, и создаёт второй детектор новизны — ровно то, что дизайн сам отклонил в альтернативе «список допустимых правок `tasks.md`».
