## Context

Разбор 13 ЗНИ в проектах СППР и PavDO — отчёты `reports/exploration-2026-09-30-sppr-small-zni.md`, `reports/exploration-2026-09-30-sppr-repeat-verify.md`, `reports/exploration-2026-09-30-pavdo-zni-audit.md`:

1. Примерно из 80 прогонов проверки ни один не нашёл дефект кода. Дефекты кода ловили стенд или приёмка, ревью и разбор трасс. Проверка ловила ошибки постановки на первом полном прогоне, петли правок и расхождения артефактов с кодом перед архивом.
2. Финальный прогон перед архивом в мелких ЗНИ был формальностью: «изменилась только отметка приёмки».
3. Соседние отчёты повторных прогонов совпадают на 72–89%; в отчётах проверки 60–70% объёма занимает шапка с хэшами, списком принятых задач и журналом решений.

Текущее поведение kit, которое порождает эти потери:

1. **Дополнение всегда ведёт к проверке.** `.cursor/skills/openspec-extend-change/SKILL.md` §7–8: следующий шаг user-extend с правками — всегда `/opsx:verify <name>`, других исходов нет.
2. **Замена значения даёт полный прогон — и на границе среза тоже.** `.cursor/skills/openspec-verify-change/SKILL.md` §1c: строка «ответ заказчика, меняющий правило» → `verify_depth: full`. Если хэш архитектурной оси изменился относительно последнего независимого разбора, проход на границе среза тоже уходит в `full` (§1c, абзац «Guardrails `incremental`»). Замена цвета в Behavior Contract меняет этот хэш, поэтому полный прогон просто переезжает на границу среза.
3. **Отметка приёмки делает финальную проверку устаревшей.** `.cursor/skills/openspec-archive-change/SKILL.md` §2a: свежий финальный отчёт — `verify_mode: post-apply` после последней правки `tasks.md`. Отметка `[x]` в `S<N>.accept` — правка `tasks.md`, и архив молча запускает полный прогон. При этом у архива есть собственные шаги: полнота требований и приёмок (§3–4) и жёсткая сверка артефактов с кодом (§3.6 Code-Truth Gate). Расхождение «ПДФ» в артефактах и «PDF» в коде в PavDO поймала именно эта сверка — по именам символов.
4. **Каждый отчёт — полная копия.** `templates/report-header.md` требует полную шапку в каждом отчёте, включая `accepted_tasks` и `closed_decisions`; `templates/executive-summary.md` требует раздел «Что меняется в постановке» в каждом отчёте. Кроме записи в сам отчёт, `accepted_tasks` и `closed_decisions` из снимка никто не читает (Grep по `.cursor/**`, подтверждён архитектурным разбором).
5. **Сверка с кодом не видит строковые значения.** `.cursor/rules/code-truth-gate.mdc` шаг 3: доменные значения строк отфильтровываются, проверяется только существование имён. Старый цвет, оставшийся в коде, эта сверка не поймает.

Две идущие ЗНИ kit уже меняют ту же область и на момент создания этой не архивированы:

1. `value-efficient-verify` — каскад проверки, кэш по хэшам, точечная инвалидация; остался открытым приём последнего среза.
2. `verify-stop-repeat` — точечный прогон после ответа заказчика внутри подхода, опора на прошлый контроль среза, стоп по теме; открыты приёмки всех пяти срезов.

Эта ЗНИ сужает их правила глубины. Единственное прямое пересечение — требование `verify-stop-repeat` «Ответ не перезапускает всё»: правка контракта поведения должна давать полный разбор. Замена значения этой ЗНИ из него явно исключается (D3).

Разбор дизайна: `reports/architecture-new-2026-09-30.md` (вердикт — принять с правками; правки способа реализации внесены ниже).

Связанные ADR: прямых нет. ADR-0003 (решения по замечаниям ревью) и ADR-0011 (модели шагов архитектора) не затрагиваются.

## Goals / Non-Goals

**Goals:**

1. Замена конкретного значения внутри уже утверждённого и проверенного правила проходит без проверки постановки — ни сразу после дополнения, ни на границе среза, ни перед архивом, — и дополнение говорит об этом явно.
2. У дополнения три исхода: проверка не требуется, достаточно короткой сверки изменённого или нужна проверка.
3. Перед архивом не повторяется полный прогон, если после последнего отчёта менялись только отметки и записи приёмки. Второй финал подряд без изменений не создаётся.
4. Повторный прогон не копирует в отчёт то, что уже лежит в журнале решений или во флажках задач.

**Non-Goals:**

1. Лёгкий маршрут создания мелкой ЗНИ с урезанным набором артефактов.
2. Облегчённый ритуал отладки для срочных правок.
3. Копии рассуждений ревьюера рядом с отчётом ревью.
4. Инкрементальная матрица контроля срезов: опору на прошлый контроль уже вводит `verify-stop-repeat`.
5. Любое ослабление первой полной проверки постановки, остановки петли приёмки, сверки артефактов с кодом перед архивом, ревью кода и ручной приёмки.

## Existing Mechanisms

1. **Таблица глубины прогона** (verify §1c): режимы `full` / `incremental` / `lite` / точечный. Новый класс изменения добавляется строкой этой же таблицы; дополнение применяет её, второй классификатор не заводится.
2. **Дельта входов и кэш** (verify §4, `templates/report-header.md`): `artifact_hashes`, `check_cache`, `invalidation_map`, путь `silent_ok` при полном совпадении входов. Нормализованный хэш задач и хэш `debug.md` без записей приёмки — дополнительные ключи того же снимка.
3. **Собственные шаги архива** (archive §3–4, §3.6 и `.cursor/rules/code-truth-gate.mdc`): полнота требований, карточка приёмок, сверка артефактов с кодом. На ветке «менялась только приёмка» архив опирается на них и не вызывает проверку.
4. **Журнал решений** в `debug.md` (`## Verify decision ledger`) — рабочий источник истины закрытых решений. Отчёт ссылается на него, копия не нужна.
5. **Запись дополнения** в `debug.md` (`## Extend — YYYY-MM-DD`) — туда же пишется класс изменения; по этим записям проверка объясняет дельту.
6. **Правило размещения дефектов** (`vertical-slices.mdc` § Defect placement): для непринятого среза — задача внутри среза перед `S<K>.accept`, для принятого — новый срез. Класс изменения это правило не меняет, а опирается на него (D1, таблица состояний).

Уровень Preference Hierarchy — расширение существующих механизмов, без новых файлов и агентов.

## Decisions

### D1. Класс изменения «замена значения»

Дополнение относится к классу «замена значения», если выполнены **все** условия:

0. ЗНИ уже прошла первую полную проверку: в последнем отчёте с `verify_depth: full` независимый разбор постановки выполнен, вердикт — можно реализовывать, открытой развилки (`open_decision_id`) нет. Без этого класс не присваивается: сначала обычная проверка.
1. Меняется значение одного наблюдаемого атрибута внутри правила, уже записанного в постановке, и по оценке воздействия замена меняет только то, что заказчик видит или получает: не состав данных, попадающих под правило, не формулу, момент или порядок шагов, не условия сценариев и не контракты с другими объектами. Закрытого перечня «разрешённых» атрибутов нет — класс определяется воздействием; подтверждённый пример — цвет оформления.
2. Названия сценариев и их условия «когда» не меняются; в ожидаемом результате меняется только это значение. Новое значение не участвует в условиях сценариев и не занято в той же ЗНИ другим состоянием (например, новый цвет не совпадает с цветом соседнего статуса).
3. Места правки — те же элементы, реквизиты и процедуры, что уже записаны в design и tasks. Новые задачи и срезы допускаются только по таблице состояний ниже.
4. Не открывается и не меняется тема внешнего контракта, кроме записи этого же указания заказчика. Это не повторная замена того же атрибута до приёмки среза: вторая замена одного значения до приёмки — сигнал петли, класс не присваивается.
5. Архитектурная ось не меняется по сути: если в текущем нормализованном тексте Decisions и Behavior Contract вернуть старое значение на место нового, хэш совпадает с хэшем оси из последнего снимка. Маскирование по хэшу невозможно — в снимке нет исходного текста, поэтому используется обратная подстановка.

**Несколько замен с прошлого снимка.** Если с прошлого снимка записей § Extend класса «замена значения» больше одной, обратная подстановка применяется к каждой, в обратном хронологическом порядке (сначала последняя замена). Подстановка неоднозначна — класс не присваивается, действует обычная таблица глубины — когда новое значение одной записи встречается в тексте оси вне мест, которые эта запись заменила, или когда пары «было → стало» разных записей пересекаются по строкам (новое значение одной совпадает со старым значением другой).

Не выполнено хотя бы одно условие — это не «замена значения». Числовые пороги и константы условий (например, «просрочено через 3 дня» → «через 5») в класс **не** входят: по тому же принципу воздействия они меняют, какие данные попадают под правило. Для них действует обычная таблица глубины.

**Оценка воздействия.** Условия 1–5 дополнение оценивает само по артефактам ЗНИ. Если из постановки не видно, влияет ли значение на поведение (например, значением различаются ветки обработки или оно похоже на признак состояния), дополнение запрашивает короткое мнение архитектора об одной этой замене: дельта «было → стало» и цитаты затронутых мест постановки, один вопрос о воздействии — без разбора всей ЗНИ, без альтернатив и без полного архитектурного отчёта. Мнение не запрашивается, когда ответ очевиден в обе стороны. Осталось сомнение и после мнения — класс не присваивается, действует обычная таблица глубины.

**Таблица состояний среза:**

| Состояние среза, где живёт значение | Что делает дополнение | Приёмка |
|-------------------------------------|------------------------|---------|
| Задачи с этим значением не выполнены | Правит нормативный текст: proposal, design, specs, текст невыполненных задач | Та же открытая `S<K>.accept` |
| Задачи выполнены, срез не принят | Текст выполненной задачи не переписывает; добавляет внутри того же среза перед `S<K>.accept` задачу «заменить значение» с поиском старого значения в затронутых файлах | Та же открытая `S<K>.accept`, заново |
| Срез принят | По правилу замороженного среза — новый срез `S<N+1>` с одной задачей замены и своей приёмкой | Новая `S<N+1>.accept` |

Во всех трёх состояниях исход дополнения — «проверка не требуется»; ручная приёмка нового значения остаётся.

Альтернатива «любая правка литерала» отклонена: порог в условии выглядит как литерал, но меняет поведение. Альтернатива «закрытый перечень атрибутов (цвет, шрифт, тексты)» отклонена заказчиком: перечень пришлось бы пополнять, а спорные случаи всё равно требуют оценки воздействия.

### D2. Три исхода дополнения, классификация в одном месте

Правила классификации живут в таблице глубины verify §1c. Дополнение их не копирует, а применяет к своей дельте и называет исход:

1. **Проверка не требуется** — класс «замена значения» (D1). До выбора исхода дополнение ищет старое значение в нормативном тексте ЗНИ: proposal, design, specs, текст невыполненных задач. Выполненные задачи, `debug.md` и `reports/` в поиск не входят. Найденные вхождения дополнение заменяет само. Запись в `debug.md` § Extend: `Класс изменения: замена значения (<атрибут>: <было> → <стало>)`, `Проверка: не требуется`. Следующий шаг — `/opsx:apply <name>`.
2. **Достаточно короткой сверки** — дельта, которую таблица относит к точечному, `incremental` или `lite` проходу. Следующий шаг — `/opsx:verify <name>`; в итоге дополнения сказано, что проверка затронет только изменённое.
3. **Нужна проверка** — всё, что таблица относит к `full`: смена подхода, контракта поведения, нового сценария, правила (формула, момент, порядок шагов, порог). Следующий шаг — `/opsx:verify <name>`, как сейчас.

Замена значения не считается изменением пользовательского сценария для обязательного вызова архитектора в дополнении. Счётчик дополнений без архитектора (`architect-gate.mdc`, объективный триггер по `debug.md`) продолжает считать и такие записи.

Альтернатива «отдельный классификатор в дополнении» отклонена: два классификатора разойдутся.

### D3. Проверка после замены значения — точечная, кто бы её ни вызвал

Строка таблицы глубины «Все изменения с прошлого снимка объяснены записями § Extend класса „замена значения“» → точечный проход. Строка срабатывает по самой дельте, а не по тому, кто вызвал проверку: пользователь, применение ЗНИ на границе среза или архив. Проверки прохода:

1. Новое значение записано согласованно в нормативном тексте ЗНИ.
2. Старое значение не осталось в нормативном тексте (та же область поиска, что в D2).
3. Условия D1 по-прежнему выполнены.

Контроль срезов, независимый разбор постановки и оценка готовности задач не запускаются. После успешного точечного прохода текущий хэш оси становится базой снимка без нового разбора, поэтому следующая граница среза не уходит в `full` из-за этой замены.

Исключения в соседних правилах:

1. Строка «ответ заказчика, меняющий правило → `full`» не действует для этого класса.
2. Абзац «Стык глубины» verify §1c получает оговорку о классе «замена значения».
3. Требование `verify-stop-repeat` «Ответ не перезапускает всё» («правка контракта поведения MUST давать полный разбор») сужается: замена значения по D1 полного разбора не даёт. После архивации `verify-stop-repeat` эта ЗНИ добавляет дельту MODIFIED к этому требованию (реализация начинается после её архивации, см. Assumptions 1).

### D4. Отметка приёмки не делает проверку устаревшей

В снимке у `tasks.md` два ключа хэша:

1. Сырой — как сейчас. Его читают кэш контролей, сверка на границе среза, правила инвалидации и выбор режима.
2. Нормализованный — состояние флажков замаскировано: `- [x]` и `- [ ]` дают один хэш; текст задачи, добавление и удаление задач хэш меняют.

Нормализованный ключ читают только два места: свежесть финальной проверки в архиве (§2a) и строка таблицы глубины «между срезами». Быстрый путь `silent_ok` дополнительно сравнивает текущий режим проверки (`pre-apply` / `post-apply`) с режимом в снимке: после отметки последней приёмки режим меняется, и быстрый путь не отдаёт устаревший совет «дальше реализация» вместо архива.

Для `debug.md` в снимке появляется ключ хэша без секции записей приёмки срезов (`## Slice Gate Decisions`). Точное имя секции сверяется при реализации.

### D5. Архив без повторного прогона, без второго финала

Archive §2a выбирает одно из трёх:

1. **Есть свежий финальный отчёт** (`post-apply` или отчёт границы последнего среза; нормализованные входы совпадают) — проверка не вызывается, в чат ничего.
2. **Нормативные ключи снимка совпали, свежего финала по ветке 1 нет.** Хэши `proposal.md`, `design.md` и `specs/**` совпали с последним отчётом, нормализованный ключ `tasks.md` совпал, ключ `debug.md` без записей приёмки совпал — проверка не вызывается. Это тот же наблюдаемый исход, что «менялись только отметки, записи о приёмке и отчёты»: условие пишется через совпадение ключей, а не через перечень изменённых файлов. Файлы `reports/` в условии не участвуют — в снимок они не входят, и правка только отчётов проверку не вызывает. Полноту требований, закрытие приёмок и сверку артефактов с кодом выполняют собственные шаги архива (§3–4, §3.6), как сейчас. Отдельное значение глубины прогона не вводится.
3. **Менялись proposal, design, specs или текст задач** — проверка по таблице глубины verify §1c (часто `incremental`), как сейчас.

Если отчёт `post-apply` с совпавшими нормализованными входами уже есть, второй финальный прогон не выполняется, в том числе когда пользователь вызывает `/opsx:verify` сразу после финального (путь `silent_ok` с учётом режима по D4).

Альтернатива «убрать внутренний прогон архива совсем» отклонена: при изменении постановки после приёмки прогон нужен (ветка 3).

### D6. Отчёт повторного прогона без копий

Для прогонов с глубиной не `full`:

1. Из снимка отчёта убираются только `accepted_tasks` (источник — флажки `tasks.md`) и `closed_decisions` (источник — журнал решений в `debug.md`). Остальной снимок остаётся как есть, в том числе отпечатки решений и время последнего разбора. Добавляется ссылка `parent_verification: <файл предыдущего отчёта>`.
2. Раздел «Что меняется в постановке» не пишется; вместо него — «Что изменилось с прошлого прогона»: изменившиеся входы, пересчитанные контроли, переиспользованные результаты.

В полном прогоне шапка и разделы — как сейчас.

## Implementation Options

**Отчёт повторного прогона (D6):**

1. **Вариант A — цепочка дельт.** Отчёт хранит только изменившиеся ключи снимка; читатель собирает состояние по цепочке до последнего полного. Экономия максимальная, но меняются все читатели снимка (применение, архив, статус, проверка), и появляется риск потерянного звена.
2. **Вариант B — снимок в `debug.md`.** Машинный снимок один, перезаписывается в `debug.md`; отчёты только человекочитаемые. Нет цепочек, но меняется место источника истины для трёх команд и растёт `debug.md`, который читают агенты.
3. **Вариант C — прежний снимок без копий журналов и без пересказа постановки (выбран).** Читатели не меняются; убирается то, что дублирует `debug.md` и `tasks.md`, и повтор раздела о постановке.

Выбран C: единственный вариант без изменения читателей снимка. Экономия меньше, чем у A, но основной объём повторов по разбору — повтор тяжёлой свиты и пересказ постановки; их закрывают D3–D5 и D6.2.

**Нормализация флажков (D4):**

1. **Два ключа хэша: сырой и нормализованный (выбран)** — сырой сохраняет кэш и инвалидацию, нормализованный читают только архив и строка «между срезами».
2. Один нормализованный ключ для всех читателей — отклонён разбором дизайна: ломает кэш зависящих от флажков контролей, сверку на границе среза и быстрый путь проверки.
3. Отдельный список «допустимых правок `tasks.md`» в архиве — второе правило, расходится с `silent_ok`.

**Проверка оси при замене значения (D1.5):**

1. **Обратная подстановка (выбрана)** — вернуть старое значение в текущий текст и сравнить с хэшем снимка; не требует хранить текст. Несколько записей с прошлого снимка — обратный хронологический порядок; неоднозначность (значение вне заменённых мест или пересечение пар «было → стало») снимает класс, см. D1.
2. Маскирование значения перед хэшированием — невозможно: в снимке только хэши.

## Behavior Contract

1. Заказчик заменил утверждённое значение (например, цвет), по оценке воздействия не меняющее поведение, через `/opsx:extend` в ЗНИ, уже прошедшей первую полную проверку, — в итоге дополнения: что изменилось (было → стало), «проверка постановки не требуется» и следующий шаг `/opsx:apply <name>`.
2. Та же замена до первой полной проверки, вторая замена того же значения до приёмки, новое значение, занятое другим состоянием, смена порога, формулы, момента, порядка шагов, нового сценария, либо сомнение в воздействии, оставшееся после короткой архитектурной оценки, — итог дополнения ведёт к `/opsx:verify <name>`.
3. Замена значения в уже принятом срезе — исход «проверка не требуется», в задаче появляется новый срез с одной задачей замены и своей приёмкой.
4. `/opsx:verify` после замены значения, в том числе на границе среза при применении ЗНИ, — точечный проход без полного разбора; в отчёте видно, что сверено только значение.
5. `/opsx:archive` после приёмки последнего среза без правок постановки — новый отчёт проверки не появляется; сверка артефактов с кодом и проверка полноты требований выполняются шагами архива.
6. Повторный `/opsx:verify` без изменений сразу после финального — новый отчёт не создаётся.
7. Отчёт повторного прогона: ссылка на предыдущий, что изменилось, результат пересчитанных контролей; без копий списка принятых задач и журнала решений.

## Design Rationale

Точка реализации — существующая таблица глубины (verify §1c) и рецепт хэша снимка (`templates/report-header.md`): оба общие для verify, apply и archive, поэтому новый класс и новые ключи сразу действуют во всех трёх командах без второго классификатора. Дополнение только применяет таблицу к своей дельте и называет исход — правило остаётся в одном месте. Точечная строка срабатывает по дельте, поэтому экономия не переезжает на границу среза. Архив опирается на собственные шаги и сверку с кодом §3.6 и не вызывает проверку, если постановка не менялась.

## Assumptions

1. Реализация начинается после архивации `value-efficient-verify` и `verify-stop-repeat`. Строка D3 встраивается в итоговую редакцию таблицы глубины, и дельта MODIFIED к требованию «Ответ не перезапускает всё» пишется к уже существующей основной спецификации.
2. Кроме автора отчёта, `accepted_tasks` и `closed_decisions` из снимка никто не читает (Grep по `.cursor/**` на момент создания, подтверждён разбором). Реализация повторяет эту проверку перед удалением копий.
3. Условия D1 проверяются по артефактам ЗНИ без чтения кода. Старое значение в коде ищет задача замены значения до отметки выполнения (таблица состояний D1); сверка артефактов с кодом строковые значения не видит.
4. Имя секции записей приёмки в `debug.md` (`## Slice Gate Decisions`) совпадает с тем, что пишет применение ЗНИ; сверяется при реализации.

## Risks / Trade-offs

1. [Под видом замены значения пройдёт смена поведения, например цвет, служивший признаком состояния, заменён на цвет другого состояния] → условия D1.2 (не занято другим состоянием, не в условиях), D1.4 (не повторная замена) и D1.5 (ось); при неочевидном воздействии — короткое мнение архитектора об одной замене; при любом оставшемся сомнении класс не присваивается; ручная приёмка остаётся.
2. [Старое значение останется в коде] → поиск в задаче замены значения до отметки выполнения; остальное ловит только ручная приёмка — сверка с кодом строковые значения не проверяет.
3. [Конфликт с идущими ЗНИ в одной таблице] → реализация после их архивации (Assumptions 1); D3 — одна строка и точечные оговорки, без переписывания соседних строк.
4. [Нормализация флажков скроет настоящую правку задачи] → нормализуется только состояние флажка, текст задачи входит в хэш; сырой ключ сохраняется для всех прежних читателей.
5. [Архив пропустит изменение постановки после приёмки] → любая правка proposal, design, specs или текста задач уводит архив в обычную проверку (D5.3).
6. [Старые отчёты без новых ключей и без `parent_verification`] → отсутствие ключа — промах кэша, а не ошибка; следующий прогон считает ключи заново.

## Решения verify (зафиксировано)

Заказчик (2026-09-30): класс «замена значения» не задаётся перечнем атрибутов. Модель сама оценивает воздействие замены; меняется только видимое или получаемое заказчиком значение — проверка не требуется. При сомнении — короткая архитектурная оценка воздействия одной замены, без полного разбора; сомнение осталось — обычная проверка.
