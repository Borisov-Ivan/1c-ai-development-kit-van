# Proposal: kit-session-api-mode

## Why

После исчерпания лимита API каждый следующий дорогой вызов снова бьётся в платную модель и только потом уходит на модель чата: шумно и зря. Нужны два явных режима в том же чате — жечь лимиты или нет — без настройки репозитория. Ключи `-noapi` / `-api` (и то же с двумя дефисами) в любом сообщении чата дают однозначный сигнал.

Источники (verified): `temp/reports/exploration-2026-08-17-model-economy-precedent.md`, `temp/reports/exploration-2026-08-17-command-flags.md`, `temp/reports/exploration-2026-08-17-project-noapi-marker.md`.

## What Changes

1. Оркестратор держит режим сессии: увидел `-noapi` или `--noapi` в чате — дальше все вызовы с конкретной моделью сразу на модели чата, пока не скажут `-api` / `--api` или не откроют новый чат.
2. После сбоя «лимит / модель недоступна» — тот же режим без повторных ударов в API; сетевой таймаут так не липнет.
3. Смысл ключей живёт в правиле выбора моделей, не копипастой по командам. В палитре команд, которые реально зовут дорогие модели, — одна строка, что ключ можно написать в чате. Команды без дорогих вызовов не объявляют ключ своим флагом и не меняют вывод; токен в том же сообщении всё равно переключает режим сессии.
4. Признак в `project.md` не вводится: два режима «сегодня есть лимит / сегодня нет» — состояние чата, не репозитория.

Вне scope: смена таблицы ролей и политики Fable; профили тона чата; проверка квоты до вызова; файл-состояние между чатами; обязательный вопрос в `/init-project`.

## Capabilities

### New Capabilities

- `session-api-mode`: сессионный режим «с API / без API» по ключам в чате и по памяти после сбоя лимита; двухшаговая цепочка выбора моделей не ломается.
