# Design Challenge — kit-session-api-mode

## Адверсариальная установка

Разбор независим от `reports/architecture-*.md` этой ЗНИ: прочитаны `proposal.md`, `design.md`, `specs/session-api-mode/spec.md`, действующее `.cursor/rules/model-selection.mdc` (двухшаговая цепочка), соседние cue в `tool-name-guard.mdc` и `session-discipline.mdc`, ADR-0001 и дельта `subagent-model-mapping` активной ЗНИ `kit-evolution-models-economy-profiles`. Кода 1С нет (kit-метапроект). Цель — отвергнуть постановку, если Why не закрыт или есть лучший путь по наблюдаемому поведению.

## Three-Question Challenge

### Q1 — Problem-Solution Fit

- **Why говорит:** после исчерпания лимита API каждый следующий дорогой вызов снова бьётся в платную модель и только потом уходит на модель чата — шумно и зря; нужны два явных режима в том же чате без настройки репозитория; ключи `-noapi` / `-api` (и с двумя дефисами) в любом сообщении дают однозначный сигнал (`proposal.md` § Why, § What Changes п.1–4).
- **Design адресует:**
  - Why «повторный удар после лимита» → D3 + D6: шаг 2 текущего вызова обязателен; липкая память (лимит / недоступность / ошибка выбора модели) пропускает шаг 1 только у **следующих** вызовов; таймаут не липнет.
  - Why «два режима в том же чате, не репозиторий» → D1: состояние оркестратора на время чата; `project.md` и `temp/session-notes.md` вне цели.
  - Why «ключи в любом сообщении» → D2: четыре литерала, регистр не важен, последний токен в сообщении побеждает.
  - Why «не ломать цепочку ролей» → D4/D6/D7 + Blast Radius: таблица ролей и шаг 2 не отменяются; в режиме без API не передаются Primary и закрытая эскалация, кроме разового явного слага.
- **Покрытие:** частичное.
  - Ядро Why закрыто: явный отказ от платных вызовов до удара (`-noapi`) и прекращение повторных ударов после липкого сбоя.
  - Остаток шума не зафиксирован: сценарий «Память после лимита» требует одну строку после первого липкого сбоя, но не запрещает повторять ту же строку на каждом следующем дорогом вызове — тогда «шумно» из Why лечится только наполовину.
  - «В любом сообщении» не доведено до однозначного разбора токена: D2 пишет «границы слова», spec запрещает срабатывание на `--api-key`. Наивный поиск подстроки `-api` внутри `--api-key` как раз сработает. Без правила «целое слово после разбиения по пробелам = один из четырёх литералов» сценарий «Ложное слово» неисполним.
  - Столкновение D2 и D5: токены в любом сообщении vs «дешёвые команды ключ игнорируют». Сценарий `/opsx:status -noapi` фиксирует только молчание вывода, не говорит, переключается ли режим сессии. Why («любое сообщение») и D2 требуют переключения; буквальное «игнорируют» можно прочитать как «не переключать». Это дыра постановки, не развилка оси.
  - Сообщение после липкого сбоя в design («дорогие модели недоступны — дальше на модели чата») совместимо с ADR-0001 (без слага и без имени агента) — здесь fit полный.

### Q2 — Optimality

- **Выбранный путь:** один признак сессии у оркестратора + четыре токена в чате + липкая память только после узкого класса сбоев; SSOT в `model-selection.mdc`; таблица ролей не переписывается.
- **Альтернативы (включая не упомянутые в design § Implementation Options):**
  1. **Отдельные команды-переключатели режима** (не в Implementation Options) — отдельные slash-команды «без API» / «с API» вместо токенов в произвольном тексте. Плюс: нет ложных срабатываний на `--api-key`. Минус: это уже не «ключ в любом сообщении» из Why; пользователь должен помнить ещё две команды; follow-up внутри `/opsx:apply` не переключает режим одной строкой. Хуже Why-fit.
  2. **Вопрос после первого сбоя лимита** (не в Implementation Options) — не липнуть автоматически, а спросить «дальше без платных вызовов?». Плюс: явный режим без сюрприза. Минус: добавляет шум в момент, который Why как раз хочет укоротить; первый удар уже состоялся. Хуже по «шумно и зря».
  3. **Пользовательская настройка Cursor вне репозитория** (не в Implementation Options; не `project.md`) — правило в настройках пользователя, а не в чате. Плюс: переживает новый чат. Минус: это всё равно настройка «навсегда», а Why — два режима «сегодня есть лимит / сегодня нет» в том же чате; переключать настройки ради одного дня тяжелее ключа. Не возвращает отклонённый признак проекта.
  4. **Токен только суффиксом команды** (`/opsx:new -noapi`, не в любом сообщении) — плюс проще парсер. Минус: прямо режет Why «в любом сообщении»; follow-up без новой команды не переключает режим.
  5. Из Implementation Options: признак проекта; только память без ключей; probe квоты (ещё в Simplicity Check). Первое отклонено пользователем 2026-08-17; второе не даёт режима до первого удара; третьего API у Cursor нет (design § Context). Не превосходят выбранный путь.
- **Вердикт по Q2:** оптимален по оси «сессия + ключи + память». Ни одна неупомянутая альтернатива не лучше по Why. Оставшиеся дыры — уточнение инвариантов (токен, молчание после памяти, cue на follow-up), не смена оси.

### Q3 — Fresh-Eye Approval

- **Согласовал бы (или нет):** с оговорками.
- **Причины:**
  - Да: точка правки — момент `Task` с конкретной моделью, а не сорок командных файлов; двухшаговая цепочка из `model-selection.mdc` остаётся, добавляется право не начинать шаг 1.
  - Да: новый чат сбрасывает режим — честно для «без файла между чатами»; смягчение тем же ключом в первом сообщении.
  - Оговорка: `model-selection.mdc` сейчас `alwaysApply: false`, а устойчивость режима на follow-up обещана через cue в `session-discipline.mdc` (always-apply). Без жёсткой фразы «перед каждым `Task` с моделью проверить режим сессии» компактный чат снова ударит в платную модель — то есть вернёт Why.
  - Оговорка: spec «Подсказка в палитре» в WHEN перечисляет не полный набор команд из proposal § Impact (`/opsx:explore`, `/opsx:extend` есть в proposal и в tasks S2, нет в spec-сценарии). Apply по spec может «законно» не подписать две команды, которые реально зовут дорогие модели.

## Verdict

**CHALLENGE** — ось решения Why закрывает, менять таблицу ролей и политику эскалации не нужно; до реализации надо закрыть инварианты токена, молчания после памяти, смысла ключа на дешёвых командах и полноты палитры, иначе apply разъедется со spec.

## Gaps for design.md

Инварианты реализации (ось сессии не менять):

1. **Токен = целое слово.** В D2 заменить «границы слова» на: разбиение текста сообщения по пробельным символам; сравнение без учёта регистра с литералами `-noapi`, `--noapi`, `-api`, `--api`; вхождение внутри другого слова (`--api-key`) не токен. Иначе сценарий «Ложное слово не включает режим» не Grep-проверяем.
2. **Дешёвая команда не глотает сигнал сессии.** Зафиксировать: `/opsx:status -noapi` (и аналоги) не меняют вывод команды и не показывают справку, но оркестратор всё равно переключает режим — потому что D2 и Why требуют «любое сообщение». S2.9 в `tasks.md` это не пишет.
3. **Повторная строка после памяти запрещена.** После первой строки про недоступность дорогих моделей (без слага, ADR-0001) следующие пропуски шага 1 в том же чате молчаливы. Иначе Why «шумно» не закрыт.
4. **Cue на каждый ход, не только описание режима.** В design § D4 / cue `session-discipline.mdc`: перед каждым вызовом с конкретной моделью проверить токены текущего сообщения, затем память сессии, затем таблицу ролей. Иначе always-apply не тащит SSOT (`model-selection.mdc` не always-apply).
5. **Палитра = proposal.** В spec-сценарии «Подсказка в палитре» добавить `/opsx:explore` и `/opsx:extend` (они уже в proposal § Impact и tasks S2.5–S2.6). Сейчас spec разрешает считать срез закрытым без двух команд, которые зовут дорогие модели.
6. **Разовый слаг и токен в одном сообщении.** Перенести порядок D7 в spec одним сценарием: явный слаг действует на этот вызов; токены задают режим дальше; сброс режима только `-api` / `--api`. Иначе apply может сбросить режим разовым override.

Не предлагать признак в `project.md`: Why закрывается сессией; пользователь отклонил файл проекта 2026-08-17; нового факта, что сессии недостаточно, нет.

## Architectural alternatives

Нет равноправной развилки по коду/поведению, которую нужно выносить пользователю. Дешёвая команда «не переключать режим» противоречит Why и D2 — это не путь B, а риск неверной реализации. Уточнения выше не отменяют D1–D7.
