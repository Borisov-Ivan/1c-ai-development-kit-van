# Design Challenge — overview-map-offer

Исход: **CHALLENGE**. Выбранный путь (намёк в постоянной строке следующего шага чата описания, сборка по согласию из отчётов ЗНИ) переживает атаку: ни одна из рассмотренных альтернатив, включая три не упомянутые в design, его не превосходит, инварианты ADR-0008 и архивного контракта не ослабляются. Но перед apply нужно закрыть три текстовых пробела: (1) несогласованность «проверка по отчётам (множ.) → в сборщика один отчёт» — намёк может пообещать вывод, который панель из одного отчёта не покажет; (2) содержимое строки следующего шага по умолчанию не задано и рискует стать заглушкой «достаточно»; (3) механика проверки трёх условий не ограничена по чтению — отчёты разбора не входят в контекст описания, и цена проверки на каждом прогоне не оговорена. Все три пробела — уточнения инвариантов реализации, архитектурной развилки нет.

## Three-Question Challenge

### Q1 — Problem-Solution Fit

- **Why говорит:** «Команда описания ЗНИ собирает связный текст для согласования… Схему механизма она не предлагает, даже когда по этой ЗНИ уже лежат отчёты разбора со связями и доказательствами. Согласующий видит этапы поставки и не видит ловушку, из‑за которой изменение затеяли.»
- **Design адресует:** боль «команда не предлагает» закрыта прямо — после записи файла инвентаризуются отчёты названных ЗНИ, при прохождении трёх условий в строке следующего шага печатается вариант «что станет видно»; согласие строит панель из отчётов, не из этапов; постановка и файл описания источником узлов не становятся (Behavior Contract 2–4, дельта «Offer by topology», «Hint only», «Map outside walkthrough»).
- **Покрытие:** **частичное по букве Why, полное по границам постановки.** Персона из Why — согласующий, но артефакт, который он получает, — md-файл описания, а панель живёт рядом с чатом разработчика и в git не попадает (ADR-0008, «живые файлы панели в git не входят»). Ловушка становится видна оператору сессии, который несёт её на согласование; напрямую согласующему — нет. Это ограничение самой постановки (What Changes п. 4 и Acceptance 4 прямо запрещают схему в файле), design его не создавал и обойти не может. Отклонённый вариант C («вставить схему в файл») — единственный, который дотянулся бы до согласующего напрямую, — отклонён обоснованно: жанр описания для ФА/заказчика запрещает механизм в тексте (ось этапов «ситуация ≠ механизм» в скилле описания), статичная схема в md теряет доказательства-переходы, а контракт способности — панель-граф, не markdown-дубликат. Вывод: design решает проблему в том объёме, в котором её зафиксировала постановка; остаточная дистанция «панель ↔ согласующий» — осознанный scope, не дыра design.

### Q2 — Optimality

- **Выбранный путь:** постоянная строка следующего шага в чате описания как слот намёка; проверка трёх условий по отчётам названных ЗНИ; сборка по согласию из отчётов; третье исключение отказа «укажите отчёт» для прямой просьбы при готовом инвентаре.
- **Альтернативы (включая не упомянутые в `## Implementation Options`):**
  1. **Только третье исключение, без намёка** (не упомянута). Расширить лишь требование «вне разбора — названный источник»: прямая просьба в сессии описания берёт отчёты ЗНИ без «укажите файл». Правится одно требование вместо пяти, нет постоянной строки и нет проверки на каждом прогоне. Отклоняю: не решает ядро Why — «схему она не предлагает». Пользователь, знающий про карту, и сейчас может попросить её с указанным отчётом; проблема в обнаруживаемости, а её закрывает только намёк.
  2. **Ссылка на журнал разбора в хвосте «Ссылки» файла описания** (не упомянута). Дёшево и дотягивается до согласующего — единственная альтернатива, работающая с персоной Why напрямую. Отклоняю как замену: сырой журнал разбора — жанр разработчика, для ФА это шум OpenSpec, которого описание сознательно избегает; связи визуально не видны; способность карты не задействуется вовсе. Как дополнение — возможна, но это правка жанра файла, выведенная постановкой из scope.
  3. **Пробная сборка манифеста картографом до намёка** (не упомянута). Вместо проверки трёх условий родителем — сухой прогон сборщика: намёк печатается только при исходе «публиковать можно». Плюс: проверка и сборка — один код, намёк никогда не обещает больше, чем покажет панель; контекст родителя не тратится на чтение журналов. Минус: вызов субагента на каждом прогоне описания, даже когда согласия не будет; картографу нужен новый режим «проверка без публикации»; латентность тонкого чата. Не превосходит вариант A, если у A ограничить чтение при проверке (см. gap 3) и связать источник проверки с источником сборки (см. gap 1) — тогда A проще при том же результате.
  4. **B/C/D из design** (отдельный вопрос; схема в файле; автосборка) — отклонены в design корректно: B ломает «намёк только на существующей строке», C разобран в Q1, D ломает инвариант ADR-0008 «без просьбы и согласия панель не создаётся».
- **Вердикт по Q2:** выбранный путь оптимален. Он единственный одновременно закрывает обнаруживаемость (намёк), сохраняет молчание и регистрацию родителем, не трогает жанр файла и переиспользует уже существующие проверку топологии, порог и раскладку из скилла карты. Преимущество альтернативы 2 (прямой выход на согласующего) реально, но куплено ценой слома жанра описания — постановка этот размен уже отвергла.

### Q3 — Fresh-Eye Approval

- **Согласовал бы:** с оговорками.
- **Причины «да»:**
  - Дельта переписывает пять требований как MODIFIED внутри той же способности, а не плодит параллельные требования рядом; сверено с главным spec — добавленные сценарии описания симметричны уже принятым сценариям исследования (исключение для текущего отчёта explore ↔ исключение для инвентаря описания).
  - Все шесть инвариантов ADR-0008 проверены построчно против Behavior Contract и Blast Radius — ни один не ослаблен; таблица Blast Radius честно перечисляет семь затронутых контрактов архива с классом и альтернативой по каждому.
  - Один срез обоснован: намёк без согласия и отказа не имеет самостоятельной приёмки, разрезать нечего.
- **Причины «с оговорками»:** три пробела ниже — свежий взгляд спотыкается на том, что именно уйдёт в сборщик при проверке по нескольким отчётам, что печатает строка шага в пустом случае и сколько стоит проверка на каждом прогоне.

## Verdict

**CHALLENGE** — решение имплементируемо и лучшей альтернативы нет, но три инварианта реализации должны быть зафиксированы в design/spec до apply, иначе намёк может обещать не то, что покажет панель.

## Gaps for design.md

1. **Проверка и источник сборки не связаны одним отчётом.** Behavior Contract п. 2 проверяет три условия «по отчётам названных ЗНИ» (объединение), а Decision 2 отправляет в сборщика **один** отчёт. Если топологический признак виден только на объединении (сущности в отчёте исследования, связи в журнале прохода), намёк сработает, а панель из одного отчёта обещанный вывод не покажет. Зафиксировать: до поставки соседней ЗНИ про несколько путей проверка трёх условий обязана пройти **на том же одном отчёте**, который станет источником сборки; объединение отчётов признаком не считается. Заодно выровнять формулировку сценария «Согласие на намёк описания рисует карту из отчётов» (сейчас — множественное «из отчётов, на которых прошла проверка») с этим правилом.
2. **Содержимое строки следующего шага по умолчанию не задано.** Decision 1 говорит «достаточно» (или иное одно действие)» — это заглушка, пограничная с запретом печатать не-события. Назвать канонический default в контракте чата описания (например, действие отправки на согласование), чтобы строка несла смысл и в прогонах без карты.
3. **Механика проверки трёх условий не ограничена.** Отчёты разбора в контекст описания не входят (скилл прямо запрещает их как основу сюжета), значит проверка требует чтения журналов и отчётов после записи файла на каждом прогоне. Зафиксировать бюджет: какие секции отчёта читаются для отсева (доказательства и связи, не весь текст), и место архитектурного отчёта в порядке предпочтения источника (Decision 2 ранжирует только журнал и разбор — может ли архитектурный отчёт быть единственным источником, и с каким отсевом «мы планируем»).
