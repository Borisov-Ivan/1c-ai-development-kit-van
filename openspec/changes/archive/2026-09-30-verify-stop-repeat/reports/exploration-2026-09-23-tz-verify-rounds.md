# Круги проверки tz-tech-project
Вопрос: обоснован ли каждый новый круг проверки новым разрывом, или он пересказывает уже закрытое.
Исходный запрос: заказчик считает, что проверка этой задачи часто ходит по кругу без новой причины, и просит это проверить по отчётам.
Симптом: за 23.09.2026 пять отчётов проверки подряд.
Объекты: пять verification-*.md

Правило, которое обрывает автокруг дописки: после `repair_attempt: 2` — `repair_next: "terminal after repair_attempt 2"` (круг 3), дальше не silent repair, а ответ в чате / `/opsx:extend`. Правило, которое обрывает круг правок среза: Layer 2.5 `acceptance-loop-detected` при `PatchRounds(S1)=5` при пороге 3 (круг 5).

## Сводка

- **Кругов из 5 с хотя бы одним НОВЫМ блокирующим замечанием:** 5 (1 — первый набор invariant; 2 — `do-not-copy-overview-entry-pause` + новые имена; 3 — каркас / неоднозначная строка; 4 — EC + два шага + округление; 5 — `acceptance-loop-detected` / мета-развилка).
- **Кругов почти целиком ПОВТОР:** 1 из 5 по сути содержания — круг 2 (почти все пункты — УТОЧНЕНИЕ круга 1 при том же следующем шаге «проверка повторяется сама»). Круг 5 почти целиком повтор по смыслу часов/вывода, но блокер другой (петля).
- **Самые длинные цепочки повторов:**
  - Часы из прозы / нижняя граница / коэффициент / надбавка → круги 1 → 2 → 3 → 4 → 5 (в 5 уже как закрытое правило, не новый разрыв).
  - Два файла / имена вывода / «один запуск пишет оба» → круги 1 → 2 → 3; с круга 4 ось сменяется на два шага (лист+согласование, техпроект отдельно) → 5 (уточнение «после подтверждения», не «по просьбе»).
  - Папка шаблонов / не runtime SSOT → круги 1 → 2 → 3 (dropped / ось копий).
  - Форма пункта листа / два варианта / одна фраза пустого листа → круги 1 → 2 → 3.
  - Ответы не из чата / сохранение ответов → круги 1 → 2.
- **Момент, после которого дальнейшие круги не меняли суть блокера содержания:** после круга 3 (`terminal after repair_attempt 2`) автодописка invariant-пробелов исчерпана; суть «дописать постановку challenge’ем» больше не двигается. После закрытия EC в круге 5 содержательные блокеры круга 4 (два шага, надбавка, округление) уже PASS; дальше круги не добавляют новый содержательный разрыв — только обрыв петли правок (`acceptance-loop-detected`).

**Ответ на вопрос исследования:** круги 1 и 3–4 опираются на новый разрыв (challenge → новые invariant; terminal repair; затем EC). Круг 2 в основном пересказывает и уточняет уже поднятое в круге 1 при том же авто-re-verify. Круг 5 не открывает новый содержательный пробел, а применяет правило обрыва круга правок среза (`acceptance-loop-detected`, PatchRounds > 3).
