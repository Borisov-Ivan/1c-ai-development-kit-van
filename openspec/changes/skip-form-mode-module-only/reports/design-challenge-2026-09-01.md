## Three-Question Challenge

### Q1 — Problem-Solution Fit

- **Why говорит:** при ЗНИ, где правят только модуль формы (номера в заголовках колонок, состав полей и кнопок не трогают), чат всё равно спрашивает «вручную / автоматически / программно»; пропуск даёт «вручную», и на реализации ждут выгрузку из Конфигуратора, хотя разметку не меняют (`proposal.md` ## Why).
- **Design адресует:**
  - Why «чат всё равно спрашивает» → классификатор; при доказанном «только модуль» выбора из трёх нет, в карточке сразу программно (`design.md` Goals 1, Behavior Contract п.1).
  - Why «пропуск = вручную → ждут Конфигуратор» → вопрос не показывают, default пропуска на **заданном** вопросе не меняют (`design.md` Non-Goals 2; spec: пустой ответ на заданный вопрос по-прежнему вручную).
  - Сохранить форму в списке, иначе дыра режима (`proposal.md` What Changes п.1; spec ADDED: форма SHALL остаться в списке).
- **Покрытие:** полное по заявленному Why. Симптом «лишний канон из трёх» и вредный default пропуска закрываются одним механизмом (не спрашивать + записать программно), а не сменой default для всех форм. Частичность — не в Why, а в операционализации классификатора (см. Gaps): слишком широкие положительные признаки могут записать «программно» там, где Why ещё не доказан.

### Q2 — Optimality

- **Выбранный путь:** классификатор «только модуль / разметка / неясно»; при доказанном «только модуль» записать программно без меню; форму из списка не выкидывать; при разметке/неясности — прежний канон из трёх (`design.md` Implementation Options, вариант A).
- **Альтернативы из design (A/B/C) — почему не лучше A:**
  - **B** (вопрос остаётся, default пропуска = программно) — Why про сам вопрос не закрывается; ломает безопасный default «пусто → вручную» для разметки.
  - **C** (выкинуть форму из списка) — дыра режима, прямо запрещена архивным Empty и текущей дельтой.
- **Альтернативы, не упомянутые в `## Implementation Options`:**
  1. **Двухвариантный вопрос только для «только модуль»** («модуль в репозитории» vs «выгрузка из Конфигуратора», без «автоматически»). Как реализуется: отдельный канон чата при срабатывании классификатора. Плюс: не молчит, оставляет выгрузку модуля из Конфигуратора явным путём. Минус: Why как раз про паузу на выбор, когда постановка уже сказала «разметку не трогаем»; второй канон расходится с ADR-0001 («три варианта, когда вопрос задаётся») и плодит протокол. Отклонена: для kit реализация модуля формы — запись `Module.bsl` в репозитории (таблица режимов в `forms-mxl-mode-gate.mdc`: программно = не менять Form.xml, UX в модуле); отдельная пауза не снимает боль Why.
  2. **Записать режим в блоке постановки explore до `/opsx:new`.** Как реализуется: handoff уже содержит поставку программно; new идёт по ветке «записанный режим не переспрашивать». Плюс: архивный MUST-вопрос формально не сужается. Минус: explore не всегда есть; прямой `/opsx:new` снова задаёт холостой вопрос; классификатор дублируется в двух командах. Отклонена: Why локализован в цикле new на design, а не в explore.
  3. **Не трогать вопрос; на реализации не ждать выгрузку разметки, если в задачах только модуль формы** (даже при записанном «вручную»). Как реализуется: эвристика apply по составу задач. Плюс: архивный MUST-вопрос цел. Минус: в карточке остаётся «вручную» при работе только с модулем (ложная поставка); Why про шум вопроса не закрыт; риск разъехаться с паузой Конфигуратора для настоящей разметки. Отклонена: лечит следствие на apply, не причину на design.
- **Вердикт по Q2:** выбранный путь оптимален. Он единственный одновременно убирает холостой вопрос, сохраняет безопасный default на заданном вопросе, не создаёт дыру режима и не пишет «автоматически» молча. Ни одна из трёх неупомянутых альтернатив не лучше по совокупности «меньше пауз / меньше инвазивности / обратимость / Blast Radius».

### Q3 — Fresh-Eye Approval

- **Согласовал бы (или нет):** да, с оговорками (не как готовый к apply текст).
- **Причины «да»:**
  - Why и Chosen совпадают: аналог уже принятого skip макета («ответ однозначен — не спрашивать»), при этом форма остаётся в списке с валидным режимом.
  - Запрет молчаливого «автоматически» и блокер пустого/`n/a` на модуль формы явно сохранены; запись программно не перенесена на apply.
- **Причины оговорок:**
  - В Behavior Contract положительные признаки «только модуль» включают «обработчики» и «видимость уже существующих элементов» без обязательного «в модуле» — это может совпасть с правкой свойств/привязок в Конфигураторе (разметка), и тогда молчаливая запись программно **хуже**, чем задать вопрос.
  - Spec Mixed требует «отдельное сообщение» для вопроса по форме с разметкой, а Behavior Contract §8 считает поясняющую строку не выбором (её можно совместить с одним каноном другой формы) — два разных наблюдаемых протокола.
  - Поясняющая строка оставлена открытым вопросом (MAY); без MUST или явного «отсутствие строки — не дефект» skip неотличим от забытого вопроса до чтения карточки.

## Verdict

**CHALLENGE** — направление верное и оптимальное относительно A/B/C и трёх неупомянутых путей, но классификатор и протокол смешанных форм нужно зафиксировать однозначно до apply.

## Gaps for design.md

1. **Сузить положительные признаки «только модуль» (implementation_invariant).** В Behavior Contract п.1 и в spec (абзац про признаки/токены) не считать достаточными сами по себе «обработчики» и «видимость уже существующих элементов». Достаточно: явная работа **в модуле** (модуль формы, тела существующих обработчиков, заголовки существующих колонок **в модуле**, программные элементы, фраза «разметку не трогаем»). Привязка нового обработчика, свойство видимости в Конфигураторе, состав полей/кнопок без «в модуле» → неясно → вопрос. Правило «добавить кнопку» уже такое; выровнять остальные токены. Иначе ложноположительный skip пишет программно на ЗНИ, где нужна выгрузка разметки.
2. **Согласовать Mixed и «один вопрос выбора за ход».** Либо spec-сценарий Mixed («отдельным сообщением») привести к Behavior Contract §8: в одном ходе допустимы запись «только модуль» (и необязательная поясняющая строка) **плюс** ровно один канон из трёх по другой форме. Либо явно запретить совмещение и требовать два хода. Сейчас implementer разъедется.
3. **Закрыть открытый вопрос про поясняющую строку.** Зафиксировать одно: (а) строка MUST при каждом skip, чтобы пропуск был виден в чате и не путался с забытым вопросом, **или** (б) MAY, и отсутствие строки не дефект, потому что критерий — запись в карточке. Сейчас design оставляет MAY и одновременно рекомендует конкретный текст — для приёмки Informing line этого мало.

ADR не создавать. Развилку «спрашивать vs не спрашивать при доказанном только модуле» не открывать: Why её закрывает.

## Architectural alternatives

Нет равноправной развилки по коду/наблюдаемому поведению: двухвариантный вопрос, запись режима в explore и «лечить на apply» уступают Chosen (см. Q2). Уточнения Gaps — инварианты реализации, не смена оси.
