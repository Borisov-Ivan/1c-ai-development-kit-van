## Context

Эволюция Cursor-kit: UX вопроса поставки управляемой формы на `/opsx:new` (этап design). Источник: блок «Постановка ЗНИ» в чате; разбор `reports/architecture-2026-09-01.md` (копия `temp/reports/architecture-2026-09-01-idle-form-mode-question.md`).

Сейчас цикл создания ЗНИ спрашивает способ поставки у каждой формы в списке без записанного режима. В список входят и явно названные формы, и задачи на модуль формы. Поэтому ЗНИ «переписать номера в заголовках колонок в модуле» всё равно получает выбор из трёх. Пропуск записывается как «вручную» — реализация ждёт Конфигуратор.

Связанные ADR: ADR-0001 (чат vs агент) — канон трёх русских вариантов только когда вопрос задаётся; enum режима — в карточке ЗНИ, не в заголовках чата. Разбор постановки не отменяет ADR-0001.

## Goals / Non-Goals

**Goals:**

1. Если после стабилизации списка форм доказано: для этой формы в работе только модуль, разметки нет — выбора из трёх нет, в карточке сразу поставка программно.
2. Если есть разметка или способ неясен — вопрос как сейчас; «автоматически» молча не выбирать; пустой ответ на заданный вопрос — вручную.
3. Форму не исключать из списка: дыра режима при задаче на модуль запрещена.
4. Справка kit описывает пропуск.

**Non-Goals:**

1. Новый набор значений режима.
2. Смена default пропуска на **заданном** вопросе.
3. Вопрос макета в new (политика макета без изменений).
4. Прикладной BSL / Form.xml / Template.xml.
5. Молчаливый выбор «автоматически».
6. Правка apply/verify, если new всегда записывает валидный режим.

## Existing Mechanisms

1. Пропуск вопроса по макету в new — тот же класс «ответ однозначен, вопрос — шум»; у формы в карточке обязан появиться режим, иначе проверка останавливается.
2. Kit / нет форм → режим «не применимо», вопроса нет. Нельзя ставить «не применимо» на реальный модуль формы.
3. Продолжение ЗНИ: записанный режим не переспрашивают.
4. Цикл «форма без режима → вопрос» — точка правки: классификатор перед каноном.
5. Default пустого ответа = вручную — только после заданного вопроса.
6. Запрет молчаливого «автоматически» — без исключений.

Почему не оставляем «всегда спрашивать»: критерий «Решено, когда» не закрывается; default «вручную» вреден для ЗНИ без разметки.

## Design Rationale

Точки правки — протоколы оркестратора, не прикладной код. Список форм не сужаем: иначе проверка увидит задачу на форму без режима. Пишем «программно» и не показываем меню. Сомнение = вопрос (не угадывать ни «автоматически», ни «программно»). Разбор постановки: вариант A; B (сменить default пропуска) оставляет холостой вопрос и ломает безопасный default для разметки; C (выкинуть форму из списка) создаёт дыру режима.

## Behavior Contract

После стабилизации списка форм, для каждой формы без уже записанного валидного режима:

1. **Только модуль.** В постановке есть признаки работы в модуле формы (модуль формы, заголовки существующих колонок, обработчики, видимость уже существующих элементов, явная фраза «разметку не трогаем»). Нет токенов разметки для этой формы (файл разметки, реквизиты как метаданные, элементы в Конфигураторе, состав полей/кнопок без указания «в модуле»). Тогда выбора из трёх нет. В карточке ЗНИ для этой формы — программно. Одна поясняющая строка в чат рекомендуется, не обязательна; это не вопрос выбора и не пауза до ответа.

2. **Разметка или неясно.** В scope есть разметка **или** форма названа, но не доказано «только модуль». Канон из трёх остаётся. «Автоматически» только явным ответом. Пустой ответ / «да» / пропуск на заданный вопрос — вручную. «Программно» не угадывать.

3. **Несколько форм.** Классификатор по каждой. Только модуль записывается без выбора; разметка/неясность — по одной форме за ход с паузой до ответа. Режим соседней формы не копировать.

4. **Kit / нет форм.** Как сейчас: «не применимо», вопроса нет (не «программно»).

5. **Макет.** Вопроса в new нет.

6. **Продолжение.** Валидный записанный режим не переспрашивать и не перезаписывать логикой пропуска.

7. **Дыра режима.** Пусто / «не применимо» при задаче на разметку **или** на модуль формы — блокер проверки/реализации. Не подставлять «программно» молча на apply: запись — обязанность new/extend.

8. **Один вопрос выбора за ход.** Поясняющая строка пропуска выбором не считается. Маркер автора и вопрос формы в одном сообщении по-прежнему нельзя.

Строка чата (рекомендуется):

```text
Для формы «<ИмяФормы>» в этой ЗНИ меняется только модуль, разметку не трогаем — записываю поставку программно.
```

Без имён служебных полей в этой строке (ADR-0001).

Голое отсутствие файла разметки **недостаточно**: нужны положительные признаки модуля и отсутствие токенов разметки. «Добавить кнопку» без «в модуле» / «в Конфигураторе» — неясно → вопрос. «Добавить кнопку в модуле» / программные элементы — только модуль → программно без вопроса.

## Implementation Options

**Вариант A.** Классификатор «только модуль / разметка / неясно»; при доказанном «только модуль» записать программно и не спрашивать.

**Вариант B.** Оставить вопрос, сменить default пропуска на программно.

**Вариант C.** Исключить форму из списка, если только модуль.

Выбран A (разбор постановки). B не убирает вопрос и ломает default для разметки. C даёт дыру режима.

## Decisions

1. **A, не B и не C.** Форма остаётся в списке; вопрос не показывают; пишут программно.
2. **Не skip по одному лишь отсутствию файла разметки.** Нужны признаки модуля и отсутствие токенов разметки.
3. **Программное создание элементов.** Явно «в модуле» — только модуль; без места поставки — неясно.
4. **Связь с архивом:** сужение MUST-вопроса из `2026-08-18-sequential-ui-mode-questions`; skip макета и запрет молчаливого «автоматически» — extends. Секция последствий ниже.
5. **ADR не создаём.** Повтор ADR-0001 на языке вопроса.
6. **Architect / verify:** `report: reports/architecture-2026-09-01.md`.
7. **Apply mechanical.**

## Assumptions

1. Классификатор читает стабилизированные What Changes / tasks / design / handoff, не внутреннюю мысль агента. Уверенность: высокая.
2. При записи «программно» и задачах только на модуль формы реализация не ждёт Конфигуратор (ветка «модуль формы»). Уверенность: высокая. Регрессия apply — вне этой ЗНИ.

## Risks / Trade-offs

- [Риск] Оркестратор ошибочно сочтёт постановку «только модуль». Mitigation: сомнение = вопрос.
- [Риск] Ошибка классификации при фактической разметке. Mitigation: проверка остановит задачу на compile разметки при режиме «программно»; тогда extend, не тихий «автоматически».
- [Риск] N форм → смесь skip и вопросов. Trade-off: осознанно; в одном сообщении не два выбора.
