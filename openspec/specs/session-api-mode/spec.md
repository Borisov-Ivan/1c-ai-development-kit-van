# session-api-mode

## Purpose

Сессионный режим «с API / без API»: ключи в чате и память после сбоя лимита направляют дорогие вызовы на модель чата. Таблица ролей и двухшаговая цепочка не переписываются.

## Requirements

### Requirement: Ключи в чате задают режим сессии
Оркестратор SHALL разбивать любое сообщение пользователя по пробельным символам и сравнивать каждый фрагмент без учёта регистра с литералами `-noapi`, `--noapi`, `-api`, `--api`. Совпадение фрагмента целиком = токен; вхождение внутри другого слова MUST NOT считаться токеном. После `-noapi` / `--noapi` до конца чата (или до `-api`) вызовы ролей с конкретной платной моделью SHALL идти сразу на модели чата. После `-api` / `--api` SHALL снова действовать таблица ролей. Признак в `project.md` MUST NOT требоваться.

#### Scenario: Ключ без API
- **WHEN** пользователь пишет в чате `-noapi` или `--noapi` и затем запускает команду, которая зовёт дорогую модель
- **THEN** этот вызов идёт на модели чата, без попытки платной модели

#### Scenario: Ключ с API
- **WHEN** сессия уже в режиме без API и пользователь пишет `-api` или `--api`
- **THEN** следующий дорогой вызов снова идёт по таблице ролей

#### Scenario: Оба токена в одном сообщении
- **WHEN** в одном сообщении есть и `-noapi`, и `-api`
- **THEN** действует тот, что стоит последним по тексту слева направо

#### Scenario: Ложное слово не включает режим
- **WHEN** в сообщении есть `--api-key` или иное слово после разбиения по пробелам, где литерал `-api` / `--api` не совпадает с фрагментом целиком
- **THEN** режим сессии не переключается

#### Scenario: Токен на дешёвой команде
- **WHEN** пользователь пишет `/opsx:status -noapi` (или другую команду без дорогих вызовов с тем же ключом)
- **THEN** режим сессии переключается: следующий дорогой вызов идёт на модели чата, без попытки платной модели

#### Scenario: Новый чат сбрасывает
- **WHEN** пользователь открывает новый чат без ключа
- **THEN** работа начинается с таблицы ролей (с API), память прошлого чата не действует

### Requirement: Память после лимита без повторных падений
После сбоя вызова «лимит / модель недоступна / ошибка выбора модели» оркестратор SHALL выполнить второй шаг **этого же** вызова на модели чата, затем до конца чата не повторять удар в платную модель. Сетевой таймаут SHALL дать второй шаг этого вызова и MUST NOT включать память на весь чат. При сомнении в классе ошибки память MUST NOT включаться.

#### Scenario: Память после лимита
- **WHEN** первый дорогой вызов сессии падает из‑за лимита API
- **THEN** этот вызов дорабатывается на модели чата, пользователь видит одну строку без имени модели; следующие дорогие вызовы в этом чате не повторяют то же падение и не повторяют эту строку

#### Scenario: Таймаут не липнет
- **WHEN** дорогой вызов падает по сетевому таймауту
- **THEN** этот вызов дорабатывается на модели чата, а следующий дорогой вызов снова пробует таблицу ролей

#### Scenario: Целостность первого сбоя
- **WHEN** вызов уже ушёл на платную модель и вернул сбой
- **THEN** второй шаг на модели чата выполняется; отчёт субагента не подменяется текстом оркестратора

### Requirement: Режим без API не отменяет разбор и не зовёт эскалацию
`-noapi` MUST NOT отменять архитектурный разбор постановки и MUST NOT создавать обход гейта (файл `.gate-override.yaml`). Пока сессия в режиме без API, оркестратор MUST NOT звать Primary и самую дорогую эскалацию, кроме разового явного указания модели пользователем на этот вызов.

#### Scenario: Не путать с пропуском архитектора
- **WHEN** пользователь пишет `-noapi` и запускает `/opsx:new` без `--skip-architect`
- **THEN** архитектурный разбор постановки остаётся в протоколе и идёт на модели чата; обход гейта не создаётся

#### Scenario: Эскалация в режиме без API
- **WHEN** сессия в режиме без API и нет явной просьбы «на самой дорогой модели»
- **THEN** дорогие роли вызываются на модели чата; самая дорогая эскалация не запускается «на всякий случай»

#### Scenario: Разовый слаг и токен в одном сообщении
- **WHEN** в одном сообщении есть явная просьба вызвать конкретную модель и ключ `-noapi` / `--noapi`
- **THEN** этот вызов идёт с указанной моделью; дальше сессия без API; сброс режима — только `-api` / `--api`

### Requirement: Подсказка без копипасты по всем командам
Смысл ключей SHALL быть описан в правиле выбора моделей. Команды, которые зовут дорогие модели, SHALL иметь одну строку, что ключ можно написать в любом сообщении чата. Команды без дорогих вызовов MUST NOT объявлять ключ своим флагом и MUST NOT показывать ошибку из‑за его наличия. Наличие ключа в таком сообщении MUST NOT отменять переключение режима сессии.

#### Scenario: Подсказка в палитре
- **WHEN** пользователь открывает описание `/opsx:new`, `/opsx:verify`, `/opsx:apply`, `/opsx:explore`, `/opsx:extend`, `/review` или `/release-review`
- **THEN** видна одна строка, что `-noapi` / `-api` можно написать в чате

#### Scenario: Команда без дорогих вызовов молчит
- **WHEN** пользователь пишет `/opsx:status -noapi`
- **THEN** статус выводится как обычно, без ошибки и без справки про ключ

#### Scenario: FAQ включает и выключает
- **WHEN** пользователь ищет в FAQ kit, как не жечь лимиты
- **THEN** есть как включить режим ключом в чате, как выключить, и чем это не является пропуском архитектора

### Requirement: Видимость режима без API — канон в том же ходе, не токен

После липкого сбоя вызова (лимит / недоступность модели / ошибка выбора модели) оркестратор SHALL написать в чат канон «дорогие модели недоступны — дальше на модели чата» **первой строкой** сообщения этого хода, без имени модели. Always-apply бюджет чата SHALL содержать эту фразу дословно и триггер в разборе сбоя субагента; on-demand правило выбора моделей MUST NOT быть единственным местом текста канона. В сессии `/opsx:verify` канон лимита и строка «Модель архитектора: Opus 5» SHALL быть разрешённым исключением из «одно финальное сообщение» / «ноль промежуточных»: они MUST NOT откладываться до карточки вердикта. Оркестратор MUST NOT печатать `-noapi` / `--noapi` как сигнал памяти и MUST NOT говорить, что «включился noapi». Текст платформы про смену модели MUST NOT заменять канон и MUST NOT цитироваться как протокол kit. Правило «не повторять строку» после первого липкого сбоя в том же чате не дублируется здесь.

#### Scenario: Канон в том же ходе

- **WHEN** дорогой вызов падает из‑за лимита, и в фоне ещё может работать другой вызов
- **THEN** первая строка сообщения оркестратора в этом ходе — канон «дорогие модели недоступны — дальше на модели чата», без имени модели; фраза есть в always-apply бюджете чата; канон не откладывается до финала команды

#### Scenario: Токен не печатается

- **WHEN** режим «без API» включился из‑за лимита, а не из‑за ключа пользователя
- **THEN** в чате нет `-noapi` / `--noapi` от оркестратора и нет фразы, что «включился noapi»

#### Scenario: Фон не отменяется

- **WHEN** в фоне ещё работает вызов с платной моделью, а другой вызов уже дал липкий сбой
- **THEN** канон всё равно в этом ходе (в `/opsx:verify` — до финальной карточки, как progress или первая строка); оркестратор не отменяет фоновый вызов; после завершения фона с тем же лимитом канон не повторяется

### Requirement: Токен пользователя не подменяется каноном лимита

Явный ключ `-noapi` / `--noapi` SHALL включать режим «без API» как раньше. Канон про дорогие модели MUST NOT дублироваться только из‑за токена, если липкой памяти ещё не было.

#### Scenario: Токен не требует канона лимита

- **WHEN** пользователь сам пишет `-noapi` и лимита в этом чате ещё не было
- **THEN** следующие дорогие вызовы идут на модели чата, и канон «дорогие модели недоступны» в чат не обязателен

### Requirement: FAQ отличает ключ от памяти после лимита

В FAQ kit SHALL быть видно: как включить режим ключом; что после лимита ключ в чат сам не появляется; сигнал тогда — короткая русская строка, а не токен.

#### Scenario: FAQ токен и память

- **WHEN** пользователь ищет в FAQ kit, почему после лимита в чате нет `-noapi`
- **THEN** есть объяснение: ключ пишет человек; после лимита оркестратор не печатает ключ; дальше работа на модели чата, и об этом говорит каноническая строка
