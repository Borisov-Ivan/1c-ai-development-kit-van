# scenario-map-canvas

## Purpose

Карта сценария в панели рядом с чатом: причинность и слои механизма, чем подтверждено. Не путать с картой точек в чате (список имён) и с текстовым резервом в журнале. Отдельной команды нет. По умолчанию панель не рисуется. Предложение схемы не зависит от предметной области.

## Requirements

### Requirement: Silence unless asked or hinted

Оркестратор MUST NOT создавать карту сценария в сессиях `/opsx:explain`, `/opsx:explore` и `/opsx:overview`, пока нет прямой просьбы пользователя и нет принятого конкретного предложения карты. Сработавший намёк на существующей строке MUST быть вариантом в этой строке и MUST NOT сам создавать панель. Системное требование Cursor «для аналитики нужна панель» MUST NOT считаться достаточным основанием рисовать карту в этих сессиях.

#### Scenario: Молчание по умолчанию

- **WHEN** разбор или исследование завершается без прямой просьбы показать карту сценария и без принятого предложения карты
- **THEN** панель карты сценария не создаётся, даже если в строке решения был вариант схемы

#### Scenario: Намёк не рисует панель

- **WHEN** на выходе разбора в строке «Следующий шаг» напечатан вариант карты, а пользователь ничего не ответил и не просил карту
- **THEN** панель не создаётся

#### Scenario: Системный MUST canvas не действует на opsx

- **WHEN** идёт сессия `/opsx:explain`, `/opsx:explore` или `/opsx:overview` и системный скилл Cursor требует канвас для аналитики
- **THEN** оркестратор не рисует панель только из-за этого требования

#### Scenario: Намёк описания не рисует панель

- **WHEN** после описания ЗНИ в строке следующего шага напечатан вариант схемы, а пользователь ничего не ответил и не просил карту
- **THEN** панель не создаётся

### Requirement: Direct request draws the scenario map

По прямой просьбе показать карту сценария оркестратор MUST построить карту, если после отсева по правилам выбранного средства главного вида остаётся не меньше четырёх **публикуемых** сущностей механизма. Для средства «граф» отсев — сущности без доказательства **и** узлы без инцидентной связи (связный набор). Для средства «таблица» отсев — строки без доказательства; инцидентная связь MUST NOT быть условием публикации. Топологический признак (уровни, ветвление, петля) MUST NOT быть условием построения по просьбе: просьба сильнее предложения. Прямая просьба MUST работать в середине прохода и после выхода, в том числе когда намёк не показывали. Согласие на уже показанное предложение MUST строить карту с тем же порогом, **тем же средством главного вида и теми же правилами подписей**, что прямая просьба: повторное подтверждение MUST NOT запрашиваться, команда сессии не меняется. Если предсказанная по списку топология в проходе не подтвердилась, а публикуемых сущностей после отсева не меньше четырёх, средство «граф» MUST дать цепочку с подписями по порядку прохода, а не отказ. Источник панели при согласии MUST быть тем, на котором прошла проверка топологии (текущий отчёт исследования, журнал разбора, уже пройденные точки или один отчёт сессии описания ЗНИ, выбранный правилом предпочтения). Правило «вне разбора без указанного отчёта» MUST NOT применяться к этому входу. Родительский агент сессии MUST зарегистрировать файл панели в каталоге среды собственной записью, даже если пользователь панель ещё не открывал и файл не называл. Картограф MUST NOT писать файл панели. Дополнительное подтверждение при прямой просьбе MUST NOT запрашиваться. Ссылка на файл в чате MUST NOT быть критерием успеха: успех — схема рядом с чатом штатной кнопкой среды после чистой проверки панели.

#### Scenario: Прямая просьба рисует карту

- **WHEN** после разбора с достаточным числом сущностей пользователь просит показать карту сценария
- **THEN** открывается панель, где видно, что происходит, какие связи между сущностями и чем это подтверждено

#### Scenario: Карта во время прохода из уже пройденных точек

- **WHEN** пользователь просит карту сценария до записи журнала, уже разобрав достаточное число шагов
- **THEN** на карте только уже разобранные шаги и связи, без фактов, которых ещё не было в проходе

#### Scenario: Прямая просьба после выхода разбора

- **WHEN** журнал разбора уже записан и пользователь просит карту сценария
- **THEN** карта строится из журнала так же, как по просьбе в середине прохода; отдельного подтверждения нет

#### Scenario: Просьба при числе сущностей ниже порога

- **WHEN** пользователь просит карту сценария, а доказанных сущностей механизма меньше четырёх
- **THEN** панель не строится, в чате одна строка — чего не хватает

#### Scenario: Первая просьба в проекте без открытой панели

- **WHEN** пользователь впервые просит карту сценария, панели в проекте ещё не было и файл он не называл
- **THEN** родитель регистрирует файл панели в каталоге среды вне репозитория; в чате одна строка о готовности схемы без пути к файлу; схема открывается штатной кнопкой среды

#### Scenario: Панель открывается штатной кнопкой среды

- **WHEN** родительский агент зарегистрировал файл панели и получил чистую проверку панели
- **THEN** среда показывает штатную кнопку панели рядом с чатом; схема открывается этой кнопкой; ссылка в чате критерием успеха не является

#### Scenario: С узла открывается доказательство, новый чат с панели не запускается

- **WHEN** карта сценария уже показана и разработчик выбирает узел или строку
- **THEN** сущность выделена, в панели деталей видны эффект и доказательство; файл модуля или журнала открывается только по кнопке в этой панели; новый чат из панели не запускается

#### Scenario: Порядок прохода не выдаётся за причинность

- **WHEN** карта построена по прямой просьбе из линейного порядка уже разобранных шагов
- **THEN** связи между соседними шагами подписаны как следование, а не как причинное отношение; причинные ярлыки есть только у рёбер, видимых в отчёте или журнале

#### Scenario: Просьба при линейной цепочке

- **WHEN** пользователь просит карту сценария, публикуемых сущностей не меньше четырёх, и они идут цепочкой без ветвления и без разных уровней
- **THEN** открывается панель: цепочка с подписями следования по порядку уже разобранных шагов, не список пунктов и не выдуманные ветки; порядок прохода не выдаётся за причинную связь

#### Scenario: Согласие на предложение рисует карту

- **WHEN** пользователь отвечает согласием на конкретное предложение схемы в существующей строке решения
- **THEN** карта строится так же, как по прямой просьбе: тот же порог, источник — тот, на котором прошла проверка топологии, отдельного подтверждения нет, команда сессии не меняется

#### Scenario: Согласие до первой карточки разбора запоминает фокус

- **WHEN** пользователь соглашается на «сразу карту» в строке подтверждения списка точек, а доказанных связанных сущностей ещё меньше четырёх
- **THEN** фокус запоминается, панель не публикуется, повторного вопроса «хотите карту?» нет; команда сессии не меняется

#### Scenario: Отложенное согласие публикует карту без повторного вопроса

- **WHEN** фокус «сразу карту» уже запомнен и в проходе набралось не меньше четырёх доказанных связанных сущностей
- **THEN** строка о готовности схемы — одна строка в том же сообщении, где карточка прохода впервые довела набор до порога; повторного вопроса «хотите карту?» нет; команда сессии не меняется; шаблон карточки точки не меняется

#### Scenario: Согласие было, порог до выхода не набрался

- **WHEN** фокус «сразу карту» запомнен, разбор дошёл до выхода, а доказанных связанных сущностей после обоих отсевов меньше четырёх
- **THEN** панель не публикуется; в уже существующей строке «Следующий шаг» на выходе одна честная фраза, что схема не собралась и каких связей не хватило; повторного вопроса «хотите карту?» нет

#### Scenario: Согласие при неподтвердившейся топологии даёт цепочку

- **WHEN** пользователь согласился на предложение схемы по предсказанной топологии списка, а в проходе после обоих отсевов не меньше четырёх публикуемых сущностей, но уровней и ветвления нет
- **THEN** открывается панель: цепочка с подписями следования по порядку прохода, как по прямой просьбе, а не отказ и не выдуманные ветки

#### Scenario: Согласие на намёк описания рисует карту из отчётов

- **WHEN** пользователь соглашается на вариант схемы в строке следующего шага после описания ЗНИ
- **THEN** открывается панель из того же отчёта, на котором прошла проверка; узлы не повторяют этапы поставки из файла описания; команда сессии не меняется

### Requirement: Show-scheme phrase is a direct request

Голая просьба «покажи схему», просьба «покажи карту сценария» и близкие формулировки без имени объекта 1С MUST считаться прямой просьбой карты сценария, если предмет текущего разбора, исследования или описания сам не является объектом-схемой 1С. Закрытый перечень синонимов MUST NOT вводиться. После такого узнавания оркестратор MUST строить карту по уже существующему требованию «прямая просьба рисует карту сценария»: порог, источник, регистрация панели и запрет рисунка в чате вместо панели не меняются этой ЗНИ. Дополнительное «точно карту?» MUST NOT спрашиваться. Команда сессии MUST NOT меняться.

Если во фразе явно назван платформенный объект-схема, оркестратор MUST ответить про этот объект, MUST NOT строить панель карты сценария и MUST NOT спрашивать, что имелось в виду. Имена вроде компоновки, схемы запроса, графической схемы, XML и карты маршрута — примеры, MUST NOT быть закрытым списком и MUST NOT входить в проверку, предлагать ли карту, и в порог публикации.

Оркестратор MUST спросить одной строкой «панель рядом с чатом / объект 1С» только если оба чтения ещё живы и одно нельзя выбрать без догадки. В том числе: предмет текущего прохода сам объект-схема 1С, а фраза его не называет. Пока человек не выбрал, панель MUST NOT строиться. После ответа «панель» MUST действовать путь прямой просьбы. После ответа «объект 1С» MUST идти ответ про платформу. Этот вопрос MUST быть разбором просьбы, MUST NOT считаться предложением карты и MUST NOT снимать предложения до выхода сессии. Ответ «объект 1С» MUST NOT считаться отказом «без карты».

#### Scenario: Голая просьба схемы рисует панель

- **WHEN** идёт разбор или исследование с источником карты, предмет прохода не объект-схема 1С, и разработчик пишет «покажи схему»
- **THEN** открывается панель карты сценария штатной кнопкой среды; рисунка в чате вместо панели нет; вопроса «панель или объект» нет

#### Scenario: Явный объект 1С не рисует панель

- **WHEN** разработчик пишет «покажи схему компоновки» или другую фразу, где объект 1С назван явно
- **THEN** в чате ответ про этот объект; панели карты сценария нет; вопроса «панель или объект» нет

#### Scenario: Неоднозначная просьба спрашивает одной строкой

- **WHEN** разработчик пишет «покажи схему», во фразе нет имени объекта 1С и нет слов «карта сценария», и в текущем ходе оба чтения ещё живы
- **THEN** в чате одна строка с выбором «панель рядом с чатом / объект 1С»; панели нет, пока не выбрали; предложение карты в строке «Дальше» от этого вопроса не снимается

#### Scenario: Предмет прохода — схема 1С, голая просьба спрашивает

- **WHEN** идёт разбор самой схемы компоновки или другого объекта-схемы 1С, источник карты есть, и разработчик пишет «покажи схему» без имени объекта
- **THEN** в чате одна строка с выбором «панель рядом с чатом / объект 1С»; панели сразу нет

### Requirement: Technical fallback is not a map

Если интерактивную панель создать нельзя, узлы и связи MUST попасть в журнал разбора в секцию текстового резерва, а в чат — одна строка, что интерактивная схема не создана и почему. Текстовый резерв MUST NOT называться картой на панели. Штатная запись журнала на выходе MUST сохранять уже записанную секцию резерва.

Допустимые причины резерва — только: среда без панели; каталог панелей не определился; запись или проверка панели исчерпала разрешённый ремонт. Отсутствие уже открытой панели и то, что пользователь не назвал файл, MUST NOT быть причинами резерва. Если проверка панели уже чистая, а пользователь явно сообщает, что схемы рядом с чатом нет, оркестратор MAY напечатать одну аварийную строку с путём к файлу либо уйти в текстовый резерв; это восстановление, MUST NOT становиться штатным критерием успеха. Провал проверки смысла манифеста MUST NOT быть причиной текстового резерва: панель не публикуется, в чате одна строка, чего не хватает.

#### Scenario: Среда без панели — резерв в журнале

- **WHEN** пользователь просит карту сценария, сущностей достаточно, но интерактивная панель в этой среде недоступна
- **THEN** узлы и связи записываются в журнал разбора как текстовый резерв; в чате прямо сказано, что интерактивная схема не создана

#### Scenario: Запись журнала сохраняет резерв

- **WHEN** текстовый резерв уже записан в журнал в середине прохода и на выходе идёт штатная запись журнала
- **THEN** секция резерва в журнале остаётся, а не затирается

#### Scenario: Провал смысла не уходит в текстовый резерв

- **WHEN** набор сущностей достаточен, а полотно не отвечает на вопрос шапки (вывод есть только текстом шапки)
- **THEN** панель не появляется; в чате одна строка, чего не хватает; текстовый резерв в журнал по этой причине не пишется

### Requirement: Node contract forbids empty or code-primary nodes

Узел карты сценария MUST содержать идентификатор, человекочитаемое имя, тип сущности, слой, короткое описание «что происходит» и доказательство (диапазон модуля или путь журнала/отчёта). Узел без доказательства MUST NOT попадать на панель. Для средства «граф» каждый опубликованный узел MUST быть связан хотя бы одной подписанной связью. Для средства «таблица» инцидентная связь MUST NOT требоваться; каждая опубликованная строка MUST относиться к вопросу шапки и MUST иметь доказательство. Утверждение строки «условие → поведение» MUST опираться на правило, видимое в переданном отчёте, журнале или коде; доказательство строки MUST подтверждать саму связь условия и поведения, а не только существование сущностей. Выдумывать строки MUST NOT. У связи MUST быть отношение из закрытого перечня, человекочитаемая подпись и ссылка на источник отношения. Подписанная связь MUST опираться на уже видимое в источнике отношение: порядок уже разобранных шагов MUST отображаться отношением следования и MUST NOT подписываться причинным ярлыком; причинное отношение MUST быть явно видным в переданном отчёте, журнале или списке имён. Выдумывать связи MUST NOT. Если после отсева по правилам выбранного средства сущностей не хватает для порога, оркестратор MUST NOT публиковать панель, MUST сказать одной строкой, чего не хватает, и MAY продолжить разбор или исследование, чтобы добрать видимые факты. Код модуля, SQL и блок «на что смотреть» MUST оставаться в чате и журнале, а не быть основным содержимым панели. Панель MUST быть статичной: без статусов «сейчас разбираем этот шаг». Главный вид панели MUST NOT быть вертикальным списком, аккордеоном или набором одинаковых карточек **без связей и без вывода**. С узла или строки панели MUST открываться доказательство одним явным действием в панели деталей; выбор MUST показать эффект и MUST NOT сам открывать файл модуля. Запуск нового чата с панели MUST NOT. Аннотации-выводы на полотне MUST NOT входить в счёт порога четырёх публикуемых сущностей механизма.

#### Scenario: Узел без доказательства не публикуется

- **WHEN** для сущности нет строки модуля и нет пути журнала
- **THEN** эта сущность на панель не попадает

#### Scenario: Панель без статусов прохода

- **WHEN** карта сценария уже показана во время или после разбора
- **THEN** на узлах нет подписи вроде «сейчас разбираем»

#### Scenario: Код остаётся в чате

- **WHEN** карта сценария показана
- **THEN** фрагменты модуля и «на что смотреть» остаются в карточке чата и журнале, а не как основное содержимое панели

#### Scenario: Список без связей не публикуется как карта

- **WHEN** собран набор пунктов с эффектом, но нет подписанных связей между ними
- **THEN** панель как карта сценария не публикуется

#### Scenario: Связь без видимого отношения не выдумывается

- **WHEN** пользователь просит карту, а между сущностями нет отношения, видного в отчёте, журнале или порядке уже разобранных шагов, в том числе если в брифе перечислены расхождения отчётов, в том числе если в брифе перечислены расхождения отчётов
- **THEN** ребро не ставится; панель не публикуется за счёт выдуманных стрелок; в чате одна строка — чего не хватает; разбор или исследование можно продолжить

#### Scenario: Строка таблицы не выдумывает правило

- **WHEN** средство — таблица, и утверждение строки «условие → поведение» не видно в переданном отчёте, журнале или коде, даже если у строки есть доказательство существования сущностей
- **THEN** панель не публикуется; в чате одна строка, чего не хватает

### Requirement: Causal map has layers or branches

Карта сценария MUST отвечать на центральный вопрос в шапке, и этот ответ MUST быть восстановим с полотна **когда текст шапки скрыт** (видимое расположение, связи, выбранный узел, строки таблицы, аннотации с доказательством), а не только из текста шапки. Проверка смысла **до записи файла** MUST опираться на поля манифеста (связи, строки, аннотации, стартовый узел) и MUST NOT считать носителем ответа раскладку, которую считает панель после записи. Главный вид MUST отвечать на вопрос шапки без клика выбранным средством из двух реализованных в шаблоне: граф со связями или таблица со смысловыми колонками. Граф — значение по умолчанию, когда содержание топологическое, и когда содержание смешанное (и топология, и правило о условиях). Список, аккордеон и стена одинаковых карточек без связей и без вывода MUST NOT быть главным видом.

Если в наборе есть причинные связи и средство — граф, шапка MUST показать главный причинный вывод. Если в наборе только следование по порядку прохода, шапка MUST назвать вывод из расположения и MUST NOT формулировать причинное утверждение о переходах. Порог публикации считается по **публикуемым сущностям механизма** после отсева по правилам выбранного средства, а не по числу шагов рассказа. Число шагов MUST NOT быть достаточным основанием строить или предлагать карту. Скобки вроде «источник, кэш, преобразование, хранилище, событие сброса, результат» — примеры ролей, MUST NOT быть закрытым списком охвата.

Если средство — граф и на панели есть топологический признак, раскладка MUST показать либо не меньше двух уровней, либо ветвление со схождением. Координаты узлов MUST считать панель. Полосы MUST группировать узлы по полю слоя, а не по рангу раскладки. Если полоса подписана, подпись MUST быть именем слоя узлов в этой полосе и MUST NOT быть рангом раскладки или слоем первого узла ранга. В запасной раскладке для карт длиннее двенадцати узлов полосы MAY оставаться без подписей; это MUST NOT считаться бюджетом разборчивости. Если публикуемых сущностей достаточно, а признака нет (линейная цепочка по прямой просьбе), раскладка MUST быть цепочкой с подписанными связями следования.

Текст полотна MUST читаться в фактической ширине панели. Полотно MUST NOT масштабироваться целиком под ширину: рисуется в натуральных размерах с горизонтальной прокруткой; цепочка длиннее пяти узлов в одном ряду MUST переноситься на следующий ряд. Если выбранное средство бюджет не удерживает, оркестратор MUST сменить средство или сузить вопрос шапки. Провал проверки смысла в круге ремонта MAY сменить средство.

Стартовый узел MUST быть носителем исхода или виновника и MUST NOT быть первым шагом прохода только потому что он первый в списке.

Находка из переданных отчётов, которая меняет действие читателя, MUST попасть на полотно узлом, подписанной связью, строкой таблицы или аннотацией с якорем и доказательством; иначе вопрос шапки MUST быть сужен, а находка явно вне охвата. Отрицательный факт («ожидаемое событие не наступает») MUST быть виден аннотацией с якорем на узел этого события. Аннотаций MUST быть не больше двух. Переключатель видов MUST NOT скрывать рёбра опубликованного набора. На панели MUST быть переключатель, скрывающий текст шапки.

#### Scenario: Слои или ветвление видны на панели

- **WHEN** карта сценария опубликована, средство — граф, и у сущностей есть разные уровни или ветвление
- **THEN** разработчик взглядом отличает уровни или ветки и видит подписанные связи между сущностями; если полоса подписана, подпись совпадает со слоем узлов в этой полосе, а не с рангом раскладки

#### Scenario: Семь линейных шагов не обязаны давать карту

- **WHEN** в разборе семь последовательных шагов без слоёв, ветвлений и повторного использования результата, и пользователь карту не просил
- **THEN** карта не предлагается и не строится только из-за числа шагов

#### Scenario: Направление связей и легенда видны без клика

- **WHEN** карта сценария опубликована, средство — граф, и на ней есть подписанные связи
- **THEN** у каждой связи видно направление; если использованы цвет или пунктир, под графом есть легенда; ничего нажимать не нужно

#### Scenario: Главный вывод виден без клика по узлу

- **WHEN** карта сценария только что открыта штатной кнопкой среды
- **THEN** один узел или одна строка уже выбраны, эффект виден в панели деталей; ответ на вопрос шапки складывается из полотна, а не только из абзаца шапки

#### Scenario: Вывод только в шапке не публикуется

- **WHEN** набор сущностей достаточен, а ответ на вопрос шапки есть только в тексте шапки, не в расположении, связях, строках таблицы и аннотациях с доказательством
- **THEN** панель не публикуется; в чате одна строка, чего не хватает

#### Scenario: Находка, меняющая действие, на полотне

- **WHEN** по теме переданы несколько отчётов и среди расхождений есть находка, из‑за которой читатель сделал бы другой шаг, и на неё есть доказательство
- **THEN** эта находка видна на панели узлом, подписанной связью, строкой таблицы или аннотацией с якорем и доказательством; либо вопрос шапки на панели сужен, и в чате одной строкой сказано, что находка вне охвата

#### Scenario: Ловушка одной подписи видна на полотне

- **WHEN** по теме переданы отчёты, в которых есть отрицательный факт «ожидаемое событие не наступает» (в том числе: смена состава подписей сбрасывает копию, смена макета — нет) и на него есть доказательство
- **THEN** на открытой панели этот факт виден аннотацией, привязанной к узлу события; читатель называет ловушку, не открывая модуль

#### Scenario: Плашка без доказательства не публикуется

- **WHEN** набор сущностей достаточен, а вывод оформлен аннотацией без доказательства, без якоря на узел или ребро, либо аннотация пересказывает текст шапки
- **THEN** панель не публикуется; в чате одна строка, чего не хватает

#### Scenario: Аннотации не добирают порог

- **WHEN** после отсева по правилам выбранного средства публикуемых сущностей механизма меньше четырёх, а в манифесте есть аннотации
- **THEN** панель не публикуется: аннотации в порог не входят; в чате одна строка, чего не хватает

#### Scenario: Переключатель вида не прячет рёбра

- **WHEN** на панели средство — граф, есть переключатель вида, и читатель его меняет
- **THEN** набор узлов и связей тот же; изменилась раскладка, а не состав рёбер; стены одинаковых карточек нет

#### Scenario: Ответ читается при скрытой шапке

- **WHEN** карта сценария опубликована и читатель скрывает текст шапки переключателем панели
- **THEN** читатель называет ответ на вопрос шапки по полотну; если без шапки ответ не читается, панель не должна была публиковаться

#### Scenario: Текст полотна читается в ширине панели

- **WHEN** карта сценария открыта штатной кнопкой среды в обычной ширине панели рядом с чатом
- **THEN** имена сущностей читаются без масштабирования всего полотна; если имена не читаются, панель не публикуется

#### Scenario: Стартово выбран носитель исхода

- **WHEN** карта сценария только что открыта штатной кнопкой среды
- **THEN** выбран узел или строка — носитель исхода или виновника, а не первый шаг прохода и не узел гигиены только потому что он первый в списке

#### Scenario: Таблица со смысловыми колонками отвечает на вопрос

- **WHEN** содержание карты — правило о условиях, а не топология, и опубликована таблица со смысловыми колонками
- **THEN** при скрытой шапке читатель называет правило по колонкам; граф из шагов в ряд не обязателен; стены одинаковых карточек нет

### Requirement: Offer by topology not by topic

Оркестратор MUST предлагать карту сценария только если можно назвать конкретный вывод, которого нет в списке, и есть хотя бы один топологический признак (слои, где один питает другой; ветвление со схождением; жизненный цикл состояний; причинная петля или повторное использование устаревшего результата; одно порождает несколько представлений; разные технические пути). На выходе разбора, в «Дальше» исследования и после записи описания ЗНИ предложение MUST требовать не меньше четырёх публикуемых сущностей после обоих отсевов. На строке подтверждения списка точек разбора предложение MAY печататься по предсказанной топологии списка (или отчёта, из которого список собран), **без** требования ≥4 публикуемых сущностей уже сейчас; публикация панели на этом шаге MUST NOT происходить — действует отложенная постройка. Предложение MUST формулироваться через сущности и вывод, а не общим вопросом «хотите карту?». Предикаты предложения MUST NOT ссылаться на предметную область, тип объекта метаданных или конкретный механизм. Замеры времени MUST NOT быть условием предложения; время MAY быть признаком только вида «временная шкала». После описания ЗНИ признак MUST определяться по форме связей **в том же одном отчёте**, который при согласии уйдёт в сборщика, MUST NOT по объединению файлов, MUST NOT по теме ЗНИ и MUST NOT по числу этапов поставки.

Отказ предложения в исследовании, на выходе разбора и после описания ЗНИ MUST NOT печататься в чат. Если пользователь отказался («без карты»), повторно предлагать до выхода сессии MUST NOT.

#### Scenario: Исследование предлагает схему при топологии без замеров

- **WHEN** отчёт исследования содержит не меньше четырёх связанных сущностей с топологическим признаком и замеров времени нет
- **THEN** в «Дальше» ровно одно действие — показать схему, с фразой, что станет видно; пошаговый разбор в том же сообщении не предлагается

#### Scenario: Разбор предлагает схему на подтверждении списка без порога публикации

- **WHEN** на строке подтверждения списка точек разбор видит предсказанную топологию списка или отчёта, из которого список собран, замеров времени нет, и есть эта строка решения
- **THEN** в этой строке есть вариант «сразу карту» с фразой, что станет видно; порог «уже четыре публикуемые сущности» не требуется; панель на этом шаге не публикуется; слов про замеры времени как условие нет

#### Scenario: Разбор предлагает схему на выходе без замеров времени

- **WHEN** на выходе разбора есть строка «Следующий шаг», после обоих отсевов не меньше четырёх публикуемых сущностей, есть топологический признак, замеров времени нет
- **THEN** в этой строке есть вариант получить схему; слов про замеры времени как условие нет

#### Scenario: На линейных двух шагах схему не предлагают

- **WHEN** разбор проходит два линейных шага без слоёв, ветвлений и состояний
- **THEN** предложения схемы нет; в чате нет строки, почему схему не предложили

#### Scenario: Предложение не зависит от темы механизма

- **WHEN** топология есть у механизма любой предметной области
- **THEN** правило предложения то же, что у любого другого механизма; отдельного условия «если это такая-то тема» нет

#### Scenario: Описание предлагает схему при топологии в отчётах

- **WHEN** после записи описания ЗНИ в каталоге этой ЗНИ есть отчёт разбора, **на этом одном отчёте** после обоих отсевов не меньше четырёх связанных сущностей, есть топологический признак формы связей и можно назвать вывод, которого нет в списке этапов
- **THEN** в уже существующей строке следующего шага есть вариант схемы с фразой, что станет видно; панель на этом шаге не создаётся; в чате нет строки, почему схему предложили

#### Scenario: Описание без отчётов схему не предлагает

- **WHEN** вызывается описание ЗНИ, где есть только постановка и решения, без отчётов разбора со связями
- **THEN** строка следующего шага напечатана, варианта схемы в ней нет; строки о причине отсутствия предложения нет

#### Scenario: Плоский набор без формы связей в описании не даёт намёка

- **WHEN** после описания ЗНИ отчёты дают не меньше четырёх доказанных связанных сущностей, но нет слоёв, ветвления, жизненного цикла и петли
- **THEN** варианта схемы в строке следующего шага нет; строки о причине нет

#### Scenario: Отказ без карты в описании не повторяется

- **WHEN** после описания ЗНИ пользователь отвечает «без карты», затем в той же сессии описание вызывается снова
- **THEN** варианта схемы до конца сессии нет; строка следующего шага остаётся

### Requirement: No dedicated map command

В наборе команд `/opsx:*` MUST NOT появляться отдельная команда карты. Вызов идёт из исследования или из разбора по прямой просьбе, по принятому предложению или по намёку на выходе, без смены команды сессии.

#### Scenario: Нет отдельной команды карты

- **WHEN** разработчик смотрит список команд кита
- **THEN** отдельной команды «нарисовать карту» нет; разбор и исследование не нужно прерывать, чтобы получить панель

### Requirement: Two map names stay distinct

В чате и в словаре кита MUST различаться карта точек (список имён эффектов в сообщении до прохода), карта сценария (панель со связями или таблицей колонок) и текстовый резерв (запись в журнале, когда панели нет). Классы точек разбора MUST NOT выводиться на панель.

#### Scenario: Карта точек и карта сценария различимы

- **WHEN** после подтверждения брифа разбора показывается список шагов в чате
- **THEN** это карта точек (имена), а не панель карты сценария

#### Scenario: Эталоны показывают средство, отвечающее на вопрос

- **WHEN** автор кита открывает скилл карты сценария
- **THEN** в нём есть эталон, который отвечает на вопрос шапки (граф или таблица), эталон списка без связей (так не публиковать) и эталон «полотно есть — смысла нет» (граф с выводом только в шапке — так тоже не публиковать)

### Requirement: Hint only on an existing decision line

Намёк или предложение показать карту сценария MUST быть вариантом в уже существующей строке решения: «Дальше» исследования, подтверждение списка точек разбора, «Следующий шаг» на выходе разбора или строка следующего шага чата описания ЗНИ — а не отдельным вопросом и не второй командой. Строка следующего шага чата описания MUST печататься всегда, включая прогоны, где карта не рассматривалась. Намёк MUST печататься только если пройдены условия предложения по топологии **и** в этом сообщении уже есть эта строка. Если на выходе разбора задан вопрос про доп. анализ, строки «Следующий шаг» нет — намёка нет. Если в исследовании проверка топологии не пройдена, а есть цепочка точек, «Дальше» MAY предложить пошаговый разбор. Если печатается блок постановки ЗНИ и строки «Дальше» нет — предложения схемы нет как следствие. Строка «Следующий шаг» в том же финале (команда создать ЗНИ) MUST NOT быть слотом предложения карты.

#### Scenario: Намёк на выходе разбора при топологии

- **WHEN** разбор закончен, проверка топологии пройдена, кандидатов анализа нет (есть строка «Следующий шаг»)
- **THEN** в той же строке «Следующий шаг» есть вариант попросить карту сценария

#### Scenario: Нет намёка, если уже вопрос анализа

- **WHEN** на выходе разбора задан вопрос, нужен ли доп. анализ
- **THEN** намёк про карту сценария не печатается

#### Scenario: Исследование не предлагает карту и разбор сразу

- **WHEN** исследование формирует «Дальше»
- **THEN** в сообщении ровно одно действие: либо схема, либо пошаговый разбор, либо иное одно действие по правилам исследования

#### Scenario: Нет предложения в финале исследования с постановкой

- **WHEN** исследование печатает блок постановки ЗНИ, и строки «Дальше» в этом сообщении нет
- **THEN** предложения схемы нет; отдельного вопроса про карту нет; строка «Следующий шаг» с командой создать ЗНИ вариантом карты не становится

### Requirement: Map outside walkthrough uses named source

Вне сессии разбора карта MUST строиться только из существующего журнала разбора или из отчёта, который пользователь указал. Иначе оркестратор MUST отказать одной строкой и MUST NOT собирать карту из произвольного контекста чата. Исключения, на которые отказ «укажите отчёт» MUST NOT применяться: (1) принятое конкретное предложение карты — источник тот, на котором прошла проверка топологии; (2) прямая просьба в активной сессии исследования, пока есть текущий отчёт исследования — источник этот отчёт; (3) прямая просьба в активной сессии описания ЗНИ, пока инвентарь отчётов этой сессии уже собран — источник один отчёт, выбранный из этого инвентаря правилом предпочтения (журнал прохода, затем разбор, затем архитектурный отчёт по теме). Постановка, список задач и файл описания ЗНИ MUST NOT быть источником узлов. Этапы поставки MUST NOT публиковаться как цепочка узлов карты.

#### Scenario: Вне разбора без источника — отказ

- **WHEN** пользователь просит карту сценария вне разбора, журнала нет, сессии исследования нет, сессии описания с собранным инвентарём нет и отчёт не указан
- **THEN** панели нет, в чате одна строка, что карта строится из журнала или указанного отчёта

#### Scenario: Просьба в исследовании берёт текущий отчёт

- **WHEN** идёт сессия исследования, есть текущий отчёт, пользователь просит карту сценария и путь к файлу не называл
- **THEN** карта строится из этого отчёта; отказа «укажите отчёт» нет

#### Scenario: Прямая просьба в описании берёт инвентарь отчётов

- **WHEN** после описания ЗНИ пользователь просит показать карту сценария, путь к отчёту не называет, и инвентарь отчётов этой сессии уже собран
- **THEN** панель строится из отчёта, выбранного из этого инвентаря правилом предпочтения; отказа «укажите отчёт» нет

#### Scenario: Этапы поставки не становятся картой

- **WHEN** карта строится по согласию или прямой просьбе после описания ЗНИ
- **THEN** ни один узел не повторяет этап поставки из файла описания; связи взяты из отчётов разбора
