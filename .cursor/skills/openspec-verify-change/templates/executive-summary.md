# Шаблон `## Executive Summary` — пятислойный отчёт verify

Структура секции `## Executive Summary` в файле `reports/verification-YYYY-MM-DD.md`. Первый абзац обязателен — это бинарный вердикт пользовательскими словами. Дальше — статусы пяти слоёв и при необходимости открытые темы.

```markdown
## Executive Summary

<Готово к apply | На обсуждение>: <одна-две фразы сути для разработчика — что это значит для запуска `/opsx:apply` сейчас. Без жаргона движка (`PASS`, `verdict: GO`, имена слоёв в стиле «Layer 4»). Лексика — `verify-user-communication.mdc`.>

### Слои проверки

- **Гигиена артефактов:** <PASS / автоправки применены / FAIL — одна строка>
- **Внутренняя согласованность плана:** <PASS / есть пометки / FAIL — одна строка>
- **План решает озвученную проблему:** <PASS / расхождения / FAIL — одна строка>
- **Независимый аудит постановки:** <APPROVE / CHALLENGE / REJECT / пропущен — одна строка с одной фразой обоснования>
- **Реализуемость задач:** <PASS / есть пометки / FAIL — одна строка>

### Что в работе (опционально)

- <2–5 буллетов: активные срезы, ожидающие приёмки `S<N>.accept`, известные owner-задачи в постановке>

### Открытые темы (только при NO-GO)

- <одна строка на каждое содержательное сомнение, в формулировке для пользователя 1С — не имена алертов>
- <предлагаемый следующий шаг: `/opsx:explore <тема>` / `/opsx:extend <name> --from-verify <отчёт>` / уточнение через обсуждение>
```

## Правила оформления

### Первый абзац

- Только два варианта зачина: «Готово к apply» либо «На обсуждение». Полная формулировка — `templates/verdict-card.md`.
- Не дублировать в первом абзаце статусы слоёв и счётчики severity — для этого блок «Слои проверки».
- Без путей файлов в первом абзаце; путь к отчёту даётся в чате последней строкой.

### Блок «Слои проверки»

- **Всегда** все пять буллетов в указанном порядке. Если слой не выполнялся (например, Layer 4 пропущен по новизне) — буллет остаётся, формулировка вида «независимый аудит — не запускался, постановка не менялась с прошлого challenge от <дата>».
- Имена слоёв в чате/отчёте — пользовательские формулировки слева от двоеточия (см. шаблон выше). Технические имена (`Layer N`, `design-challenge`, `task-readiness`) — только в YAML или в строке «Источники» внутри файла.

### Блок «Что в работе»

- Опциональный. Включать, если есть `[ ]` задачи или ожидающая приёмка `S<N>.accept`.
- Не повторять полный список задач — только уровень среза/контекста.

### Блок «Открытые темы»

- Появляется **только** при `verdict: NO-GO`.
- Не дублирует развёрнутые карточки развилок ниже по отчёту — это краткий обзор для быстрой ориентации.
- Каждая строка — суть на пользовательском языке + рекомендуемый следующий шаг.

## Анти-примеры

Не писать в Executive Summary:

- «PASS / FAIL / verdict: GO» (это в YAML).
- «Layer 4: APPROVE» (это в YAML `layer_status`).
- «Phase A complete» / «Slice Coherence OK» (внутренние термины).
- Полное тело развилок (для них — отдельные блоки `card-decision.md` ниже в отчёте).
