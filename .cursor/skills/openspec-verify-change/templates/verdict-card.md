# Шаблон первой строки `/opsx:verify` — формулировки вердикта

Используется **первой строкой** ответа пользователю в чате и **первой строкой** секции «Резюме для разработчика» в файле отчёта `reports/verification-YYYY-MM-DD.md`.

Главный вопрос разработчика: «**могу ли я безопасно запустить `/opsx:apply`?**». Ответ — одна из двух формулировок. Бинарный смысл сохраняется, но в чате имена `GO` / `NO-GO` / `verdict` **не используются** — это внутренний код движка, остаётся в YAML отчёта.

---

## Вариант 1 — можно запускать apply

Все проверки пройдены, содержательных развилок нет. Допускаются авто-правки гигиены и информационные пометки, не влияющие на запуск.

```
<change-name> — можно запускать apply.
```

Опционально + одна техническая фраза «что важно знать», если есть нюанс на языке кода 1С:

```
<change-name> — можно запускать apply. <Одна техническая фраза: например «правка локализована в одной экспортной функции `cf` модуля `<имя>`».>
```

Запреты для варианта 1:

- Не использовать «PASS», «verdict: GO», «slice-pre», «pre-apply», «layer status» — внутренние коды движка остаются в YAML.
- Не указывать счётчики «N CRITICAL / M WARNING» в строке вердикта.
- Не использовать штампы «Готово к apply», «Готово», «OK», «зелёный свет» — формулировка одна, конкретная.

---

## Вариант 2 — до apply нужно решение

Есть содержательная развилка: расхождение плана с озвученной проблемой, возражение архитектора-адверсария, нереализуемая задача.

```
<change-name> — до apply нужно решение: <одна техническая фраза сути на языке 1С>.
```

«Одна техническая фраза» — суть на языке кода, а не имя слоя/шага. Опорные приёмы для формулировки:

- Назвать **место в коде** (общий модуль, экспортная функция, директива расширения, объект метаданных).
- Назвать **тип решения** (выбрать точку перехвата / зафиксировать поведение / добавить задачу в срез / принять регресс).

Примеры:

- «<change-name> — до apply нужно решение: выбрать точку перехвата `ПолучитьШаблоны` — объектный модуль обработки или модуль формы.»
- «<change-name> — до apply нужно решение: сохранить ли автоподстановку в `pav_ПриСозданииНаСервереПосле` при единственном комплексном шаблоне после слияния списков.»
- «<change-name> — до apply нужно решение: задача S2.1 «обновить ТЧ Визы» не указывает конкретную процедуру и реквизит — реализатор будет угадывать.»

Запреты для варианта 2:

- Не использовать «REJECT», «CHALLENGE», «верный путь», «нужен пересмотр», «На обсуждение» — это лексика движка / штампы.
- Не использовать «возможно стоит», «может быть имеет смысл» — формулировка от лица архитектора, прямо и технически.
- Не дублировать в первой строке весь блок «Решения до apply» — он идёт ниже в `templates/chat-summary.md`.

---

## Связь с дальнейшим сообщением

После строки вердикта — короткие блоки по `templates/chat-summary.md`:

- **Вариант 1 (можно apply) + авто-правки** → одна строка «Подправил в постановке: <что>» и одна строка пути к отчёту.
- **Вариант 1 без авто-правок** → одна-две строки резюме (что делает план в коде) и одна строка пути к отчёту.
- **Вариант 2 (нужно решение)** → 2–4 предложения резюме «архитектор — разработчику», секция «Решения до apply» с пронумерованными развилками прозой, одна строка пути к отчёту.

В файле отчёта (`reports/verification-YYYY-MM-DD.md`) первая строка секции `## Резюме для разработчика` повторяет одну из двух формулировок выше.

---

## Анти-пример

Не использовать в чате:

- «ЗНИ: name — Готово к apply.» / «На обсуждение.» — старые штампы.
- «verdict: GO» / «verdict: NO-GO» — внутренний код движка.
- «Layer 4: CHALLENGE» — имя слоя.
- «Готово к apply с замечаниями» — размытая формулировка, не бинарная.
