# `/opsx:publish` — публикация поставки kit

Обновить ветку поставки (`main`) содержимым `.cursor/` + `AGENTS.md` из ветки разработки. Ветки не сливаются, история не переписывается.

**Не делает:** правки `.bsl` и XML, создание ЗНИ, публикацию из проекта 1С, `push --force`, публикацию без подтверждения пользователя.

SSOT состава и запретов — спека `kit-distribution` (`openspec/specs/kit-distribution/spec.md`; существует только в репозитории kit). Канон веток — `.cursor/docs/kit-template-workflow.md`.

---

## Шаг 1 — Kit-only guard (HALT)

Молча проверить (Glob/Read, без git-команд):

| Условие | Требование |
|---------|-----------|
| `.cursor/docs/kit-template-workflow.md` | существует |
| `tools/publish-dist.ps1` | существует |
| `openspec/project.md` | **отсутствует** |
| `src/*/cf/Configuration.xml` | **отсутствует** |

Любое нарушение — **стоп**, одна строка в чат: «Это не репозиторий kit — публикация поставки здесь не выполняется.» Ничего не запускать.

## Шаг 2 — Состояние репозитория

```bash
git status --porcelain
git rev-parse --abbrev-ref HEAD
```

- Дерево не чистое → стоп: «Есть незакоммиченные правки — публикую только чистое дерево.» Список файлов в чат не выводить.
- Текущая ветка не `develop` → одна строка предупреждения с именем ветки и вопрос, публиковать ли с неё. Ждать ответа.

## Шаг 3 — Состав поставки (dry-run)

```bash
pwsh -File tools/publish-dist.ps1 -DryRun
```

Если `pwsh`/`powershell` недоступен — `bash tools/publish-dist.sh --dry-run` (тот же алгоритм).

В чат — компактно: количество файлов `.cursor/**`, наличие `AGENTS.md` и витринного `README.md`, исходный коммит. Полный список файлов в чат не выводить.

## Шаг 4 — Подтверждение

Одна строка: что будет обновлено (`origin/main`), с какого коммита, и просьба подтвердить словом. Без подтверждения — **стоп**. Ключ `--dry-run` в вызове пользователя означает «остановиться здесь».

## Шаг 5 — Публикация

```bash
pwsh -File tools/publish-dist.ps1
```

Скрипт: fetch → рабочее дерево на `main` → замена файлов по манифесту → commit с исходным коммитом `develop` в сообщении → `push origin main`. Без `--force`.

При `--tag vX.Y.Z` — после успешного push:

```bash
git tag vX.Y.Z origin/main
git push origin vX.Y.Z
```

## Шаг 6 — Проверка после публикации

```bash
git ls-tree --name-only origin/main
```

Ожидается ровно `.cursor`, `AGENTS.md`, `README.md`. Любой лишний путь — сообщить как дефект публикации и предложить откат: `git revert` коммита поставки на `main`.

## Шаг 7 — Чат

Формат — лимит «финал готово» (`.cursor/rules/chat-output-budget.mdc`): одна строка результата + одна строка следующего шага для проектов.

```markdown
Поставка обновлена: `origin/main` ← `<sha7 develop>` (<N> файлов `.cursor`).

**Следующий шаг:** в проектах — `git submodule update --remote vendor/kit-van` и `tools\sync-kit.cmd`.
```

При `--dry-run` — состав и строка «изменений в удалённом репозитории нет».

## Guardrails

- Kit-only guard — до любых git-команд.
- `push` только после подтверждения пользователя в этом ходе.
- Никогда `push --force`, никогда `git merge develop` в `main`.
- Не публиковать при незакоммиченных правках.
- Ветка `main` в чате называется «ветка поставки»; внутренние коды и списки файлов — в файле/выводе скрипта, не в чате.
