# openspec-docs

Генерация проектных документов на основе спецификаций OpenSpec.

## Принцип

Документы генерируются без додумывания: если информации нет в источниках — она не попадает в документ. Источники зависят от типа документа: для технического проекта — `openspec/specs/`, `project.md`, `architecture-extension.md`; для ТЗ по ЗНИ (change-tz) — артефакты конкретного change в `openspec/changes/<name>/`.

ТЗ по ЗНИ — документ для **согласования с заказчиком**, не для разработки. Для разработки используются артефакты напрямую (design.md, specs, tasks.md). ТЗ содержит паспорт задачи и функциональные требования. Реализационные детали (код, API, аннотации расширений, развёртывание, откат, архитектура) — уровень design.md, не ТЗ.

Генерация ТЗ управляется параметром `generate_tz: auto | no | deferred` в блоке `## Metadata` файла `proposal.md`. Команда `/opsx:verify` читает этот параметр для авто-генерации. Команда `/opsx:doc-tz` игнорирует параметр и генерирует ТЗ по явному запросу.

**Output style:** сопроводительная сводка для пользователя (что сгенерировано, где лежит, замечания к артефактам) выводится по шаблону **T-REPORT** из `.cursor/docs/opsx-output-style.md` §5.3 (Summary → Замечания к артефактам по Severity → Action items → ссылки). Сам генерируемый документ (ТЗ / технический проект) подчиняется правилам §1 «Три слоя» и §3 «Запрет внутренних ID в пользовательских полях» — формулировки для заказчика должны быть в UX-слое, без `S<N>.T<M>/D<N>/R<N>`. Перед выводом сводки — self-check-5 (§7 стайл-гайда).

## Поддерживаемые типы документов

| Тип | Команда | Промпт | Аудитория |
|-----|---------|--------|-----------|
| **ТЗ по ЗНИ** | `/opsx:doc-tz <name>` | `prompts/change-tz.md` | Заказчик (согласование) |

## Алгоритм

### Для типа change-tz (ТЗ по одному ЗНИ)

1. **Определить тип документа** `change-tz` и **имя change** из запроса пользователя (например `pav-exclusion-two-level-settings`). Имя — имя каталога в `openspec/changes/`. Если имя не указано — запросить у пользователя.

2. **Проверить наличие change:** каталог `openspec/changes/<name>/` должен существовать и содержать как минимум `proposal.md` и `design.md`.

3. **Прочитать артефакты change в порядке:**
   - `openspec/changes/<name>/proposal.md`
   - `openspec/changes/<name>/design.md`
   - все `openspec/changes/<name>/specs/*/spec.md`
   - при наличии: один актуальный `openspec/changes/<name>/reports/architecture-*.md` (по дате в имени выбрать последний)
   - при наличии: один актуальный `openspec/changes/<name>/reports/exploration-*.md`
   - при необходимости контекста: `openspec/project.md`

4. **Прочитать промпт** `prompts/change-tz.md`.

> Перед вызовом Task в шагах 5–6 — **Task Pre-call Checklist** из `.cursor/rules/tool-name-guard.mdc` (subagent_type из списка; `model` не передавать).

5. **Генерация ТЗ (субагент).** Делегировать генерацию документа субагенту через `Task(subagent_type="openspec-doc-writer")`. Передать в промпт субагента содержимое `prompts/change-tz.md` и тексты всех собранных артефактов. Попросить субагента выступить в роли технического писателя и вернуть готовый текст ТЗ. Промпт включает секцию «Верификация артефактов» — субагент должен выполнить проверку и вывести замечания к артефактам после текста ТЗ.

6. **Архитектурное ревью ТЗ (субагент).** Делегировать ревью субагенту через `Task(subagent_type="onec-code-architect")` с шаблоном «Architect — ТЗ quality review» из `.cursor/skills/1c-agent-patterns/architect.md`.

   **Важно:** ревью выполняется субагентом, не оркестратором. Оркестратор передаёт все данные в промпт Task и получает структурированный ответ.

   **Входные данные (передать в prompt субагента):**
   - Текст сгенерированного ТЗ (полностью)
   - Все исходные артефакты: proposal.md, design.md, specs/\*/spec.md (полный текст каждого)
   - Замечания из самопроверки промпта (если были)
   - При наличии: reports/architecture-\*.md (полный текст)

   **Обработка результатов субагента:**
   - **Замечания к ТЗ** (document-level) → применить исправления к тексту ТЗ.
   - **Замечания к артефактам ЗНИ** (artifact-level) → объединить с замечаниями из самопроверки промпта в единый блок.
   - Сохранить полный отчёт ревью в `openspec/changes/<name>/reports/tz-review-YYYY-MM-DD.md` (см. `preserve-subagent-reports.mdc`).

6b. **Пополнение словаря лексики.**
    Если архитектор в замечаниях к ТЗ (document-level) указал нарушения лексики (англицизмы, жаргон, несуществующие слова, **терминология 1С**):
    1. Для каждого замечания проверить: есть ли уже запись в `.cursor/docs/tz-lexicon-dictionary.md` — в таблице «Словарь» (колонка «Запрещено») **или** в секции «Терминология объектов метаданных 1С» (колонка «Некорректно / разговорно»).
    2. Если записи НЕТ — предложить пользователю: «Архитектор обнаружил "\<термин\>" (→ "\<замена\>"). Добавить в словарь лексики ТЗ?»
    3. По подтверждению — добавить строку: англицизмы/жаргон — в таблицу «Словарь»; пары терминов 1С — в «Терминология объектов метаданных 1С». При необходимости расширить **контекстный** Grep-паттерн (секция «Grep-паттерны»); не добавлять в паттерн голые слова, если это даёт ложные срабатывания.
    4. Если пользователь отклонил — не добавлять, продолжить.

7. **Показать результат пользователю:**
   - Финальный текст ТЗ (с учётом исправлений по ревью).
   - Если есть замечания к артефактам — бриф замечаний после текста ТЗ (формат — в промпте `change-tz.md`, секция «Формат замечаний»).
   - Спросить, нужны ли корректировки или запись в другой путь.

8. **Записать** после подтверждения в `openspec/changes/<name>/ТЗ.md` (по умолчанию). По запросу пользователя — в другой путь.

### Для типа technical (технический проект)

1. **Определить тип документа** из запроса пользователя.

2. **Прочитать контекст проекта:**
   ```
   openspec/project.md
   openspec/architecture-extension.md
   ```

3. **Прочитать все спецификации:**
   ```
   openspec/specs/*/spec.md
   ```
   Если у спека нет секции Purpose — определять уместность по Requirements и сценариям.

4. **Определить slug** (см. раздел ниже) и **прочитать промпт** из `prompts/technical.md`.

5. **Применить промпт** к собранным данным — сгенерировать документ.

6. **Показать результат** пользователю и спросить, нужны ли корректировки.

7. **Записать** в `docs/<slug>/Технический проект.md` после подтверждения.

## Определение slug

Slug — имя подкаталога в `docs/`, в который складываются документы по одному решению. Формируется из имени продукта в `openspec/project.md` (секция «Продукт» или «Назначение»): привести к kebab-case, латиница. Пример: «ргОблачныеПодписиKonturCryptoAPI» → `oblachnye-podpisi-kontur-cryptoapi` или кратко `kontur-cryptoapi`. При нескольких решениях в проекте — отдельный подкаталог на каждое.
