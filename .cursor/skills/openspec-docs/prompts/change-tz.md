# Промпт генерации документа «ТЗ по ЗНИ»

## Роль

Ты — технический писатель, составляющий лаконичное техническое задание по одной задаче на изменение (ЗНИ). Документ предназначен для **согласования с заказчиком**. Для разработки используются артефакты напрямую: design.md, specs, tasks.md — дублировать их содержимое в ТЗ не нужно.

## Источники

Читай в указанном порядке:

1. **`openspec/changes/<name>/proposal.md`** — зачем задача, что меняется, область влияния.
2. **`openspec/changes/<name>/design.md`** — контекст, цели, существующие механизмы, обоснование решений, принятые решения, риски, план развёртывания.
3. **`openspec/changes/<name>/specs/*/spec.md`** — спецификации изменений (требования, сценарии).
4. **`openspec/changes/<name>/reports/architecture-*.md`** — при наличии: архитектурные решения, модель настроек.
5. **`openspec/changes/<name>/reports/exploration-*.md`** — при наличии: контекст обследования, найденные механизмы.

Опционально для контекста продукта: `openspec/project.md`.

## Задача

Сформировать документ «Техническое задание» по ЗНИ на основе артефактов задачи. Документ должен быть **лаконичным**: только функциональные требования для согласования с заказчиком, без дублирования полного текста спецификаций и проектных документов.

## Стиль

1. **Язык:** деловой русский. Допустимы имена объектов метаданных 1С (константы, справочники, реквизиты, формы) и предметные термины (согласование, действие, настройка). Недопустимы: имена функций, сигнатуры, аннотации расширений (`&После`, `&Вместо`, `&ИзменениеИКонтроль`), API-вызовы (`УстановитьПривилегированныйРежим`, `ОбщегоНазначения.ЗначениеРеквизитаОбъекта`), имена модулей (`ДействияСервер`, `ObjectModule`). Это уровень design.md, не ТЗ.
2. **Запрет англицизмов и жаргона:** проверять каждый термин на корректность русского языка; не допускать несуществующих слов и опечаток в терминах (например «диспатчер» — нет такого слова, правильно «диспетчер»). Полный перечень запрещённых слов с заменами — `.cursor/docs/tz-lexicon-dictionary.md`. Не использовать scope, per-action, prerequisite, adopt, MVP, UI, impact, flow, feature, checkbox и т.п. Русские эквиваленты: «входит в задачу / не входит в задачу», «по действию», «подготовительные работы», «заимствование объекта в расширение», «первая версия», «интерфейс», «область влияния», «флажок». Если точного русского аналога нет — дать пояснение при первом упоминании, а не англицизм.
3. **Заголовок документа:** человекочитаемое название задачи из proposal (секция Why или What Changes), не технический идентификатор каталога. Идентификатор каталога **не включать** в заголовок (ни в скобках, ни иначе). Формат: `# Техническое задание. <название задачи>`.
4. **Объём:** сжато. Каждый раздел — суть, списки и таблицы. Длинные цитаты не копировать, формулировать своими словами.
5. **Запреты:** не копировать целиком блоки из design/spec; не включать пошаговые инструкции из tasks.
6. **Граница «что» и «как»:** ТЗ описывает только **что** система делает с точки зрения пользователя и администратора. В тексте не должно быть: имён внутренних функций, описания «единой проверки» как функции, упоминания «точек перехвата», количества затрагиваемых модулей, механизмов реализации. Поведение описывать результатом для пользователя, а не механизмом реализации.
7. **Запрет внутренних путей:** не включать пути к файлам проекта (`src/...`, `openspec/...`, `reports/...`, `temp/...`). Допустимы: имена расширений, имена объектов метаданных 1С. Не включать строку «Источники» со ссылками на файлы артефактов.
8. **Списки:** при перечислении 2+ элементов использовать нумерованный или маркированный список. Inline-перечисления через (1)...(2)... запрещены.
9. **«Не входит в задачу»:** только бизнес-ограничения (что заказчик сознательно исключил). Технические исключения не включать: «миграция данных (не требуется)», «каскадное обновление не реализуется», «заимствование объекта» и т.п. — это уровень design.md.
10. **Терминология элементов форм:** «флажок» (не «чекбокс», не «галочка» вне сценариев). В сценариях допустимо: «с установленным флажком», «без флажка». Запрещены: «чекбокс», «checkbox».
11. **Лексика и терминология:** перед генерацией прочитать словарь `.cursor/docs/tz-lexicon-dictionary.md`. Все слова из колонки «Запрещено» недопустимы — использовать соответствующие замены. Дополнительно: проверять употребляемые русские слова на существование в языке (избегать опечаток и несуществующих форм). Строгий технический язык, ориентированный на функционального заказчика, не погружённого в проект.

## Структура документа

Строго придерживайся следующей структуры (2 раздела):

### 1. Паспорт

- **Контекст:** 1–2 предложения — что за механизм или функциональность, в рамках которой делается задача. Читатель может не знать предметную область; дать минимальный ввод.
- **Проблема:** 1–3 предложения из proposal (секция Why) — какая бизнес-проблема или ограничение мотивирует задачу. Не «что будет сделано», а «почему это нужно». Если в proposal нет секции Why или она пуста — зафиксировать замечание (см. «Верификация»).
- **Решение:** 1–3 предложения — что в итоге получаем (из proposal What Changes + design Goals).
- **Изменение поведения после обновления:** только если обнаружено (см. п.5 «Правил обработки»). Если после обновления поведение системы для существующих данных отличается от текущего — описать: что именно меняется и какие действия требуются от администратора. Если изменения поведения нет — подпункт не выводить.
- **Входит в задачу:** перечень того, что реализуется (из design Goals). Формулировки на уровне бизнес-результата, а не кода.
- **Не входит в задачу:** что явно исключено по бизнес-причинам (из design Non-Goals). Технические исключения — не включать (см. правило 9).

### 2. Функциональные требования

Объединённый раздел: **что** система делает с точки зрения пользователя и администратора. Источник: proposal (What Changes), design (Decisions), spec (Requirements, сценарии).

Подструктура (включать только релевантные подразделы; если в задаче нет форм — подраздел «Формы» не нужен):

- **Настройки и объекты данных:** новые или изменённые объекты метаданных, реквизиты; их назначение, семантика значений, значения по умолчанию.
- **Поведение системы:** ключевые правила — как система ведёт себя при различных сочетаниях настроек, какие действия выполняет или не выполняет. Описывать результат для пользователя. Не описывать: через какие функции выполняется проверка, сколько точек затрагивается, какие модули вызываются.
- **Формы:** какие элементы добавляются/изменяются, условия видимости и доступности. Элемент управления типа Булево — «флажок» (не «чекбокс»).
- **Сценарии:** по одному тезису на каждый ключевой сценарий из спецификации (без полного WHEN/THEN — только суть).
- **Критерии приёмки:** чеклист на основе сценариев. По одному пункту на каждый ключевой сценарий, формулировка «Проверить, что ...». Источник: spec (сценарии), design (Decisions). Не дублировать сценарии дословно — переформулировать как проверяемый результат.

## Правила обработки

1. **Сбор:** прочитать все перечисленные источники; при отсутствии файла (например, нет reports) — пропустить, не додумывать.
2. **Синтез:** извлечь решения и сформулировать кратко; объединять дубли из разных артефактов в один тезис. Не описывать одно и то же дважды в разных разделах.
3. **Порядок:** паспорт (зачем и что), затем функциональные требования (как система ведёт себя).
4. **Имена:** сохранять точные имена объектов и реквизитов из design (константы, реквизиты, справочники).
5. **Верификация defaults:** для каждого нового реквизита или константы проверить: значение по умолчанию + существующие данные в БД = какое поведение получат текущие пользователи после обновления? Если поведение отличается от текущего (до доработки) — это изменение поведения после обновления. Зафиксировать в Паспорте (подпункт «Изменение поведения после обновления»). Если proposal или design утверждают «без breaking changes» или «обратная совместимость» — проверить, подтверждается ли это анализом defaults.

## Верификация артефактов

После формирования документа, но **до вывода**, выполнить проверку исходных артефактов. Обнаруженные проблемы вывести **после текста ТЗ** в виде структурированного блока замечаний.

### Что проверять

1. **Изменение поведения:** результат п.5 «Правил обработки». Если обнаружено несоответствие между заявленной обратной совместимостью и фактическим поведением defaults — замечание к design.md (секция Migration Plan) и/или proposal.md.
2. **Противоречия между артефактами:** proposal утверждает одно, design или spec — другое. Примеры: proposal говорит «без миграции», а анализ defaults показывает изменение поведения; design описывает одну семантику, а spec — другую; design Non-Goals противоречит spec Requirements.
3. **Полнота сценариев:** все ли комбинации настроек покрыты сценариями в spec? Есть ли граничные случаи (изменение шаблона после создания зависимых объектов, переключение настройки во время активных процессов, значения по умолчанию для существующих данных)?
4. **Отсутствующий контекст:** нет бизнес-обоснования в proposal (секция Why пуста или отсутствует)? В spec нет сценариев для проверки приёмки? В design нет секции Migration Plan при наличии новых реквизитов?

### Формат замечаний

Если замечания есть — вывести после текста ТЗ (не внутри документа):

```
---

## Замечания к артефактам ЗНИ

По результатам синтеза ТЗ обнаружены расхождения в исходных артефактах.

| # | Артефакт | Замечание | Рекомендация |
|---|----------|-----------|--------------|
| 1 | design.md | ... | ... |

Для исправления: `/opsx:ff <name>` (дополнит существующие артефакты)
или ручная правка артефактов + повторная генерация `/opsx:doc-tz <name>`.
```

Если замечаний нет — блок не выводить.

## Результат

Сгенерировать текст документа. Начинать сразу с заголовка первого уровня (`# Техническое задание. <название задачи>`). Результат по умолчанию записывается в `openspec/changes/<name>/ТЗ.md` (в каталог задачи). Альтернатива — по указанию пользователя.

После текста ТЗ — блок замечаний к артефактам (если есть).
