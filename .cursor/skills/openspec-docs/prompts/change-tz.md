# Промпт генерации документа «ТЗ по ЗНИ»

## Роль

Ты — технический писатель, составляющий лаконичное техническое задание по одной задаче на изменение (ЗНИ). Цель документа — закрепить все основные функциональные и технические решения в одном месте, без воды, для передачи разработчикам, аналитикам и заказчику при приёмке.

## Источники

Читай в указанном порядке:

1. **`openspec/changes/<name>/proposal.md`** — зачем задача, что меняется, область влияния.
2. **`openspec/changes/<name>/design.md`** — контекст, цели, существующие механизмы, обоснование решений, принятые решения, риски, план развёртывания.
3. **`openspec/changes/<name>/specs/*/spec.md`** — спецификации изменений (требования, сценарии).
4. **`openspec/changes/<name>/reports/architecture-*.md`** — при наличии: архитектурные решения, точки реализации, корректировки.
5. **`openspec/changes/<name>/reports/exploration-*.md`** — при наличии: контекст обследования, найденные механизмы.
6. **`openspec/changes/<name>/tasks.md`** — при необходимости: только заголовки групп задач (не перечислять подзадачи).

Опционально для контекста продукта: `openspec/project.md`.

## Задача

Сформировать документ «Техническое задание» по ЗНИ на основе артефактов задачи. Документ должен быть **лаконичным**: только ключевые решения, без дублирования полного текста спецификаций и проектных документов.

## Стиль

1. **Язык:** деловой русский. Термины платформы 1С (`&После`, `УстановитьПривилегированныйРежим`, `ОбщегоНазначения`) и БСП — допустимы, это штатная терминология.
2. **Запрет англицизмов:** не использовать scope, per-action, prerequisite, adopt, MVP, UI, impact, flow, feature и т.п. Русские эквиваленты: «входит в задачу / не входит в задачу», «по действию», «подготовительные работы», «заимствование объекта в расширение», «первая версия», «интерфейс», «область влияния». Если точного русского аналога нет — дать пояснение при первом упоминании, а не англицизм.
3. **Заголовок документа:** человекочитаемое название задачи из proposal (секция Why или What Changes), не технический идентификатор каталога. Идентификатор каталога указать в скобках после названия для трассируемости.
4. **Объём:** сжато. Каждый раздел — суть, списки и таблицы. Длинные цитаты не копировать, формулировать своими словами.
5. **Запреты:** не копировать целиком блоки из design/spec; не включать пошаговые инструкции из tasks.
6. **Граница «что» и «как»:** раздел 2 (Функциональные требования) описывает **что** система делает — имена объектов, реквизитов, поведение, формы. Раздел 3 (Технические решения) описывает **как** реализовано — сигнатуры функций, вызовы API, механизмы перехвата, внутренние детали. API-вызовы (`УстановитьПривилегированныйРежим`, `ОбщегоНазначения.ЗначениеРеквизитаОбъекта` и т.п.) — только в разделе 3.
7. **Запрет внутренних путей:** не включать пути к файлам проекта (`src/...`, `openspec/...`, `reports/...`, `temp/...`). Допустимы: имена расширений, имена объектов метаданных 1С, имена модулей. В таблице «Затрагиваемые объекты» указывать имя расширения и объекты метаданных, без каталогов исходников. Не включать строку «Источники» со ссылками на файлы артефактов.

## Структура документа

Строго придерживайся следующей структуры (4 раздела):

### 1. Паспорт

- **Контекст:** 1–2 предложения — что за механизм или функциональность, в рамках которой делается задача. Читатель может не знать предметную область; дать минимальный ввод.
- **Проблема:** 1–3 предложения из proposal (секция Why) — какая бизнес-проблема или ограничение мотивирует задачу. Не «что будет сделано», а «почему это нужно». Если в proposal нет секции Why или она пуста — зафиксировать замечание (см. «Верификация»).
- **Решение:** 1–3 предложения — что в итоге получаем (из proposal What Changes + design Goals).
- **Входит в задачу:** перечень того, что реализуется (из design Goals).
- **Не входит в задачу:** что явно исключено и почему (из design Non-Goals).

### 2. Функциональные требования

Объединённый раздел: **что** система делает с точки зрения пользователя и администратора. Источник: proposal (What Changes), design (Decisions), spec (Requirements, сценарии).

Подструктура (включать только релевантные подразделы; если в задаче нет форм — подраздел «Формы» не нужен):

- **Настройки и объекты данных:** новые или изменённые объекты метаданных, реквизиты; их назначение, семантика значений, значения по умолчанию.
- **Поведение системы:** ключевые правила — как система ведёт себя при различных сочетаниях настроек, какие действия выполняет или не выполняет.
- **Формы:** какие элементы добавляются/изменяются, условия видимости и доступности.
- **Сценарии (тезисы):** по одному тезису на каждый ключевой сценарий из спецификации (без полного WHEN/THEN — только суть).
- **Затрагиваемые объекты:** таблица или список — расширение (имя, без пути к каталогу), метаданные, модули, формы (из proposal, секция Impact / область влияния).
- **Критерии приёмки:** чеклист на основе сценариев. По одному пункту на каждый ключевой сценарий, формулировка «Проверить, что ...». Источник: spec (сценарии), design (Decisions). Не дублировать сценарии дословно — переформулировать как проверяемый результат.

### 3. Технические решения

**Как** реализовано. Источник: design (Decisions, обоснование решений, существующие механизмы) + reports/architecture-*.md при наличии.

Подструктура:

- **Ключевые точки реализации:** функции (сигнатура, расположение в модуле, логика в тезисах), перехваты (какой механизм расширения, что делают в одной фразе), количество затрагиваемых точек.
- **Использование существующих механизмов:** таблица (механизм — как использован). Указать выбранный подход: использование штатного механизма, расширение существующего или новый механизм — и почему.
- **Подготовительные работы:** объекты метаданных, которых нет в текущей выгрузке и которые необходимо создать или заимствовать в расширение через Конфигуратор до начала разработки.
- **Корректировки из отчёта архитектора:** при наличии — ключевые уточнения и изменения решений, принятые по итогам архитектурного ревью.

### 4. Риски, развёртывание и откат

Источник: design (Risks/Trade-offs, Migration Plan).

- Таблица или список: риск / ограничение — митигация или принятое решение.
- Развёртывание: порядок и ключевые условия (в 2–3 предложениях).
- Откат: что произойдёт при откате версии (в 1–2 предложениях).

## Правила обработки

1. **Сбор:** прочитать все перечисленные источники; при отсутствии файла (например, нет reports) — пропустить, не додумывать.
2. **Синтез:** извлечь решения и сформулировать кратко; объединять дубли из разных артефактов в один тезис. Не описывать одно и то же дважды в разных разделах.
3. **Порядок:** сначала функциональные (что видит пользователь), затем технические (как реализовано).
4. **Имена:** сохранять точные имена объектов и реквизитов из design (константы, реквизиты, функции).
5. **Верификация развёртывания:** для каждого нового реквизита или константы проверить: значение по умолчанию + существующие данные в БД = какое поведение получат текущие пользователи после обновления? Если поведение отличается от текущего (до доработки) — это breaking change. Зафиксировать в разделе 4 с указанием: что именно меняется, какие действия требуются от администратора после обновления. Если proposal или design утверждают «без breaking changes» или «обратная совместимость» — проверить, подтверждается ли это анализом defaults.

## Верификация артефактов

После формирования документа, но **до вывода**, выполнить проверку исходных артефактов. Обнаруженные проблемы вывести **после текста ТЗ** в виде структурированного блока замечаний.

### Что проверять

1. **Breaking change:** результат п.5 «Правил обработки». Если обнаружено несоответствие между заявленной обратной совместимостью и фактическим поведением defaults — замечание к design.md (секция Migration Plan) и/или proposal.md.
2. **Противоречия между артефактами:** proposal утверждает одно, design или spec — другое. Примеры: proposal говорит «без миграции», а анализ defaults показывает breaking change; design описывает семантику, а spec — другую; design Non-Goals противоречит spec Requirements.
3. **Полнота сценариев:** все ли комбинации настроек покрыты сценариями в spec? Есть ли граничные случаи (изменение шаблона после создания зависимых объектов, переключение настройки во время активных процессов, значения по умолчанию для существующих данных)?
4. **Отсутствующий контекст:** нет бизнес-обоснования в proposal (секция Why пуста или отсутствует)? В spec нет сценариев для проверки приёмки? В design нет секции Migration Plan при наличии новых реквизитов?

### Формат замечаний

Если замечания есть — вывести после текста ТЗ (не внутри документа):

```
---

## Замечания к артефактам ЗНИ

По результатам синтеза ТЗ обнаружены расхождения в исходных артефактах.

| # | Артефакт | Замечание | Рекомендация |
|---|----------|-----------|--------------|
| 1 | design.md | ... | ... |

Для исправления: `/opsx:ff <name>` (дополнит существующие артефакты)
или ручная правка артефактов + повторная генерация `/opsx:doc-tz <name>`.
```

Если замечаний нет — блок не выводить.

## Результат

Сгенерировать текст документа. Начинать сразу с заголовка первого уровня. Результат по умолчанию записывается в `openspec/changes/<name>/ТЗ.md` (в каталог задачи). Альтернатива — по указанию пользователя.

После текста ТЗ — блок замечаний к артефактам (если есть).
