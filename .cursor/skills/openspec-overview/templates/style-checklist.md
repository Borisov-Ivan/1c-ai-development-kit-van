# Style checklist — overview для заказчика / ФА

Это стиль **файла для ФА/заказчика**, не HALT чата разработчику. В `/opsx:*` к разработчику `UI` допустим (lexicon Слой 3). Коды OpenSpec (`S1`, `Layer`) — `.cursor/docs/chat-lexicon.md` Слой 1, не копировать сюда как второй словарь.

Прогнать **до** Write файла. Любой пункт = HALT, переписать.

Читатель — **аналитик / функциональный архитектор**.  
Жанр — **лаконичное описание проекта** (постановка поставки), не письмо-туториал и не краткий `design.md`.

**Критерий абзаца:** отвечает только на «что делаем / при каких условиях / чего нет в первой поставке». Иначе — удалить или вынести в секцию стыка с ТЗ.

---

## Запрещённые англицизмы и жаргон OpenSpec

В теле документа (вне хвоста «Ссылки») не должно быть:

- `runtime`, `UX`, `UI` (как англ.), `kill-switch`, `master`, `factory`, `fallback`, `handoff`, `scope`, `MVP`, `хардкод` / `хардкодом` (писать «зашито в код»), `скалярные` (писать «обычные доп. настройки вида имя → значение»)
- `Behavior Contract`, `Non-Goals`, `Blast Radius`, `Intercept Map`
- `ADR-` / `ADR ` в заголовках и как опора аргумента (если нужна отсылка — «модель обычных доп. настроек» прозой)
- коды срезов/решений — не копировать; см. lexicon Слой 1

Допустимы привычные сокращения предметной области 1С/ДО, если они уже в ТЗ заказчика: РС, РГ, ЭДО, БП, ТЧ, ИБ — лучше расшифровать при первом упоминании («регистр сведений», «рабочая группа»).

## Ситуация ≠ механизм (обязательно)

**Тест жаргона:** можно ли сказать фразу вслух аналитику, не объясняя термины разработки? Если нет — переписать.  
Тест **не** оправдывает разжёвывание и педагогику (см. Laconic / anti-tutor).

**Заголовок этапа** = когда / что для людей (ситуация, эффект), не как это подключено в коде.

### Маркеры HALT в заголовках и первых фразах этапа

| Нельзя (механизм) | Замена (ситуация) |
|-------------------|-------------------|
| автомат / автоматически срабатывает | само / при сохранении … |
| алгоритм / серверный алгоритм | пересчёт / логика пересчёта (в теле, не в заголовке) |
| серверн* (сервер проходит…) | система / при сохранении |
| ядро | — убрать или «общая логика пересчёта» |
| триггер | при сохранении / по кнопке |
| перехват | — не в overview |
| вызов при записи | при сохранении процесса |
| контур (поставки) | этап / способ |
| актуализац* | пересчёт / подтянуть под условия |

«Что появляется» — наблюдаемое для админа или пользователя (кнопка, вкладка, поведение при сохранении, выключатель).  
Не инвентарь модулей: запрещены как начало пункта «единый серверный алгоритм», «общий модуль», «перехват», «ядро».  
Ремарка «в расширении Демо» допустима внутри пункта, не как пункт №1 про «алгоритм».

Вводный абзац этапа — 0–2 предложения **факта** (тот же регистр, что «Как это работает»), без обучения читателя.

## Laconic / anti-tutor (HALT)

| Категория | Маркеры | Действие |
|-----------|---------|----------|
| Мета ТЗ/документа | «по сути то, о чём говорилось…», «так достигается цель исходного ТЗ», отсылки «как в исходном направлении» **внутри этапа** | только секция «Как это закрывает…» или удалить |
| Педагогика | CRUD-разжёвывание («добавляют, правят, сохраняют»), «не A, а B», «не одна „магическая“…», «Итого этап N», повтор того, что ясно из заголовка/списка | удалить |
| Уговаривание | «привычное место», «ломать не нужно», «удобно потому что», защита выбора вместо факта | сухой факт решения |
| Совет стенда / опция | «логична группа вроде…», «при желании — как у синей кнопки…» | контракт поля; пример заполнения стенда — не в модель |

**Одна мысль — одно место.** Резюме этапа («В итоге») — только если даёт *новый* инвариант; иначе опустить. Канцелярит «Итого этап N:» — запрещён всегда.

## Запрещённая форма

- markdown-таблицы «как в design» (поле | тип | смысл) — заменить нумерованным списком;
- ASCII / mermaid-схемы;
- заголовки этапов = kebab-имя change (`sample-change`, `another-change`) или «ЗНИ 1 / ЗНИ 2»;
- заголовки этапов = название механизма (см. Ситуация ≠ механизм);
- перечни путей `.bsl` / Form.xml как основа сюжета;
- «как понял», «бриф для исследования», имена субагентов;
- канцелярит «Итого этап N:»;
- мета-ТЗ, педагогика, уговоры, советы стенда в теле этапов (см. Laconic / anti-tutor).

## Обязательная форма

- связная проза + нумерованные списки; плотность выше «письма с пояснениями»;
- этапы = **ситуация / эффект** (что появляется / как работает);
- имена процедур в backticks — только если это уже язык ТЗ («штатный подход»);
- финальный блок «Что требуется согласовать» — 3–7 пунктов на языке решений, не задач разработчика.

## Self-check (да/нет)

1. Этапы названы по смыслу поставки, не по именам change?
2. Нет запрещённых англицизмов / OpenSpec-кодов из списка выше?
3. Нет таблиц design и ASCII-схем?
4. Есть «Как сейчас» + «Зачем» + этапы + «Согласовать»?
5. При наличии ТЗ — есть секция стыка?
6. Объём не раздут сверх ~x2 эталона на схожую тему?
7. Нет жаргона механизма в заголовках (автомат, алгоритм, ядро, триггер, перехват)?
8. «Что появляется» — наблюдаемое поведение, не инвентарь модулей?
9. Нет мета-ТЗ / педагогики / уговоров / советов стенда в теле этапов?
10. Каждый абзац — факт поставки, а не обучение читателя и не защита решения?
