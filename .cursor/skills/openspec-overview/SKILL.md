# `/opsx:overview` — лаконичное описание проекта

Компилятор: из артефактов одной или нескольких ЗНИ собирает **связный md** «как сейчас → зачем → этапы поставки → что согласовать» для функционального архитектора / заказчика. Пишет только `overview-*.md` в каталог change; `proposal`/`design`/`tasks`/`specs` не трогает.

**Жанр:** краткая постановка проекта (факты поставки). Не туториал, не защита решения, не письмо с разжёвыванием.

**Не делает:** правки `proposal`/`design`/`tasks`/`specs`, вызов writer/explorer/architect, обследование `.bsl`. Сборщик манифеста карты — исключение, только по согласию (см. Guardrails).

**Эталон структуры:** [`fixtures/golden-88781-overview.md`](fixtures/golden-88781-overview.md)  
**Эталон голоса этапа:** [`fixtures/voice-good-stage.md`](fixtures/voice-good-stage.md)  
**Скелет:** [`templates/customer-overview.md`](templates/customer-overview.md)  
**Стиль HALT:** [`templates/style-checklist.md`](templates/style-checklist.md)  
**Чат:** T-OVERVIEW в `.cursor/docs/opsx-output-style.md` §5.6

## Входные данные

```
/opsx:overview <change> [<change2>…] [--tz <path>] [--audience фа|заказчик]
```

| Аргумент | Смысл |
|----------|--------|
| `<change>` | Active: `openspec/changes/<name>/`. Archive: поиск `openspec/changes/archive/**/<name>` или каталог, имя которого оканчивается на `-<name>`. |
| `--tz` | Путь к исходному ТЗ (md) — тон и секция «Как это закрывает исходное направление». |
| `--audience` | Default `фа`. На текст влияет слабо (тот же стиль); в шапке можно не писать. |
| без аргументов | Список из `openspec list --json`; пользователь указывает имя текстом. Архив — только если явно попросил. |

**Control / без паузы:** если вход задан файлом `fixtures/control-run.md` или пользователь сразу дал change + ось этапов + «да» — бриф в чат **не** требует END TURN; компилировать сразу.

## Ось этапов (жёстко)

**Этап документа ≠ имя change, ≠ код `S1`, ≠ название механизма.**

Приоритет:

1. Явная рамка пользователя в команде или брифе («этапы: настройки → кнопки»).
2. Названия срезов / колонка «пользовательский сценарий» из `design.md` **без** префиксов `S1`/`S2` — **пересказанные ситуацией** (что происходит для людей), не калька технического ярлыка.
3. Заголовок ≠ механизм: запрещены «автомат», «алгоритм», «ядро», «триггер», «перехват», «серверный…» в заголовке. Только ситуация / эффект («Пересчёт при сохранении процесса», «Кнопка на вкладке Визы»).
4. Мульти-ЗНИ — **одна** сквозная история; если порядок неочевиден — спросить в брифе (один вопрос).

Если ось этапов **явно** задана пользователем (или control-run), не пересобирать этапы «по одной главе на change». Параллельный узкий сюжет (вторая ЗНИ) — короткая ремарка внутри нужного этапа или в «Стыке с ТЗ», а не второй равноправный сюжет, размывающий ось.

Имена change — только в хвосте «Ссылки», не в заголовках этапов.  
Запрещены заголовки вида `another-change`, «ЗНИ 1», «этап change X», «Автомат при записи…».

## Entry Protocol

### 1. Resolve changes

Для каждого имени:

1. Если есть `openspec/changes/<name>/proposal.md` — active.
2. Иначе Glob `openspec/changes/archive/**/proposal.md` и взять каталог, где имя папки = `<name>` или оканчивается на `-<name>`.
3. Не найдено — сообщить и END.

Несколько change — все в одном документе.

### 2. Бриф B1 (синхрон)

Форма — `.cursor/docs/templates/brief-card.md`, уровень **B1** (без плана работ).

Слоты:

| Слот | Содержание |
|------|------------|
| **Изменение** | Тема одним предложением |
| **Контекст** | Пути change (+ `--tz` если есть) |
| **Уточнить до старта** | Только если мульти-ЗНИ и ось этапов не задана: «какая ось этапов?» |
| **Подтвердить?** | да |

После «да» (или control-run) — компиляция.  
**HALT:** не писать overview до подтверждения, кроме control-run / явного «сразу собери».

### 3. Источники (только Read)

Две ветки. Они не смешиваются.

**Сюжет файла** (компиляция описания) — на каждый change:

- `proposal.md` — Why, What Changes, Metadata (ID ТЗ из suffix при наличии);
- `design.md` — Goals / Non-Goals, Behavior Contract (смысл прозой), Slices (имена сценариев), Open questions / Decisions → «согласовать» без кодов `D*`.

Опционально: файл `--tz`.

**Инвентарь карты** (после записи файла, шаг 6) — отчёты разбора, журналы пошагового прохода и архитектурные отчёты по теме в каталогах названных ЗНИ. В компиляцию описания эти файлы **не** входят.

**Не входят ни в одну ветку:** `tasks.md`, отчёты проверки постановки (`verification-*`, `architecture-task-readiness-*`, `architecture-extend-coherence-*`, `architecture-loop-redesign-*`), `.bsl`, Form.xml. Сам файл описания не источник узлов карты.

Допустимо до 2× Read ТЗ / proposal для тона.

### 4. Компиляция

Собрать текст по [`templates/customer-overview.md`](templates/customer-overview.md):

1. Шапка: тема, ID ТЗ если известен, зона (расширение простым языком).
2. Как сейчас → Зачем → «Предлагается в N этапов» (или «Сделано в N этапов» для архивной закрытой темы — по смыслу Why в прошедшем, если change archived и пользователь не просил «как будем»).
3. Этапы по оси выше.
4. Секция стыка с ТЗ — только если был `--tz` или control с ТЗ.
5. «Что требуется согласовать».
6. Хвост «Ссылки» с именами change. Заголовок в файле — ровно `## Ссылки` (инструкцию компилятору в заголовок не копировать).

Не додумывать scope: пробелы → пункты «нужно решить / уточнить».

### 5. Style gate (три прохода)

1. **OpenSpec / англицизмы** — [`templates/style-checklist.md`](templates/style-checklist.md) (верхняя секция).
2. **Ситуация ≠ механизм** — секция «Ситуация ≠ механизм» + сверка с [`fixtures/voice-good-stage.md`](fixtures/voice-good-stage.md): заголовки этапов, вводные, «Что появляется».
3. **Laconic / anti-tutor** — секция «Laconic / anti-tutor» того же checklist: мета-ТЗ внутри этапов, педагогика, уговоры, советы стенда — вырезать до Write.

При провале любого прохода — переписать **до** Write. Не считать style пройденным, если убраны только `runtime`/`S1`, а остались tutor-обороты или механизмные заголовки.

### 6. Write + чат

- Файл: `openspec/changes/<name>/overview-YYYY-MM-DD.md` (корень каталога change, не `temp/`, не `reports/`).  
  - `<name>` — resolved-каталог **первой** ЗНИ из списка (active или archive); мульти-ЗНИ — один файл, без копий.  
  - Повтор в тот же день — перезапись того же имени.  
  - control: путь из `control-run.md` (`openspec/changes/sample-change/overview-control-88781.md`).
  - Протокол панели в файл описания **не** писать.
- Чат (три элемента, всегда): путь к файлу; 3–5 пунктов из «Что требуется согласовать»; одна строка следующего шага. **Не** печатать весь документ в чат. Канон строки шага — «Передать файл на согласование» (идемпотентна на повторном прогоне в той же сессии). Заглушка «достаточно» не печатается. Это не команда `/opsx:…`.

**Инвентарь отчётов (после записи файла).** Для каждой названной ЗНИ резолвить каталог тем же способом, что шаг «Resolve changes» (active и archive равноправны). Временные отчёты вне каталога ЗНИ — только если путь уже назван в этой сессии.

Тип файла: если в `reports/_manifest.yaml` есть запись с этим `file` — взять поле `type`; если манифеста нет **или** файла в нём нет — по префиксу имени (`explain-*` — журнал прохода, `exploration-*` — разбор, `architecture-*` — архитектурный). «Манифест есть» не значит «манифест полон».

В инвентарь **не** включать: сам `_manifest.yaml`; `verification-*`; `quality-control-*`; `design-challenge-*`; `handoff-acceptance-*` / `slice-acceptance-*`; семейства `architecture-task-readiness-*`, `architecture-extend-coherence-*`, `architecture-loop-redesign-*` (даже при `type: architecture` или префиксе `architecture-*`).

Выбрать **один** отчёт **до** проверки (исход проверки выбор не меняет):

1. Журнал прохода.
2. Иначе отчёт разбора.
3. Иначе архитектурный отчёт по теме — только если в нём уже есть вывод про механизм, а не план этапов; формулировки «мы планируем» источником панели не являются.

Ничья одного разряда (две ЗНИ с журналом прохода и т.п.) — отчёт **первой названной** ЗНИ. Объединение нескольких отчётов признаком не считается.

**Предложение панели — на выбранном одном отчёте** (читать вывод и структуру, не сюжет файла описания и не этапы поставки):

Картинку предлагать только если без неё легко перепутать ветки, условия или уровни. Этапы поставки — не источник полотна. Если авто-критерий не выполнен — намёка нет; причину в чат **не** печатать. Строка шага остаётся.

Все условия выполнены **и** в этой сессии ещё не сказали «без схемы» — в уже существующей строке шага добавить вариант панели с фразой, **что станет видно**. Панель на этом шаге **не** создавать.

**Ответ пользователя**

- Согласие — родитель сам собирает данные из выбранного отчёта и текущего ответа; файл пишет родитель по скиллу визуального объяснения; сборщик манифеста **не** вызывается. Вопрос панели — «зачем меняем», не перечень этапов. Постановка, список задач и файл описания — не источник элементов.
- Молчание — панель не создавать.
- «Без схемы» — до выхода сессии намёк не повторять; строка шага остаётся.

## Guardrails

- BSL / XML write guard — не применять (нет правок кода). Обследование `.bsl` и правки модулей из этой команды **запрещены**.
- Не вызывать `Task` к 1С-агентам (writer / explorer / architect / reviewer / trace) из этой команды.
- Не править `proposal`/`design`/`tasks`/`specs`. **Write** `overview-*.md` в корень каталога change — разрешён.
- Имена субагентов и T-коды — не в чат пользователю.

## Self-check перед END

1. Ось этапов — ситуация/эффект, не имена change и не механизмы («автомат», «алгоритм»…)?
2. Style-checklist пройден: англицизмы + ситуация≠механизм + Laconic / anti-tutor?
3. Нет мета/резюме-для-тугого/уговоров/советов стенда в теле этапов?
4. Файл записан в корень каталога первой ЗНИ (`overview-YYYY-MM-DD.md`), не в `temp/` и не в `reports/`?
5. Чат — три элемента (путь, блок «Что согласовать», одна строка следующего шага), без пересказа design? Строка шага напечатана и когда панели нет?
6. При `--tz` — есть стык с исходным направлением (и мета не продублирована внутри этапов)?
7. Хвост — заголовок `## Ссылки` без скобок-инструкций?
