# `/opsx:overview` — лаконичное описание проекта

Read-only компилятор: из артефактов одной или нескольких ЗНИ собирает **связный md** «как сейчас → зачем → этапы поставки → что согласовать» для функционального архитектора / заказчика.

**Жанр:** краткая постановка проекта (факты поставки). Не туториал, не защита решения, не письмо с разжёвыванием.

**Не делает:** правки `proposal`/`design`/`tasks`, вызов writer/explorer/architect, обследование `.bsl`.

**Эталон структуры:** [`fixtures/golden-88781-overview.md`](fixtures/golden-88781-overview.md)  
**Эталон голоса этапа:** [`fixtures/voice-good-stage.md`](fixtures/voice-good-stage.md)  
**Скелет:** [`templates/customer-overview.md`](templates/customer-overview.md)  
**Стиль HALT:** [`templates/style-checklist.md`](templates/style-checklist.md)  
**Чат:** T-OVERVIEW в `.cursor/docs/opsx-output-style.md` §5.6

## Входные данные

```
/opsx:overview <change> [<change2>…] [--tz <path>] [--audience фа|заказчик]
```

| Аргумент | Смысл |
|----------|--------|
| `<change>` | Active: `openspec/changes/<name>/`. Archive: поиск `openspec/changes/archive/**/<name>` или каталог, имя которого оканчивается на `-<name>`. |
| `--tz` | Путь к исходному ТЗ (md) — тон и секция «Как это закрывает исходное направление». |
| `--audience` | Default `фа`. На текст влияет слабо (тот же стиль); в шапке можно не писать. |
| без аргументов | Список из `openspec list --json`; пользователь указывает имя текстом. Архив — только если явно попросил. |

**Control / без паузы:** если вход задан файлом `fixtures/control-run.md` или пользователь сразу дал change + ось этапов + «да» — бриф в чат **не** требует END TURN; компилировать сразу.

## Ось этапов (жёстко)

**Этап документа ≠ имя change, ≠ код `S1`, ≠ название механизма.**

Приоритет:

1. Явная рамка пользователя в команде или брифе («этапы: настройки → кнопки»).
2. Названия срезов / колонка «пользовательский сценарий» из `design.md` **без** префиксов `S1`/`S2` — **пересказанные ситуацией** (что происходит для людей), не калька технического ярлыка.
3. Заголовок ≠ механизм: запрещены «автомат», «алгоритм», «ядро», «триггер», «перехват», «серверный…» в заголовке. Только ситуация / эффект («Пересчёт при сохранении процесса», «Кнопка на вкладке Визы»).
4. Мульти-ЗНИ — **одна** сквозная история; если порядок неочевиден — спросить в брифе (один вопрос).

Если ось этапов **явно** задана пользователем (или control-run), не пересобирать этапы «по одной главе на change». Параллельный узкий сюжет (вторая ЗНИ) — короткая ремарка внутри нужного этапа или в «Стыке с ТЗ», а не второй равноправный сюжет, размывающий ось.

Имена change — только в хвосте «Ссылки», не в заголовках этапов.  
Запрещены заголовки вида `podpisanie-cherez-soglasovanie`, «ЗНИ 1», «этап change X», «Автомат при записи…».

## Entry Protocol

### 1. Resolve changes

Для каждого имени:

1. Если есть `openspec/changes/<name>/proposal.md` — active.
2. Иначе Glob `openspec/changes/archive/**/proposal.md` и взять каталог, где имя папки = `<name>` или оканчивается на `-<name>`.
3. Не найдено — сообщить и END.

Несколько change — все в одном документе.

### 2. Бриф B1 (синхрон)

Форма — `.cursor/docs/templates/brief-card.md`, уровень **B1** (без плана работ).

Слоты:

| Слот | Содержание |
|------|------------|
| **Изменение** | Тема одним предложением |
| **Контекст** | Пути change (+ `--tz` если есть) |
| **Уточнить до старта** | Только если мульти-ЗНИ и ось этапов не задана: «какая ось этапов?» |
| **Подтвердить?** | да |

После «да» (или control-run) — компиляция.  
**HALT:** не писать overview до подтверждения, кроме control-run / явного «сразу собери».

### 3. Источники (только Read)

На каждый change:

- `proposal.md` — Why, What Changes, Metadata (ID ТЗ из suffix при наличии);
- `design.md` — Goals / Non-Goals, Behavior Contract (смысл прозой), Slices (имена сценариев), Open questions / Decisions → «согласовать» без кодов `D*`.

Опционально: файл `--tz`.

**Не читать как основу сюжета:** `tasks.md`, `reports/verification-*`, `.bsl`, Form.xml.

Допустимо до 2× Read ТЗ / proposal для тона.

### 4. Компиляция

Собрать текст по [`templates/customer-overview.md`](templates/customer-overview.md):

1. Шапка: тема, ID ТЗ если известен, зона (расширение простым языком).
2. Как сейчас → Зачем → «Предлагается в N этапов» (или «Сделано в N этапов» для архивной закрытой темы — по смыслу Why в прошедшем, если change archived и пользователь не просил «как будем»).
3. Этапы по оси выше.
4. Секция стыка с ТЗ — только если был `--tz` или control с ТЗ.
5. «Что требуется согласовать».
6. Хвост «Ссылки» с именами change.

Не додумывать scope: пробелы → пункты «нужно решить / уточнить».

### 5. Style gate (три прохода)

1. **OpenSpec / англицизмы** — [`templates/style-checklist.md`](templates/style-checklist.md) (верхняя секция).
2. **Ситуация ≠ механизм** — секция «Ситуация ≠ механизм» + сверка с [`fixtures/voice-good-stage.md`](fixtures/voice-good-stage.md): заголовки этапов, вводные, «Что появляется».
3. **Laconic / anti-tutor** — секция «Laconic / anti-tutor» того же checklist: мета-ТЗ внутри этапов, педагогика, уговоры, советы стенда — вырезать до Write.

При провале любого прохода — переписать **до** Write. Не считать style пройденным, если убраны только `runtime`/`S1`, а остались tutor-обороты или механизмные заголовки.

### 6. Write + чат

- Файл: `temp/overview-YYYY-MM-DD-<slug>.md`  
  - slug — из темы (kebab) или первого change;  
  - control: путь из `control-run.md` (`temp/overview-control-88781.md`).
- Чат (T-OVERVIEW): путь к файлу + 3–5 пунктов из «Что требуется согласовать». **Не** печатать весь документ в чат.

## Guardrails

- BSL / XML write guard — не применять (нет правок кода).
- Не вызывать `Task` к 1С-агентам из этой команды.
- Не править артефакты OpenSpec.
- Имена субагентов и T-коды — не в чат пользователю.

## Self-check перед END

1. Ось этапов — ситуация/эффект, не имена change и не механизмы («автомат», «алгоритм»…)?
2. Style-checklist пройден: англицизмы + ситуация≠механизм + Laconic / anti-tutor?
3. Нет мета/резюме-для-тугого/уговоров/советов стенда в теле этапов?
4. Файл записан в `temp/`?
5. Чат тонкий (путь + согласовать), без пересказа design?
6. При `--tz` — есть стык с исходным направлением (и мета не продублирована внутри этапов)?
