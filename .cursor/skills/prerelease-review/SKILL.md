Провести предрелизное ревью расширения 1С. Результат — структурированный отчёт с замечаниями по уровням. После — предложение создать openspec change на устранение.

**Input**: Опционально — название расширения или путь. Если не указано — определить из контекста или спросить.

---

## Шаг 0. Определение scope

Если пользователь указал конкретное расширение (имя папки в `src/*/cfe/`, файлы или change) — использовать.

Иначе — найти доступные расширения:

```bash
# Найти расширения в src/
dir src\*\cfe\ -Directory
```

Использовать **AskUserQuestion tool** для выбора. Показать список расширений (например, `pav_ИсключениеУчастниковПоУсловию`).

Также проверить активные openspec changes:

```bash
openspec list --json
```

Если есть активный change — уточнить, является ли ревью частью его workflow.

**ВАЖНО**: Не начинать ревью до получения чёткого scope.

## Шаг 1. Сбор контекста

### 1.1 Прочитать стандарты проекта

- `.cursor/rules/1c-coding-standards.mdc` — стандарты BSL проекта.
- `.cursor/agents/onec-code-reviewer.md` — категории и правила ревью (в т.ч. отсылка к вендорским стандартам).
- **Вендорские стандарты 1С** (для полноты предрелизной проверки): `.cursor/skills/1c-vendor-standards/SKILL.md` — чеклисты по доменам; навигация — `.cursor/docs/standard/1c-standards-navigator.md`; полный текст по доменам — `.cursor/docs/standard/std-*.md` (метаданные, запросы, транзакции, формы и т.д.). Согласовано с AGENTS.md и onec-code-reviewer.

### 1.1a Соглашения по комментариям BSL (openspec/project.md)

**До шагов 1.7, 1.7b и 1.7c** прочитать [openspec/project.md](../../../openspec/project.md), секцию **«Форматы и соглашения по комментариям BSL»**. Если секции нет — whitelist и обязательный контроль **пусты**.

Извлечь **две** таблицы (если есть подзаголовки **Whitelist предрелиза** и **Обязательный контроль**):

**Whitelist**

- для каждой строки с заполненным **Префикс** — исключать комментарии, у которых после `//` (и пробелов) текст начинается с этого префикса;
- для каждой строки с заполненным **Regex** (на всю строку `//…`) — исключать комментарии, если **вся** строка комментария (от `//` до конца строки) удовлетворяет regex;
- строки-заглушки вроде «*(пока нет)*» не считать активными правилами.

**Обязательный контроль**

- перенести в бриф (шаг 1.5) все активные строки: **ID**, «Где проверять», «Требование / пример», **Regex допустимой строки**, **Уровень**, **kind**;
- если в таблице только пример (например EX-001), который команда не приняла — пользователь должен удалить строку из `project.md`, иначе предрелиз будет требовать соблюдения.

Кратко в брифе (шаг 1.5):

- **Whitelist форматов комментариев (project.md):** имена и правила (префикс/regex) или «нет»;
- **Обязательный контроль комментариев (project.md):** список ID и требований или «нет».

Памятка по колонкам (без дублирования таблиц): [.cursor/docs/bsl-comment-formats-project.md](../../docs/bsl-comment-formats-project.md).

### 1.2 Прочитать спецификацию расширения (если есть)

Искать в `openspec/docs/` файл со спецификацией расширения. Извлечь:

- Префикс расширения (например, `pavIU_`).
- Точки перехвата (список `&Вместо`/`&Перед`/`&После`).
- Префикс журнала регистрации.

Если спецификация не найдена — попросить у пользователя префикс расширения.

### 1.3 Собрать список .bsl файлов

Использовать Glob по директории расширения (`src/*/cfe/<название>/`). Перечислить все `.bsl` файлы с путями.

### 1.4 Загрузить артефакты активного change (если есть)

Если ревью в контексте change:

```bash
openspec instructions apply --change "<name>" --json
```

Прочитать `design.md`, `tasks.md` — для понимания контрактов и ожидаемого поведения.

### 1.5 Сформировать контекст для ревьювера

Подготовить структурированный бриф. Использовать его в промптах батчей (шаг 2.1). Шаблон:

- **Расширение:** название, префикс, префикс журнала (если есть).
- **Файлы в scope:** по батчу — список .bsl с путями (из 1.6: группы A/B/C).
- **Директория расширения (полный путь):** `src/*/cfe/<название>/` — для Grep по вызовам процедур/функций при проверке unused code (категория 15). Передавать явно, чтобы ревьювер мог проверять вызовы не только в файлах батча, но и во всём расширении.
- **Стандарты:** 1c-coding-standards.mdc, 1c-vendor-standards/SKILL.md, конфигурация onec-code-reviewer.md.
- **Whitelist форматов комментариев (project.md):** из шага 1.1a — перечень имён и правил (префикс/regex) или «нет».
- **Обязательный контроль комментариев (project.md):** из шага 1.1a — ID, где проверять, пример допустимой строки, regex (если есть), уровень/kind; или «нет».
- **Режим:** mode=prerelease; для каждого замечания указывать kind (functional / style / release-hygiene).
- **Naming quality:** AP-031 — доменный тест + тест уровня абстракции + контрастный тест (см. onec-code-reviewer.md Phase 0 Q6 и bsl-antipatterns AP-031). Применять ко всем идентификаторам в ревьюируемом scope.

### 1.6 Классификация модулей

Автоматически разбить список .bsl файлов на группы:

- **Группа A (глубокий ревью):** собственные модули расширения — путь содержит префикс расширения (например `рг` в имени папки/модуля: `ргСервисКриптографии*`, `ргЭкземпляры*` и т.д.). Содержат оригинальный код проекта.
- **Группа B (стандартный ревью):** перехваты типовых модулей — общие/объектные модули с аннотациями &Вместо/&Перед/&После/&ИзменениеИКонтроль, но не в группе A. Проверка: аннотации, корректность структуры #Вставка/#Удаление (директивы не удалять — это синтаксис переопределения), минимальные паттерны.
- **Группа C (лёгкий ревью):** модули форм — пути содержат `\Forms\` и `Form\Module.bsl` или `Form.xml`. Структура, обработчики, базовые паттерны.

Указать в контексте: количество файлов и суммарное число строк (если доступно) в каждой группе. Если группа A содержит >10 файлов — разбить её на 2 батча (A1 и A2 по 5–8 файлов), иначе ревьювер не осилит глубокий проход.

### 1.7 Механическая проверка: ссылки на артефакты разработки

До батчевого ревью — запустить Grep по всем `.bsl` расширения для обнаружения процессных ссылок в комментариях (rule 17, категория 9 reviewer). Совпадения автоматически включаются в отчёт как HIGH [release-hygiene] без ожидания от ревьювера.

```bash
# Kebab-case идентификаторы в комментариях (имена changes: fix-signing-result и т.п.)
rg "//.*[a-z]+-[a-z]+-[a-z]+" --glob "*.bsl" <dir>

# Англоязычные процессные термины в комментариях
rg -i "//.*\b(design|decision|proposal|architecture|exploration)\b" --glob "*.bsl" <dir>

# Нумерованные решения / ссылки на задачи
rg "//.*Decision\s+\d+" --glob "*.bsl" <dir>
```

Допустимые исключения (не флагуются):
- Общепринятые технические англицизмы: HTTP, XML, API, XDTO, COM, base64, hex, JSON, UUID.
- Ссылки на внешние стандарты: RFC, ИТС, v8std.
- Директивы расширения: #Вставка, #КонецВставки, #Удаление, #КонецУдаления.
- TODO/FIXME (технический долг, не процессный маркер).
- **Строки комментариев, попадающие под whitelist** из шага 1.1a (префикс после `//` или совпадение regex на всю строку комментария).

Перед добавлением в отчёт: для каждого совпадения grep проверить whitelist из [openspec/project.md](../../../openspec/project.md) (секция whitelist, шаг 1.1a) — если комментарий подпадает под префикс/regex whitelist, **не включать** в сводку.

При обнаружении (после фильтра whitelist) — добавить в сводку (шаг 2.2) с `kind=release-hygiene`, уровень HIGH. Формат замечания: `файл:строка — [release-hygiene] Ссылка на артефакт разработки в комментарии. Рекомендация: переписать комментарий в доменных терминах.`

### 1.7b Механическая проверка: англоязычный жаргон в комментариях

До батчевого ревью — запустить Grep по всем `.bsl` расширения на **англоязычный технический жаргон** в однострочных комментариях `//` (не в строковых литералах `НСтр` и многострочных блоках — возможны ложные срабатывания; при сомнении сверить строку вручную).

```bash
# Жаргон и устойчивые англ. термины в комментариях (расширяемый набор)
rg -i "//.*\b(fail-fast|feature.toggle|workaround|fallback|downstream|re-raise|first.wins|last.wins|accumulate|per-action|pending|signal)\b" --glob "*.bsl" <dir>
```

Дополнительно (по смыслу проекта) можно прогнать термины из колонки «Запрещено» [.cursor/docs/tz-lexicon-dictionary.md](../../docs/tz-lexicon-dictionary.md), если они уместны для комментариев кода — только в комментариях `//`.

Исключения (не флагуются): те же, что в шаге 1.7 (HTTP, XML, API, XDTO, COM, base64, hex, JSON, UUID, RFC, ИТС, v8std, TODO/FIXME, директивы расширения) **плюс** явные ссылки на платформенные типы и методы в комментарии (`COMОбъект`, `HTTPСоединение` и т.п.) **плюс** **whitelist** из шага 1.1a (префикс или regex на всю строку комментария).

Перед добавлением в отчёт — фильтр whitelist, как в 1.7.

Совпадения после фильтра — **HIGH [release-hygiene]** в сводку (шаг 2.2), `kind=release-hygiene`. Формат: `файл:строка — [release-hygiene] Англоязычный жаргон в комментарии. Рекомендация: переписать на русском (допустимы аббревиатуры HTTP, XML, API, XDTO, COM, JSON, UUID, MD5, RFC и ссылки на типы платформы).`

### 1.7c Механическая проверка: обязательные форматы комментариев (project.md)

Если в [openspec/project.md](../../../openspec/project.md) в таблице **«Обязательный контроль»** есть активные строки с непустым **Regex допустимой строки** — выполнить проверку по каталогу расширения `<dir>`. При **нескольких** правилах с разными условиями — выполнить проверку **отдельно для каждого ID** по колонке «Где проверять» (ниже — базовая механика для правил вида «первый `//` после `#Вставка`»).

1. `rg "#Вставка" --glob "*.bsl" -n <dir>` — список вхождений (файл, номер строки).
2. Для каждого вхождения: открыть файл, идти **вниз** от строки с `#Вставка`, пропуская пустые строки; первую строку, начинающуюся с `//` (после возможных пробелов в начале строки), сравнить с **Regex допустимой строки** из соответствующего правила (для правила EX-001 и аналогов — «первый `//` после `#Вставка`»; если в `project.md` для другого ID указано иное «Где проверять» — следовать ему, даже если механика сложнее одного прохода — тогда зафиксировать остаток проверки ревьюеру).
3. Если первый значимый однострочный комментарий `//` после блока не совпадает с regex допустимой строки — добавить в сводку (шаг 2.2) замечание с **ID правила** из таблицы, **уровнем** и **kind** из таблицы, `файл:строка`, краткое описание несоответствия и ссылку на колонку «Требование / пример».

Если regex в таблице для правила **пуст** — механика 1.7c для этого правила не выполняется; проверка только у ревьюера (батчи 1b, 2).

Если таблица обязательного контроля пуста или все строки — заглушки — шаг 1.7c пропустить.

**Важно:** в `project.md` должны оставаться только правила, которые команда реально требует; иначе возможны массовые замечания.

## Шаг 2. Батчевый ревью параллельными субагентами

### 2.0 Входные данные

Использовать группы A/B/C из шага 1.6 и общий контекст из 1.5. Имя расширения, префикс, стандарты, режим mode=prerelease — едины для всех батчей.

### 2.1 Параллельные вызовы onec-code-reviewer (до 4 одновременно)

Вызвать **Task** с `subagent_type: onec-code-reviewer` для каждого батча. Запускать батчи параллельно, где возможно.

**Батч 1a — Группа A, логика и безопасность:**
- Файлы: список модулей группы A (или A1, если A разбита).
- Промпт: «Провести **глубокий** предрелизный ревью собственных модулей расширения — фокус на логике и безопасности. Прочитай КАЖДЫЙ указанный файл целиком. Проверь: (1) логику и потоки данных, обработку ошибок, (2) Performance — запросы в циклах, индексы, (3) Security — инъекции, доступ, (4) **транзакционные паттерны**: НачатьТранзакцию без Попытки/Исключения, НачатьТранзакцию без ЗафиксироватьТранзакцию/ОтменитьТранзакцию, отсутствие ОтменитьТранзакцию в Исключении, пользовательское взаимодействие внутри транзакции, (5) **утечка ресурсов**: COM-объекты без Попытки/Исключения с освобождением, HTTP/FTP-соединения без обработки ошибок, файловые операции без закрытия в пути ошибки, (6) заглушки — функции, возвращающие пустые/невалидные значения, (7) Попытка/Исключение без логирования при проглатывании ошибки, (8) **неиспользуемый и устаревший код** (std-01 п.2.2, std-06 п.2, std-10 п.3.1): для каждой Процедуры/Функции в ревьюируемых файлах выполни Grep по имени во ВСЕЙ директории расширения (не только в файлах батча) — если вызовов нет, это неиспользуемый код. Исключения: обработчики событий, команды БСП (ExternalDataProcessorInfo), callback-процедуры (переданные строкой в ОписаниеОповещения). Невызываемая экспортная функция/процедура = HIGH [unused-code] kind=functional; невызываемая служебная = MEDIUM [unused-code] kind=style. Найди также процедуры/функции с комментарием «Устарела:» / «Deprecated» или расположенные в #Область УстаревшиеПроцедурыИФункции — MEDIUM [obsolete] kind=style. Если устаревшая процедура ещё вызывается из неустаревшего кода — HIGH [obsolete] kind=functional. (9) **пустые процедуры и функции**: найди все процедуры/функции с пустым телом (тело не содержит исполняемых операторов — только пустые строки, комментарии или сразу КонецПроцедуры/КонецФункции). Для каждой выполни Grep по имени во ВСЕЙ директории расширения. Если вызовов нет (исключения: обработчики событий, БСП-команды, callback по строке) → empty-unused, HIGH [release-hygiene], рекомендация: удалить. Если пустая, но вызывается → empty-body, MEDIUM [style], рекомендация: реализовать или удалить. (10) **Язык комментариев (предрелиз):** комментарии к процедурам, функциям и блокам — на русском; англоязычный технический жаргон (fail-fast, workaround, fallback, downstream, feature toggle, pending, per-action и т.п.) — HIGH [release-hygiene] kind=release-hygiene. Исключения: аббревиатуры HTTP, XML, API, XDTO, COM, JSON, UUID, MD5, RFC; ссылки на типы платформы; директивы расширения (#Вставка и т.п.). **Комментарии в whitelist** из [openspec/project.md](../../../openspec/project.md) (переданы в брифе шага 1.5) — не флаговать жаргоном/мусором и не предлагать удалять или переписывать только из-за шаблонной лексики, если строка укладывается в формат whitelist. (11) **Качество именования (AP-031):** применить доменный тест, тест уровня абстракции (убрать реализационное слово — остаётся ли доменный смысл?) и контрастный тест (доменные данные в безликом контейнере) ко всем идентификаторам (переменные, параметры, процедуры) в ревьюируемом scope. Имя, описывающее роль в коде без доменного квалификатора — MEDIUM [style]. Экспортные — HIGH [style]. В finding обязательно предложить доменный синоним. Для каждого замечания укажи файл:строка, уровень, kind, категорию (empty-unused / empty-body / и т.д.), описание, рекомендацию. РЕЖИМ: mode=prerelease.»

**Батч 1b — Группа A, структура и гигиена:**
- Файлы: те же модули группы A (или A1, если A разбита).
- Промпт: «Провести предрелизный ревью собственных модулей расширения — фокус на структуре, документации и релизной гигиене. Прочитай КАЖДЫЙ указанный файл целиком. Проверь: (1) БСП compliance, (2) аннотации расширений, (3) структуру модуля (#Область/#КонецОбласти — дублирование), (4) документацию методов, (5) Specific 1C Patterns (ТекущаяДата/ТекущаяДатаСеанса, Сообщить, Свойство, НСтр), (6) ЭтаФорма вместо ЭтотОбъект в оповещениях, (7) Экспорт в секции СлужебныеПроцедурыИФункции, (8) имя метода противоречит директиве компиляции, (9) опечатки и смешение кириллицы/латиницы в пользовательских строках, (10) **релизная чистота комментариев**: маркеры в комментариях (автор, дата, заявка, строки // НАЧАЛО/КОНЕЦ, +++/---), временные инструкции, закомментированный старый код — такие замечания = HIGH [release-hygiene]. Директивы #Вставка/#Удаление не удалять и не помечать как мусор — это синтаксис переопределения расширения. (11) **пустые процедуры и функции**: те же правила, что в батче 1a — пустое тело (нет исполняемого кода), Grep по имени в расширении; empty-unused = HIGH [release-hygiene], empty-body = MEDIUM [style]. ### 2.5 Архитектурный анализ (Tier 2, параллельно с шагом 2.1)

Запустить **Task** с `subagent_type: onec-code-explorer` **параллельно** с батчами reviewer (шаг 2.1). Explorer читает ВСЕ .bsl файлы расширения разом (не батчами) и выполняет кросс-модульные проверки, недоступные пофайловому reviewer.

**Входные данные:** полный список .bsl файлов расширения из шага 1.3 (все группы A/B/C вместе). Контекст из шага 1.5 (имя расширения, префикс).

**Промпт explorer:**

«Провести архитектурный анализ расширения [имя] для предрелизного ревью. Прочитай ВСЕ указанные .bsl файлы. Выполни 5 кросс-модульных проверок:

1. **Error strategy consistency:** Найди все блоки Попытка/Исключение во всех модулях. Для каждого классифицируй стратегию: (a) лог + ВызватьИсключение, (b) лог + Возврат fallback, (c) лог + Продолжить цикл, (d) без лога (silent). Сгруппируй по типу ошибки (получение объекта, запись, внешний вызов и т.д.). Если один тип ошибки обрабатывается 2+ разными стратегиями в разных модулях — флаг: inconsistent error strategy. Уровень: MEDIUM.

2. **Implicit contracts (ДополнительныеСвойства):** Найди все обращения к ДополнительныеСвойства: `.Вставить("ключ", ...)` и `.Свойство("ключ", ...)`. Построй матрицу: свойство → модуль-writer → модуль-reader. Если writer-модуль ≠ reader-модуль — это скрытый межмодульный контракт. Если >3 таких свойств без единого документированного реестра (комментария в шапке модуля или спецификации) — флаг. Уровень: MEDIUM.

3. **Repeated type-dispatch:** Найди все блоки `Если ТипЗнч(X) = Тип("...")`. Сгруппируй по набору проверяемых типов (например, ДеревоЗначений / ДанныеФормыДерево / ДанныеФормыКоллекцияЭлементовДерева). Если один и тот же набор типов проверяется в 3+ процедурах — флаг: кандидат на утилитную функцию. Уровень: MEDIUM.

4. **Semantic duplication:** Для каждой процедуры/функции извлеки: (a) входные сущности (типы параметров, обращения к реквизитам), (b) ключевые операции (вызовы БСП-методов, записи объектов, обращения к регистрам), (c) выходные действия (возврат, установка свойств). Найди пары процедур в разных модулях с >70% совпадением по этим признакам — кандидаты на рефакторинг в общую процедуру. Уровень: MEDIUM.

5. **Scope creep в обработчиках расширений:** Для каждого перехвата (&Перед/&После/&Вместо) определи, какую функциональность расширения он реализует (по именам вызываемых процедур с префиксом расширения). Если обработчик содержит вызовы, не связанные ни с одной функциональностью расширения (другой префикс, другой домен) — флаг: scope creep. Уровень: MEDIUM.

Для каждого замечания укажи: файлы (все затронутые), уровень, kind=architecture, категорию (error-strategy / implicit-contract / type-dispatch / semantic-duplication / scope-creep), описание, рекомендацию. РЕЖИМ: mode=prerelease.»

## Шаг 4. Предложение openspec change

Если обнаружены замечания уровня **CRITICAL**, **HIGH** или **MEDIUM** (включая kind=style, release-hygiene, architecture Tier 2):

Использовать **AskUserQuestion tool**:

> «Обнаружено N замечаний уровня CRITICAL/HIGH/MEDIUM (в т.ч. стиль и гигиена комментариев). Создать openspec change `prerelease-fix-<расширение>` для их устранения? MEDIUM войдут в tasks.md и proposal кратким списком.»

**Варианты:**
- Да, создать change
- Нет, только отчёт

### Если пользователь выбрал «Да»

1. Создать новый change (имя в kebab-case, например `prerelease-fix-rg-kontur-cryptoapi`):

```bash
openspec new change "prerelease-fix-<расширение-kebab>" --schema prerelease-fix
```

Если схема `prerelease-fix` недоступна — использовать `--schema spec-driven` и создать обязательный артефакт specs по инструкции схемы.

2. Сформировать proposal (описание задачи) на основе отчёта:
   - Суть: устранение замечаний предрелизного ревью расширения `<название>`.
   - Список замечаний **CRITICAL** и **HIGH** (с указанием kind: functional / style / release-hygiene / architecture).
   - **Краткий список MEDIUM** (по категориям или перечислением) — обязателен, если такие замечания есть.
   - Ссылка на отчёт: `reports/prerelease-review-ГГГГ-ММ-ДД.md`.

3. Сформировать tasks.md по правилам:
   - **CRITICAL** = отдельная задача на каждое замечание (блокер).
   - **HIGH functional** = отдельная задача на каждое замечание.
   - **HIGH style** и **HIGH release-hygiene** = отдельная задача на каждое замечание (как functional) — стиль и гигиена до релиза обязательны для кода заказчику.
   - **HIGH style / HIGH release-hygiene / MEDIUM (массовые):** если замечание одного типа затрагивает >3 файлов — одна задача с подзадачами по файлам (чекбоксы-подпункты). Пример:
     ```markdown
     - [ ] **2.2** [HIGH/style] Разметка #Область
       - [ ] CommonModules\РаботаСЭП\Ext\Module.bsl
       - [ ] CommonModules\РаботаСКартинками\Ext\Module.bsl
       - [ ] ...
     ```
   - **Все остальные MEDIUM** (включая kind=architecture из Tier 2) — каждая находка в **tasks.md** (отдельная задача или группировка по категории, 1 задача на категорию при множестве однотипных).
   - **LOW** — одна групповая задача «Технический долг».
   - **Неиспользуемый и устаревший код (группировка):**
     - `unused-code` (>3 процедур/функций): одна задача «Удалить неиспользуемый код» с подзадачами по файлам.
     - `obsolete` (>3 процедур/функций): одна задача «Вычистить устаревший код» с подзадачами.
     - Единичные unused/obsolete — отдельными задачами по обычным правилам уровня HIGH/MEDIUM.
   - **Пустые процедуры и функции (группировка):**
     - `empty-unused` (>3 штук): одна задача «Удалить пустые неиспользуемые процедуры и функции» с подзадачами по файлам (чекбоксы по каждому файлу или по каждой процедуре).
     - `empty-handler`: для каждого — отдельная задача «Удалить пустую процедуру <Имя> из <путь к Module.bsl>». Если у обработчика есть привязка в форме — добавить к задаче или в отдельный артефакт **инструкцию ручного конфигурирования** по шаблону из `.cursor/rules/1c-xml-write-guard.mdc`: **Форма:** <полное имя формы>, **Конфигурация/расширение:** <имя>. **Действия в Конфигураторе:** 1) Открыть форму; 2) Найти элемент/событие, к которому привязан обработчик <Имя>; 3) Удалить привязку обработчика события. **После выгрузки:** в Form.xml исчезнет соответствующий атрибут события у элемента.
     - Единичные empty-unused / empty-body — отдельными задачами по уровню HIGH/MEDIUM.
   - Удаление кода в .bsl выполняется при `/opsx:apply` через onec-code-writer; Form.xml не править — только инструкция пользователю.

   Формат задачи (одиночное замечание):
   ```markdown
   - [ ] [CRITICAL] Файл:строка — Категория: Описание. Рекомендация.
   - [ ] [HIGH] [functional] Файл:строка — ...
   - [ ] [HIGH] [style] Файл:строка — ...
   - [ ] [HIGH] [release-hygiene] Файл:строка — ...
   - [ ] [MEDIUM] [architecture] Описание (Tier 2) — ...
   ```

4. Сохранить отчёт ревью в `openspec/changes/prerelease-fix-<расширение>/reports/prerelease-review-ГГГГ-ММ-ДД.md`.

5. Сообщить пользователю:
   - Название созданного change.
   - Количество задач в tasks.md.
   - Следующий шаг: `/opsx:apply prerelease-fix-<расширение>`.

## Граничные случаи

- **Замечаний нет**: сообщить «Замечаний, блокирующих релиз, не найдено. Расширение готово к релизу.»
- **Только LOW**: предложить создать задачу технического долга или пропустить.
- **Нет спецификации расширения**: выполнить ревью с общими правилами; в отчёте отметить, что проверка соответствия спецификации не выполнена.
- **Нет активного change**: ревью выполняется в standalone-режиме; отчёт сохранить в `temp/reports/prerelease-review-<расширение>-ГГГГ-ММ-ДД.md`.

## Интеграция

- **Tier 1 (Code Review):** `onec-code-reviewer` v1.6 с поддержкой `mode=prerelease`, категориями 1-15 и новыми проверками (parameter mutation, magic constants, mixed responsibilities, prefix consistency, excessive logging).
- **Tier 2 (Architecture Review):** `onec-code-explorer` — кросс-модульный анализ (error strategy, implicit contracts, type-dispatch, semantic duplication, scope creep). Запускается параллельно с Tier 1. Только в prerelease.
- Стандарты кода: `1c-coding-standards.mdc` v1.4 (rules 1-22, включая rule 21 Parameter Integrity и rule 22 No Duplicated Literals).
- Стандарты вендора и навигация: `AGENTS.md` → секция «Стандарты вендора 1С»; `.cursor/docs/standard/` (1c-standards-navigator.md, std-*.md) и `.cursor/skills/1c-vendor-standards/SKILL.md` — единый набор для предрелизной проверки.
- Если после ревью обнаружены архитектурные замечания (новые объекты, изменение API, структуры хранения) — не создавать задачи writer, остановиться и показать пользователю.
- Отчёт сохраняется согласно `preserve-subagent-reports.mdc`.
- **Соглашения по комментариям BSL:** [openspec/project.md](../../../openspec/project.md) — whitelist (шаг 1.1a; механика 1.7 / 1.7b не флагует совпадения whitelist) и **обязательный контроль** (механика 1.7c + ревьюер в батчах 1b/2). Памятка по колонкам: `.cursor/docs/bsl-comment-formats-project.md`.
