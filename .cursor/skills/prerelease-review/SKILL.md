Провести предрелизное ревью расширения 1С. Результат — структурированный отчёт с замечаниями по уровням. После — предложение создать openspec change на устранение (или дополнение существующего ЗНИ в режиме change-scoped).

**Input**:

- **Без аргументов** — определить расширение из контекста или спросить; режим **`full-extension`** (как раньше).
- **Один аргумент** — имя расширения (папка в `src/*/cfe/`); режим **`full-extension`**.
- **Два аргумента** — `<расширение> <change-name>`; режим **`change-scoped`**: Tier 1 и механика 1.7/1.7b/1.7c только по `target_files` ЗНИ (multi-source resolver: `architecture-*.md` → `tasks.md` → `design.md`, git fallback); reference-файлы используются только как контекст; Tier 2 (explorer) — по всему расширению.

## Шаг 0. Определение scope и режима (`full-extension` / `change-scoped`)

**Acknowledgement first:** При получении запроса на предрелизное ревью **первой строкой** ответа, до вызова любых инструментов (Glob, Shell, Read), вывести:
> «Понял: запускаю предрелизное ревью. Уточняю scope...» (или подставить расширение/change, если они уже указаны в запросе).

### 0.1 Режим

| Ввод пользователя | `review_mode` | Действие |
|-------------------|---------------|----------|
| Только расширение или без аргументов (после уточнения) | `full-extension` | Поведение как до версии 1.3: все шаги без условий change-scoped. |
| Расширение + имя каталога change | `change-scoped` | Выполнить шаг 1.3a; валидацию change (ниже). |

**Имя change (`change-name`):** полное имя папки в `openspec/changes/<name>/` **или** `openspec/changes/archive/<name>/`. Порядок поиска: сначала `openspec/changes/<name>/`, затем `openspec/changes/archive/<name>/`.

При `change-scoped`:

1. Убедиться, что существует `.../<name>/tasks.md`. Иначе — **СТОП**: сообщить ошибку; перечислить доступные каталоги в `openspec/changes/` и `openspec/changes/archive/` (Glob `**/tasks.md` или `dir` по двум корням).
2. Зафиксировать путь к change: `change_dir = openspec/changes/<name>/` или `.../archive/<name>/`.
3. Зафиксировать `change_in_archive = true`, если путь содержит `/archive/`.

### 0.2 Расширение

Если пользователь указал конкретное расширение (имя папки в `src/*/cfe/`) — использовать. Пути к cf/cfe — из [openspec/project.md](../../../openspec/project.md), секция «Структура репозитория».

Иначе — найти доступные расширения:

```bash
# Найти расширения в src/
dir src\*\cfe\ -Directory
```

Использовать **AskUserQuestion tool** для выбора. Показать список расширений (например, `pav_ИсключениеУчастниковПоУсловию`).

Также проверить активные openspec changes:

```bash
openspec list --json
```

При `full-extension`, если есть активный change — уточнить, является ли ревью частью его workflow (опционально).

**ВАЖНО**: Не начинать ревью до получения чёткого scope (расширение + при `change-scoped` — валидный `change_dir`).

Согласовано с AGENTS.md и onec-code-reviewer.

### 1.1a Соглашения по комментариям BSL (openspec/project.md)

**До шагов 1.7, 1.7b и 1.7c** прочитать [openspec/project.md](../../../openspec/project.md), секцию **«Форматы и соглашения по комментариям BSL»**. Если секции нет — whitelist и обязательный контроль **пусты**.

Извлечь **две** таблицы (если есть подзаголовки **Whitelist предрелиза** и **Обязательный контроль**):

**Whitelist**

- для каждой строки с заполненным **Префикс** — исключать комментарии, у которых после `//` (и пробелов) текст начинается с этого префикса;
- для каждой строки с заполненным **Regex** (на всю строку `//…`) — исключать комментарии, если **вся** строка комментария (от `//` до конца строки) удовлетворяет regex;
- строки-заглушки вроде «*(пока нет)*» не считать активными правилами.

**Обязательный контроль**

- перенести в бриф (шаг 1.5) все активные строки: **ID**, «Где проверять», «Требование / пример», **Regex допустимой строки**, **Уровень**, **kind**;
- если в таблице только пример (например EX-001), который команда не приняла — пользователь должен удалить строку из `project.md`, иначе предрелиз будет требовать соблюдения.

Кратко в брифе (шаг 1.5):

- **Whitelist форматов комментариев (project.md):** имена и правила (префикс/regex) или «нет»;
- **Обязательный контроль комментариев (project.md):** список ID и требований или «нет».

Памятка по колонкам (без дублирования таблиц): [.cursor/docs/bsl-comment-formats-project.md](../../docs/bsl-comment-formats-project.md).

### 1.2 Прочитать спецификацию расширения (если есть)

Искать в `openspec/docs/` файл со спецификацией расширения. Извлечь:

- Префикс расширения (например, `pavIU_`).
- Точки перехвата (список `&Вместо`/`&Перед`/`&После`).
- Префикс журнала регистрации.

Если спецификация не найдена — попросить у пользователя префикс расширения.

### 1.3a Извлечение файлов ЗНИ (только `review_mode = change-scoped`)

Цель — построить четыре списка с provenance:

- **`target_files`** — `.bsl` внутри выбранного `src/*/cfe/<расширение>/`; идут в Tier 1 и механику 1.7–1.7c.
- **`reference_files`** — `.bsl` вне выбранного cfe (cf, старое расширение-источник, другие cfe); передаются reviewer-у только как read-only context, findings по ним запрещены.
- **`doc_files`** — markdown/spec/project-артефакты; не идут в BSL reviewer.
- **`ambiguous_files`** — сокращённые пути (`.../Form/Module.bsl`) и пути без `src/`, которые не удалось однозначно восстановить.

Каждый элемент хранит `path`, `source` (`architecture` / `tasks` / `design` / `git` / `debug-soft` / `slice-soft`) и при необходимости `warning`.

#### Источники и приоритет

1. **`reports/architecture-*.md`** — YAML front-matter `scope.files`. Если найден хотя бы один релевантный отчёт, его `scope.files` задаёт **canonical target set**: это primary-источник для `target_files`; `tasks.md` и `design.md` могут добавлять файлы, но не сужают список.
2. **`tasks.md`** — только задачи со статусом `[x]`. Извлечь пути из backticks. Секции `##` (имена файлов) задают контекст для задач под ними.
3. **`design.md`** — извлечь пути из backticks (обычно в `## Implementation Options` или `## Slices`).
4. **Git fallback** — если списки 1–3 пусты: `git log --oneline --grep="<change-name>"`; диапазон `git diff <parent>^..HEAD --name-only`.
5. *Soft warnings* — `debug.md` и `slice-acceptance`: если файл упомянут там, но не попал в `target_files`, добавить в отчёт warning «Файл упомянут в debug/приёмке, но не найден в tasks/design/architecture».

#### Обработка `ambiguous_files` (Suffix matching)

Для каждого пути, не начинающегося с `src/` (например, `Forms/MyForm/Ext/Form/Module.bsl`):

1. Выполнить `Glob **/<suffix>`.
2. Если найдено ровно 1 совпадение внутри `src/` — перенести в `target_files` (или `reference_files` по префиксу) с пометкой `source: <source> (resolved)`.
3. Если найдено >1 совпадения — оставить в `ambiguous_files`.
4. Если 0 совпадений — оставить в `ambiguous_files`.

#### Scope Preview (только при наличии `ambiguous_files` или пустом `target_files`)

Если `target_files` пуст или `ambiguous_files` не пуст — **AskUserQuestion tool**:

> «**Scope Preview:**
> Target files: N
> Reference files: M
> Ambiguous files: K (не удалось однозначно найти в репозитории: [список])
>
> Продолжить с найденным scope / Переключиться в `full-extension` / Остановиться?»

Если всё ОК — продолжить без вопроса.

### 1.3b Review Boundaries (только `review_mode = change-scoped`)

Цель — ограничить ревьювера только изменёнными процедурами/функциями внутри `target_files`.

1. Для каждого файла из `target_files` получить unified diff (baseline: `working tree vs HEAD` или `git merge-base main HEAD`).
2. Извлечь номера изменённых строк (префикс `+`).
3. Прочитать файл, найти границы процедур/функций (regex `^\s*(Процедура|Функция)` / `КонецПроцедуры|КонецФункции`).
4. Сопоставить изменённые строки с процедурами. Строки вне процедур — `[module-level]`.
5. Сформировать блок `## Review Boundaries` (как в `/review` шаг 1.5.5).

**Важно:** Механические проверки (шаги 1.7, 1.7b, 1.7c) при `change-scoped` также должны фильтровать свои находки: сообщать только о строках, попадающих в диапазоны из `Review Boundaries`.

### 1.3c Формирование `extension_all_bsl`

Независимо от режима, собрать полный список `.bsl` файлов расширения (Glob `src/*/cfe/<расширение>/**/*.bsl`).

- При `full-extension` этот список используется для Tier 1 и Tier 2.
- При `change-scoped` этот список используется **только для Tier 2 (explorer)**; Tier 1 использует `target_files`.

### 1.4 Разбивка на батчи (Tier 1)

Ревьювер (Tier 1) обрабатывает файлы батчами.

- При `full-extension`: разбить `extension_all_bsl` на группы.
- При `change-scoped`: разбить **только `target_files`** на группы.

**Группа A (Глубокий ревью):**
Модули объектов, менеджеров, общие модули (кроме вызовов сервера и глобальных).
Если файлов > 5, разбить на A1 и A2 (по 3-5 файлов в батче).

**Группа B (Серверные вызовы):**
Общие модули с суффиксом `ВызовСервера`, `Глобальный`.

**Группа C (Лёгкий ревью):**
Модули форм (`Forms/*/Ext/Form/Module.bsl`).

## Шаг 1.7. Механическая проверка: закомментированный код (evidence)

Выполняется оркестратором (Grep/Read) ДО вызова агента. Результаты передаются агенту как evidence.

**Scope:**
- При `full-extension`: все файлы из `extension_all_bsl`.
- При `change-scoped`: только файлы из `target_files`.

**Правила фильтрации (Whitelist):**
Если строка комментария подпадает под одно из правил **Whitelist** (шаг 1.1a) — игнорировать её (не считать закомментированным кодом).

**Правила фильтрации (Review Boundaries):**
При `change-scoped` — игнорировать строки, не попадающие в диапазоны `Review Boundaries` (шаг 1.3b).

Для каждого файла найти строки, начинающиеся с `//` (с учётом пробелов), которые похожи на код:
- Заканчиваются на `;`
- Содержат `Если ... Тогда`, `КонецЕсли`, `Цикл`, `КонецЦикла`
- Содержат `Процедура`, `Функция`, `КонецПроцедуры`, `КонецФункции`

Собрать список: `файл:строка` и сам текст комментария.
Сформировать блок `## Commented Code Signals (evidence)` и передать в промпт ревьювера (батчи 1a, 1b, 2).
Ревьювер обязан классифицировать их (AP-042 или dismiss).

## Шаг 1.7b. Механическая проверка: отладочный код (evidence)

Выполняется оркестратором (Grep/Read) ДО вызова агента.

**Scope:** как в 1.7.
**Фильтрация (Review Boundaries):** как в 1.7.

Искать:
- `Сообщить(`
- `ПоказатьОповещениеПользователя(` (если не в UI-модуле)
- `ЗаписьЖурналаРегистрации(` с уровнем `Отладка` или `Информация` (если не обосновано)

Сформировать блок `## Debug Code Signals (evidence)` и передать в промпт ревьювера (батчи 1a, 1b, 2).
Ревьювер классифицирует (AP-043 или dismiss).

## Шаг 1.7c. Механическая проверка: Обязательный контроль комментариев (evidence)

Выполняется оркестратором ДО вызова агента, **только если** в таблице «Обязательный контроль» (шаг 1.1a) есть строки с непустым **Regex допустимой строки**.

**Scope:** как в 1.7.
**Фильтрация (Review Boundaries):** как в 1.7.

Для каждого активного правила (ID, Regex, Уровень, kind):
1. Найти все комментарии `//…` в целевых файлах.
2. Исключить те, что подпадают под Whitelist (шаг 1.1a).
3. Проверить оставшиеся: если комментарий по смыслу подпадает под правило (например, содержит маркер `[ID#`), но **не соответствует** Regex — это сигнал нарушения.
4. Сформировать блок `## Mandatory Control Signals (evidence)`:
   ```markdown
   ## Mandatory Control Signals (evidence)
   | Rule ID | File:Line | Observed | Expected (regex) |
   |---------|-----------|----------|------------------|
   | DIR-001 | X.bsl:12 | // стандарт... | ^//\s*Required:\s*.+$ |
   ```
5. Передать в промпт ревьювера (батчи 1a, 1b, 2, 3). Ревьювер классифицирует (confirm/dismiss).

**Промпт explorer:**

«Провести архитектурный анализ расширения [имя] для предрелизного ревью. Прочитай ВСЕ указанные .bsl файлы. Выполни 5 кросс-модульных проверок:

1. **Error strategy consistency:** Найди все блоки Попытка/Исключение во всех модулях. Для каждого классифицируй стратегию: (a) лог + ВызватьИсключение, (b) лог + Возврат fallback, (c) лог + Продолжить цикл, (d) без лога (silent). Уровень: MEDIUM.

2. **Implicit contracts (ДополнительныеСвойства):** Найди все обращения к ДополнительныеСвойства: `.Вставить("ключ", ...)` и `.Свойство("ключ", ...)`. Построй матрицу: свойство → модуль-writer → модуль-reader. Если writer-модуль ≠ reader-модуль — это скрытый межмодульный контракт. Если >3 таких свойств без единого документированного реестра (комментария в шапке модуля или спецификации) — флаг. Уровень: MEDIUM.

3. **Repeated type-dispatch:** Найди все блоки `Если ТипЗнч(X) = Тип("...")`. Сгруппируй по набору проверяемых типов (например, ДеревоЗначений / ДанныеФормыДерево / ДанныеФормыКоллекцияЭлементовДерева). Если один и тот же набор типов проверяется в 3+ процедурах — флаг: кандидат на утилитную функцию. Уровень: MEDIUM.

4. **Semantic duplication:** Для каждой процедуры/функции извлеки: (a) входные сущности (типы параметров, обращения к реквизитам), (b) ключевые операции (вызовы БСП-методов, записи объектов, обращения к регистрам), (c) выходные действия (возврат, установка свойств). Найди пары процедур в разных модулях с >70% совпадением по этим признакам — кандидаты на рефакторинг в общую процедуру. Уровень: MEDIUM.

5. **Scope creep в обработчиках расширений:** Для каждого перехвата (&Перед/&После/&Вместо) определи, какую функциональность расширения он реализует (по именам вызываемых процедур с префиксом расширения). Если обработчик содержит вызовы, не связанные ни с одной функциональностью расширения (другой префикс, другой домен) — флаг: scope creep. Уровень: MEDIUM.

**Если сессия change-scoped (ЗНИ указан):** расширение анализируется **целиком**; доработки по ЗНИ затронули target-файлы: [перечислить `target_files`]. Замечания помечай тегом **`[change-scope]`** в начале строки описания **только** если они касаются `target_files` или прямого поведения ЗНИ. Файлы из `reference_files` используй только для сравнения/контекста; не считай их scope расширения и не помечай findings по ним.

Для каждого замечания укажи: файлы (все затронутые), уровень, kind=architecture, категорию (error-strategy / implicit-contract / type-dispatch / semantic-duplication / scope-creep), описание, рекомендацию. РЕЖИМ: mode=prerelease.»

## Шаг 4. Предложение openspec change / дополнение ЗНИ

Если обнаружены замечания уровня **CRITICAL**, **HIGH** или **MEDIUM** (включая kind=style, release-hygiene, architecture Tier 2):

**Маршрутизация:** если **`review_mode = change-scoped`** и **`change_in_archive = false`** — выполнить **только** раздел **4A**. Во всех остальных случаях (`full-extension` или change-scoped с ЗНИ в `archive/`) — раздел **4B**. Для 4B новый `prerelease-fix-*` предлагать только при CRITICAL/HIGH или явных release blockers; MEDIUM-only сохранять в отчёт как optional backlog suggestion без AskUserQuestion.

### 4A. `review_mode = change-scoped` и change **не** в `archive/`

**Не** предлагать создание нового `prerelease-fix-*` по умолчанию — ЗНИ уже существует.

Использовать **AskUserQuestion tool**:

> «Обнаружено N замечаний уровня CRITICAL/HIGH/MEDIUM. Добавить задачи устранения в `tasks.md` существующего change `<change-name>`? (Соблюдать [.cursor/rules/vertical-slices.mdc](../../rules/vertical-slices.mdc): если ЗНИ в slice mode — каждая группа замечаний оформляется как fix-срез `S<N+1>: Исправление prerelease-замечаний (<категория>)` либо вставляется в подходящий непринятый срез; если legacy — в подходящую секцию.)»

**Варианты:**
- Да, дополнить tasks.md
- Нет, только отчёт

**Если «Да»:** отредактировать `change_dir/tasks.md` по правилам группировки из блока **«3. Сформировать tasks.md по правилам»** (ниже), без создания нового каталога change. Сохранить отчёт в `change_dir/reports/prerelease-review-ГГГГ-ММ-ДД.md` (если каталога `reports/` нет — создать) и рядом `...-reasoning.md`.

**Если «Нет, только отчёт»:** сохранить отчёт в `change_dir/reports/prerelease-review-ГГГГ-ММ-ДД.md` (и `...-reasoning.md`) или в `temp/reports/prerelease-review-<расширение>-<change-slug>-ГГГГ-ММ-ДД.md` (и `...-reasoning.md`) по выбору пользователя.

### 4B. `review_mode = full-extension` **или** `change-scoped` с **`change_in_archive = true`**

Разделить по максимальному уровню замечаний:

- **Есть CRITICAL/HIGH или явные release blockers:** использовать **AskUserQuestion tool**:

  > «Обнаружено N замечаний уровня CRITICAL/HIGH (и M MEDIUM). Создать openspec change `prerelease-fix-<расширение-kebab>` для устранения блокеров релиза? MEDIUM войдут в tasks.md и proposal кратким списком.»

  (Для **архивного** ЗНИ причина: change уже заархивирован — новые задачи вносятся в отдельный change.)

  **Варианты:**
  - Да, создать change
  - Нет, только отчёт

- **MEDIUM-only:** **не** задавать AskUserQuestion о создании `prerelease-fix-*`. Сохранить отчёт. В отчёт добавить секцию `Backlog suggestion (optional)` со списком MEDIUM по категориям и текстом: «Можно оформить отдельный backlog change при необходимости; релизный gate не требует автоматического `prerelease-fix-*` только из-за MEDIUM.»

### Если пользователь выбрал «Да» (новый prerelease-fix change)

1. Создать новый change (имя в kebab-case, например `prerelease-fix-rg-kontur-cryptoapi`):

```bash
openspec new change "prerelease-fix-<расширение-kebab>" --schema prerelease-fix
```

Если схема `prerelease-fix` недоступна — использовать `--schema spec-driven` и создать обязательный артефакт specs по инструкции схемы.

2. Сформировать proposal (описание задачи) на основе отчёта:
   - Суть: устранение замечаний предрелизного ревью расширения `<название>`.
   - Список замечаний **CRITICAL** и **HIGH** (с указанием kind: functional / style / release-hygiene / architecture).
   - **Краткий список MEDIUM** (по категориям или перечислением) — обязателен, если такие замечания есть.
   - Ссылка на отчёт: `reports/prerelease-review-ГГГГ-ММ-ДД.md`.

3. Сформировать tasks.md по правилам (те же правила при **дополнении** существующего change в п. 4A):
   - **CRITICAL** = отдельная задача на каждое замечание (блокер).
   - **HIGH functional** = отдельная задача на каждое замечание.
   - **HIGH style** и **HIGH release-hygiene** = отдельная задача на каждое замечание (как functional) — стиль и гигиена до релиза обязательны для кода заказчику.
   - **HIGH style / HIGH release-hygiene / MEDIUM (массовые):** если замечание одного типа затрагивает >3 файлов — одна задача с подзадачами по файлам (чекбоксы-подпункты). Пример:
     ```markdown
     - [ ] **2.2** [HIGH/style] Разметка #Область
       - [ ] CommonModules\РаботаСЭП\Ext\Module.bsl
       - [ ] CommonModules\РаботаСКартинками\Ext\Module.bsl
       - [ ] ...
     ```
   - **Все остальные MEDIUM** (включая kind=architecture из Tier 2) — каждая находка в **tasks.md** (отдельная задача или группировка по категории, 1 задача на категорию при множестве однотипных).
   - **LOW** — одна групповая задача «Технический долг».
   - **Неиспользуемый и устаревший код (группировка):**
     - `unused-code` (>3 процедур/функций): одна задача «Удалить неиспользуемый код» с подзадачами по файлам.
     - `obsolete` (>3 процедур/функций): одна задача «Вычистить устаревший код» с подзадачами.
     - Единичные unused/obsolete — отдельными задачами по обычным правилам уровня HIGH/MEDIUM.
   - **Пустые процедуры и функции (группировка):**
     - `empty-unused` (>3 штук): одна задача «Удалить пустые неиспользуемые процедуры и функции» с подзадачами по файлам (чекбоксы по каждому файлу или по каждой процедуре).
     - `empty-handler`: для каждого — отдельная задача «Удалить пустую процедуру <Имя> из <путь к Module.bsl>». Если у обработчика есть привязка в форме — добавить к задаче или в отдельный артефакт **инструкцию ручного конфигурирования** по шаблону из `.cursor/rules/1c-xml-write-guard.mdc`: **Форма:** <полное имя формы>, **Конфигурация/расширение:** <имя>. **Действия в Конфигураторе:** 1) Открыть форму; 2) Найти элемент/событие, к которому привязан обработчик <Имя>; 3) Удалить привязку обработчика события. **После выгрузки:** в Form.xml исчезнет соответствующий атрибут события у элемента.
   - Удаление кода в .bsl выполняется при `/opsx:apply` через onec-code-writer; Form.xml не править — только инструкция пользователю.

   Формат задачи (одиночное замечание):
   ```markdown
   - [ ] [CRITICAL] Файл:строка — Категория: Описание. Рекомендация.
   - [ ] [HIGH] [functional] Файл:строка — ...
   - [ ] [HIGH] [style] Файл:строка — ...
   - [ ] [HIGH] [release-hygiene] Файл:строка — ...
   - [ ] [MEDIUM] [architecture] Описание (Tier 2) — ...
   ```

4. Сохранить отчёт ревью в `openspec/changes/prerelease-fix-<расширение>/reports/prerelease-review-ГГГГ-ММ-ДД.md` (и `...-reasoning.md`).

5. Сообщить пользователю:
   - Название созданного change.
   - Количество задач в tasks.md.
   - Следующий шаг: `/opsx:apply prerelease-fix-<расширение>`.

## Граничные случаи

- **Замечаний нет**: сообщить «Замечаний, блокирующих релиз, не найдено. Расширение готово к релизу.»
- **Только LOW**: предложить создать задачу технического долга или пропустить.
- **Нет спецификации расширения**: выполнить ревью с общими правилами; в отчёте отметить, что проверка соответствия спецификации не выполнена.
- **Нет активного change** (`full-extension`): ревью выполняется в standalone-режиме; отчёт сохранить в `temp/reports/prerelease-review-<расширение>-ГГГГ-ММ-ДД.md`.
- **Change-scoped: каталог change не найден** после поиска в `openspec/changes/` и `openspec/changes/archive/`: СТОП; вывести список доступных имён (по подкаталогам с `tasks.md`).
- **Change-scoped: в `tasks.md` нет `[x]`**: предупредить; предложить **`full-extension`** или СТОП (см. шаг 1.3a).
- **Change-scoped: после architecture/tasks/design + git fallback список `target_files` пуст**: предупредить; предложить **`full-extension`** или СТОП.
- **Change-scoped: есть `ambiguous_files` после suffix matching**: Scope Preview + AskUserQuestion (продолжить с найденным scope / full-extension / остановиться).
- **Change-scoped: пути вне `cfe/<расширение>`**: классифицировать как `reference_files`; передавать только read-only context, не включать в findings.
- **Замечаний нет при `change-scoped`**: шаг 4 не применять; отчёт сохранить в `change_dir/reports/` или `temp/reports/` по согласованию с пользователем.
- **Linter недоступен**: warning в Summary, продолжить ревью.
- **Reviewer выдал `prompt_contract_version mismatch`**: warning в Summary, продолжить (fail-open).
- **`## Investigation Request` непуст**: залогировать warning, сохранить список в отдельный файл (шаг 2.6).

## Self-check (Conversational Discipline)

Перед выводом финального сообщения пользователю проверить:
1. **Acknowledgement:** первая строка ответа была «Понял: запускаю предрелизное ревью...» (шаг 0).
2. **Карточка 4 слота:** сводка выведена строго в 4 слота (Что отрецензировано / Итог / Что важно / Куда дальше).
3. **Risk Surfacing:** слот «Что важно» заполнен (ограничения change-scoped или full-extension).
4. **Honest Subagent:** сбои агентов названы честно (`failed` / `interrupted-by-user`), без выдуманных причин.
5. **HALT-жаргон:** в чате нет CRITICAL/HIGH/MEDIUM/LOW, нет внутренних ID.
6. **Полный отчёт:** счётчики и технические детали сохранены в файл `reports/prerelease-review-*.md`.
