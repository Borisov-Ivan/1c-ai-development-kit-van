Провести полное подробное ревью кода в объёме по контексту запроса пользователя, делегировать ревью **onec-code-reviewer**, сохранить отчёт, затем по подтверждению пользователя передать замечания **onec-code-writer** для устранения с обязательным повторным ревью (макс. 2 итерации).

**Input**: путь к модулю (.bsl), каталог, список файлов, имя расширения, имя ЗНИ (каталог `openspec/changes/<name>`), «текущий файл», либо **без аргументов** (тогда scope — изменения `.bsl` в рабочем дереве git).

**Review Focus Level:** `full` — ревью всего указанного кода в файлах; `diff-focused` — замечания только в изменённых процедурах/функциях и `[module-level]` участках (см. шаг 1.5 и `onec-code-reviewer.md`, Review Boundaries).

---

## Шаг 1. Resolve scope

Определить scope по **приоритету** (первое совпадение из контекста запроса пользователя). Зафиксировать **`review_focus`** глобально и/или **пофайлово** (см. шаг 1.5).

| Вход пользователя | Действие | `review_focus` |
|-------------------|----------|----------------|
| **Явные пути** к `.bsl` или каталогу | Нормализовать относительно корня репо; для каталога — все `*.bsl` под ним (Glob). | `full` |
| **Текущий/открытый файл** («ревью этого модуля», `review current file`) | Путь из IDE; файл должен быть `.bsl`. | `full` |
| **Расширение** (имя папки cfe или «ревью расширения X») | `openspec/project.md` → пути cfe; Glob `*.bsl` в каталоге расширения. | `full` |
| **Имя ЗНИ / каталог change** (`openspec/changes/<name>`, `.../archive/<name>`, или явное имя в тексте) | Валидировать `tasks.md`. Список файлов: как в prerelease-review шаг 1.3a — только задачи `[x]`, пути из `` `src/...bsl` `` + наследование «тот же файл» в секции `##`. При пустом списке — git-fallback по slug (как prerelease 1.3a). | `diff-focused` |
| **Без аргументов / scope неясен** | `git diff --name-only HEAD` ∪ `git diff --name-only --cached`, оставить пути, оканчивающиеся на `.bsl`, существующие в рабочем дереве. | Если список не пуст → `diff-focused` (**рабочее дерево vs HEAD**). Если пуст → **AskQuestion**: указать файл/каталог, расширение, имя ЗНИ или подтвердить полное ревью с явным scope. |

**Активный change без явного scope:** если пользователь выбирает «только файлы change» — трактовать как **diff-focused**: файлы из `git diff --name-only HEAD` ∪ `--cached`, фильтр `*.bsl` и (по возможности) каталог расширения из `design.md`; при пустом diff — парсинг `tasks.md` на пути `.bsl` для задач `[x]`. Вариант «всё расширение» — **`full`** (все `.bsl` расширения).

**Валидация:** пути существуют, расширение `.bsl`. Исключить удалённые-only файлы из списка ревью (нечего читать).

**Итог шага:** список путей к `.bsl` + для каждого файла черновик режима (`full` | `diff-focused`); окончательно уточняется в шаге 1.5.

## Шаг 1.5. Diff extraction и procedure mapping (при `diff-focused`)

Выполнять для файлов, которым назначен **`diff-focused`**. Для **`full`** — шаг пропустить (секцию `## Review Boundaries` в промпт **не** вставлять).

### 1.5.1 Baseline для `git diff`

1. **Рабочее дерево (без аргументов, есть незакоммиченные `.bsl`):** взять объединение диффов `git diff HEAD -- <file>` и `git diff --cached -- <file>` для каждого файла. В описании baseline указать: `working tree vs HEAD (+ index)`.
2. **Ветка ≠ основной:** определить основную ветку: `main`, иначе `master`, иначе `origin/main`. `BASE=$(git merge-base <main> HEAD)`; затем `git diff $BASE..HEAD -- <files>`. В baseline указать: `merge-base <main>..HEAD = <hash>`.
3. **На основной ветке + scope по ЗНИ:** из имени change извлечь slug (как prerelease 1.3a); `git log --oneline --grep="<slug>"` (и варианты); по коммитам, затрагивающим `change_files`, построить диапазон: `git diff <parent_самого_раннего_релевантного>^..HEAD -- <files>` или согласованный диапазон; если коммиты не найдены — fallback п.4.
4. **Fallback:** `git log --oneline -10 -- <file>`; **AskQuestion** выбрать baseline-коммит или перейти на **`full`** для затронутых файлов с предупреждением в сводке.
5. **Пустой diff при ненулевом списке файлов из ЗНИ:** предупредить; предложить **`full`** по этим файлам или уточнить baseline (п.4).

### 1.5.2 Новый файл в diff

Если для файла дифф показывает **новый файл** (`new file mode` / `from /dev/null`) — для этого файла выставить **`per_file_focus = full`** (весь файл в зоне изменений); в `## Review Boundaries` для него: `Focus: full`.

### 1.5.3 Извлечение номеров строк в текущей версии

Из unified diff для каждого файла собрать множество номеров строк **новой** версии, которые соответствуют строкам с префиксом `+` (добавления/замена), не считая `+++`. Учитывать заголовки `@@ -a,b +c,d @@`: вести счётчик строки в новом файле по контексту и `+`.

### 1.5.4 Маппинг на процедуры BSL

Для каждого файла прочитать текущее содержимое. Построчно найти границы методов regex-ом (упрощённо): начало `^\s*(Процедура|Функция)\s+(\w+)`; конец `^\s*КонецПроцедуры\b` / `^\s*КонецФункции\b` (без учёта вложенности — в BSL нет вложенных процедур). Каждую изменённую строку из п.1.5.3 отнести к процедуре/функции, в диапазон которой она попадает, иначе — **`[module-level]`** с диапазоном строк соседних изменённых строк.

**Результат по файлу:** список `{kind: Процедура|Функция, name, startLine, endLine}` + опционально `[module-level]` диапазоны.

### 1.5.5 Сборка секции `## Review Boundaries` для промпта

Вставить в промпт ревьювера (перед `## Reasoning focus` в шаблоне):

```markdown
## Review Boundaries

### Файл: <нормализованный путь>
Focus: full | diff-focused
Baseline: <краткое описание из п.1.5.1>

#### Изменённые процедуры/функции (только при Focus: diff-focused)
- Процедура Имя (строки N–M)
- Функция Имя2 (строки N–M)
- [module-level] (строки N–M) — кратко что изменено, если уместно

#### Unified diff (контекст; усечь при переполнении контекста)
\`\`\`diff
<фрагмент unified diff по этому файлу>
\`\`\`

### ИНСТРУКЦИИ (для ревьюера)
1. Читай файл целиком для контекста.
2. Замечания (включая Phase 0, Phase 2.5, категорию 15 unused/obsolete) — **только** внутри перечисленных границ; при `Focus: full` на файл границ по процедурам нет.
3. Не рефакторить и не «полировать» код вне границ (при diff-focused).
4. Нарушение контракта, влияющее за пределы границ — только `[BOUNDARY_EXCEPTION]` с обоснованием.
```

Для батча с **смешанными** файлами повторить подзаголовок `### Файл: ...` для каждого файла. Если **все** файлы в батче `full` — секцию `## Review Boundaries` **не** добавлять.

Сохранить собранный блок в памяти сессии для повторных вызовов ревьювера (шаги 3.5 и 6).

## Шаг 2. Контекст для ревьювера

- Прочитать `.cursor/rules/1c-coding-standards.mdc`. Ссылка на `.cursor/agents/onec-code-reviewer.md` для категорий, Phase 0 и **Review Boundaries Protocol**.
- Сформировать бриф:
  - Список файлов (пути).
  - Стандарты: 1c-coding-standards.mdc.
  - Задача: «Полный подробный ревью (все категории). Без mode=prerelease.» + при `diff-focused`: «Соблюдать секцию ## Review Boundaries (замечания только в границах).»
  - Для scope «расширение» (`full`): префикс расширения и полная директория расширения (для Grep при проверке неиспользуемого кода).
  - При **`diff-focused`:** вставить в промпт блок **`## Review Boundaries`** из шага 1.5 **только для файлов, входящих в данный вызов/батч**.
- **Архитектурный контекст (Architectural Context):**
  - Если ревью выполняется в рамках ЗНИ (`openspec/changes/<name>`), проверить наличие файлов `design.md` и `reports/architecture-*.md` в каталоге ЗНИ.
  - Если файлы найдены, прочитать их (или извлечь ключевые выдержки/целевую модель) и передать в промпт ревьювера в секцию `## Architectural Context`.
- **Для файлов с `&ИзменениеИКонтроль`:** прочитать `openspec/project.md`, взять путь к cf из секции «Структура репозитория». В пути к файлу расширения заменить сегмент `cfe/<ExtName>/` на путь к cf из project.md, сохраняя тот же родительский корень — получить полный base-путь. Передать в промпт reviewer: «Base-файл (для &ИзменениеИКонтроль): <полный путь к base>» по файлу (EXTENSION GATE из `1c-agent-delegation.mdc`).

## Шаг 3. Делегирование ревью

Вызвать **Task**(`subagent_type="onec-code-reviewer"`) с промптом по шаблону «Reviewer (ревью кода)» из `.cursor/skills/1c-agent-patterns/SKILL.md`:

- Файлы: список из шага 1 (для батча — подмножество).
- Стандарты: 1c-coding-standards.mdc.
- Диагностики линтера: «линтер не выявил ошибок» (до правок линт не запускался).
- Base-файл(ы): из шага 2 для файлов с &ИзменениеИКонтроль.
- **Review Boundaries:** при `diff-focused` — блок из шага 1.5, отфильтрованный по файлам батча; при полном `full` батче — не вставлять.
- **Resolved Contracts:** если это повторный вызов после шага 3.5 (Investigation Loop) — включить блок `## Resolved Contracts` из результата explorer. При первом вызове — без Resolved Contracts.
- Включить блоки: Reasoning focus (Phase 0), Стандартный фокус, Проверка соблюдения gates (HALT-compliance), Зрелость интеграции.
- **Не** передавать mode=prerelease.

**Батчи:** если файлов больше 5–8 — разбить на батчи по 5–8 файлов, запускать вызовы reviewer параллельно где возможно. Для каждого батча формировать **свой** фрагмент `## Review Boundaries` (только файлы батча). Итоговый список замечаний — объединение выводов всех батчей с дедупликацией по «файл:строка:категория».

## Шаг 3.5. Investigation Loop (резолв контрактов по запросу ревьювера)

1. **Парсинг:** в выводе ревьювера искать секцию `## Investigation Request`. Если секция отсутствует — пропустить шаг, перейти к шагу 4.
2. **Если секция есть:** извлечь таблицу (Метод, Контекст вызова, Что нужно определить).
3. **Вызов explorer:** один вызов **Task**(`subagent_type="onec-code-explorer"`) по глубокому шаблону «Explorer — contract resolution (deep)» из `.cursor/skills/1c-agent-patterns/SKILL.md`. Передать всю таблицу из Investigation Request одним батчем. Explorer возвращает блок `## Resolved Contracts`.
3a. **Сохранение артифакта.** Сохранить полный вывод explorer (блок `## Resolved Contracts` + Evidence + вердикт) в файл:
   - При активном change: `openspec/changes/<id>/reports/resolved-contract-<scope-slug>-YYYY-MM-DD.md`
   - Без change: `temp/reports/resolved-contract-<scope-slug>-YYYY-MM-DD.md`
   Формат содержимого: заголовок (дата, scope, цель), затем блок Resolved Contracts целиком от explorer. Это артифакт ЗНИ — доступен в следующих сессиях.
4. **Повторное ревью:** вызвать **Task**(`subagent_type="onec-code-reviewer"`) — тот же scope (шаг 1), тот же контекст (шаг 2) + блок `## Resolved Contracts` из сохранённого файла (шаг 3a) + при наличии тот же блок `## Review Boundaries`, что и в первом прогоне (шаг 1.5). Промпт: «Повторное ревью с Resolved Contracts. Обновить Phase 2.5 (Defensive Checks, Попытка Audit), Contract Map и findings. Секцию Investigation Request НЕ включать.»
5. **Максимум 1 итерация:** investigation loop выполняется не более одного раза (reviewer → explorer → reviewer). После второго прогона ревьювера — перейти к шагу 4 в любом случае.

**Сохранение отчёта первого прогона:** первый отчёт (с Investigation Request) сохраняется с суффиксом `-initial` в имени файла. Итоговый отчёт (после investigation loop) сохраняется без суффикса в шаге 4.

## Шаг 4. Отчёт

- Сохранить **полный** вывод reviewer в файл (собственное правило скилла; `preserve-subagent-reports.mdc` не применяется к reviewer):
  - При активном change: `openspec/changes/<id>/reports/review-<scope-slug>-YYYY-MM-DD.md`.
  - Иначе: `temp/reports/review-<scope-slug>-YYYY-MM-DD.md`.
  - `<scope-slug>` — короткий идентификатор (например имя модуля, имя расширения или `change-<id>`); YYYY-MM-DD — текущая дата.
- При выполненном шаге 3.5 — в reports/ также сохранён `resolved-contract-*.md` (артифакт ЗНИ). Упомянуть путь в сводке пользователю.
- Вывести пользователю сводку: количество замечаний по уровням (CRITICAL, HIGH, MEDIUM, LOW), разделение на кодовые и архитектурные (если reviewer явно пометил), путь к полному отчёту.

## Шаг 5. Предложение устранить

Если есть кодовые замечания (уровни critical / high / medium / low) или замечания REFACTOR:

**AskQuestion:** 
1. Если есть MUST_FIX: «Устранить дефекты через onec-code-writer? (Да / Нет, только отчёт)»
2. Если есть REFACTOR (и нет MUST_FIX, или после их исправления): «Код работает, но ревьювер нашел N «запахов кода» (Action: REFACTOR). Запустить агента onec-code-simplifier для рефакторинга и наведения красоты? (Да / Нет)»

- **Нет** — перейти к шагу 7 (Итог), не вызывать агентов.
- **Да** — перейти к шагу 6.

Если кодовых замечаний и замечаний REFACTOR нет — перейти к шагу 7.

---

## Шаг 6. Устранение (при «Да»)

- **Архитектурные замечания** (Type: ARCHITECTURE) — не передавать writer/simplifier. Вывести их списком пользователю с пометкой, что для них нужны отдельные решения.
- **MUST_FIX замечания** — отфильтровать: передавать writer ТОЛЬКО замечания, у которых одновременно **Action: MUST_FIX** И **Type: CODE**. 
- **REFACTOR замечания** — передавать **onec-code-simplifier** ТОЛЬКО замечания с **Action: REFACTOR**.

**Порядок устранения:**
1. Сначала исправить MUST_FIX через `onec-code-writer`.
2. Затем (если пользователь согласился) выполнить рефакторинг через `onec-code-simplifier`.

**Чеклист перед вызовом writer/simplifier (если был шаг 3.5):**
- Файл `reports/resolved-contract-*.md` существует (сохранён на шаге 3a).
- Полный блок `## Resolved Contracts` из этого файла включён в промпт агента.
- Без блока вызов агента **не выполнять** для замечаний, затрагивающих контракты из Investigation Request.

Для каждого затронутого файла:
  1. **Для MUST_FIX:** Вызвать **Task**(`subagent_type="onec-code-writer"`) по шаблону **«Writer — review fix»** из `.cursor/skills/1c-agent-patterns/SKILL.md`. 
  2. **Для REFACTOR:** Вызвать **Task**(`subagent_type="onec-code-simplifier"`) по шаблону **«Simplifier (рефакторинг кода)»**. Передать замечания REFACTOR.
  3. **LINT GATE:** ReadLints по изменённым .bsl. При ошибках — исправить (повторный writer/simplifier или точечная правка), затем снова ReadLints.
  4. **API EXISTENCE CHECK:** по правилам из `1c-agent-delegation.mdc` (секция API EXISTENCE CHECK) проверить новые вызовы вида `МодульИмя.МетодИмя(` в diff. При WARNING — AskQuestion пользователю.
  5. При наличии `&ИзменениеИКонтроль` в файле — **EXTENSION VERIFICATION** (сравнение кода вне #Вставка/#Удаление с base в cf/). При расхождении — вернуть агента на исправление.
  6. Вызвать **Task**(`subagent_type="onec-code-reviewer"`) по изменённым файлам: передать контекст «ревью после устранения замечаний по отчёту /review», вывод линтера, base-пути при необходимости. Передать в промпт reviewer блок `## Resolved Contracts` из файла `reports/resolved-contract-*.md` (если был). **Пересобрать `## Review Boundaries`:** заново выполнить шаг 1.5 только для изменённых файлов (diff после агента) или временно использовать прежние границы + пометить в промпте, что код мог сместиться — предпочтительно пересчитать diff и процедуры.
- При новых замечаниях после первого ревью — повторить цикл writer/simplifier → LINT → API CHECK → (EXTENSION VERIFICATION) → reviewer. **Максимум 2 итерации** (первое устранение + один повтор). После этого перейти к шагу 7 даже при оставшихся замечаниях.

## Шаг 7. Итог

- Краткое резюме: что отрецензировано (scope), сколько замечаний устранено, путь к полному отчёту.
- Не устранённые архитектурные замечания — списком.
- Если выявлены архитектурные замечания, сообщите пользователю: «Выявлены архитектурные проблемы, которые не могут быть исправлены кодером автоматически. Рекомендуется запустить `/opsx:explore` или `/opsx:debug` для вызова архитектора, пересмотра `design.md` и обновления плана задач».

## Интеграция

- **command-skill-gate.mdc:** первый и единственный инструмент в первом батче — Read этого скилла.
- **command-session-persistence.mdc:** протокол действует на каждом ходе сессии /review (resolve scope → review → report → ask fix → fix loop).
- **bsl-write-guard / 1c-agent-delegation:** правки .bsl только через onec-code-writer; после правок — обязательный onec-code-reviewer; LINT GATE и API EXISTENCE CHECK после writer; EXTENSION GATE и EXTENSION VERIFICATION при &ИзменениеИКонтроль. **Investigation Loop** (шаг 3.5) — reviewer запрашивает исследование контрактов, оркестратор делегирует explorer, перезапускает ревью с Resolved Contracts. Формат и шаблон — секция CONTRACT RESOLUTION в `1c-agent-delegation.mdc`.
- **Review Focus Boundaries:** при `diff-focused` оркестратор формирует `## Review Boundaries` (шаг 1.5); ревьювер следует `onec-code-reviewer.md` (Review Boundaries Protocol).
- **APPLY GATE:** вызов writer и reviewer в рамках /review разрешён без /opsx:apply — см. исключение в `.cursor/rules/1c-agent-delegation.mdc` (секция APPLY GATE).

## Граничные случаи

- **Замечаний нет:** сообщить «Замечаний не найдено», указать путь к сохранённому отчёту.
- **Только архитектурные:** предложение устранить не показывать; вывести список архитектурных замечаний и перейти к шагу 7.
