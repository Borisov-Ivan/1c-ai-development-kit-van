# Улучшение качества verify: анализ по существу

## Проблема

Verify выполняет механические проверки (чекбоксы, Grep по маркерам размытости, наличие architecture-отчётов), но пропускает семантические дефекты:

- Задачи описывают логику, но не UI/форму — непонятно, что именно реализовывать
- «Создать» в tasks, когда объект уже есть в репозитории
- Неразрешённые альтернативы через `/` (не только «или»)
- Нет проверки, что design содержит исчерпывающие инструкции для ручных шагов (метаданные, формы)

## Принцип

- **Описание формы** (элементы, группы, таблицы, команды, UX-сценарий) — в design.md. Задача ссылается на секцию design, а не дублирует.
- **Ручная конфигурация** (создание метаданных, добавление реквизитов, форм) — в design.md с исчерпывающими инструкциями: имена, типы, длины, порядок, подсистемы. Пользователь должен по design создать объект без дополнительных вопросов.
- **Архитектор** привлекается verify не только для gate-проверки (триггеры сработали/нет), а для **ревью полноты задач для реализации** — может ли writer/form-generator реализовать задачу без дополнительных вопросов.

## Изменение 1: verify SKILL.md — новый шаг «Manual Configuration Sufficiency» (после шага 7)

Между шагами 7 (Task Quality) и 8 (Architect Gate) добавить **шаг 7.5: Проверка полноты ручных конфигурационных инструкций**.

Логика:

- Grep tasks.md на маркеры ручной конфигурации: `создать в расширении`, `добавить форму`, `создать обработку`, `создать регистр`, `добавить реквизит`, `создать справочник`
- Для каждого найденного: проверить в design.md наличие соответствующей секции Decision с:
  - Для **метаданных** (РС, справочник, документ, обработка): имена, типы, длины полей, измерения, ресурсы, подсистема
  - Для **формы**: описание элементов (группы, поля, таблицы с колонками, команды/кнопки), UX-сценарий (шаги пользователя)
  - Для **реквизитов**: имя, тип, длина, назначение
- Если описание в design отсутствует или неполно: **CRITICAL** — «Задача N.M требует ручной конфигурации, но в design.md нет исчерпывающих инструкций для: [список]. Рекомендация: дополнить design секцией с полным описанием.»
- Файл: `[.cursor/skills/openspec-verify-change/SKILL.md](.cursor/skills/openspec-verify-change/SKILL.md)`, вставка после шага 7D

## Изменение 2: verify SKILL.md — проверка «Tasks vs Repo Consistency»

Добавить в шаг 7 (Task Quality) подшаг **7E: Repo Consistency**:

- Для задач с маркером «создать» (РС, обработку, справочник, форму): Glob по репозиторию на наличие объекта с указанным именем
- Если объект **уже существует**: WARNING — «Задача N.M говорит "создать X", но X уже существует в репозитории (путь). Уточнить: "доработать" / "наполнить содержимым"?»

## Изменение 3: verify SKILL.md — расширить детекцию неразрешённых альтернатив

В шаге 7C (Ambiguity markers) добавить паттерны:

- `Неопределено/пуст` — CRITICAL: какой контракт возврата?
- `X или Y` в контексте «вернуть» / «использовать» — уже ловится, но добавить: когда рядом стоят глаголы действия + `/` между существительными → WARNING
- Ссылку задачи на другую задачу без зафиксированного решения (напр. 5.1 «добавить X или получать Y») — тот же паттерн «или» между глаголами действия

## Изменение 4: verify SKILL.md — привлечение архитектора для ревью полноты задач

В шаге 16 (Remediation) добавить новый тип ремедиации:

**При наличии CRITICAL/WARNING из шагов 7.5 (Manual Config) или множественных 7B/7C:** предложить запустить **onec-code-architect** с фокусом: «Ревью полноты задач для реализации»:

- Может ли writer реализовать каждую кодовую задачу без дополнительных вопросов?
- Может ли form-generator/пользователь создать форму/метаданные по описанию в design?
- Все ли альтернативы разрешены?
- Совпадает ли «создать/доработать» с реальным состоянием репозитория?

Отчёт сохранять в `reports/task-quality-review-YYYY-MM-DD.md`.

## Изменение 5: architect-gate.mdc — новый Design Completeness триггер

В секцию **DESIGN REVIEW ТРИГГЕРЫ** добавить:

- **Триггер:** Grep tasks.md на маркеры ручной конфигурации (`создать в расширении`, `добавить форму`, `создать обработку`, `создать регистр`)
- **Как проверить:** Grep tasks.md + проверка наличия в design.md секций с полным описанием (имена, типы, элементы формы)
- **Действие:** если tasks содержат ручную конфигурацию, а design не содержит исчерпывающих инструкций → WARNING в отчёте verify; при ремедиации → architect с фокусом на Design Completeness

Файл: `[.cursor/rules/architect-gate.mdc](.cursor/rules/architect-gate.mdc)`

## Не меняем

- Шаги 6 (Format), 8-11 (Gates), 12-14 (Post-apply) — без изменений
- Механические проверки (чекбоксы, нумерация) — работают, не трогаем
- Архитектурный gate (architecture-*.md) — работает, не дублируем
