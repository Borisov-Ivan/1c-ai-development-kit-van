## 1. Покрытие — что кит уже требует

Карта «тезис статьи → механизм кита». Суть требования — коротко; путь — якорь.

### 1.1. Контроль: человек может сказать модели «нет», код не появляется «с потока»

| Механизм | Файл | Суть |
|----------|------|------|
| Архитектура до кода | `.cursor/rules/sdd-workflow.mdc` | Поток: исследование → постановка → проверка постановки → код по срезам → приёмка. Принцип: «Архитектура до кода: design.md ревьюируется … до реализации». |
| Запрет писать код вне реализации ЗНИ | `.cursor/rules/1c-halt-triggers.mdc` § APPLY GATE | Writer/ревью кода и прямая правка модулей — только в команде реализации. Есть постановка, команды реализации нет → стоп. |
| Оркестратор не диктует «как писать» | `.cursor/rules/1c-writer-pipeline.mdc` § ПРОМПТ WRITER | В промпт на код — задача, контракты, пути, ожидаемое поведение. Запрещены рецепты (`Попытка`, `ТипЗнч()`, структура кода). |
| Стандарты сильнее постановки | `.cursor/agents/onec-code-writer.md` G20 | Если постановка предписывает антипаттерн — остановка, конфликт вызывающему, не «сделать как в design». |
| Метаданные не рисует ИИ | `.cursor/rules/1c-no-metadata-creation.mdc` | XML объектов, новые каталоги метаданных, модули в несуществующих объектах — запрет. Нет объекта → пауза человеку: создать в Конфигураторе, выгрузить, продолжить. |
| Развилка до кода, не обход проверки | `.cursor/docs/chat-lexicon.md` (слой вариантов) + шаблон challenge | Вариант = разница в коде или в наблюдаемом поведении. «Кодить сейчас / отложить проверку / принять риск как равноправный путь» — не развилка архитектора. |
| Приёмка среза человеком | `.cursor/rules/vertical-slices.mdc` | После кода среза — пауза. Человек принимает сценарий в базе, отклоняет или фиксирует дефект. Агент сам не ставит «принято». |
| Открытая развилка блокирует вход в реализацию | `.cursor/skills/openspec-apply-change/SKILL.md` | Если в последней проверке постановки остался нерешённый выбор — на входе реализации карточка «что решить», ждать ответа. |

Это прямой ответ на «вайбкодинг = контроль исчез, потому что некому сказать нет»: кит разделяет **постановку**, **код**, **приёмку** и даёт человеку точки отказа (срез, метаданные, развилка, конфликт со стандартом).

### 1.2. Не демо функции, а система: границы, модель, контракты, что отложить

| Слой статьи | Механизм | Файл | Суть |
|-------------|----------|------|------|
| Границы / не изобретать параллельную систему | Preference Hierarchy + антипаттерны Shadow Storage, Parallel Workflow, API Bypass, Substituted Authority | `.cursor/rules/existing-mechanism-priority.mdc` | Сначала штатный механизм базы/БСП, потом расширение точки, потом паттерн базы, и только с обоснованием — свой контур. Без обследования интеграции — стоп, сначала обследование кода. |
| Границы охвата хука | Identity Filter Gate + AP-055 | `architect-gate.mdc`, `existing-mechanism-priority.mdc`, `openspec/specs/hardcode-justification-gate/spec.md` | Список имён форм/объектов в хуке **не** выбранный вариант, пока нет секции `## Hardcode Justification` (фильтр уже у callee? набор закрыт навсегда? план N+1?). «Временно на первый релиз» не закрывает. Writer (G21) не реализует список без секции. |
| Модель данных | Карта объектов в отчёте архитектора + запрет создания XML | `onec-code-architect.md` Implementation Map; `1c-no-metadata-creation.mdc` | Архитектор перечисляет, что создать/изменить. Физическое создание — человек в Конфигураторе. ИИ не подделывает UUID. |
| Контракты поведения | `## Behavior Contract` в design | `openspec-new-change/SKILL.md` Artifact Creation Guidelines | Наблюдаемое поведение, инварианты, условия вкл/выкл — не имена процедур, пока они не подтверждены кодом. |
| Контракты данных | Data Contract Gate | `onec-code-architect.md` Phase 2 п.7; writer G14 | Защитные `Свойство`/`ТипЗнч` не ставятся «на всякий случай» при фиксированном контракте. |
| Наблюдаемость для приёмки (не прод-мониторинг) | Спеки + вертикальность среза | `.cursor/rules/openspec-specs-gate.mdc`; `vertical-slices.mdc` критерии 8 / 8b / 9 | Сценарий описывает, что видит пользователь в базе, не «вызвать функцию в отладчике». Срез без пользовательского исхода запрещён как отдельная точка приёмки. |
| Что отложить | `## Goals / Non-Goals`, Follow-up вне срезов, Lite | `architect-gate.mdc` (чтение Non-Goals у архива); `vertical-slices.mdc` карта non-scenario; `sdd-workflow.mdc` порог ≤5 задач | Явный «не в этой ЗНИ»; архитектурный замер — Follow-up, не приёмка среза. |
| Стоимость изменения / простота | Simplicity Check | `architect-gate.mdc`; шаблон в `onec-code-architect.md` | ≥2 варианта или доказательство «единственный viable»; выбран самый простой исполнимый; бюджет сложности (файлы, хуки, ветки). |
| Альтернативы в постановке | `## Implementation Options` | `openspec-new-change/SKILL.md` | Для UI, интеграций, перехватов: A/B, выбранный, почему проще, что отклонено. |
| Не ломать прошлое молча | Precedent Regression + Blast Radius | `.cursor/rules/precedent-regression-gate.mdc`; `.cursor/rules/adr-format.mdc` | Отмена архивного требования / несущего решения — только с секцией «что потеряет пользователь 1С», альтернативами и обоснованием. |

### 1.3. «Готово» в терминах кита (не SaaS)

Статья: понятно, проверяемо, наблюдаемо, разворачивается повторяемо, предсказуемые сбои, следующая задача не раскопки.

| Критерий статьи | Аналог кита | Насколько жёстко |
|-----------------|-------------|------------------|
| Понятно | `proposal` / `design` / отчёт архитектора / ADR | Процесс сильный; долгоживущая запись решения — в основном **после** архивации ЗНИ |
| Проверяемо | delta-спеки, `S<N>.accept`, проверка постановки до кода | Спеки и приёмка среза — жёстко; проверка постановки **не** закрывает вход в код (см. §2) |
| Наблюдаемо | black-box сценарий в базе (форма, проводка, ЖР как исход приёмки) | Жёстко для **приёмки среза**. Это не наблюдаемость промышленной базы (метрики, алерты) |
| Повторяемый выкат | пауза «создай объект в Конфигураторе и выгрузи»; маркеры автора в коде | Повторяемость **разработки в git + Конфигуратор**, не выкат на прод-контур заказчика |
| Предсказуемые failure modes | шаблон Error Handling / права / блокировки у архитектора | Есть в шаблоне отчёта (с порога «средняя сложность»); **нет** отдельного гейта «без failure modes — нельзя в код» |
| Следующая задача не раскопки | ADR при архиве, KB-факты, прецеденты, маркеры в коде, `project.md` | Сильно для **процесса кита**; в этом репозитории KB ещё не развёрнута |

Вертикальные срезы прямо бьют в «демо показывает функцию»: запрещён фундамент-срез с приёмкой «ревью API», пока пользовательский исход живёт в следующем срезе (`foundation-slice-with-gate`).

Петля приёмки (патчи по кругу без подписанного среза) → обязательный редизайн архитектором (`vertical-slices.mdc` § детектор петли; `architect-gate.mdc` триггер). Это защита от «ещё один вайб-патч» вместо смены подхода.

### 1.4. Цена ранней архитектурной ошибки

| Механизм | Файл | Суть |
|----------|------|------|
| Несущие решения | `adr-format.mdc` статус Load-Bearing, `Protects-invariants` | Последующие ЗНИ не отменяют молча; замена — Blast Radius |
| Извлечение инвариантов | archive шаг 5.5.b, режим `invariant-extraction` | После ЗНИ: несущее ADR vs факт базы знаний vs отклонить |
| Независимый удар по постановке | verify, режим `design-challenge` | Три вопроса: та ли проблема, оптимален ли путь, согласился бы с холодной головой. ≥2 альтернативы, не упомянутые в постановке |
| Почему-почему-почему до фикса | `.cursor/rules/verified-cause-gate.mdc` | Гипотеза без плана проверки — стоп. UX/системный масштаб → архитектор до кода |
| Согласованность расширения scope | extend + `architecture-extend-coherence-*.md` | Обычный старый отчёт архитектора **не** закрывает drift scope |

### 1.5. Вопросы подрядчику: кто принимает решения и как они живут

| Вопрос статьи | Что есть в ките |
|---------------|-----------------|
| Кто принимает архитектурные решения? | **Не одна роль.** Агент-архитектор предлагает Chosen и срезы. Оркестратор запускает гейты и не пишет прикладной код. Человек: подтверждает срезы, создаёт метаданные, принимает сценарий в базе, отвечает на развилки, может легально обойти архитектора флагом. Имени «архитектор заказчика» в metadata ЗНИ нет. |
| Как документируются? | На ЗНИ: `design.md` (Rationale, Existing Mechanisms, Behavior Contract, Options, Blast Radius, Decisions). На проект: `openspec/adrs/`, опционально KB, `openspec/project.md` (только явно подтверждённое). Discovery ADR/KB/архива — перед вызовом архитектора (`architect-gate.mdc`). |
| Trade-offs до первой строки? | Да, **если** пройдены Design Gate и отчёт архитектора с Simplicity Check / Options. Нет отдельной карточки «человек подписал Chosen». |
| Failure modes до кода? | В шаблоне архитектора (Error Handling, права, транзакции) — да как ожидание качества. Как обязательный заполненный артефакт с проверкой — нет. |

Формат ADR (`adr-format.mdc`): Контекст / Решение / Альтернативы (таблица плюс-минус-почему отклонён) / Последствия / Связи / при замене несущего — Blast Radius. Критерий создания: влияет на будущие ЗНИ, неочевидный trade-off, контракт или принцип. Точечное решение одной ЗНИ остаётся в отчёте архитектора.

### 1.6. Кто что делает (архитектор vs оркестратор vs человек)

```
Человек          Оркестратор              Агент-архитектор
  │                    │                         │
  │  подтвердить бриф  │                         │
  │  «запустить        │  триггеры гейта         │
  │   разбор?»         │────────────────────────►│  Chosen, альтернативы,
  │                    │  ADR/KB/архив в промпт  │  границы, карта объектов,
  │                    │                         │  срезы, tasks
  │  принять срезы     │◄────────────────────────│
  │  Mode форм         │  записать design/tasks  │
  │  метаданные в      │  не писать .bsl         │
  │  Конфигураторе     │                         │
  │                    │  проверка постановки    │  удар по чужому design
  │  развилка A/B      │  (в т.ч. challenge)     │  оценка «можно кодить»
  │                    │                         │
  │  /реализация       │  writer: ЧТО не КАК     │  (здесь уже не он)
  │  приёмка среза     │  reviewer после кода    │
```

**Архитектор (агент)** — единственная роль «спроектировать / ударить / разрезать на срезы / сказать, реализуемы ли задачи». Режимы: `design`, `design-challenge`, `task-readiness`, `slice-decomposition`, `deep-analysis` (петля приёмки), аудиты scope/прецедентов, извлечение инвариантов. Обязательный Simplicity Check во всех режимах **выбора** решения; в аудитах/challenge — нет (это не новый Chosen). HALT: нет обследования при ≥3 модулях — не выдумывать паттерны (`INSUFFICIENT CONTEXT`).

**Оркестратор** — диспетчер гейтов, не автор архитектуры. Обязан: ADR/KB/Precedent Discovery; двухшаговая цепочка вызова архитектора; сохранить полный отчёт; не закрывать гейт самодельным текстом **пока цепочка жива**. Исключение: агент упал после retry → `architecture-new-selfreview-*.md` с пометкой fallback (`openspec-new-change/SKILL.md`). В код: только «что», не «как». Apply-gate: не запускать writer вне реализации ЗНИ.

**Человек** — заказчик/разработчик конфигурации. Точки «нет»: отказ запустить архитектора в исследовании (с причиной); флаг `--skip-architect` при создании ЗНИ; не принять срез; не создавать объект в Конфигураторе; выбрать A/B на развилке; «продолжить без проверки постановки»; явный workaround с follow-up (`verified-cause-gate.mdc`). Подтверждение **срезов** — AskQuestion «Принять / Скорректировать / Пересобрать». Подтверждение **самого Chosen** отдельным вопросом не требуется: правки design из отчёта архитектора оркестратор вносит и показывает diff.

Схема отчёта: `.cursor/docs/architect-report-schema.md` — YAML `scope.files` / `modules`, `confidence`, манифест `reports/_manifest.yaml`. Гейт закрывается файлом с **пересечением scope**, не любым старым отчётом.

## 2. Дыры vs статья — только честные

Классификация: **нет аналога** | **есть процесс, но не enforcement** | **есть, но легко обойти флагом**.

### 2.1. Проверка постановки не держит вход в код

**Класс:** есть процесс, но не enforcement.

`sdd-workflow.mdc`: pre-apply verify **не блокирует** apply.  
`openspec-apply-change/SKILL.md`: нет `reports/verification-*.md` → мягкое предупреждение «Запустить verify / Продолжить без». «Verify check is advisory — does not block apply».

Статья: «готово» = решение проверяемо **до** того, как система уехала дальше. В ките независимый удар по архитектуре (`design-challenge`) живёт внутри verify. Verify может сказать «не кодить», но реализация умеет пойти мимо.

Смягчение: открытая **продуктовая** развилка на входе apply всё же стопит. Стек «пропустить архитектора + пропустить verify» — нет.

### 2.2. Легальный пропуск архитектора и challenge

**Класс:** есть, но легко обойти флагом.

| Обход | Где | След |
|--------|-----|------|
| `--skip-architect <причина>` | new Design Gate | `.gate-override.yaml` `gate: architect`. В исследовании отказ — `declined: <reason>`; без подтверждения флагом в new гейт вспыхивает снова |
| `.gate-override.yaml` `gate: design-challenge` | verify, ≤7 дней | Независимый удар по постановке пропускается. Срок кончается — снова обязателен. **Не** закрывается флагом new |
| `.gate-override.yaml` `gate: acceptance-loop` | петля приёмки, ≤7 дней | Редизайн среза можно отложить |
| Light / Mechanical | `architect-gate.mdc` исключения; `1c-halt-triggers.mdc` | Точечная правка 2–10 строк / find-replace — без архитектурного гейта (если нет семантических триггеров и смены UX) |

Статья: контроль держится, пока человек **обязан** сказать «нет» плохому решению. Флаги — как раз легальное «не спрашивать архитектора». Аудит-след есть; принуждения нет.

### 2.3. Гейт закрывается фактом файла, не качеством решения

**Класс:** есть процесс, но не enforcement (качества).

`architect-gate.mdc` ЗАКРЫТИЕ: любой `architecture-*.md` с пересечением `scope` **или** override.  
«Design Rationale ≠ закрытие Gate» — самописный текст агента не считается; **файл отчёта** считается.  
`confidence: low` → одна строка в чат, гейт **не** провален, если файл есть и Simplicity Check заполнен.  
Нет альтернатив в отчёте: гейт всё равно пройден «по факту вызова»; verify **должен** дать WARNING `architect-simplicity-missing`.

Проверка по репозиторию: строка `architect-simplicity-missing` встречается **только** в `architect-gate.mdc`. В `openspec-verify-change/SKILL.md` её **нет**. Verify также **не** grep'ает `## Existing Mechanisms` и `## Design Rationale` (семантические триггеры запуска архитектора не повторены как структурная проверка постановки).

Итог: «должен дать WARNING» — намерение без проводки в скилл проверки.

### 2.4. Fallback оркестратора вместо архитектора

**Класс:** есть, но легко обойти (деградация модели / сбой агента).

При падении агента оркестратор сам пишет `architecture-new-selfreview-*.md` по шаблону. Это закрывает «файл есть». Статья как раз про исчезновение экспертизы: форма отчёта без независимого разбора.

Отдельно: challenge **запрещено** закрывать файлом авторского `architecture-*.md` и наоборот — роли разведены хорошо. Дыра не в смешении ролей, а в self-review на Design Gate.

### 2.5. Долгоживущие решения появляются поздно

**Класс:** есть процесс, но не enforcement «до первой строки».

Основная точка ADR — **archive** (`adr-format.mdc` «КОГДА СОЗДАВАТЬ»; archive auto-extract).  
До кода живут `design.md` и отчёт ЗНИ. Они уезжают в архив вместе с change; обнаруживаемость для **следующей** ЗНИ — через Cross-Archive + ADR Discovery.

Статья: подрядчика спрашивают, как решения **документируются** как контракт проекта, не как черновик текущей задачи. Кит умеет ADR, но **не требует** Proposed ADR до кода. Trade-off может остаться только в отчёте одной ЗНИ («не заслуживает ADR»).

В этом kit-репозитории прикладных ADR нет — только процессные. Для поставки кита это нормально; для прикладного проекта 1С «пустой каталог ADR после нескольких ЗНИ» — дыра дисциплины, не дыра спецификации формата.

### 2.6. Failure modes, отказоустойчивость, стоимость после запуска

**Класс:** нет аналога как гейта; шаблон есть.

Архитектор: Error Handling, State, Testing, Performance, Security, Access Rights — с **порога сложности** (Simple = без Error Handling; Medium = + Error Handling; Complex = + Sequence, Performance, Security, Rights).  
Нет триггера «перехват проведения / обмен / регламент → обязательная таблица сбоев».  
Нет требования: журнал регистрации, права, управляемые блокировки, откат — заполнены и проверены до кода.

«Стоимость изменений после запуска» в статье — экономика сопровождения. В ките ближайшее: Complexity budget, Preference Hierarchy, Blast Radius при **отмене прошлого контракта**. Нет поля «как дорого будет расширить через год», и это правильно не считать в часах (запрет ROI); но и качественного «N+1 / обновление типовой / второй хук» кроме Identity Filter нет как универсального чеклиста.

### 2.7. «Готово» ≠ промышленный контур

**Класс:** нет аналога (и не должен быть полным — см. §4).

Наблюдаемость статьи (алерты, SLO, трассировка прода) ≠ наблюдаемость среза (пользователь видит результат в форме).  
Повторяемый деплой статьи (образ, пайплайн) ≠ «выгрузили XML после Конфигуратора».  
Кит явно: «Verify оценивает постановку, не приёмку на ИБ» (`openspec-verify-change/SKILL.md`). Приёмка в базе — человек на slice-gate / archive. Это закрывает «демо на ноутбуке», не «выкат на контур заказчика».

### 2.8. Кто именно подписал архитектуру

**Класс:** нет аналога (роль в metadata).

Есть `developer` для маркеров в коде. Нет поля «архитектуру принял ФИО / роль».  
Chosen может быть внесён в design по отчёту агента + diff в чат, без явного «принимаю trade-off».  
Срезы подтверждаются; ось решения («перехват vs подписка vs штатный API») — нет обязательной человеческой подписи.

### 2.9. Lite и «маленькая ЗНИ»

**Класс:** есть, но легко обойти масштабом.

≤5 задач — декомпозиция срезов опциональна. Глубина verify по таблице скилла не обязана падать вместе с Lite — но Light Mode обходит OpenSpec целиком при 2–10 строках. Статья: цена ошибки растёт после запуска независимо от размера диффа, если задет контракт. Promotion-триггеры (`1c-halt-triggers.mdc`: транзакции, экспортный контракт, RLS, подписки, регламенты) частично закрывают; «маленький хук на форму» может пройти Light.

### 2.10. Что статья закрывает китом хорошо (чтобы не завысить дыры)

Не дыры:

- Запрет вайб-кода в обход постановки (apply-gate + исследование без writer).
- Адверсариальный разбор постановки отдельно от авторского design.
- Иерархия «не плодить вторую систему» + identity-filter.
- Приёмка как пользовательский сценарий, не как «функция существует».
- Защита от молчаливой отмены прошлого контракта.
- Человек создаёт метаданные; ИИ не собирает конфигурацию из XML-копии.
- Writer может отказать постановке, если она ломает стандарты (G20/G21).

## 3. Кандидаты на усиление

Только зона кита (процесс ЗНИ, гейты, артефакты, роли агентов). Без часов и ROI. 6 пунктов.

### 3.1. Не входить в реализацию, если архитектурный удар не состоялся или отверг постановку

- **Зачем:** сейчас «не кодить» живёт в отчёте проверки, а реализация умеет «продолжить без». Стек skip-architect + continue-without-verify = вайбкодинг с аудит-следом. Связка закрывает главный зазор статьи «готово проверяемо».
- **Куда вставлять:** `openspec-apply-change` pre-flight: если сработали триггеры `architect-gate.mdc` (или в постановке есть перехват / новый объект / смена контракта) — нет актуального `design-challenge` **или** последний challenge = отвержение без закрытой развилки → стоп, не мягкий вопрос. Override — тот же `.gate-override.yaml` с причиной и сроком, что уже есть у challenge.
- **Риск если не делать:** подрядчик показывает «у нас есть архитектор в процессе», а в проде оказывается код, который проверка постановки так и не подтвердила.

### 3.2. Явное принятие Chosen человеком (не только срезов)

- **Зачем:** статья — «кто принимает решения». Сейчас подпись человека на нарезке сценариев, не на trade-off (свой регистр vs штатный, `&Вместо` vs `&После`). Diff design в чат легко пролистать.
- **Куда вставлять:** после Design Gate и отчёта архитектора, **до** генерации tasks — один вопрос: «принимаем выбранный путь (кратко: что выбрали / что отвергли / какой сбой ожидаем)». Запись в `design.md` § Decisions + поле metadata вроде `architecture_accepted_by` (зеркало `developer`, не путать с маркером кода).
- **Риск если не делать:** ответственность размазана: «модель предложила, оркестратор записал, человек принял срезы». При разборе инцидента не видно, кто сказал «да» оси решения.

### 3.3. Проводка уже описанного предупреждения «нет альтернатив в отчёте архитектора»

- **Зачем:** `architect-gate.mdc` уже требует WARNING `architect-simplicity-missing`, скилл verify его не знает. Это дыра **спецификации vs код процесса**, не новая идея.
- **Куда вставлять:** `openspec-verify-change` — grep секции Simplicity Check / Implementation Options при наличии `architecture-*.md`; нет 2+ вариантов и нет формулы «единственный viable + ссылка» → WARNING (как задумано). Параллельно: отсутствие `## Existing Mechanisms` при интеграции / отсутствие `## Design Rationale` — тот же слой структурной проверки (сейчас только триггер **запуска** архитектора в new).
- **Риск если не делать:** Chosen без сравнения выглядит как вайб-выбор; гейт зелёный, потому что файл отчёта существует.

### 3.4. Proposed ADR (или обязательный блок «решения, которые переживут ЗНИ») до кода, не только при архиве

- **Зачем:** статья спрашивает документацию решений **до первой строки**. Кит уже умеет формат ADR и Discovery. Сдвиг «извлечь достойные ADR» с archive на new/verify (статус Proposed → Accepted при приёмке/архиве) закрывает «черновик ЗНИ vs контракт проекта».
- **Куда вставлять:** критерий `adr-format.mdc` «заслуживает ADR» + шаг new после Chosen / шаг verify после challenge APPROVE. Не плодить ADR на каждое точечное; порог тот же (будущие ЗНИ, неочевидный trade-off, контракт). Archive остаётся точкой перевода Proposed → Accepted / Load-Bearing.
- **Риск если не делать:** следующая ЗНИ находит решение только если оркестратор хорошо попал в Cross-Archive (бюджет 3 архива / 10 каталогов). Молчаливый drift вероятнее, чем при именном ADR.

### 3.5. Обязательная таблица сбоев для перехватов и интеграций (не по числу файлов)

- **Зачем:** шаблон Error Handling привязан к «средняя сложность = 3–5 файлов». Перехват одной процедуры проведения — часто 1–2 файла и максимальный blast. Статья: предсказуемые failure modes до кода. Аналог кита — не Terraform, а: нет прав, объект заблокирован, типовая выбрасывает, обмен недоступен, частичный отказ записи — что видит пользователь, что в ЖР, откатывается ли транзакция.
- **Куда вставлять:** `onec-code-architect.md` (режим design) + Design Completeness в new: если design содержит `&Перед/&После/&Вместо`, подписку, регламент, обмен — секция «Ожидаемые отказы» обязательна независимо от Simple/Medium. Verify Layer 5: пустая секция при этих маркерах → пробел готовности, не « infо».
- **Риск если не делать:** Chosen проходит Simplicity Check («тонкий `&После`»), а поведение при исключении типовой остаётся вайбом writer'а. G19 ловит лишнюю `Попытку`, не отсутствие стратегии отказа.

### 3.6. Запрет складывать обходы на одну ЗНИ без повторного «да» человека

- **Зачем:** каждый override по отдельности честный. Вместе skip-architect + SKIPPED-override challenge + «продолжить без verify» + Light на соседнем файле — контроль статьи рассыпается, формально ничего не нарушено.
- **Куда вставлять:** apply pre-flight: если в change есть `.gate-override.yaml` **и** нет verification-отчёта (или challenge пропущен override) — не предлагать «продолжить без» как равноправный пункт; только повтор проверки **или** новая явная причина в том же yaml («принимаю код без независимого разбора постановки»). Не отменять одиночный легальный skip для тривиальной ЗНИ.
- **Риск если не делать:** аудит видит три аккуратных файла-override и не видит, что экспертиза ни разу не смотрела постановку.

### Не предлагать (намеренно)

- Обязательный «архитектор-человек заказчика в каждой ЗНИ» как штат — это договор подряда, не правило кита (киту достаточно поля «кто принял Chosen»).
- Оценка часов/стоимости владения.
- Прод-мониторинг, CI выката, SLA — §4.

## 4. Вне зоны кита

Кит — процесс ИИ-разработки **конфигураций и расширений 1С** в git + Конфигуратор, не сборка SaaS.

Не надо закрывать китом и не надо имитировать Terraform/Vercel:

- Хостинг и контур заказчика: кластер 1С, веб-публикация, лицензии, обновление платформы, резервное копирование, RPO/RTO.
- Повторяемый выкат **промышленной** базы (Cf/Cfe-поставка через их pipeline, кольца обновлений, синяя-зелёная схема).
- SLO/SLA приложения, on-call, инцидент-менеджмент, APM, дашборды облака.
- Мультиарендность, биллинг, CDN, секреты облака.
- Юридический RACI подрядчика, акты, гарантийные письма «кто архитектор с печатью».
- Нагрузочное тестирование на пром-объёме как обязательный гейт кита (нет универсальной стендовой инфраструктуры; NFR в ките — static/код и Follow-up).
- «Наблюдаемость» в смысле OpenTelemetry — у 1С свой Журнал регистрации / технологический журнал; кит может требовать **стратегию отказа в design**, но не заменить эксплуатацию ИБ.

Честная граница: кит делает так, чтобы **изменение конфигурации** было понятным, нарезанным на принимаемые сценарии, с выбранными границами относительно типовой и с памятью прошлых контрактов. Он не делает систему «развёрнутой и наблюдаемой в проде». Это остаётся контуром заказчика.

|-------|----------------|
| Вайбкодинг ≠ AI-assisted: нужен «нет» | **Закрыто процессом** (гейты, приёмка среза, G20). **Ослаблено** advisory-verify и skip-флагами. |

## Для заказчика

Кит уже не даёт модели сразу писать конфигурацию «как получилось за выходные». Сначала фиксируется, зачем меняем поведение, как это встроится в уже существующие механизмы типовой, что пользователь увидит в базе, и только потом идёт код. Новый справочник или форму искусственный интеллект сам не создаёт: это делается в Конфигураторе человеком, иначе легко сломать конфигурацию.

Отдельный разбор предлагает путь и отвергает более хитрые обходы. Потом постановку ещё раз бьют «чужими глазами»: та ли это боль, нет ли проще. Нарезка работ — не «сначала все таблицы, потом всё остальное», а куски, каждый из которых можно принять в рабочей базе. Пока кусок не принят человеком, задача не считается сделанной.

Слабое место относительно статьи про вайбкодинг: проверку постановки можно обойти и пойти в код; архитектора можно официально пропустить с записью причины; «как система ведёт себя при ошибке» не всегда требуют записать до кода. Долгоживущие решения (чтобы через полгода не раскапывать «почему так») сейчас чаще появляются в конце задачи, а не в начале.

Кит не заменяет ваш контур обновления баз, резервные копии и сопровождение серверов 1С. Он закрывает другое: чтобы подрядчик с моделью не сдал «кнопка в демо есть», а сдал изменение с понятными границами, приёмкой в базе и памятью, что нельзя тихо отменить потом.

Имеет смысл усилить три вещи в процессе, не в инфраструктуре: не начинать код, если разбор постановки так и не подтвердил решение; чтобы выбранный путь подписывал человек, а не только список сценариев; чтобы для перехватов типовых процедур заранее было сказано, что увидит пользователь при отказе прав, блокировке и ошибке типовой.
