# Исследование: кит vs претензии статьи про вайбкодинг в production

**Дата:** 2026-08-29  
**Профиль:** вопрос по покрытию kit (не дефект конфигурации 1С).  
**Контент 1С (`src/**`, `.bsl`, XML метаданных) не читался.** Правки — только этот файл.  
**Статья:** https://habr.com/ru/articles/1075256/ (тезисы из постановки; сайт не открывался).  
**Existing Knowledge:** Discovery выполнен, совпадений нет. Каталога `openspec/knowledge/` с `_index.yaml` в этом репозитории kit нет (это шаблон; база знаний появляется в проекте заказчика после `/init-project`).

## Вопрос

Какие претензии статьи (тесты шире unit; наблюдаемость; инфра и откат; поддерживаемость; вопросы подрядчику) уже закрывает кит на слоях тестирование / наблюдаемость / эксплуатация / восстановление / поддерживаемость — и что усилить.

## Решено, когда

Доказательная карта: что кит **требует до и после кода** vs формула «тестовый сценарий прошёл → можно выкатывать»; где живут логи/трассы; что есть вместо rollback/бэкапа; как передаются знания и проект другой команде. Честно разделены **процесс разработки в Cursor** и **эксплуатация рабочей базы 1С у заказчика**.

---

## Граница кита (обязательная рамка)

Кит — цикл **постановка → независимая проверка постановки → внедрение в выгрузке 1С → ручная приёмка среза на информационной базе → архив ЗНИ**. Это не Kubernetes, не CI/CD выкладки cf/cfe в рабочую базу, не мониторинг кластера.

| Слой статьи | Аналог кита | Где живёт |
|-----------|-------------|-----------|
| Тесты | Наблюдаемый сценарий приёмки среза + ревью кода + (редко) «если в проекте есть YaXUnit/Vanessa» | Cursor + человек на ИБ |
| Наблюдаемость | Разбор трассы/стека **как вход расследования**; кейсбук журнала регистрации **как рецепт кода** | Cursor + выгрузка; не дашборд рабочей ИБ |
| Инфра / rollback / бэкап | Пауза, пока в выгрузке нет объектов; git/маркеры расширения; откат **транзакции в коде** | Не бэкап рабочей ИБ |
| Поддерживаемость | Соглашения, ревью, архив, ADR, база знаний, обзор для заказчика, маркеры автора | Репозиторий проекта |

**Два контура, которые нельзя смешивать:**

1. **Контур разработки (A+B).** Cursor, выгрузка `src/`, ЗНИ, человек прогоняет сценарий на **стенде/копии**. Кит здесь сильный.
2. **Контур рабочей базы заказчика (C).** Сколько падает в проде, latency, деньги, бэкап, проверка восстановления, rollback выкладки, дежурный, алерты. Кит здесь почти не присутствует.

Формула статьи «один зелёный сценарий → в прод» кит **ломает внутри контура 1** (нельзя закрыть ЗНИ, пока срезы не приняты человеком; нельзя честно сказать «код совпадает с постановкой», если имена в плане — фантомы). Формулу **не заменяет** для контура 2: принятый срез ≠ «выкатили на рабочую базу и там дышит».

# 1. Покрытие — механизмы кита с путями

## A. Качество постановки и кода в репозитории

Это ответ кита на «модель написала diff — можно мержить». Здесь требования **до кода** и **сразу после правки файлов**, без запуска ИБ.

### A1. Нельзя чинить симптом без доказанной причины

- `.cursor/rules/verified-cause-gate.mdc` — до фикса, меняющего поведение: причина **подтверждена** (трасса / код / лог / воспроизведённый сценарий) или явная пометка «фикс по гипотезе» с обязательной проверкой после. Цепочка «почему» минимум на три уровня. Иначе стоп.
- `.cursor/rules/1c-error-analysis.mdc` + `.cursor/agents/onec-trace-analyst.md` — ошибка со стеком/файлом трассы (`.pff`, `*_TRACE_*`, `*_PERF.txt`) не разбирается «на глаз»: отдельный разбор трассы с сверкой строк кода, факты vs гипотезы, запрос полной трассы если компактной мало.
- `.cursor/skills/openspec-explore/SKILL.md` — вход расследования: сначала бриф и согласие, потом делегирование; отчёты в `temp/reports/trace-analysis-*.md` и `exploration-*.md`. Архивные гипотезы — кандидаты, не автоматическая причина.
- `.cursor/agents/onec-code-explorer.md` — обследование кода: цепочки вызовов, факты с `file:line`, конфликт с базой знаний если факт устарел.

**Закрывает из статьи:** «не чинить вслепую»; часть «кто разбирает инцидент» **в режиме разработки** (есть протокол «как искать причину»).  
**Не закрывает:** дежурство 24/7, SLO, «сколько денег теряем в проде».

### A2. Постановка должна решать заявленную проблему и быть исполнимой до первой строки кода

- `.cursor/skills/openspec-verify-change/SKILL.md` — независимая проверка **постановки**, не прогона на ИБ. Прямая цитата принципа: verify оценивает постановку, не приёмку на ИБ; отсутствие тестовых данных **не** блокирует старт реализации. Исключение: структурно недостижимый сценарий приёмки внутри среза (это дыра плана, не «нет данных»).
- Пять слоёв (имена — только для этого отчёта): гигиена артефактов; согласованность плана + совпадение имён с выгрузкой; петля «патчим срез по кругу без приёмки»; след «зачем → требования → сценарии → задачи»; независимый вызов подхода; исполнимость задач as-is.
- `.cursor/rules/openspec-specs-gate.mdc` — без дельты спецификаций требования теряются при архиве. Сценарии обязаны описывать **наблюдаемый** исход на ИБ, не «функция вернула структуру».
- `.cursor/rules/vertical-slices.mdc` — срез = то, что человек может принять независимо одним пользовательским сценарием. Приёмка — чёрный ящик. Код-ревью и «вызвать API в отладчике» — не приёмка среза. Запрещён «фундамент без UX» как отдельная точка приёмки.
- `.cursor/rules/task-triage.mdc` — опечатка в docs ≠ полный цикл; точечный фикс 2–10 строк в одном модуле может идти упрощённо; смена контракта экспорта / транзакции / RLS → полный цикл.

**До кода кит требует:** согласованные proposal / design / specs / tasks; наблюдаемые сценарии; достижимая приёмка среза его собственными задачами; ручная конфигурация с именами объектов, а не «настройте как-нибудь».

### A3. После кода в репозитории: не «компилятор молчит», а совпадение плана и символов + ревью

- `.cursor/skills/openspec-apply-change/SKILL.md` — реализация только в этом контуре (кроме Light/Mechanical). Writer → линтер → ревьюер. После каждой BSL-задачи: журнал реальных символов в `debug.md`, точечная сверка, что имя есть в файле. На границе среза — карта правок `reports/code-map.md`.
- `.cursor/rules/code-truth-gate.mdc` — после apply / на финальной проверке / на архиве: имена процедур, аннотаций расширения, стабильных элементов формы в design/tasks/debug/specs **существуют в выгрузке**. Фантом на принятом срезе — жёсткий стоп архива.
- `.cursor/skills/review/SKILL.md` + `.cursor/docs/review-guide.md` — три уровня: ревьюер на каждой задаче apply; `/review` по diff/модулю; `/release-review` перед выкладкой расширения (опечатки в пользовательских строках, заглушки, гигиена комментариев, эскалация серьёзности). Это **ревью исходников**, не smoke после деплоя.
- `.cursor/docs/standard/reviewer-checks.md` §12 «Release Readiness» — по факту: опечатки кириллица/латиница в строках UI, заглушки, логирование в `Попытка`. Не метрики продакшена.
- `.cursor/agents/onec-code-architect.md` секция Testing — **если** в проекте есть YaXUnit / Vanessa, архитектор может заложить автотесты; иначе — ручные сценарии в критериях приёмки. Инфраструктуру тестов кит **не создаёт и не требует**.
- `.cursor/docs/agents-CHANGELOG.md` — генератор автотестов в kit снят: «автотесты в проекте не используются, 0 вызовов».
- `.cursor/rules/1c-halt-triggers.mdc` — Light Mode (1 файл, 2–10 строк) **обходит полный цикл ЗНИ**, но writer+reviewer и verified-cause для бага остаются. Mechanical — замена по шаблону + обязательный ревьюер.

**Итог A:** кит закрывает претензию «нет ревью, нет постановки, имена выдуманы, чинят симптом». Не закрывает «есть пирамида автотестов и контрактные/нагрузочные прогоны в CI».

### A4. Регрессия контрактов между ЗНИ (не регресс-сьют автотестов)

- Verify Layer 2.4 + `.cursor/rules/precedent-regression-gate.mdc` (по ссылке из verify) — молчаливая отмена ранее принятого контракта / несущего ADR / инварианта KB.
- `.cursor/rules/verified-cause-gate.mdc` HALT 4 — перед фиксом в зоне архивной ЗНИ: blast radius или аудит «расширяет vs отменяет».
- Архив шаг 5.5.b (`.cursor/skills/openspec-archive-change/SKILL.md`) — выжимка инвариантов поведения в ADR/KB для будущих проверок.

Это **документированная регрессия смысла**, не прогон старых Vanessa-сценариев.

## B. Приёмка на информационной базе человеком

Это ответ кита на «написали код — дальше само». Кит **не считает срез принятым**, пока человек не прогнал **главный** пользовательский сценарий на ИБ (или явно не подтвердил это при архиве).

### B1. Что обязательно

- `.cursor/rules/vertical-slices.mdc` — для `[x]` на приёмке среза блокирует только **Primary**: один user-journey Given→When→Then на типовой базе без отладчика. Остальные сценарии spec — опциональные пункты или проверка **по коду** агентом. Регресс существующего поведения — optional-буллет или статическая проверка, **не** обязанность пользователя гонять стенд посередине среза.
- `.cursor/skills/openspec-apply-change/SKILL.md` — после рабочих задач среза: внутренний узкий verify постановки → карточка «что сделано / карта правок / что проверить СЕЙЧАС / как вернуться». Оркестратор **ждёт**. Следующая сессия начинается с вердикта: принят / не принят / дефект в предыдущем срезе.
- Непринятый срез: доработка **внутри того же среза** (инвариант размещения дефекта), не новый «хвост фаз».
- Детектор петли приёмки (тот же `vertical-slices.mdc`): один срез многократно уходит на проверку без подписи → стоп и разбор постановки, а не бесконечные патчи.

### B2. Архив не равен «тесты зелёные в CI»

- `.cursor/skills/openspec-archive-change/SKILL.md` шаг 3.5 — непринятые приёмочные задачи среза: **жёсткий стоп** с карточкой. Вариант A — пользователь **подтверждает**, что главный сценарий пройден на ИБ (ответственность на нём). Вариант D / `--force-legacy` — архив **без** отметки приёмки (осознанный обход).
- Нельзя подписать приёмку среза, чей результат появляется только после следующего среза.
- Фантомные имена на принятом объёме — архив блокируется (`code-truth-gate.mdc`).
- Внутренний финальный verify постановки перед архивом, если нет свежего.

### B3. Что кит явно **не** считает приёмкой

Из `openspec-verify-change/SKILL.md` и `vertical-slices.mdc` (out of scope для контролёра срезов):

- нет тестовых данных / эталона ИБ / выгрузки в базу — **временное**, не дыра плана;
- smoke «вне задач» — зона apply/archive, но **шаблона обязательного post-deploy smoke нет**;
- NFR/нагрузка — задача «посмотреть по коду / при возможности по технологическому журналу», не пункт «срез принят»;
- негатив, контракты API, миграции данных, fault injection — не обязательная матрица.

Тип задачи в handoff: «Ручной тест», «Ручная регрессия» — человек, не раннер.

**Итог B:** кит закрывает «никто не смотрел глазами на сценарий». Не закрывает пирамиду тестов статьи. Риск: один счастливый Primary + optional пропущены = формально срез принят. Риск: `--force-legacy` и Light Mode без ЗНИ.

## C. Продакшен-наблюдаемость, бэкапы рабочей базы, эксплуатация

**Вердикт: слабо или вне кита.** Ниже — всё, что **похоже** на тезисы статьи, и почему это другой контур.

### C1. Логи и трассы — диагностика разработки, не «сколько падает / latency / какая версия / сколько денег»

- `.cursor/docs/casebooks/logging-strategy.md` — **как** писать в журнал регистрации, **если задача явно просит лог** (интеграции, фон, проведение, откат транзакции, необработанные исключения). Правило большого пальца: логировать то, что нельзя восстановить потом. Уровни Ошибка→мониторинг (Zabbix/ELK/Prometheus **как внешняя карта**, не часть кита). Имена событий `Подсистема.Операция.Исход`. Запрет секретов и ПДн. Ротация/выгрузка ЖР — «настройте в администрировании платформы»; realtime-хвост — «вне платформы, технологический журнал».
- Непрошеный `ЗаписьЖурналаРегистрации` — антипаттерн (ссылки из кейсбука на `bsl-antipatterns.md` / стандарты). Наблюдаемость **не включена по умолчанию** в каждую ЗНИ.
- Якорь KB типа `event-name` (`.cursor/rules/knowledge-format.mdc`) — можно закрепить **имя события**, которое уже использует мониторинг заказчика. Это мост к внешнему мониторингу, не сам мониторинг.
- Trace-analyst + PERF — разбор **приложенного** файла трассы в чате. Нет агента «снять метрики с рабочей ИБ», нет вопроса «какая сборка в проде».

### C2. Инфра, секреты, IaC, CI/CD, окружения

- `.cursor/docs/delivery-integrity.md` + `.cursor/docs/kit-template-workflow.md` — **copy-smoke поставки самого кита**: копируются `.cursor/` + `AGENTS.md`, нет npm/Python. Это целостность **шаблона Cursor**, не пайплайн выкладки конфигурации 1С.
- Optional smoke: `.cursor/docs/mxl-roundtrip-fixture.md`, `.cursor/docs/proportional-surface.md` — фикстуры **кита**, каталог `temp/fixtures/` не в поставке.
- В репозитории kit **нет** `.github/workflows` (поиск workflows = 0). Нет описания стендов (dev/test/prod), секретов, IaC.
- `.cursor/skills/openspec-apply-change/SKILL.md` pause-wait — нет объекта в выгрузке / форма вручную в Конфигураторе: стоп и список «что создать». Аналог «окружение не готово» **только для метаданных в выгрузке**, не матрица сред заказчика.

### C3. Бэкап, восстановление, rollback выкладки

Grep по `.cursor` на rollback/бэкап/откат:

| Что нашлось | Смысл | Не то, что в статье |
|-------------|--------|-------------------|
| `logging-strategy.md` «Transactional rollback» | Писать в ЖР причину отката **транзакции документа** | Не restore ИБ |
| `std-05-transactions.md`, кейсбуки locks/platform-solutions | Откат транзакции платформы | Не rollback релиза |
| `onec-code-writer` Phase 5 rollback | Откат порчи кода вне `#Вставка` при `&ИзменениеИКонтроль` | Git/патч модуля |
| `openspec-knowledge-add` rollback bundle | Откат записи KB при поломке каталога | Не ИБ |
| `init-project-protocol.md` backup `_index.yaml` | Копия индекса знаний в `temp/backups/` | Не ИБ |
| `openspec-explain` «откати» | Правка журнала разбора в чате | Не прод |

**Проверки бэкапа рабочей базы, репетиции restore, rollback выкладки cf/cfe в прод — в ките нет.**

### C4. Инциденты и дежурство

Нет runbook «кто дежурит», эскалации, postmortem. Ближайшее: `/opsx:explore` при ошибке + трасса. Это **разбор в Cursor**, когда разработчик уже здесь.

### C5. Сессии Cursor ≠ восстановление продакшена

- `.cursor/skills/session-save/SKILL.md` / `session-restore/SKILL.md` — заметки чата в `temp/session-notes.md` (в `.gitignore`), без секретов ИБ, **без** автозапуска реализации. Передача **контекста диалога**, не disaster recovery.

## Поддерживаемость (сквозной слой A+B, слабо C)

Статья: документация, соглашения, зависимости, ownership, code review; код читаем в 03:00.

| Претензия | Механизм кита | Путь |
|-----------|---------------|------|
| Документация «как есть» | База знаний (якоря на процедуры/события ЖР), TTL, drift | `.cursor/rules/knowledge-format.mdc`; создание: archive шаг 5.5, `/opsx:knowledge-add` (`.cursor/skills/openspec-knowledge-add/SKILL.md`) |
| Решения с развилкой | ADR при архиве из architecture-отчётов | archive шаг 5; `.cursor/rules/adr-format.mdc` |
| Требования | delta specs → main specs при архиве | specs-gate; `openspec-sync-specs` |
| Ownership кода | Маркеры `// +++ ФИО дата` / cf-префикс; дисбаланс open/close — стоп архива | apply Metadata; archive шаг 3.2 |
| Code review | apply-reviewer; `/review`; `/release-review` | `review/SKILL.md`, `review-guide.md` |
| Читаемость ночью | Именование (доменный тест), гигиена комментариев, simplifier поверхности, `/opsx:explain` по карте правок | writer-pipeline, halt-triggers, `openspec-explain` |
| Передача другой команде | Архив ЗНИ целиком; `code-map.md`; handoff приёмки; `/opsx:overview` для ФА; `/opsx:status`; session-save | archive, overview, status, session-* |
| Соглашения | Стандарты + кейсбуки + антипаттерны (только ревьюер) | `.cursor/docs/standard/`, `casebooks/` |
| Зависимости | Граф срезов, existing-mechanism-priority, не плодить метаданные | `existing-mechanism-priority.mdc`, `1c-no-metadata-creation.mdc` |

**Дыра поддерживаемости vs статья:** нет карты «кто owner подсистемы в проде»; нет SBOM/зависимостей внешних сервисов; overview собирает **постановку поставки**, не runbook эксплуатации.

# 2. Дыры vs статья

Сопоставление тезисов статьи и вопросов подрядчику. Оценка: **закрыто** / **частично** / **нет** — относительно контура кита (разработка 1С в Cursor), не Kubernetes.

## Тесты

| Тезис статьи | Кит | Оценка |
|-------------|-----|--------|
| Не только unit | Автотесты не обязательны; YaXUnit/Vanessa — «если уже есть» | **нет** как требование |
| Интеграция, контракты, миграции данных | Нет раннера; «миграция» в ките = перестройка **задач ЗНИ** с фаз на срезы, не миграция БД | **нет** |
| Негатив | Может попасть в spec/optional; не mandatory матрица | **частично** (можно написать в постановке, никто не требует) |
| Регрессия | Optional-буллет / проверка по коду; precedent по контрактам ЗНИ | **частично** (смысл да, сьют нет) |
| Smoke после деплоя | Нет шага «после загрузки в рабочую ИБ». Copy-smoke — про копирование кита | **нет** (для ИБ) |
| Нагрузка, fault | PERF-трасса вручную; NFR «по коду / ТЖ» не блокирует приёмку среза | **нет** как ворота |

**Главный зазор:** кит запрещает считать «зелёным» **план без наблюдаемого сценария**, но **разрешает** считать поставку закрытой после **одного** ручного Primary. Это лучше чем «unit прошёл», и хуже чем пирамида статьи.

Verify **специально** не спрашивает про тесты и не блокирует apply из-за отсутствия данных ИБ.

## Наблюдаемость

| Вопрос статьи | Кит |
|--------------|-----|
| Сколько падает | Нет |
| Где latency | Только если принесли PERF/трассу в чат |
| Какой сервис / какая версия | Маркеры автора в коде; не версия выкладки в проде |
| Сколько денег теряем | Нет (и оценка ROI в правилах кита запрещена: `.cursor/rules/no-roi-estimates.mdc`) |

Кейсбук журнала — **как писать**, не «метрики до запуска обязательны». Непрошеный лог запрещён → интеграция без задачи «журнал» может уйти в прод без событий для мониторинга.

## Инфра / эксплуатация / восстановление

| Вопрос подрядчику из статьи | Кит |
|----------------------------|-----|
| Какие тесты обязательны | Только формулировка Primary среза (+ опционально остальное). Нет чеклиста видов тестов | **частично** |
| Окружения | Пауза Конфигуратора/выгрузки; нет матрицы сред | **нет** |
| Воспроизводимая инфра | Копирование `.cursor`+`AGENTS.md`; PowerShell 5.1 | **другой объект** (кит, не стенд 1С) |
| Неуспешная миграция данных | Стандарты транзакций (откат/компенсация) как **совет при написании кода** | **частично** (паттерн кода, не процедура релиза) |
| Rollback выкладки | Git + откат вставок расширения | **нет** для ИБ |
| Проверка бэкапа | Нет | **нет** |
| Метрики до запуска | Нет обязательного раздела в proposal | **нет** |
| Кто разбирает инцидент | Протокол explore+трасса для разработчика в Cursor | **частично** (как разбирать, не кто дежурит) |
| Как передать другой команде | Архив + specs + ADR + KB + overview + карта правок + маркеры | **сильно в контуре репозитория** |

## Обходы, которые ослабляют даже контур A+B

1. Pre-apply verify **рекомендуется**, но apply можно продолжить без него (`openspec-apply-change` advisory).
2. `--force-legacy` / вариант D архива — ЗНИ в архиве с непринятыми срезами.
3. Light Mode — без ЗНИ, без среза, без Primary на ИБ.
4. Пользователь «без агентов / без ревью» — исключение halt-triggers.
5. Optional-сценарии не блокируют `[x]` на срезе.

# 3. Кандидаты на усиление (без оценок выгоды)

Не «добавить Kubernetes». Усиления **внутри миссии кита** (постановка и поставка в выгрузке 1С), чтобы честнее отвечать подрядчику.

1. **Чеклист видов проверки в постановке (шаблон, не раннер).** В `proposal`/`design` явная таблица: главный сценарий (уже есть) / негатив / регресс соседнего / проверка после загрузки расширения в ИБ / «не требуется, потому что…». Verify не гоняет ИБ, но может требовать, чтобы таблица **была заполнена**, а не молча пуста. Закрывает вопрос статьи «какие тесты обязательны» без притворства, что кит — CI.

2. **Отдельный Follow-up «после загрузки в базу».** В `vertical-slices.mdc` уже есть карман Follow-up вне срезов для «релизной валидации». Сделать его **видимым** в handoff последнего среза и в archive: «срез принят на стенде ≠ загружено в рабочую; вот 3 шага smoke на копии». Не автоматизация, а запрет путать приёмку среза с выкладкой.

3. **Контракт журнала в ЗНИ с интеграцией/фоном/проведением.** Если срез трогает эти зоны — в design обязательны имена событий ЖР (как в кейсбуке) и якорь под KB `event-name`. Иначе наблюдаемость статьи остаётся «прочитайте кейсбук, если вспомните». Не включать непрошеный лог во все задачи — только когда зона совпала.

4. **Пакет передачи другой команде — одна команда-опись.** Сейчас знания размазаны: archive, overview, status, session-notes, code-map, explain-журнал. Кандидат: чеклист «новому исполнителю» (архив ЗНИ, обзор для заказчика, где карта правок, какие срезы приняты человеком, какие optional не гонялись, какие KB/ADR). Без нового агента — склейка существующих артефактов.

5. **Явный дисклеймер контура C в overview/status.** Одна секция «этот кит не заменяет: бэкап ИБ, проверка restore, дежурство, алерты, rollback выкладки». Чтобы подрядчик не продавал «у нас OpenSpec = production-ready» по статье.

6. **Негатив и отказ как наблюдаемые сценарии spec, не только happy Primary.** Specs-gate уже требует наблюдаемый THEN. Усиление: для bug-fix и интеграций — хотя бы один Scenario отказа/пустых данных в spec, покрытый optional или отдельной задачей по коду. Сейчас это не норма.

7. **Трасса/PERF как вход приёмки производительности — только по флагу ЗНИ.** Не делать нагрузку воротами каждого среза. Если в Why есть «медленно» — verify Layer 5 / design требуют в Follow-up «приложить PERF или явно waive». Связка уже есть в explore (профиль бага + PERF); нет моста в обязательный хвост ЗНИ.

Не предлагать: встроенный CI 1С, агент бэкапа, расчёт «денег в инциденте», генератор Vanessa «на все проекты» (уже снимали из-за нулевого использования).

# 4. Вне зоны кита

Честный список, чтобы не усиливать кит тем, чем он не должен быть.

- Выкладка cf/cfe на рабочую / тестовую ИБ, хранилище конфигурации, CI обновления, секреты кластера, IaC.
- Бэкап информационной базы, проверка восстановления, журнал транзакций СУБД как процедура релиза.
- Rollback **выкладки** (вернуть предыдущий cfe на проде); откат **данных** после неуспешной обработки обновления (кроме паттернов транзакций в коде).
- Мониторинг рабочей ИБ: дашборды, алерты, SLO, «какая версия в проде», стоимость простоя.
- Нагрузочный контур, chaos/fault по сети и СУБД.
- Онколл, расписание дежурств, postmortem как процесс заказчика.
- Матрица сред (dev/test/preprod/prod) и данные-эталоны как сервис.
- Автотесты как обязательная инфраструктура проекта 1С (YaXUnit/Vanessa остаются выбором проекта).
- Копирование `openspec/` репозитория **kit** в проект заказчика: по `kit-template-workflow.md` в consumer едут `.cursor/` + `AGENTS.md`; `openspec/` проекта создаёт `/init-project`. Эволюция самого кита (`develop`/`main`) — не цикл ЗНИ в конфигурации заказчика.

Платформенные аналоги статьи, которые **уже в кейсбуках/стандартах как советы кода**, но не как ops-ворота: транзакции и вложенность, журнал регистрации, технологический журнал для утечек/планов запросов (`.cursor/docs/standard/std-07-client-server.md`, `std-04-queries.md`).

## Доказательная карта: до кода / после кода / «сценарий прошёл → выкатывать»

```
До кода (A)
  причина verified или явная гипотеза+проверка
  постановка: зачем → требования → наблюдаемые сценарии → срезы с достижимым Primary
  независимая проверка постановки (не прогон ИБ)
  имена ручной конфигурации конкретны

После правки файлов, ещё до ИБ (A)
  линтер + ревьюер
  символы из журнала writer есть в выгрузке
  карта правок для человека
  опционально: /review, перед выкладкой расширения /release-review (исходники)

На ИБ человеком (B)
  один обязательный user-journey на срез
  пауза; непринятое → чинить этот срез
  архив без подписи приёмки — только явный обход

«Сценарий прошёл → выкатывать в рабочую» (C)
  кит этого ворота не ставит
  нет smoke-после-деплоя, бэкапа, rollback выкладки, метрик, дежурного
```

Логи/трассы: **вход расследования в Cursor** + **рецепт ЖР в коде**. Не ответ «сколько падает в проде».  
Откат: **транзакция документа** и **патч модуля/git**. Не restore базы.  
Знания: архив ЗНИ, ADR, KB (в проекте после init), overview. В самом репо kit KB-каталога нет.  
Другая команда: читает архив + карту правок + обзор; session-notes — только хвост чата.

## Для заказчика

Кит не даёт зелёную галочку «можно на рабочую базу». Он не даёт выкатывать, пока в плане нет понятного сценария «человек открыл, сделал, увидел результат», и пока этот сценарий по срезу не подтвердили на информационной базе — либо вы явно не сказали «архивируем без этой отметки».

До первой правки кода кит проверяет, что задача лечит названную проблему, сценарии описаны глазами пользователя, а не «внутренняя функция вернула структуру», и что кусок работы можно принять отдельно, не дожидаясь конца всей заявки.

После правки модулей кит сверяет, что в тексте задачи и в выгрузке одни и те же имена, гоняет ревью модуля и перед выкладкой расширения может прогнать более жёсткое ревью исходников. Это не автотесты, не нагрузка и не проверка «после загрузки в рабочую».

Разбор сбоя в ките — это «принесите трассу или стек, найдём место в коде». Это не экран «сколько сейчас падает у пользователей, какой билд, сколько простоя». Журнал регистрации кит учит писать, когда вы сами закладываете интеграции и фон; сам мониторинг рабочей базы он не поднимает.

Откат в ките — откат операции в базе документом и откат правки в git. Проверки резервной копии рабочей базы, репетиции восстановления и отката выкладки расширения на прод в ките нет.

Передать работу другой команде можно пакетом: архив заявки, описание для заказчика, карта какие модули трогали, решения и факты в базе знаний проекта (после настройки проекта). Это передача **репозитория и смысла**, не инструкции «кто дежурит ночью и куда звонить».

Точечная правка на несколько строк может обойти полный цикл заявки — тогда обязательного сценария на базе может не быть. Архив «всё равно унести» тоже существует: это ваш риск, кит его помечает, но не притворяется, что приёмка была.

Итог для подрядчика по статье: спрашивайте отдельно стенды, резервные копии, откат выкладки, метрики до запуска и дежурство — кит на эти вопросы не отвечает. Спрашивайте, есть ли у каждой поставки сценарий на базе, ревью кода, совпадение плана с выгрузкой и архив с решениями — здесь кит как раз жёсткий.
