# Покрытие кита: безопасность, права, данные vs тезисы статьи о вайбкодинге

Дата: 2026-08-29  
Слой: безопасность + данные + модель доступа  
Источник тезисов: статья Хабра (конспект заказчика; страница не открывалась).  
Discovery KB: совпадений нет; каталога `openspec/knowledge/` в этом репозитории нет.  
Контент 1С (`src/**`, `.bsl`, XML метаданных конфигурации) не читался.

Аналог веб-SaaS в зоне 1С: роли, ограничения на уровне записей, привилегированный режим, экспорт серверных процедур формы, параметры запросов, внешний код (`Выполнить`/`Вычислить`), хранилище паролей БСП, журнал регистрации. Не требовать CSP/заголовки браузера.

## 1. Покрытие — что кит реально проверяет

Ниже — только то, что есть в файлах кита. Разделение: **обязательный проход** (всегда на полном ревью / после правки BSL) vs **опциональный** (загружается по типу задачи, если агент «заметит» домен, или инструмент не встроен в конвейер).

### 1.1. Обязательный проход (полное ревью и ревьюер после apply)

| Что | Файл | Суть | Аналог тезиса статьи |
|---|---|---|---|
| «Не пропускать security» | `.cursor/agents/onec-code-reviewer.md` § CRITICAL RULES п.1 | В ядре роли ревьюера: не пропускать безопасность и рассогласование персистентного состояния | Функция работает ≠ безопасно (как принцип роли, без чеклиста угроз) |
| Чеклист Security Review | `.cursor/docs/standard/reviewer-checks.md` §3 | Маркеры: SQL injection, XSS в формах, insufficient access control, hardcoded credentials, unsafe data handling, RLS bypass | OWASP-список «как помнить»; детекторов и примеров 1С в этом блоке нет |
| Phase 2 Security audit | `reviewer-checks.md` Phase 2 п.2 | SQL injection, input sanitization, access control, hardcoded secrets | То же: обязательный пункт фазы, без grep/AP |
| Security Patterns | `reviewer-checks.md` § Security Patterns | Уязвимости: конкатенация в запросе; XSS; missing RLS; пароли в коде. Практики: параметры запроса, валидация ввода, проверка прав до операции, encrypted storage | Карточка-памятка; не отдельный AP |
| Ось риска `blast_radius=security` | `onec-code-reviewer.md` RISK MODEL | Находка с осью security поднимает приоритет исправления | Приоритизация, не обнаружение |
| Соответствие постановке ≠ ок по качеству | `openspec/specs/review-quality-disposition/spec.md`; `openspec/adrs/ADR-0003-review-quality-disposition.md`; `review/SKILL.md` шаг 4.5 | Слабый/рискованный код не закрывается цитатой design; заказчик явно выбирает «оставить / в очередь» | Процесс: «работает по ТЗ» не заменяет оценку качества (в т.ч. спорной безопасности, **если** ревьюер её вынес) |
| Инъекция в текст запроса (частично) | `bsl-antipatterns.mdc` AP-034, AP-035 | AP-034: патч типового запроса через `СтрЗаменить`/конкатенацию. AP-035: сборка запроса через `+ Символы.ПС` вместо литерала `\|`. Карточки: `.cursor/docs/antipatterns/bsl-antipatterns.md` | Близко к SQL injection / хрупкому запросу; в каталоге это architecture/formatting, не «безопасность» |
| Гонка и целостность записи | `bsl-antipatterns.mdc` AP-015, AP-023, AP-032; `reviewer-checks.md` §13 | Транзакция без безопасного шаблона; диалог внутри транзакции; запись в `Попытка` без повторного исключения при зависимости downstream. Inline: read-then-write без управляемой блокировки | Race / порча данных; не IDOR |
| Экспорт из модуля формы | AP-033 | `Экспорт` в `Forms/*/Module.bsl` запрещён (кроме подключаемых/callback) | Частичный аналог «серверный метод формы вызываем с клиента»; **не** покрывает неэкспортные `&НаСервере` процедуры формы |
| Скрытие строк ≠ отбор | AP-052 | Фильтрация таблицы через условное оформление `Видимость=Ложь` вместо `ОтборСтрок` | «Не видно в UI ≠ недоступно» — узкий UX/данные, не RLS |
| Три уровня ревью | `.cursor/docs/review-guide.md`; `review/SKILL.md` | После задачи BSL — ревьюер apply; `/review`; предрелиз `/release-review` | Процесс: ownership review, эскалация ARCH (права/RLS) к человеку, не автофикс |
| RLS/права выводят из «маленького фикса» | `.cursor/rules/1c-halt-triggers.mdc` Promotion; `.cursor/rules/task-triage.mdc` | Правка, затрагивающая RLS/права/роли, идёт в полный цикл; Light не ослабляет ревьюера | Процесс: не клик по форме, а маршрут постановки |
| Нельзя молча создать роль/объект | `.cursor/rules/1c-no-metadata-creation.mdc`; `.cursor/rules/1c-xml-write-guard.mdc` | Сырой Write XML (в т.ч. `Rights.xml`) оркестратору запрещён; нет объекта → пауза человеку в Конфигураторе | Не подмена security review; снижает риск «ИИ сам нарисовал широкие права» |
| Форма: XML не из воздуха | `.cursor/rules/forms-mxl-mode-gate.mdc` | Режим поставки формы (вручную / skill / только BSL); заимствование всегда стоп | Процесс поставки UI, не проверка авторизации на форме |

В таблице CHECKLISTS ревьюера (`.cursor/agents/onec-code-reviewer.md`) для **любого BSL** указаны разделы `reviewer-checks.md` §1–4, §6, §9, §10 и фазы 0, 1, 1b–1d, 2, 2.5. §3 Security Review входит в этот обязательный набор. Vendor-стандарты (включая домен безопасности) — отдельной строкой Phase 2: «по затронутым доменам».

### 1.2. Обязательный контур процесса (не детектор уязвимости)

| Что | Файл | Суть |
|---|---|---|
| ARCH по правам/RLS не правится кодом модуля | `review/SKILL.md` Apply-контур | Замечания «новый объект, API, хранение, RLS» → стоп, к заказчику / архитектору |
| Предрелиз эскалирует тяжесть | `review-guide.md`; AP-каталог колонка Prerelease | Не отдельный security-gate; гигиена Category 12 — опечатки/stubs, не модель доступа |
| Verify: security·correctness не «прощать капом» | `.cursor/skills/openspec-verify-change/SKILL.md` | Если независимый разбор постановки отверг постановку по security/корректности — нельзя ехать дальше по потолку замечаний | Это gate **постановки**, не проход по ролям в `Rights.xml` |
| Ручная настройка роли в задачах | `openspec-verify-change/SKILL.md` §5.1 | Маркер «настроить роль» требует таблицы имён в design | Полнота инструкции человеку, не аудит RLS |
| Writer самопроверка | `.cursor/agents/onec-code-writer.md` Phase 5 п.4 | «No SQL injection? Access rights checked? No hardcoded secrets?» | Writer **не** читает каталог антипаттернов (`bsl-antipatterns.mdc` writer_section без паролей/`Выполнить`); это напоминание, не детектор |

### 1.3. Опционально / только если агент загрузит домен или человек вызовет инструмент

| Что | Файл | Когда срабатывает | Ограничение |
|---|---|---|---|
| Вендор: API сервера, пароли, `Выполнить`, роли, привилегированный режим, `РАЗРЕШЕННЫЕ`, `ПравоДоступа` vs `РольДоступна` | `.cursor/skills/1c-vendor-standards/SKILL.md` §8; `.cursor/docs/standard/std-08-security.md`; навигатор `.cursor/docs/standard/1c-standards-navigator.md` | Ревьюер/архитектор читают домен, **если** решат, что код его затронул. Отдельного AP и grep нет | Нет fail-closed: привилегированный режим в diff не обязан породить находку |
| Вендор: файлы, таймаут HTTP | `std-07-client-server.md` | Тот же on-demand | Таймаут — доступность, не SSRF/подпись webhook |
| Модель сервиса / разделители | `std-11-general.md` (регламенты в разделителях) | Справочник вендора | Не чеклист multi-tenancy в постановке ЗНИ |
| Архитектор: права, RLS, валидация, injection, XSS | `.cursor/agents/onec-code-architect.md` § Security, § Access Rights | Когда сработал Architect Gate и вызван архитектор | Gate (`architect-gate.mdc`) **не** содержит триггера «права/RLS/HTTP/секреты»; триггеры — перехват, новый объект, >1 файл, UX и т.д. |
| Разведка: RLS как сквозная тема | `.cursor/agents/onec-code-explorer.md` § Architecture Analysis | Только Full Feature Exploration | Не обязательный IDOR-проход |
| Анализ существующей роли | `.cursor/skills/1c-roles/info/SKILL.md` | Человек/агент явно вызвал info по `Rights.xml` | **Не** встроен в `/review` / apply как evidence-блок (в отличие от линтера) |
| Сборка роли из JSON | `.cursor/skills/1c-roles/compile/SKILL.md`; строка в `1c-xml-write-guard.mdc` | Теоретически через skill | Конфликт с запретом создавать метаданные: compile описывает запись `Roles/*.xml` и `ChildObjects` в `Configuration.xml`. На практике новая роль = пауза в Конфигураторе |
| RLS регистров, тест не под админом | `.cursor/docs/casebooks/registers-design.md` §10 | Правило дизайна: админ обходит RLS | Кейсбук on-demand при проектировании регистра; не автотест |
| Привилегированный режим в СКД | `.cursor/docs/casebooks/dcs-design.md` §6 | Не расширять видимость молча; пара `Истина`/`Ложь` | Только если читают кейсбук отчёта |
| Не логировать секреты и ПДн | `.cursor/docs/casebooks/logging-strategy.md` §6 | Запрет паролей/токенов/PII в журнале | On-demand при «как логировать»; AP-042 запрещает **лишний** журнал, не утечку секрета в литерале |
| Гонки/блокировки | `.cursor/docs/casebooks/locks-and-transactions.md` | Порядок блокировок, запрет диалога в транзакции | Целостность данных, не модель доступа |
| HTTP/обмен | `.cursor/docs/standard/std-12-integration-exchange.md` | Сериализация ссылок, имена полей, тексты ошибок | Триггер ревьюера при JSON/HTTP; **нет** проверки подписи входящего сообщения |
| Webhook в журнале | `logging-strategy.md` таблица §1 | Логировать inbound webhook (источник, размер, reject) | Аудит события обмена, не HMAC/replay |

### 1.4. Что ревью **намеренно пропускает** (важно для «обязательный vs клик»)

| Режим | Файл | Следствие для безопасности |
|---|---|---|
| Light-review (пробелы/комментарии/rename) | `review/SKILL.md` шаг 1.4 | Пропускаются Phase 0, Phase 2 (включая Security audit), Identity Audit, AP-пасс. Остаются линтер, whitelist, гигиена имён/комментариев | Тривиальный diff **не** гоняет security-проход |
| diff-focused | `review/SKILL.md` шаг 1.5; reviewer Review Boundaries | Замечания только в изменённых процедурах | Обход RLS / широкий привилегированный режим **рядом** с правкой может не попасть в отчёт (кроме BOUNDARY_EXCEPTION) |
| Apply не спрашивает «так задумано» | spec disposition; ADR-0003 | Спорное качество (в т.ч. слабая защита, если помечена слабой) остаётся со следом на `/review` | Скорость цикла; финальный суд по спорному — не в apply |

**Итог покрытия:** кит **жёстко** закрывает процесс «не верить зелёной форме и цитате ТЗ» (ревьюер, disposition, стоп по метаданным/ролям, полный цикл при RLS) и **жёстко** ловит несколько классов порчи данных и хрупких запросов. Отдельного обязательного контура «модель авторизации + секреты + чужой объект» **нет**: пункты §3/`std-08` живут как память агента.

## 2. Дыры vs статья (только по факту файлов)

Сопоставление тезисов статьи с тем, чего **нет** как обязательной проверки или артефакта.

| Тезис статьи | В ките | Факт |
|---|---|---|
| Сгенерированный код функционально ок, но небезопасен | Частично | Принцип роли + disposition. Нет каталога угроз 1С (привилегированный режим, `Выполнить`, широкая RLS, параметр-ссылка чужого объекта) с детектором |
| OWASP / IDOR | Нет как чеклист | Нет сценария «открыть/записать объект другого пользователя по ссылке из параметра формы / HTTP / номера». `ПравоДоступа` есть в `std-08`, не в AP |
| Слишком широкая RLS | Частично | Ревьюер должен «видеть» RLS bypass (`reviewer-checks.md` §3). Инструмент `1c-roles/info` показывает `[RLS]` в `Rights.xml`, но **не** вызывается оркестратором ревью. Кейсбук регистров: «тестировать не админом» — совет дизайна |
| SSRF | Нет | Нет правила «URL из ввода пользователя / константы в `HTTPСоединение`». `std-07` — таймаут |
| Race | Частично | Транзакции/блокировки (AP-015/023, кейсбук locks). Не TOCTOU «проверил право → изменил чужую ссылку» |
| Проверка подписи webhook | Нет | `std-12` про GUID в JSON; `logging-strategy` — факт приёма, не криптоподпись |
| Login ≠ авторизация | Частично, справочно | `std-08`: проверять `ПравоДоступа` на метаданные, не `РольДоступна` для прикладных прав; не класть бизнес-логику в сервер формы (клиент может вызвать `&НаСервере` после получения формы). Кит кодирует только AP-033 (экспорт формы), не весь серверный API формы |
| RLS не видна в UI | Частично | AP-052 (видимость ≠ отбор). Нет прохода «элемент скрыт ролью / условным оформлением, а серверный метод пишет всё равно» |
| Security review ≠ клик по форме | Да, процесс | Три уровня ревью, Mode Gate форм про **поставку** XML, не про права на команде формы |
| Нужен threat model | Нет | Нет шага/секции `## Threat model` в explore/new/design. Architect Gate не включает «интеграция/роли/файлы» как отдельный триггер |
| Секреты | Справочно | `std-08` безопасное хранилище БСП; writer/reviewer bullets «hardcoded secrets»; `logging-strategy` §6. Нет AP, нет grep `Пароль = "`, нет запрета реквизита формы с паролем |
| Права / роли как задача поставки | Процесс, не аудит | Pause-wait + verify «настроить роль» с таблицей имён. Нет обязательного diff `Rights.xml` в ревью BSL |
| Multi-tenancy | Справочно вендор | `std-11` / платформенные разделители. Нет чеклиста «область данных / общий реквизит» в постановке |
| Ввод пользователя | Слабо | Phase 2: «Validate input sanitization» без критериев 1С. AP про контракт данных (AP-004…) — про лишние проверки, не про доверие вводу |
| Файлы | Справочно `std-07`/`std-08` | Расширения, каталог программы, внешние обработки. Нет halt «загрузка файла / открытие внешней обработки» |
| Rate limiting | Нет | Нет |
| Защита админки | Справочно `std-08` стандартные роли, интерактивное открытие внешних обработок | Нет задачи «роль админа не в профиле оператора» в ревью |
| Headers (CSP и т.п.) | Вне зоны | См. §4 |
| Зависимости (пакеты, CVE) | Нет | Иной мир (cf/cfe, БСП, расширения), не npm audit |
| Аудит событий | Частично и в обратную сторону | AP-042: **не** писать отладочный журнал без требования. Позитивный аудит — `logging-strategy` (интеграции, фон, проведение). Нет обязательного «событие доступа к чужим данным» |
| Ownership, актуальные правила, review, эскалация | Да, процесс | Команды ревью, disposition, architect на ARCH, halt на метаданных, promotion при RLS |
| Вопросы подрядчику: как проверяется авторизация; где секреты | Нет | Нет шаблона в explore/handoff/overview |

Отдельно: в AP-каталоге **нет** идентификаторов на `УстановитьПривилегированныйРежим`, `Выполнить`/`Вычислить`, `РольДоступна`, литералы паролей, `РАЗРЕШЕННЫЕ` в запросе, вызов HTTP по пользовательскому URL.

Конфликт инструкций по ролям (факт файлов): `1c-xml-write-guard.mdc` делегирует `Rights.xml` скиллу `1c-roles/compile`; `1c-no-metadata-creation.mdc` запрещает создавать XML ролей и править `Configuration.xml`. Для новой роли побеждает пауза человеку; автоматического «сузь RLS» в apply нет.

## 3. Кандидаты на усиление

Без оценок срока/выгоды. Точка вставки — куда класть норму.

1. **Fail-closed проход «режим без проверки прав + динамический код»**  
   Точка: ревьюер — `reviewer-checks.md` §3 и Phase 2 п.2; плюс 2–3 карточки в `bsl-antipatterns.mdc` (привилегированный режим шире операции / в экспорте «Вызов сервера»; `Выполнить`/`Вычислить` без безопасного режима; `РольДоступна` вместо `ПравоДоступа`).  
   Зачем: сейчас это только `std-08`, который читают «по затронутому домену».

2. **Чеклист авторизации «объект не своего контура»**  
   Точка: постановка — шаблон в explore/new (`design.md` секция поведения при ссылке/номере/ключе извне); ревьюер — тот же §3 с 1С-сценариями (параметр формы, HTTP-сервис, номер документа, отбор СКД).  
   Зачем: прямой аналог IDOR; в файлах отсутствует.

3. **Секреты как правило каталога, не bullet**  
   Точка: ревьюер (AP + evidence grep оркестратора по образцу Identifier Hygiene); writer bulletin одной строкой «не литерал пароля/токена». Опора: `std-08` + `logging-strategy.md` §6.  
   Зачем: «hardcoded secrets» уже названы, детектора нет.

4. **`1c-roles/info` в evidence ревью, если в ЗНИ есть `Rights.xml` / задача на роль**  
   Точка: оркестратор `review/SKILL.md` (как блок линтера); verify §5.1 — не только имена объектов, но «какие права/ограничения записей».  
   Зачем: RLS «не видна в форме» тогда хотя бы видна в отчёте роли.

5. **Серверный API формы по `std-08`, шире AP-033**  
   Точка: ревьюер (новая карточка или расширение §3); архитектор при задачах на модуль формы.  
   Зачем: статья «клик по кнопке ≠ авторизация»; вендор прямо пишет, что `&НаСервере` формы вызывается после `ПолучитьФорму`.

6. **Секция модели доступа в постановке при триггерах**  
   Точка: архитектор + `architect-gate.mdc` (семантический триггер: роли, RLS, привилегированный режим, HTTP/файлы, внешние обработки); `openspec-new-change` — обязательная секция «кто может / кто не может / что обходит ограничение записей». Не полноценный threat model веб-SaaS, а 1С-карточка угроз.  
   Зачем: статьи «нужен threat model» сейчас ноль артефактов.

7. **Halt/promotion: привилегированный режим, входящий HTTP, загрузка файла**  
   Точка: `1c-halt-triggers.mdc` рядом с уже существующим «RLS / права / роли».  
   Зачем: мелкий фикс не должен обходить полный цикл там, где статья как раз предупреждает.

Не дублировать: повтор Category 12; CSP; отдельный Cursor `security-review` без 1С-роли (в `.cursor` кита не подключён).

---

## 4. Вне зоны кита

- Заголовки HTTP/CSP, cookies, CORS, защита «админки» как веб-панели SaaS.  
- Сканер зависимостей npm/OSV, supply-chain CI.  
- Нагрузочный rate limit на edge (API gateway).  
- Проверка подписи провайдера (Stripe-подобные webhook) как универсальный протокол — в 1С это прикладной контракт конкретного обмена, не механизм кита.  
- Интерактивный прогон под пользователем без полных прав (Конфигуратор / предприятие) — кит советует в кейсбуке регистров, не автоматизирует.  
- Модель 1cFresh/разделителей как эксплуатация сервиса — вендорский текст, не pipeline ЗНИ.  
- Подмена native Cursor security-review: кит делегирует `onec-code-reviewer`, не этот канал.

## Для заказчика

Кит уже не считает «кнопка на форме нажалась» доказательством безопасности: после правки кода всегда идёт разбор кода, спорные места нельзя закрыть фразой «так в постановке», права и ограничения записей нельзя тихо дорисовать в XML, а задача про роли/ограничения записей не идёт как крошечный фикс.

По данным кит ловит порчу записи (транзакция, блокировки, скрытый частичный результат) и опасную сборку текста запроса строками. Это близко к «запрос из кусков» и к гонкам при проведении, но это не проверка «пользователь не прочитает чужой документ».

Чего нет: отдельной модели угроз; обязательного сценария «объект другого пользователя»; автоматического разбора файла прав; правил на пароли в коде и на обход прав привилегированным режимом; проверки подписи входящего обмена и ограничений частоты вызовов.

Аналоги веб-статей в 1С — роли, ограничения записей, привилегированный режим, серверные процедуры формы, параметры запроса, журнал без паролей; не заголовки браузера.

Имеет смысл усилить три места: разбор кода (права, чужой объект, секреты, привилегированный режим), постановку (кто может и что обходит ограничение записей), вход в полный цикл (не только слово «роли», но и привилегированный режим / входящий обмен / файлы).

Инструмент разбора роли из XML уже есть (`.cursor/skills/1c-roles/`), но в обычное ревью он не подключён. Вендорский текст про безопасность лежит в `.cursor/docs/standard/std-08-security.md` и читается, только если исполнитель сам откроет домен.
