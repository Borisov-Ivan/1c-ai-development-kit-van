# Исследование: охват B-explain и handoff «после ревью/кода → explain»

**Дата:** 2026-08-09  
**Тип:** процесс kit (не BSL продукта)  
**user-goal:** спроектировать handoff, где после `/review` / `/release-review` / реализации кода предлагается `/opsx:explain`, а B-explain бриф показывает охват = обработанный код (из отчёта ревью или списка изменённых `.bsl`), и пользователь подтверждает рамку до карты точек.

---

## 1. Свод (для заказчика)

Сейчас `/opsx:explain` **не умеет сам** «подхватить» результат ревью или apply. На входе он всегда показывает короткий **бриф B-explain** и ждёт подтверждения рамки. В брифе охват — это не список модулей, а **рамка сценария** («что разбираем»): либо один абзац **Охват**, либо 2–3 **Варианта** на выбор (нельзя оба сразу). Пути к отчётам — только в слоте **Контекст**. Список точек с именами эффектов появляется **после** «да», отдельной картой.

После `/review` и `/release-review` в чате есть слот **«Куда дальше»**, но там сейчас только устранение замечаний / extend / «только отчёт» — **explain не предлагается**. После реализации среза (`/opsx:apply`) в приёмочном handoff есть отличный список обработанного кода (**Карта правок** / `code-map.md`), но следующий шаг — проверка на ИБ, не разбор кода.

**Предложение:** в конце ревью (после отчёта; особенно после confirm→fix) и в конце apply-среза (рядом с приёмкой) одной строкой предлагать `/opsx:explain`. При согласии оркестратор **prefills** бриф: **Охват** = обработанные эффекты/процедуры языком сценария (из Review Boundaries / code-map), пути — в **Контекст**, без списка `pav…`-модулей в теле охвата. Если рамка неоднозначна (например, «только наши правки» vs «вся цепочка с типовым») — вместо **Охват** дать **Варианты**. Подтверждение пользователя остаётся обязательным до карты точек.

## 2. Текущий entry B-explain: Охват / Варианты / Контекст

### 2.1 Источники SSOT

| Артефакт | Роль |
|----------|------|
| `.cursor/commands/opsx-explain.md` | Вход: Read skill; ввод — трасса, отчёт `temp/reports/…`, change, путь модуля, «как работает X» |
| `.cursor/skills/openspec-explain/SKILL.md` § Entry Protocol | До подтверждения брифа запрещены Task / массовый Read `.bsl`; допустимы ≤3 указанных отчёта |
| `openspec-explain/templates/entry-brief.md` | SSOT слотов и эталонов A/B |
| `.cursor/docs/templates/brief-card.md` § B-explain | Индекс + XOR + разбор ответа |
| `openspec-explain/templates/inventory-card.md` | **После** брифа: карта точек (имена эффектов), не часть брифа |
| `fixtures/voice-good-brief.md` | Эталон голоса (сценарий замера + Варианты) |

### 2.2 Слоты брифа (обязательность)

| Слот | Обяз. | Содержание |
|------|-------|------------|
| **Сценарий** | да | Действия пользователя / операции замера (≤3 пункта) |
| **Вопрос** | да | Якорь прохода («что хотим понять») |
| **Варианты** *или* **Охват** | да | **XOR** |
| **Контекст** | опц. | Пути трассы / отчёта / change — маркированный список |
| **Подтвердить?** | да | номер варианта / «да» / уточнение |

Бюджет: ≤6 заполненных слотов; пути **только** в **Контекст**.

### 2.3 Как формируется **Охват** vs **Варианты** сегодня

Правило из `entry-brief.md` + skill:

1. **Рамка неочевидна** (две операции в одном замере, несколько смысловых срезов) → слот **Варианты**: 2–3 взаимоисключающие рамки. Пользователь отвечает номером; «да» = вариант 1.  
   Эталон A: «обе операции» / «только открытие» / «только клик и старт».

2. **Рамка уже ясна из команды** → слот **Охват**: один абзац на языке сценария/эффекта («только операция клика: от клиентской команды до …; без разбора появления кнопки»).  
   Эталон B. Ответ: «да» или уточнение.

3. **После подтверждения** — второй гейт: **карта точек** (`inventory-card.md`) внутри утверждённой рамки. Имена эффектов, без кода, без классов в чат. Модули и `file:line` — на карточках точек, не в брифе.

### 2.4 HALT, важные для handoff «обработанный код»

Из `entry-brief.md` / skill Self-check брифа:

| Запрещено в чат-брифе | Куда относится |
|-----------------------|----------------|
| Список модулей (`pav…`, M01…) | В карту точек / карточки |
| **Варианты** и **Охват** одновременно | XOR |
| Цель / Источник / Решено когда | Устаревшие слоты |
| «Сейчас соберу карту…» в хвосте | Достаточно «номер или да» |
| Имена агентов, жаргон движка | как в `brief-card.md` |

**Следствие для дизайна:** «обработанный код» в брифе **нельзя** вываливать списком путей `.bsl`. Охват = **рамка эффекта** («правки среза S2: проверка подписи и сообщение пользователю»), а пути к `review-*.md` / `code-map.md` — в **Контекст**. Детальный список процедур — либо сворачивается в один абзац Охвата, либо уходит во внутренний inventory после «да».

### 2.5 Что идёт после брифа (кратко)

1. Подтверждение брифа → собрать точки в утверждённой рамке (из explore/trace отчёта или 1× Task inventory).  
2. Карта ≤12 строк → подтверждение списка.  
3. Walk: одна точка за ход (`point-card.md`).  
4. Выход + обязательный `explain-*.md` (`explain-report.md`: мета включает «Охват / Вариант»).

Команда `/opsx:explain` уже принимает отчёт `@temp/reports/…` как ввод — но примеры и skill ориентированы на **trace/explore**, не на `review-*`.

## 3. Откуда сегодня можно взять «обработанный код»

Приоритет источников для prefill (от наиболее пригодного к наименее).

### 3.1 После `/opsx:apply` (лучший structured source)

| Артефакт | Поля / формат | Пригодность для Охвата |
|----------|---------------|------------------------|
| `openspec/changes/<name>/reports/code-map.md` | Строка: `S<N>.<M> · <модуль> · <процедура> (<created\|modified>) — <суть>. [path]:start-end` | **Высокая:** есть процедура + суть на русском + строки |
| Чат / файл `handoff-acceptance-S<N>-*.md` → «Карта правок» | До 5 пунктов прозой + citation; в файле — полный список секции среза | **Высокая** для брифа (проза уже на языке эффекта) |
| `debug.md` → `### Code-Truth — <task-id>` | `symbols: name @ file:lines, action=` | Внутренний journal; для Охвата брать через code-map, не сырой YAML в чат |
| `tasks.md` `[x]` + backticks `src/...bsl` | Пути задач | Fallback, без процедур |

SSOT apply: `.cursor/skills/openspec-apply-change/SKILL.md` (Карта правок, Slice Gate); язык карты — `.cursor/docs/opsx-output-style.md` §5.2 «Язык карты».

**Важно:** acceptance-handoff сейчас **не** предлагает `/opsx:explain` в «Как вернуться» / Short-cut — только тест на ИБ и `/opsx:apply` / `/opsx:extend`.

### 3.2 После `/review` (операционное ревью)

| Артефакт | Поля | Пригодность |
|----------|------|-------------|
| Main report `…/reports/review-<scope-slug>-YYYY-MM-DD.md` или `temp/reports/review-*.md` | Summary YAML: `File(s): <пути>`; Findings: `File` / `Procedure` / `Line` | **Средняя–высокая:** File(s) + уникальные Procedure из findings и Review Boundaries |
| Промпт/evidence `## Review Boundaries` (в сессии; в отчёт может не копироваться целиком) | `File` + `Target Procedures: name (lines a-b)` | **Лучший** список «обработанных точек» для diff-focused; нужно **явно писать** Boundaries (или выжимку) в main report / Summary, если ещё не пишется стабильно |
| Карточка чата слот 1 «Что отрецензировано» | UX-формулировка scope | Хороший черновик **Сценария**/рамки, но без процедур |
| `git diff` `.bsl` + procedure mapping (шаг 1.5) | Изменённые процедуры / `[module-level]` | Эквивалент Boundaries; доступен оркестратору в сессии review |

Резолв scope (`review/SKILL.md` §1.2): явные пути → full; change → diff-focused по `[x]`/backticks; без аргументов → git diff `.bsl`.

**Сейчас в «Куда дальше» (шаг 4.4):** устранение / extend / archive — **без** `/opsx:explain`.  
После шага 6 (fix) Boundaries **пересобираются** по новому diff — это и есть финальный список «обработанного после confirm».

### 3.3 После `/release-review`

| Режим | Список файлов | Для explain |
|-------|---------------|-------------|
| `full-extension` | все `*.bsl` расширения (`extension_all_bsl`) | **Не тащить целиком** в Охват — раздувание; только Варианты «ключевые цепочки» / явный поднабор |
| `change-scoped` | Tier 1 = `target_files` (из architecture/tasks/design/git); Tier 2 = всё расширение (только обзор) | Prefill из **Tier 1** (+ процедуры Boundaries), не из Tier 2 |
| Карточка «Куда дальше» | extend `--from-review` при ARCH/MUST_FIX scope; иначе writer / «только отчёт» | Explain отсутствует |

Источники `target_files` (шаг 1.3a): `reports/architecture-*.md` (`scope.files`) → `tasks.md` → `design.md` → git fallback по slug.

### 3.4 Сводная матрица «что считать обработанным кодом»

| Ситуация | Канон списка | Язык для слота **Охват** |
|----------|--------------|---------------------------|
| Apply, срез принят/на приёмке | `code-map.md` секция среза | Сути задач + имена эффектов («что изменили для пользователя») |
| Review diff-focused (+ после fix) | Review Boundaries / procedure map | «Изменённые процедуры сценария X: …» без полного path-dump |
| Review full одного модуля | Файл + ключевые процедуры из findings/Summary | «Модуль формы/объекта Y — точки A, B» |
| Release full-extension | Не весь список | Только **Варианты** или отказ от auto-prefill |
| Light-review (whitespace/comments/renames) | — | **Не предлагать** explain |

## 4. Предложение handoff: post-review / post-apply → explain brief prefill

### 4.1 Когда предлагать (триггеры)

| Момент | Условие offer | Не предлагать |
|--------|---------------|---------------|
| `/review` шаг 4.4 / 7.1 | Есть ≥1 содержательный `.bsl` в scope **и** не light-review; есть цепочка/несколько процедур **или** пользователь явно чинил логику | Light-review; пустой scope; только comment/whitespace |
| `/review` после шага 6 (confirm→writer→re-review) | **Предпочтительно** — код уже «обработан» замечаниями; Boundaries свежие | Пользователь отказался от фикса и сказал «только отчёт» *и* код тривиален |
| `/release-review` | Только `change-scoped` Tier 1 с осмысленным diff; или пользователь сузил scope | Автоматически на весь `full-extension` |
| `/opsx:apply` Slice Gate (acceptance) | Срез с BSL-задачами; есть `code-map` | Только Configurator/ручные задачи без кода; срез без символов |
| Параллель (вне scope этого исследования) | Слой weak/as-designed/queue ревью — **не** смешивать; offer explain — отдельная строка next-step | — |

Прецедент в kit: `/opsx:explore` уже предпочитает `/opsx:explain` в слоте **Дальше**, если в отчёте есть цепочка точек (`openspec-explore/SKILL.md` §2 синтез) — «одной строкой, без второго брифа» до согласия. Тот же паттерн перенести на review/apply.

### 4.2 Что писать в чат (тонкий handoff)

**После review (слот «Куда дальше» — расширить, не ломая приоритет фикса):**

1. Если есть MUST_FIX → сначала устранение (как сейчас).  
2. Параллельно или после отказа/завершения фикса — одна строка:

> Можно пройти обработанный код по точкам: `/opsx:explain` (охват подставлю из отчёта ревью — подтвердите рамку).

**После apply acceptance** (рядом с «Как вернуться», не вместо теста):

> После проверки на ИБ (или параллельно): разобрать внесённые правки по шагам — `/opsx:explain` (охват из карты правок среза).

Не создавать `temp/explain-handoff-*.md` (skill explain явно запрещает отдельный handoff-файл). Достаточно строки в чате + пути в **Контекст** при старте explain.

### 4.3 Prefill B-explain при старте `/opsx:explain` из этого handoff

Алгоритм оркестратора (Entry Protocol, до END TURN брифа):

1. **Разрешить Read** исходного артефакта (уже в лимите ≤3): `review-*.md` и/или `code-map.md` / `handoff-acceptance-*.md`.  
2. Собрать внутренний список «обработанных якорей» (процедуры + суть).  
3. Выбрать XOR:
   - **Один связный сценарий / один срез / один diff** → слот **Охват** (эталон B).  
   - **Два+ осмысленных среза рамки** (наши правки vs цепочка с типовым; два независимых модуля; Tier1 vs «с соседями») → слот **Варианты**, не Охват.  
4. Заполнить слоты:

```markdown
Бриф: <тема среза / ревью>

**Сценарий** — <что делали: «доработали проверку подписи в срезе S2» / «прошли ревью и устранили замечания по diff»>.

**Вопрос** — как устроены внесённые правки: что зашито, где ветки, на что смотреть при приёмке/релизе.

**Охват** — обработанный код этого прохода: <2–4 эффекта/процедуры языком сценария>; без разбора нетронутого типового контура и файлов вне отчёта.

**Контекст**
- `openspec/changes/<name>/reports/review-….md`  <!-- или temp/… -->
- `openspec/changes/<name>/reports/code-map.md`   <!-- если apply -->
- change `<name>`                                 <!-- если есть -->

Подтвердить? — «да» или уточните (например, «без типовых вызовов ДО»).
```

5. **Не** дублировать path-list в **Охват**.  
6. После «да» — карта точек строится **только** из утверждённой рамки; agent-класс `типовое` помечает `(можно не разбирать)`.

### 4.4 Сохранение XOR Варианты/Охват

| Ситуация | Слот |
|----------|------|
| Scope однозначен (один срез code-map, один модуль full review) | **Охват** |
| Пользователь может хотеть «только наши +» vs «с вызывающим типовым» | **Варианты** (2–3), без абзаца Охват |
| Release full-extension | **Варианты** «какие цепочки» **или** спросить сужение до change/diff; не auto-Охват на всё cfe |

Никогда: одновременно нумерованные Варианты и абзац Охват.

### 4.5 Минимальный контракт «обработанный код» → текст Охвата

Внутренне (не в чат-бриф как список модулей):

```
processed[] = { effect_or_procedure, file?, lines?, source: boundaries|code-map|finding }
```

В **Охват** (чат): 1 абзац, ≤3 «эффекта», язык заказчика.  
В **Контекст**: пути отчётов.  
В **карту** после «да»: пункты 1…N из `processed[]` (+ необходимые связующие точки call-chain, помеченные как типовые при необходимости).

## 6. Риски

| Риск | Почему | Митигация |
|------|--------|-----------|
| Раздувание охвата | `/release-review` full-extension = десятки `.bsl`; Summary `File(s)` длинный | Prefill только Tier 1 / diff; иначе Варианты или отказ auto-Охват |
| Конфликт XOR Варианты/Охват | Оркестратор «на всякий случай» даст и список вариантов, и абзац охвата | Жёсткий HALT (уже в entry-brief); в prefill-правиле: ровно один слот |
| Список модулей в брифе (HALT) | Заказчик просит «обработанный код» = пути | Пути → **Контекст**; в Охвате — эффекты/процедуры по-русски |
| Шум типового кода | Diff-focused Boundaries = только изменённые процедуры, но карта explain может потянуть call-chain ДО | В Охвате явно «без разбора типового контура»; в карте — `(можно не разбирать)` |
| Конфликт с приёмкой apply | Explain отвлекает от теста на ИБ | Offer **после** блока «Что проверить СЕЙЧАС» или «после проверки»; не единственный next-step |
| Конфликт с MUST_FIX | Explain вместо фикса | Сначала AskQuestion устранения; explain — вторая линия или после фикса |
| Устаревший diff | Review до фикса vs после шага 6 | Prefill из **финальных** Boundaries / повторного отчёта |
| Light-review | Нет содержательных точек | Не offer |
| Двойной бриф | Explore сказал «без второго брифа», но explain **обязан** B-explain | Offer в review/apply = ссылка на команду; бриф — только внутри сессии `/opsx:explain` (как у explore: одна строка Дальше → пользователь запускает explain → бриф) |
